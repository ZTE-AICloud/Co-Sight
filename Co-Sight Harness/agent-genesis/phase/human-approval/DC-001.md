# DC-001: 构建方案审批（深度优先）

> **触发**: Step 3c (build-planner) 完成之后、Step 4 (agent-executor) 之前
> **协议类型**: structured_walkthrough
> **目标**: 杜绝"草率 yes"，用户必须在结构化决策里审核方案
> **v0.15+ 新增**: 替代旧版单 yes_no 流程
> **历史问题**: `RETROSPECTIVE.md` §二 问题 2（DC-001 被压成 yes/no，用户草率 approve）

---

## 审批主界面：判断题清单（S3b，第 1 轮）

human-review 顶层是判断题清单（非 prose），Main Agent 按清单逐题询问，每项标注【机检 ✓】/【需人判】:
- 机检项: 直接告知"已机检通过（G017 M6 / G023 cross）"，不消耗确认
- 人判项固定三类: ①角色拆分语义对齐 ②manual_verify 逐条认可 ③G017 CONCERNS 逐条裁决
- 判断题 ≤7，每题三选项: 接受 / 修改（说明） / 转 Cancel

## 多轮审核协议（S3c）

- **硬性阻塞**: 仅 APPROVED / CANCEL 两出口。Request Adjustments 是回路不是出口——planner 修订后
  必须重新摆到人面前显式确认，禁止"修订完成自动进入 Step 4"
- **增量复审（第 N≥2 轮）**: 只重列受 override 影响的判断题 + "其余 M 项维持上轮裁决"；确认成本不随轮次膨胀
- **不设轮次上限**: 每轮皆用户主动发起，无失控风险
- **直接编辑通道**: 用户可直接编辑 build-plan 后要求"按现稿确认"（=全文 override 落盘，planner 以现稿为基底）
- **留痕**: 每轮裁决写 `dc001-decisions.yaml`（round / 项 / verdict / override 用户原话 / spot-check 结果），
  作为 planner `--revision-input` 的唯一权威依据

## 必填顺序（不可跳步）

### Step 1: 文件清单展示（Main Agent 必须先做）

列出构建方案会创建的所有文件（≥10 项），每个文件含：

| 列 | 说明 |
|----|------|
| `file_path` | 相对路径或绝对路径 |
| 1 行说明 | 这个文件做什么 |
| 行数预估 | 范围（如 50-150 行） |

格式：Markdown 表格

**示例**：

| 文件 | 说明 | 行数 |
|------|------|------|
| `output/agents/{name}/v1/CLAUDE.md` | 主入口，可读 | 300-500 |
| `output/agents/{name}/v1/.claude/settings.json` | Hooks 配置 | 30-50 |
| ... | ... | ... |

---

### Step 2: 已知风险列表

≥2 个风险，每个含：

| 等级 | 含义 |
|------|------|
| **critical** | 用户必须立即处理，否则 Agent 不能用 |
| **major** | 用户接下来 1 周会踩到，建议处理 |
| **minor** | 用户可能没注意到，可以延后 |

> **C2**: build-planner 从 pattern-matcher 推导的方案风险之外，step-2 产出后自检（pattern-matcher 内）的 G017 检查
> 可能产生 CONCERNS（关键维度低置信度 / cascade_opposed / 非标准模式行等），
> 由 build-planner 透传进本小节，标注来源「G017」。用户对本小节的 G017 条目
> 必须显式裁决（接受 / 要求回到 step-2 重匹配），不允许静默带过。

> **契约核心**: human-review.md 第 9 节「方案落地清单」
> （模式|机制|落点文件|验证方式）是 Step 1 文件清单之上的**决策落地核对面**——
> Main Agent 展示 Step 1 时必须同步展示该表，用户须确认每个选中模式都有落点与验证方式；
> 其中标注 `manual_verify` 的验收项（不可机械化的 acceptance 转化）也须逐项确认。

每个风险格式：

```markdown
- **[critical/major/minor]** [风险描述]
  - 触发条件: [用户什么场景下会踩到]
  - 缓解方案: [代码层或文档层的 fix]
```

---

### Step 3: 用户 spot-check 计划

≥3 个具体操作，让用户事后能验证。每个操作含：

```markdown
- [ ] "读 X 文件的 Y 行，应是 Z"
- [ ] "跑命令 W，应看到结果 Q"
- [ ] "如果不通过，反馈给谁/什么命令"
```

**最低标准**：3 项操作覆盖：
1. 文件内容验证（如 "读 SKILL.md 第 X 行")
2. 命令行验证（如 "bash command → 期望输出"）
3. 失败回退路径（如 "如果失败，回退到 Step X 重跑"）

---

### Step 4: 单项 yes_no

只有 Step 1-3 全部展示后才询问：

- **Approve** — 进入 Step 4 (agent-executor)
- **Request Adjustments** — 不进入 Step 4, 携带用户建议回到 build-planner
- **Cancel** — 终止整个 Pipeline，不删除已有产出

## 反草率机制（v0.15+ 新增）

| 触发 | 检测方法 | 处理 |
|------|---------|------|
| 用户回答 < 30 token | 简单 token 数估算 | 追问："能否更详细？" |
| 缺 file_refs | 计数用户回答中 `file_path:line` 格式 | 追问 |
| 缺 risk acknowledgment | 用户未确认见到 Step 2 风险列表 | 追问 |
| 用户连续 2 次草率 | Main Agent 内部 state | escalate_to: human-team-lead |
| 没有走 Step 1-3 直接 yes | Main Agent 内部 state | 阻断 |

---

## escalation 路径

如用户连续 2 次草率 → 不再追问用户，escalate 到 human-team-lead。

escalation 报告模板：

```
[DC-001 ESCALATION]
原因: 用户连续 2 次草率 approve
证据: 
  - 第一次回答: "{回答1}"
  - 第二次回答: "{回答2}"
建议:
  - 暂缓 Step 4
  - 人类团队负责人接手审核 build-planner 的产出
  - 用户对此 Process 反馈（是否过严？是否合理？）
```

## 两级通道（P3: 对称 DC-010 fast/full）

> 对称 DC-010 已有的 fast/full 通道（C3），DC-001 标准场景补齐。

**通道判定**: `bash scripts/dc001-channel.sh {work_dir}`（确定性脚本，不允许 LLM 裁断）

**四项判定标准**:

| # | 标准 | 通过条件 |
|---|------|---------|
| 1 | G017 verdict | = pass **且** concerns = [] |
| 2 | manual_verify invariants | ≤ 2 条（build-plan 内） |
| 3 | build_type | single_agent；build-plan 内 type: subagent 出现次数 < 3 |
| 4 | 风险等级 | human-review.md「已知风险」节无 critical 级（前缀 `[临界]` / `[critical]`） |

**任一不过 → full**；四项全过 → fast。

**通道面板**:

| 通道 | 触发 | 展示 | 出口 |
|------|------|------|------|
| **fast** | dc001-channel.sh 输出 `{"channel":"fast"}` | 压缩面板：文件清单表（全列，本就 ≥10 行）+ 物化摘要表 + 风险 top-2 + 一键 Approve/Adjust/Cancel | 同 full（APPROVED 才进 Step 4） |
| **full** | 任一标准未过 | 现有 Step 1-4 完整流程 | 不变 |

**防退化与留痕**（继承 DC-010 的两个要求）:

- fast 面板必须含物化摘要表全列（决策落地核对面不允许省略——这是契约的审批核心）
- Main Agent 把通道判定写入 `dc001-decisions.yaml` 的 `channel` 字段 + 四项标准逐项判定结果

**应急兜底**: `DC001_FORCE_FULL=1` 环境变量 → 一律强制 full（保留通道存在性，门仍在）
