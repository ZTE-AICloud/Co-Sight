# DC-010: 需求澄清审批

> 触发: Step 1（agent 线需求澄清完成后）/ Step 0（skill-foundry create 模式, v0.18 新增）
> 协议类型: content_review
> 目标: 确保需求理解正确，后续步骤基于正确的需求执行
> v0.18 泛化: agent 三条原文不动，skill 通道以追加节形式添加

## 审批流程

需求澄清器（requirement-clarifier）完成诊断式访谈后，输出 `clarified-{agent|skill}-requirements.yaml`。
Main Agent 在进入 Step 2a（agent 线）或 step-s1-skill-plan-create（skill-foundry）之前，必须按 **mode 感知**的三项标准确认。

### Agent 模式（原文, 不动）

1. `clarified-agent-requirements.yaml` 的 `confidence >= 70`
2. `why` / `what` / `how` / `quality` / `acceptance_criteria` 五个维度均有内容
3. `open_questions` 中标记为 `blocked` 的项不超过 1 个

### Skill 模式（v0.18 追加, 与 agent 互不覆盖）

1. `clarified-skill-requirements.yaml` 的 `confidence >= 70`
2. Q1-Q4 决策（`operation_mode` / `knowledge_assets` / `granularity_hint`）+ `trigger_scenarios` + `acceptance_criteria` 均非空
3. `open_questions` 中标记为 `blocked` 的项不超过 1 个

> **R4 缓解 (unified-requirement-clarifier.md §6)**: agent 三条标准原文保留, skill 标准以「Skill 模式」追加节形式添加, 两节互不覆盖。Main Agent 按 mode 路由判定。

## 两级通道（C3）

三项标准**全部通过** → **快速通道**；任一未通过 → **完整通道**（维持原有 content_review 流程不变）。
无论走哪条通道，审批门本身不跳过——取消/调整选项始终可用。

| 通道 | 判定 | 展示 | 适用场景 |
|------|------|------|----------|
| 快速通道 fast | 三项标准全过 | 一行摘要 + 确认/调整/取消 三选项 | 标准澄清流程走完、无阻塞项 |
| 完整通道 full | 任一标准未过 | 「展示内容」全部四项逐条展示 + 标注未过标准及原因 | 有未决问题 / 低置信度 / 维度缺口 |

**摘要防退化要求 (agent 模式)**: 快速通道的一行摘要必须包含 YAML 五个维度各自至少一个具体事实
（如 why 的用户角色、what 的边界、how 的核心流程、quality 的指标、验收标准的 given/when/then），
禁止泛化文本（"一个高质量的 Agent" 这类空洞表述不允许）。

**摘要防退化要求 (skill 模式, v0.18 新)**: 快速通道的一行摘要必须包含
- skill 名称（`skill_name`）
- 操作模式（`operation_mode`，引用 guide.yaml §1 Q1, 不内联 mode 名称）
- 粒度（`granularity_hint`：split / single, 引用 guide.yaml §2 G1-G2 阈值, 不内联 400 行数值）
- 触发场景（`trigger_scenarios` 至少 1 条）
- 验收标准（`acceptance_criteria` 至少 1 条 given/when/then）
禁止泛化文本（"一个高质量的 Skill" 这类空洞表述不允许）。

**可追溯要求**: Main Agent 在 AskUserQuestion 后，把通道选择（fast/full）写入
orchestrator-state.yaml 的 steps[] 中对应 step_id 的 `human_approval_channel` 字段，含三项标准的逐项判定结果。
- agent 线: `step-1-requirement-clarification`
- skill-foundry: `step-s0-clarify`（v0.18 新 step_id, 见 skill-foundry/references/workflow.md §Step 0）

## 展示内容

完整通道下向用户展示需求理解摘要（按 mode 提取）:

**agent 模式:**
- 一句话描述构建什么
- 用户角色和使用场景
- 核心功能边界（包含/不包含）
- 主要风险或担忧

**skill 模式 (v0.18 新):**
- 一句话描述这个 Skill 干什么
- 操作模式（引 guide.yaml §1 Q1, 不内联）+ 粒度（引 guide.yaml §2）
- 触发场景（trigger_scenarios）
- 验收标准（acceptance_criteria 首条 given/when/then）
- 知识资产覆盖（references / scripts / templates 哪几类）

## 审批选项

- **确认，继续** — 进入 Step 2a（agent）/ step-s1-skill-plan-create（skill）
- **需要调整** — 携带修改意见回到 Step 1（agent）/ Step 0（skill）重新澄清
- **取消** — 终止 pipeline

## 与 DC-001 / DC-002 的关系

DC-010 是前置审批（需求层面），DC-001（agent）/ DC-002（skill）是后置审批（方案层面）。
skill-foundry 模式下, DC-010 → DC-002 二次审批; agent 线 DC-010 → DC-001 二次审批。
