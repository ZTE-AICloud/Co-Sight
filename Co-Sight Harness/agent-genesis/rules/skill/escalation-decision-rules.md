# 升级判定规则 — Skill 优化 vs Agent 优化

> 适用: Skill Foundry step-s1（optimize / diagnose 模式, 边界判定）
> 加载者: skill-planner（optimize / diagnose 模式）, Main Agent（diagnose mode 早终止决策）

---

## 1. Skill vs Agent 问题判定矩阵

不是所有 Skill 问题都能在 Skill 层面解决。以下矩阵用于判定根因是否超出 Skill 范围：

| 问题类型 | Skill 范围（可优化） | Agent 范围（需升级） |
|---------|:---:|:---:|
| **Role/Identity** — Agent 身份定义错误、职责边界模糊 | | ✓ |
| **Prompt 结构** — 步骤顺序不合理、单步过大、缺 I/O 契约 | ✓ | |
| **逻辑一致性** — 步骤间 I/O 断裂、指令自相矛盾、条件分支不可判定、输入不足以支撑输出 | ✓ | |
| **知识加载** — 知识太大、来源缺失、L2/L3 策略不当 | ✓ | |
| **Memory 噪声** — 长期记忆积累错误信息、历史干扰当前决策 | | ✓ |
| **Tool 权限** — 缺少必要工具、权限范围不当、工具选择策略 | | ✓ |
| **中间产物** — 步骤间产物未持久化、数据传递方式不当 | ✓ | |
| **校验机制** — 缺 G1 审查、缺自动校验、缺 Schema 约束 | ✓ | |
| **状态管理** — 缺 checkpoint、断点恢复失败、进度不可见 | ✓ | |
| **单步任务质量** — 单步任务（非 Pipeline）执行质量低 | | ✓ |
| **输出格式** — 格式不固定、缺 Schema、下游难消费 | ✓ | |
| **确定性操作** — LLM 在做精确比对/格式校验等非推理任务 | ✓ | |
| **Agent 间协调** — Multi-Agent 间调度、上下文隔离、权限分级 | ✓ | ✓ |
| **设计形态** — 目录分层、渐进式加载、命名约定、描述公式 | ✓ | |
| **全局上下文** — Role/Tool/I/O/Safety 与 Agent 定义的对齐 | ✓ | ✓ |
| **跨 Skill 关系** — 多 Skill 功能重叠、职责矩阵、调用依赖 | ✓ | |

> ✓ 标记表示该问题类型的主战场。混合标记（Skill ✓ \| Agent ✓）表示两者都可能涉及，需根据根因深度判断。

---

## 2. 边界判定流程

```
诊断根因
  │
  ▼
Q1: 根因是否可以通过修改 SKILL.md（含 rules/、commands/、agents/ 同级文件）解决？
  │
  ├── 是 → Q2: 修改范围是否 ≤ 2 个文件？
  │         ├── 是 → 纯 Skill 优化 → 继续
  │         └── 否 → 标注"变更范围较大" → 继续（仍属 Skill 优化）
  │
  └── 否 → Q3: 根因是否涉及 Agent 级配置（CLAUDE.md Role/Memory/Tool/Permission）？
            ├── 是 → Q4: Skill 优化能否部分缓解问题？
            │         ├── 能 → 混合场景 — 先做 Skill 优化 + 输出 Agent 优化建议
            │         └── 不能 → 完全是 Agent 问题 — 输出 Agent 优化建议 → 退出
            └── 否 → 需要更多信息 → 返回 Phase 1 进一步诊断
```

## 3. Agent 优化触发条件（任一满足即建议升级）

以下具体信号表明问题超出 Skill 范围，应建议走 Agent 优化：

1. **Agent Role 定义错误**
   - 信号: Skill 执行正确但 Agent 整体定位不对（如把分析 Agent 当构建 Agent 用）
   - 判定: 修改 SKILL.md 无法改变 Agent 的核心行为和身份

2. **Memory 噪声积累**
   - 信号: Agent 在同一会话中越执行越差，新开会话后恢复；旧结论干扰新决策
   - 判定: Skill prompt 无法控制 Memory 写入策略

3. **Tool 权限/选择问题**
   - 信号: Skill 调用某工具始终失败（权限不足）；或 Agent 选择了错误工具
   - 判定: 需要修改 Agent 的 tools: 列表或权限范围

4. **单步任务质量低（非 Pipeline）**
   - 信号: 单体 Agent（无 SubAgent）执行单步任务质量差，但 Skill 指令已足够清晰
   - 判定: 问题在 Agent 基础能力或模型选择，非 Skill 结构问题

5. **上下文窗口过载**
   - 信号: Skill 已拆分合理，但 Agent 仍因上下文窗口爆炸导致质量骤降
   - 判定: 可能需要拆分为 Multi-Agent 以利用独立上下文窗口（Agent 架构变更）

## 4. 升级报告模板

当判定为"部分超出"或"完全超出"时，输出以下结构化报告：

```markdown

**来源**: {skill-name} 优化诊断
**日期**: {timestamp}

## 发现的 Agent 级问题

| # | 类型 | 严重级别 | 证据 |
|---|------|:---:|------|
| 1 | {类型: Role/Memory/Tool/单步质量/上下文} | CRITICAL/HIGH | {从诊断报告中引用的具体证据} |

## Root Cause

{为什么这个问题超出了 Skill 优化的范围？}

## 建议优化方向

1. {具体建议 1}
2. {具体建议 2}

## Skill 层面已完成的事项

```

## 5. 多 Skill 场景判定

> **范围限定**: 多 Skill 分析仅处理 **功能性** 冲突（输出路径碰撞、依赖循环、触发词歧义、共享资源提取、功能重叠导致的 DRY 违反）。**不得**基于结构相似性（行数、目录结构、步骤格式、分解粒度）触发合并/重组。详见 [skill-diagnosis-rules.md §6.5](skill-diagnosis-rules.md#65-反模式-姐妹-skill-结构对齐禁止)。

当用户提交 2+ 个 Skill 同时优化时，触发额外的判定逻辑：

### 5.1 多 Skill 输入类型

| 场景 | 输入特征 | 优化策略 |
|------|---------|---------|
| 独立多 Skill | 用户提交多个无关 Skill | 逐个诊断，独立优化，并行执行 |
| 关联多 Skill | Skill 间存在调用/数据/文件依赖 | 先建依赖矩阵 → 联合诊断 → 批量协调优化（模式 10+11） |
| 候选合并 Skill | 功能高度重叠（同逻辑在 2+ Skill 中重复实现，非仅结构相似）、各自行数 <300 | 诊断是否应合并为一个 Skill → 推荐合并方案 |
| 候选拆分 Skill | 单个 Skill >800 行、含 2+ 独立功能域 | 诊断是否应拆分 → 推荐拆分方案（模式 9） |

### 5.2 多 Skill 关联判定流程

```
收到 2+ Skill 优化请求
  │
  ▼
Q1: 这些 Skill 属于同一个 Agent 吗？
  │
  ├── 否 → 独立优化，不交叉
  │
  └── 是 → Q2: Skill 间是否存在文件引用、数据传递、调用关系？
              │
              ├── 否 → 独立优化，但共享 Global Context 检查（同 Agent 约束一致）
              │
              └── 是 → Q3: 依赖关系的复杂度？
                        ├── 简单（单向 A→B）→ 按依赖顺序优化，先底层后上层
                        ├── 复杂（双向/网状/未明确）→ 全局批量优化（模式 11）
                        └── 重叠（功能高度重合）→ 推荐合并或重分配（模式 10）
```

### 5.3 Agent 调用流更新提示

当执行模式 9（拆分）或模式 10（重组）时，必须生成调用流变更提示：

```markdown
# Agent 调用流变更提示

**变更来源**: {skill-name} {拆分/重组}
**影响范围**: {Agent 名称} 的 Skill 调用流程
**变更类型**: 拆分 / 合并 / 重分配 / 提取共享

## 当前调用流

（当前 Agent 中调用该 Skill 的方式和位置）

## 变更后调用流

（更新后的调用方式、顺序、触发条件）

## 需修改的文件

| 文件 | 变更说明 | 优先级 |
|------|---------|:---:|
| {CLAUDE.md / Orchestrator / Command} | {具体需修改的内容} | HIGH/MEDIUM |

## 迁移步骤

1. {步骤 1}
2. {步骤 2}

## 兼容性

- 旧调用方式是否仍可用？{是/否}
- 如不可用，过渡期方案：{方案}
```

### 5.4 跨 Skill 冲突检测

批量优化时必须检测以下冲突类型：

| 冲突类型 | 信号 | 解决策略 |
|---------|------|---------|
| 输出路径冲突 | 两个 Skill 输出到相同文件路径 | 协商唯一输出路径，或明确覆盖规则 |
| 触发词重叠 | 两个 Skill 的 description 覆盖相同触发场景 | 细化触发条件，或合并为一个 Skill |
| 工具权限不一致 | 同 Agent 下 Skill A 调用工具 X，Skill B 无权限 | 统一权限声明，或标注为差异化授权 |
| 状态文件冲突 | 两个 Skill 使用同名状态文件 | 加 Skill 前缀隔离，或统一状态文件格式 |
| 依赖循环 | Skill A 依赖 B 的输出，B 依赖 A 的输出 | 打破循环：提取公共依赖为独立 Skill，或合并两者 |

## 6. Plan Mode 升级话术

### 6.1 Agent 级升级话术

当在 Plan Mode 展示方案时，如果涉及 Agent 级升级建议：

```
## 诊断结果

{展示诊断摘要和优化方案}

---

> **注意**: 诊断发现 {N} 个问题超出 Skill 优化范围，属于 Agent 级问题：
> - {问题 1}
> - {问题 2}
>
> 以上问题涉及 Agent {Role/Memory/Tool/...} 的调整，Skill 优化无法解决。
> 建议走 Agent 优化路径。Agent 优化能力将在后续版本中提供。
>
> 当前可继续执行 Skill 层面的优化（{可解决的方面}），剩余部分是否需要输出 Agent 优化建议报告？
```

### 6.2 多 Skill 场景话术

当用户提交 2+ 个 Skill 时：

```
## 多 Skill 分析

| Skill | 诊断结果 | 与其他 Skill 关系 |
|-------|---------|-----------------|
| {Skill A} | {N} 项发现 | 被 {Skill B} 依赖 |
| {Skill B} | {M} 项发现 | 依赖 {Skill A} 的输出 |
| {Skill C} | {K} 项发现 | 与 {Skill A} 功能重叠（相似度: X%） |

### 推荐策略

{独立优化 / 关联协调优化 / 合并 / 拆分}

### 优化顺序

1. {先优化的 Skill}（原因: {依赖关系}）
2. {后续 Skill}

---
是否按此策略继续？
```

### 6.3 Skill 拆分/重组话术

当推荐拆分或重组时：

```
## 拆分/重组建议

### 当前状态
- SKILL.md: {N} 行，{M} 个功能域

### 建议: {拆分为 X 个 Skill / 合并 / 重分配}

| 新 Skill | 职责 | 预计行数 |
|----------|------|:---:|
| {skill-a} | {职责描述} | ~{N} |
| {skill-b} | {职责描述} | ~{M} |

### Agent 调用流变更

原调用: `{原始调用方式}`
新调用: `{更新后的调用方式}`

> 详细变更提示见 work/{skill-name}/optimize-skill/call-flow-changes.md

### 迁移路径

1. 创建新 Skill 目录
2. 更新 Agent 调用流
3. 保留旧 Skill 作为兼容层（{是/否}）

---
是否执行以上拆分/重组方案？
```
