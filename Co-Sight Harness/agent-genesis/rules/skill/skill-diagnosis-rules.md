# Skill 诊断规则

> 适用: Skill Foundry step-s1（optimize / diagnose 模式）
> 加载者: skill-planner（optimize / diagnose 模式, 阶段1诊断）
> 参考: Anthropic 官方 Skill 规范 — 目录结构 (SKILL.md + references/ + scripts/ + templates/)、三级渐进式加载 (L1/L2/L3)、描述公式、命名约定

---

## 1. 6 维诊断框架

### 维度 1: Decomposition（分解）

| 症状 | 诊断问题 | 根因假设 |
|------|---------|---------|
| Skill 执行时间明显过长 | 单体 prompt 是否超过有效上下文窗口？ | 步骤过多未拆分，中间产物丢失需重复推理 |
| 输出质量随执行进度衰减 | 后段步骤是否因前段上下文占满而"失焦"？ | 上下文窗口竞争，后期指令被稀释 |
| 中间步骤产物不可追溯 | 步骤间是否有明确 I/O 契约和文件落盘？ | 纯 context 传递，无中间产物持久化 |
| 修改一步需要重新执行全部 | 步骤间耦合度是否过高？ | 无模块化隔离，牵一发动全身 |

### 维度 2: Information（信息）

| 症状 | 诊断问题 | 根因假设 |
|------|---------|---------|
| 输出出现幻觉（编造内容） | Skill 引用的知识是否太大无法一次加载？ | 缺失关键知识，LLM 自行"填补" |
| 不同执行间输出不一致 | 是否有外部权威来源未对接？ | LLM 内嵌知识不稳定，缺乏固定参考源 |
| 关键信息遗漏 | 知识加载策略是否合理（L2/L3）？ | 知识未加载或加载不全 |
| 引用错误（参数名/字段名/版本号） | 是否定义了知识边界（CD3）？ | 未区分 LLM 可信域与外部检索域 |

### 维度 3: State（状态）

| 症状 | 诊断问题 | 根因假设 |
|------|---------|---------|
| 中断后无法从断点恢复 | 执行到哪一步了？是否有 checkpoint？ | 无状态持久化，进程内存级状态丢失 |
| 重复执行已完成步骤 | 步骤完成状态是否记录在文件系统中？ | 纯 context 记忆，重启后遗忘 |
| 进度不可见 | 用户能看到当前执行到哪步吗？ | 缺少进度汇报机制（IV1） |
| 并发执行时状态冲突 | 多实例是否共享状态文件？ | 无锁/无隔离，竞态条件 |

### 维度 4: Verification（校验）

| 症状 | 诊断问题 | 根因假设 |
|------|---------|---------|
| 错误从中间步骤传播到最终输出 | 关键中间步骤有校验门禁吗？ | 缺 G1 审查或 Hook 检查，错误下传 |
| 输出格式不固定，下游难消费 | LLM 是否在做它不擅长的事（精确比对、格式校验）？ | 依赖 LLM 做确定性操作，应改用脚本 |
| 人工检查成本高 | 有没有自动化质量评估？ | 缺 Review Agent 或自动校验机制 |
| 相同输入多次执行结果差异大 | 非确定性步骤是否被校验约束？ | 缺 DF1 Schema 或确定性命令 |

### 维度 5: Logic Consistency（逻辑一致性）

> 检查 Skill 内部指令的逻辑自洽性：步骤间 I/O 是否闭合、是否存在矛盾指令、依赖顺序是否合理、条件分支是否完备。这是**功能性维度**，与 Design Form（结构性维度）互补。

#### 5.1 步骤间 I/O 闭合

| 症状 | 诊断问题 | 根因假设 |
|------|---------|---------|
| 某步骤的输入来源不明 | 该步骤的输入是否由前序步骤产出或外部输入提供？ | 缺少前置步骤，或 I/O 契约未声明 |
| 某步骤的输出未被后续消费 | 该步骤的产出是否在后续步骤中有明确消费者？ | 死步骤（产出无用）或消费者遗漏 |
| 中间产物传递断裂 | 步骤 A 声称产出 X，步骤 B 声称消费 X——X 的定义/格式是否一致？ | 同名不同义，或格式不匹配 |
| 缺少关键中间数据 | 从输入到输出的推理链中是否有"魔法步骤"（无明确输入却产生输出）？ | 隐含依赖未声明，或步骤缺少输入来源 |

#### 5.2 指令内在矛盾

| 症状 | 诊断问题 | 根因假设 |
|------|---------|---------|
| 同一 Skill 中存在互斥指令 | 是否有"A 必须做 X"和"A 不应做 X"的矛盾声明？ | 不同时期添加的指令未协调，历史积累导致冲突 |
| 安全约束与执行步骤冲突 | Safety Constraints 禁止的操作是否在 Execution Steps 中被调用？ | 安全约束后加，未回溯清理执行步骤 |
| 触发条件与职责描述不匹配 | description 声明的触发场景与实际执行步骤的适用场景是否一致？ | description 修改后未同步更新步骤，或反之 |

#### 5.3 步骤顺序合理性

| 症状 | 诊断问题 | 根因假设 |
|------|---------|---------|
| 先消费后生产 | 步骤 N 的输入依赖步骤 N+1 的输出？ | 步骤排序错误，或依赖声明有误 |
| 并行步骤被错误串行化 | 两个无依赖关系的步骤被强制先后执行？ | 未识别独立性，导致不必要的执行时间 |
| 关键校验放在太靠后的位置 | 应该在步骤早期执行的校验（如输入合法性）被放到后期？ | 校验步骤添加时机不当，错误传播距离长 |

#### 5.4 条件分支完备性

| 症状 | 诊断问题 | 根因假设 |
|------|---------|---------|
| 分支条件不可判定 | "如果 X 则 A，否则 B"——X 是否有明确的判定标准？ | 条件描述模糊（如"如果质量好"缺少质量标准） |
| 分支覆盖不完整 | 是否存在输入情况不被任何分支覆盖？ | 分支枚举遗漏边界情况 |
| 死分支 | 是否存在永远不满足条件的分支？ | 条件过于严格或与其他条件互斥 |

#### 5.5 输入输出支撑

| 症状 | 诊断问题 | 根因假设 |
|------|---------|---------|
| 输入不足以支撑输出 | 声明的输入是否足够产出声明的输出？ | 缺少必要的中间知识或数据源 |
| 输出粒度与输入不匹配 | 输入是粗粒度但输出要求细粒度（或反之）？ | 缺少中间细化/聚合步骤 |
| 输出格式未定义 | 步骤产出输出但格式未声明，下游无法消费？ | 缺少 Schema 或格式约定 |

### 维度 6: Design Form（设计形态）— 基础性优先维度

> **FOUNDATIONAL**: Design Form 是基础性维度。结构分层问题（单体文件、有需分层内容但未建立对应目录、无渐进式加载）必须**最优先诊断和修复**，因为结构形态决定了后续所有功能优化（分解、信息加载、校验、状态管理）的实施方式。
>
> 参考 Anthropic 官方 Skill 规范：目录结构分层、三级渐进式加载、描述公式、命名约定

#### 5.0 强制结构检查（优先执行）

> 以下 4 项为**硬检查**，在诊断开始时优先执行。任一项 FAIL → Design Form 维度自动 FAIL，严重级别 ≥ HIGH。

| # | 强制检查 | 通过标准 | FAIL 严重级别 |
|:--:|---------|---------|:------------:|
| DF-M1 | **目录分层（条件性）** | 如有需分层的内容（参考文档/脚本/模板），应有对应目录；精简 Skill 无此类内容则 PASS | HIGH |
| DF-M2 | **渐进式加载** | SKILL.md 不内联 >100 行的参考文档或代码块；详细文档通过文件引用指向 references/；可执行逻辑通过 Bash 调用指向 scripts/ | CRITICAL |
| DF-M3 | **描述公式** | `description` 包含「做什么」+「何时触发」+「输入」+「输出」 | HIGH |
| DF-M4 | **脚本独立（条件性）** | 如有确定性操作（校验/格式化/计算/转换），应通过 Bash 调用 scripts/ 脚本；无确定性操作则 PASS | HIGH |

> **执行顺序**: 诊断启动后 → 先执行 DF-M1~M4 → 再执行下方症状表 → 最后执行 SF-1~8 检查清单。

| 症状 | 诊断问题 | 根因假设 |
|------|---------|---------|
| SKILL.md 过长（>300 行），所有内容内联 | 是否违反了渐进式加载原则（L1/L2/L3）？ | 未使用 references/ 分离详细文档，未使用 scripts/ 分离可执行逻辑 |
| 有参考文档/脚本/模板但无目录分层 | 是否有需要分层的内容未放入对应目录？ | 内容需要分层但未建立目录结构（精简 Skill 无此类内容跳过） |
| 描述模糊，触发条件不明确 | description 是否包含「做什么」+「何时用」+「输入/输出」？ | 缺少功能描述公式，Agent 无法准确判断何时触发 |
| Skill 名称不够具象化 | 名称是否包含领域关键词（如「Python」「Security」「Code Review」）？ | 名称过于宽泛（如「helper」「utils」），与其他 Skill 区分度低 |
| 资源文件路径混乱 | references/ 和 scripts/ 下的文件是否有明确的命名和引用约定？ | 缺乏文件组织规范，引用路径依赖硬编码 |
| SKILL.md 中大量代码示例或脚本 | 可执行脚本是否提取到 scripts/ 目录？ | 代码嵌入 Markdown 导致阅读困难、无法独立测试 |
| 缺少使用示例或模板 | 是否有 templates/ 提供可复用的输入/输出模板？ | 用户每次需要从头构造输入，使用门槛高 |
| 与其他 Skill 存在功能重叠 | Skill 的职责边界是否清晰？与其他 Skill 是否有明确区分？ | 缺少 Skill 间职责矩阵，功能重叠导致触发歧义 |
| references/ 中文件未被 SKILL.md 引用 | 是否有孤立文件（未被任何入口引用）？ | 渐进式加载的 L3 引用链断裂 |

**Anthropic Skill 规范检查清单**:

| # | 检查项 | 规范要求 |
|:--:|------|---------|
| SF-1 | 目录结构 | SKILL.md 位于根，有需分层的内容时 references/、scripts/、templates/ 按需分层 |
| SF-2 | L1 启动加载 | name + description 在 Agent 启动时加载，description 含功能+触发条件+输入/输出 |
| SF-3 | L2 按需加载 | SKILL.md body 在 name/description 匹配时加载，含核心指令和 references 引用 |
| SF-4 | L3 深度加载 | references/ 下文件仅在 SKILL.md 明确引用时才 Read，不预加载 |
| SF-5 | 命名约定 | Skill 名称具象化，含领域关键词，kebab-case 命名目录 |
| SF-6 | 描述公式 | `「做什么」+「何时触发」+「接收什么输入」+「产出什么输出」` |
| SF-7 | 脚本独立 | scripts/ 下脚本可独立运行和测试，不依赖 LLM 上下文 |
| SF-8 | 模板可用 | templates/ 下模板可直接复制使用，含必要占位符和说明 |

### 维度 7: Global Context（全局上下文）

> 检查 Skill 与所在 Agent 整体设计的契合度，确保不违反 Agent 设计原则

**6.1 Agent 设计原则对齐**

| 症状 | 诊断问题 | 根因假设 |
|------|---------|---------|
| Skill 的行为与 Agent Role 定义冲突 | Skill 的职责边界是否与 Agent 的 Role & Boundaries 一致？ | Skill 越权执行了不属于 Agent 职责范围的操作 |
| Skill 要求的工具权限超出 Agent 授权 | Skill 依赖的工具是否在 Agent 的 tools: 白名单中？ | Skill 设计时未考虑 Agent 权限边界 |
| Skill 的输出格式与 Agent 下游期望不符 | 下游消费者（人/机器/SubAgent）能否直接消费输出？ | 缺少 Agent 级 I/O Contract 对齐检查 |
| Skill 的 Safety Constraints 与 Agent 不一致 | 是否存在 Skill 允许但 Agent 禁止的操作？ | Skill 和 Agent 的安全约束未统一 |

**6.2 共享文件系统与中间产物**

| 症状 | 诊断问题 | 根因假设 |
|------|---------|---------|
| 中间文件路径与 Agent 的 work/ 约定冲突 | Skill 的中间产物路径是否遵循 Agent 的文件系统约定？ | 路径硬编码，未使用 Agent 统一的 work/ 目录 |
| 输出文件位置不一致 | 最终输出是否落盘到 Agent 约定的目录？ | 缺少统一的输出路径约定 |
| 临时文件残留 | Skill 是否清理执行过程中产生的临时文件？ | 缺少临时文件生命周期管理 |
| 文件名冲突 | 多 Skill 并行时是否可能产生文件名冲突？ | 使用固定文件名而非唯一化命名 |

**6.3 状态管理与 Agent 生命周期**

| 症状 | 诊断问题 | 根因假设 |
|------|---------|---------|
| Skill 状态文件与 Agent 状态机不同步 | Skill 内部状态是否与 Agent 全局状态（如 Phase）一致？ | 两套独立状态系统，不同步 |
| 断点恢复与 Agent 中断策略冲突 | Skill 的 checkpoint 机制是否兼容 Agent 的恢复策略？ | 各自维护恢复逻辑，冲突 |
| 长期运行 Skill 无进度上报 | Agent 能否感知 Skill 的执行进度？ | 缺少进度回调或状态更新机制 |

**6.4 Review 策略对齐**

| 症状 | 诊断问题 | 根因假设 |
|------|---------|---------|
| Skill 自审代替 Agent 级审查 | Skill 内部审查是否绕过 Agent 的 G1 Reviewer？ | 用 Skill 内自审替代独立审查，缺乏 game mechanism |
| 错误处理与 Agent 升级策略不匹配 | Skill 的错误重试次数和升级条件是否与 Agent 一致？ | 各自定义重试/升级策略，行为不一致 |

**全局上下文检查清单**:

| # | 检查项 | 判定方法 |
|:--:|------|---------|
| GC-1 | Role 一致性 | 比对 Skill 职责描述与 CLAUDE.md Role & Boundaries 章节 |
| GC-2 | Tool 权限对齐 | 对比 Skill 调用的工具与 Agent tools: 白名单 |
| GC-3 | I/O Contract 对齐 | 检查 Skill 输入/输出格式是否匹配下游期望 |
| GC-4 | Safety 约束一致性 | 对比 Skill 安全策略与 CLAUDE.md Safety Constraints |
| GC-5 | 文件路径约定 | 检查中间/输出文件路径是否符合 Agent work/ 约定 |
| GC-6 | 状态机同步 | 检查 Skill 状态标记是否与 Agent Phase 兼容 |
| GC-7 | Review 策略对齐 | 确认 Skill 不自审代替 Agent G1 审查 |
| GC-8 | 临时文件管理 | 确认有临时文件清理策略，无残留风险 |

### 6.5 反模式: 姐妹 Skill 结构对齐（禁止）

> **CRITICAL**: Global Context 的对齐目标是 **Agent 的整体设计**（CLAUDE.md 中定义的 Role、Tools、I/O Contract、Safety Constraints、State Machine、文件系统约定），**不是**同目录下其他 Skill 的结构或风格。

**禁止行为**:

| 反模式 | 错误做法 | 正确做法 |
|--------|---------|---------|
| **行数对齐** | 因 Skill A 319 行、Skill B 534 行 → 要求 Skill C 也接近此范围 | 每个 Skill 的行数由其功能复杂度决定，不因姐妹 Skill 而异 |
| **结构对齐** | 因姐妹 Skill 有 references/ 目录 → 要求目标 Skill 也必须有 | 是否需 references/ 取决于 Skill 自身知识量，非姐妹 Skill 结构 |
| **风格对齐** | 因姐妹 Skill 用 YAML 定义步骤 → 要求目标 Skill 也改用 YAML | 步骤描述格式由 Skill 自身语义决定，不同功能可能需要不同格式 |
| **分解对齐** | 因姐妹 Skill 拆分为 N 个 SubAgent → 要求目标 Skill 也拆 N 个 | 是否拆分取决于单 Skill 的复杂度和耦合度，非姐妹 Skill 的拆分数 |
| **命名对齐** | 因姐妹 Skill 用特定前缀 → 要求目标 Skill 加同样前缀 | 命名反映 Skill 自身功能，不因姐妹 Skill 的命名约定而修改 |

**允许的跨 Skill 关注（仅功能性冲突）**:

| 允许 | 条件 |
|------|------|
| 输出路径冲突检测 | 两个 Skill 写入同一文件路径 → 需要协调 |
| 依赖循环检测 | Skill A 读 Skill B 输出，Skill B 读 Skill A 输出 → 死锁 |
| 触发词歧义 | 两个 Skill 的 description 触发条件完全相同 → 路由歧义 |
| 共享资源提取 | 多个 Skill 引用相同的 references/ 文件 → 可提取到 Agent 级共享位置 |

**判定原则**: "这个修改是因为 Agent 要求如此，还是因为姐妹 Skill 如此？" —— 前者保留，后者删除。

## 2. 诊断流程

```
Step 1: 收集
  - 读取目标 SKILL.md 完整内容
  - 收集用户反馈（问题症状、期望行为）
  - 如用户提供目标路径，检查文件存在并记录文件大小/行数

Step 2: 逐维对照（Design Form 优先）
  - **先执行维度 6**: Design Form — 执行 DF-M1~M4 强制结构检查 → 逐症状对照 → SF-1~8 检查清单
  - **再执行维度 5**: Logic Consistency — I/O 闭合、指令矛盾、步骤顺序、分支完备性、输入输出支撑
  - 维度 1-4: Decomposition / Information / State / Verification（Skill 内核）
  - 维度 7: Global Context — 检查 Skill 与 Agent 整体设计的契合度
  - 每个维度: 有症状 → 记录症状 + 诊断问题 + 根因假设
  - 无症状 → 标注 PASS

Step 3: 优先级排序
  - CRITICAL: 输出幻觉、安全性问题（CD2 缺失）
  - HIGH: 错误传播、不可恢复中断
  - MEDIUM: 执行效率、用户可见进度
  - LOW: 轻微不一致

Step 4: 输出诊断报告
  - 按模板输出，含证据引用（SKILL.md 具体行号或章节）
```

## 诊断摘要
