# Skill Router — 意图路由与分发

在多能力共存的项目中，用户的一个请求常常同时命中多个候选能力。本 Skill
提供一套确定性路由约定：路由表分路、消歧规则排序、链式调用手动化、
能力边界决策框架。核心原则：**路由是规则驱动（K4）的查表行为，不是语义
猜测**——相同的输入必须路由到相同的目标。

## When to Use

- 用户请求含糊，多个专项能力都可能匹配（"帮我看看这段代码"——是审查还是调试？）
- 为项目设计或维护多 Skill 路由约定（路由表、消歧规则、串联协议）
- 新增能力后需要决定它的触发边界与既有能力的消歧关系
- 判断一项新能力应该写成 Skill（LLM 判断）还是脚本（确定性执行）

## 核心机制（四件）

### 1. 阶段分路路由表

把触发词按工作流阶段分组，建立"触发特征 → 目标能力"的集中索引表。
阶段划分参考软件生命周期四段：动手前（设计/方案）、交付前（审查/发布）、
出问题（诊断/排错）、内容进出（读写/研究）。完整表格模式与列约定见
`references/routing-table.md`。

### 2. 特异性排序的消歧规则

多命中时按规则逐条判定，规则按特异性从高到低排列，格式统一为
`IF <具体条件> THEN route to <具体能力>`。例："已交付走 PR"→审查能力；
"跑不通有报错"→诊断能力。规则集与编写要点见
`references/disambiguation-rules.md`。

### 3. 手动链式调用

能力之间默认**不自动串联**。每个能力完成后停下，由用户决定下一步——
除非当前请求已明确授权后续动作（如"review then ship if green"）。
这是关键决策点的人类控制权保留（IH3 同构原则）。

### 4. Fat Skill vs Deterministic Script 决策框架

新增能力时先问一个问题：

```
需要判断 / 适应场景 / 追问用户？  →  Skill（Markdown 指令 + LLM 判断）
同入同出 / 只是校验和列举？      →  脚本或规则（确定性执行）
```

两个极端都要避免：全写成 Skill（成本高、不稳定），全写成脚本（灵活性差）。
决策细节与反例见 `references/fat-vs-script.md`。

## Execution Steps

### Step 1 — 路由查表

按请求特征匹配路由表中最高特异性的阶段分路。单命中直接给目标能力；
多命中进 Step 2。

### Step 2 — 消歧判定

按消歧规则逐条核对，取第一条命中的规则。无规则覆盖时：读候选能力的
"不适用"段用排除法；仍模糊则追问用户，不猜测。

### Step 3 — 输出路由结论

给出目标能力 + 命中依据（哪条规则/哪个触发特征）。如需串联后续动作，
停下来等用户确认，不自动执行。

## 路由表维护约定

- 路由表是集中索引：新增能力时同步登记触发特征，并声明与既有能力的
  消歧关系（哪条规则区分两者）。
- 消歧规则按特异性排序存放，新规则插入时保持序——兜底规则永远最后。
- 路由表与能力定义（description）必须一致；漂移即失效，定期对照。

## Not for

- 单能力项目（无路由问题，不用本 Skill）
- 需要实时动态加载/卸载能力运行时的场景（本 Skill 是静态路由约定）
- 跨会话状态传递（每次路由独立执行，无状态管理）
