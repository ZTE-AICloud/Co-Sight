# 知识库（RAG Studio 工作流）

> 状态：**已定稿（2026-10-28）**。本文定义 `GET /knowledge/workflows/list`：创建 / 优化智能体时选择「知识检索」工作流的唯一数据源。
> 代码落点：`server/src/modules/knowledge/*`。
> 验收测试：`server/tests/knowledge.test.ts`（认证头、只列已发布、字段映射、上游失败翻译）。

## 1. 为什么是代理

知识检索工作流由 **RAG Studio**（co-knowledge）维护，本服务只做**只读代理**：

- 上游原生 REST 没有 CORS 预检（`OPTIONS` 直接 404），浏览器不能直连；
- 原生 `/workflows` 走本地会话 / 网关鉴权，Agent Key 不生效（401）；**Agent API `/agent/workflows` 才认 Agent Key**；
- 列表只取「已发布」，这个口径属于产品规则，放在服务端比放在每个调用方稳。

凭据（Agent API Key）只存在服务端环境变量里，永不下发浏览器。

## 2. 端点

```http
GET /api/smart-factory/v1/knowledge/workflows/list
```

无请求参数，无分页：一次拉全量（上游 `page=1&size=500`），搜索在前端做。

### 2.1 成功响应

```json
{
  "items": [
    { "id": "RAG_Workflow_89f4", "name": "顺序检索", "description": "测试顺序检索" },
    { "id": "RAG_Workflow_e69d", "name": "图谱检索测试", "description": "" },
    { "id": "RAG_Workflow_780f", "name": "test1", "description": "" }
  ],
  "total": 3
}
```

| 字段 | 说明 |
|---|---|
| `items[].id` | 上游 `workFlowId`（大写 F）；拼进 harness-create 的 `--knowledge-workflow-id` |
| `items[].name` | 展示名；上游缺失时退回 `id` |
| `items[].description` | 上游描述，缺失为空串 |
| `total` | 上游报告的**过滤前**总数，仅用于排查；前端不据此分页 |

**只返回已发布**：`/agent/workflows` 会按 `publishType=1` 过滤（实测 `total=3`），但代理仍按返回字段**再筛一遍** —— 换部署或上游回退到不认参数的原生 `/workflows` 时，草稿（`publishType=0`）不能漏出去；草稿送进 `/query` 只会 `404 published_workflow_not_found`。
**id 必须合法**：`^[A-Za-z0-9_-]{1,128}$`（与注入器同一把尺子），不合法的条目不出现。

### 2.2 失败响应

统一 `502 BAD_GATEWAY`，`message` 是可直接显示的中文，`messageKey` 为 `error.bad_gateway.knowledge`（**刻意不在前端词表登记**，否则通用文案会盖掉「该改哪个变量」）。

| 场景 | message 关键内容 |
|---|---|
| 没有任何服务地址（框架无生效路由且 `CO_KNOWLEDGE_BASE_URL` 为空） | 同时指出「框架设置」与 `CO_KNOWLEDGE_BASE_URL`（只到根地址，不带路径） |
| 没有任何 Agent Key（框架两层都没有且 `CO_KNOWLEDGE_API_KEY` 为空） | 同时指出「框架设置」与 `CO_KNOWLEDGE_API_KEY`（`ragk_...` 形态） |
| 上游 401 / 403 | 检查 Agent Key 是否有效 |
| 上游非 2xx | `知识库返回 HTTP <status>` |
| 超时 / 连不上 | `连不上知识库服务（<base>）：超时（>Nms）` |
| 响应不是 JSON / 缺 `items` | 明确说结构不符，**不降级成空列表** |

## 3. 配置

**来源优先级：框架设置 → 环境变量。** 每次请求现取（不缓存），设置里改完立即生效。

1. 框架模块面 `GET /api/framework/v1/rag-knowledge/active`（令牌 `$COSIGHT_HOME/.module-token`）：
   - 基址 = `routeUrl` 的 **origin**（`new URL(routeUrl).origin`，丢掉 path / query / hash）。
     出厂默认 `http://rag-studio.example.com/#/login?redirect=/kb` → `http://rag-studio.example.com`。
   - Key = 响应里的 `apiKey`。它是**生效值**：路由自己的 Key 优先，没配时是框架服务端的默认
     （`COSIGHT_KNOWLEDGE_API_KEY` / `CO_KNOWLEDGE_API_KEY`），所以不必再判断框架那一层。
2. 框架不可达（没启动 / 令牌不可用 / 没有生效路由 `data: null`）或字段缺失时，逐字段回落到下面两个环境变量。

落点：`server/src/modules/knowledge/knowledge-source.ts`；用例：`server/tests/knowledge-source.test.ts`。

| 变量 | 缺省 | 说明 |
|---|---|---|
| `CO_KNOWLEDGE_BASE_URL` | 空 | **兜底**服务根地址，如 `http://rag-studio.example.com`；代理自己拼 `/api/co-knowledge/v1/agent/workflows` |
| `CO_KNOWLEDGE_API_KEY` | 空 | **兜底** Agent API Key（`ragk_...`），走 `X-API-Key` |
| `CO_KNOWLEDGE_LIST_TIMEOUT_MS` | `8000` | 列表请求超时 |

> 派生基址只在「知识库网页与 Agent API 同源」时成立。默认部署（出厂路由指向的 RAG Studio）如此；
> 若以后前端与 API 分属不同主机/端口，`routeUrl` 的 origin 就会指错，此时应让用户在框架里填
> API 所在源，或退回 `CO_KNOWLEDGE_BASE_URL`（框架没有生效路由时自动兜底）。

> 注意：同名的 `CO_KNOWLEDGE_*` 也会被引擎子进程继承。产物里的 `rag-knowledge-search` 技能与本模块
> **共用同一套来源与同一枚 Agent API Key**：技能同样优先读框架生效路由（`routeUrl` + `apiKey`），
> 框架不可用时才回落 `CO_KNOWLEDGE_BASE_URL` / `CO_KNOWLEDGE_API_KEY`，调用
> `POST /api/co-knowledge/v1/agent/query`（`Authorization: Bearer`）。区别只在用途——本模块用于列表代理，
> 技能用于问答检索；框架里换 Key 会同时改变两边。

## 4. 上游事实（实测，2026-10-28）

```http
GET http://rag-studio.example.com/api/co-knowledge/v1/agent/workflows?page=1&size=500&publishType=1
X-API-Key: ragk_...
```

```json
{ "items": [ { "workFlowId": "RAG_Workflow_780f", "name": "test1", "description": "",
               "publishType": 1, "status": 1, "template": "Blended", "knowledgeType": "knowledgeBase" } ],
  "total": 3, "page": 1, "pageSize": 500 }
```

| 上游路径 | 认证 | `publishType=1` | 备注 |
|---|---|---|---|
| `/api/co-knowledge/v1/agent/workflows` | `X-API-Key`（或 `Authorization: Bearer`） | **生效**（`total=3`） | 本服务固定走这条 |
| `/api/co-knowledge/v1/workflows` | 本地会话 cookie / 网关 | **被忽略**（`total=8`，5 条草稿） | 浏览器也不能直连（无 CORS） |

- 响应字段名是 `workFlowId`，不是 `workflowId` / `id`。
- 两种 Agent Key 传法都收：`X-API-Key: ragk_...` 与 `Authorization: Bearer ragk_...`；本服务用前者。

## 5. 刻意不做

- 不代理建库、上传、检索、问答（管理面与 `/query` 都在 RAG Studio；本服务只列工作流）。
- 不缓存：列表小、变更少，但缓存会让「刚发布的工作流选不到」成为难排查的问题。
- 不校验 workflow 是否真的可问答：`/query` 只接受已发布工作流，格式与发布态已经足够；真正的连通性在预览阶段试问时暴露。

## 6. 选中值存在哪

本接口只管「有哪些可选」。选中值属于**智能体自己的配置**：

- 创建时随首条消息的参数（`--knowledge-workflow-id RAG_Workflow_xxx`）落进 `agents.knowledge_workflow_id`（服务端从 `init.input` 解析）；
- 之后在设计页的 chip 上改 / 取消，走 `POST /agents/{agentId}/update` 的 `knowledgeWorkflowId` 字段（空串 = 取消，不传 = 不改）；
- 发送 harness-create 消息时，前端按这份配置拼参数 —— 取消之后不会再带，历史消息里的旧参数也不会把它复活。

它只决定**下一次请求参数**；已注入产物的 `rag-knowledge-search` 技能不会因此删除。

要真正从产物里移除，需要一次**重建**：详情里的 `knowledgeInjected` 回答「产物里现在有没有」，
设计页据此提示「产物仍在使用知识检索」，并给一个「移除并重建」按钮。按钮只使用 harness-create
**现有的入口接口**发一条自然语言请求（不带 `--knowledge-workflow-id`，明确要求按 create 重建、
移除知识检索）——agent-genesis 不在本模块的可修改范围内，所以没有专用移除参数；产物里的知识
章节能否清掉，取决于它现有的重建流程。只删技能目录不行：CLAUDE.md / workflow / rules 里的
知识章节会变成断链。

详见 [5.01 Agent](../05-openapi/5.01-agent-openapi.yaml) 与 [`../03-architecture/08-agent.md`](../03-architecture/08-agent.md) §3.1。
