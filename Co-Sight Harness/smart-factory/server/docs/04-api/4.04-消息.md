# 消息

> 状态：**已定稿**。消息是会话里的一条产出或一次挂起，是前端渲染的唯一数据源，本篇给出 3 个消息端点的请求与响应全貌、全字段表与 `content` 形状。
> 代码落点：`server/src/modules/session/session.service.ts`、`server/src/shared/store/messages.repo.ts`。
> 验收测试：`server/tests/session-api.test.ts`、`server/tests/approval.test.ts`、`server/tests/api-contract.test.ts`。
> 相关篇：[4.02 通用规范](./4.02-通用规范.md)（前缀、id 传法、分页与错误体）、[4.03 会话](./4.03-会话.md)、[4.05 运行](./4.05-运行.md)、[4.06 实时通道](./4.06-实时通道.md)、[审批与交互](../03-architecture/06-approval.md)。

## 1. 端点总表

| 方法 | 路径 | 请求 | 成功响应 |
|---|---|---|---|
| GET | `/api/smart-factory/v1/messages/list` | `?sessionId=&runId=&beforeSeq=&afterSeq=&limit=&status=` | `200` `{ items: Message[], nextAfterSeq: number \| null }` |
| POST | `/api/smart-factory/v1/messages/send` | `{ sessionId, prompt, attachments? }` 或 `{ agentId, modelId, mode?, effort?, prompt, attachments? }` | `200` `{ sessionId, runId, instanceId, status, effort, modelId, modelName, modelFellBack, message: Message, run: Run }` |
| POST | `/api/smart-factory/v1/messages/respond` | `{ messageId, decision? }` 或 `{ messageId, answers? }` | `200` `Message` |

历史消息**一律走 REST**，WebSocket 只做实时（见 [`4.06 实时通道`](./4.06-实时通道.md)）。
本文 curl 以 `http://localhost:4100` 为基址，端口取自 `PORT`（缺省 4100）。

## 2. Message 全字段表

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 消息 id，形态 `msg_<uuid>`，全局唯一；前端渲染与去重都以它为准 |
| `sessionId` | string | 所属会话 id |
| `runId` | string \| null | 产出它的 run；`messages/send` 落的那条 user 消息为 `null`，引擎产出与挂起消息为本次 run 的 id |
| `seq` | number | **会话内**从 1 起单调递增的排序键，`(sessionId, seq)` 唯一；列表一律按它升序 |
| `role` | `'user'` \| `'assistant'` \| `'system'` | 发言方，用于气泡归属；判断渲染形态请用 `type` |
| `type` | 见下表 | 消息种类，决定 `content` 的形状 |
| `status` | `'pending'` \| `'approved'` \| `'approved_all'` \| `'rejected'` \| `'answered'` \| `'aborted'` \| null | **只有 `approval` 与 `tool_interactive` 非 null**，其余类型恒为 `null` |
| `content` | object | 永远是对象（库内是 JSON 字符串，接口上一律解析成对象）；形状由 `type` 决定，见 §3 |
| `createdAt` | string | ISO 8601，如 `2026-10-15T02:20:33.220Z` |

`type` 取值与产出方：

| `type` | 由来 | 典型 `role` |
|---|---|---|
| `text` | `messages/send` 落的用户输入；引擎的每个文本块 | `user` / `assistant` |
| `thinking` | 引擎的每个思考块 | `assistant` |
| `tool_use` | 引擎的每次工具调用 | `assistant` |
| `tool_result` | 引擎的每个工具结果 | `assistant`（工具结果块也落成助手消息，前端按 `type` 区分调用与结果，不要看 `role`） |
| `approval` | 引擎请求工具审批时由服务端挂起（或 `approved_all` 自动放行） | `assistant` |
| `tool_interactive` | 引擎请求结构化提问时由服务端挂起（Claude 适配器走 `AskUserQuestion`） | `assistant` |
| `error` | run 失败时服务端补落一条，`content.message` 与 `run.error` 同源 | `system` |
| `status` | 预留类型，当前实现不产出 | - |

落库粒度：真实引擎下，**每个** assistant 文本块、思考块、`tool_use` 块，以及**每个** `tool_result` 块，各落一条 message。
`AskUserQuestion` 的 `tool_use` 与 `tool_result` **不落库**，它由 `type='tool_interactive'` 那条挂起消息承载（结算后带 `answers`）。

`status` 的状态机：

```text
approval:          pending --> approved | approved_all | rejected | aborted
tool_interactive:  pending --> answered | aborted
```

## 3. `content` 按 type 的形状

`content` 在库里是 JSON 字符串，在接口上一律是对象，前端按 `type` 对号入座。

### 3.1 `text` / `thinking`

```json
{ "text": "我先读一下仓库结构。" }
```

`text` 是该段的**整体值**，不是增量，见 §7。

`role='user'` 且由 `messages/send` 落下的那条，可能多一个 `files`：

```json
{
  "text": "看看这两份材料",
  "files": [
    { "id": "file-1", "name": "/home/u/project/CLAUDE.md" },
    { "id": "file-2", "name": "/home/u/project/spec/api.yaml" }
  ]
}
```

`files` 是**这条消息自己的字段**，不是本地临时状态：历史接口、`message` 事件、`chat.final` 的 `messageId` 指到的终稿都能读到它，所以刷新、换标签页、别的客户端看到的附件一致。`name` 是绝对路径，展示时建议取最后一段并把完整路径挂 `title`。

### 3.2 `tool_use`

```json
{
  "toolCallId": "toolu_01H8k2mN",
  "toolName": "Bash",
  "input": { "command": "echo hi" }
}
```

### 3.3 `tool_result`

```json
{
  "toolCallId": "toolu_01H8k2mN",
  "output": "hi\n",
  "isError": false
}
```

`toolCallId` 与对应的 `tool_use` 相同，前端据此把结果挂到调用卡片上。

### 3.4 `approval`（结算前后）

挂起时（`status='pending'`）：

```json
{
  "toolCallId": "toolu_01H8k2mN",
  "toolName": "Bash",
  "title": "允许执行 Bash？",
  "description": "echo hi",
  "input": { "command": "echo hi" },
  "allowAll": false
}
```

- `toolCallId` 是该次工具调用的 SDK `toolUseID`，与对应 `tool_use` 消息的 `toolCallId` 同值，前端据此把审批卡挂到调用条目上（适配器拿不到时字段缺省）。
- `title` / `description` 是给人看的卡片文案：适配器优先采用 SDK 已渲染好的文案，缺失时回退到按工具名与输入拼装，前端原样展示，不要自己拼。
- `allowAll` 是**可选**字段：只有引擎明确要求本次询问不得提供「本会话全部允许」时才出现且恒为 `false`（示例即这种形态），字段缺省表示可以提供，前端据此决定是否展示该按钮。

用户应答后（`status='approved' | 'approved_all' | 'rejected'`）：在挂起内容之上**追加**两个字段，原有字段不丢。

```json
{
  "toolCallId": "toolu_01H8k2mN",
  "toolName": "Bash",
  "title": "允许执行 Bash？",
  "description": "echo hi",
  "input": { "command": "echo hi" },
  "allowAll": false,
  "decision": "approved",
  "decisionSource": "user"
}
```

`decision` 取值 `'approved' | 'approved_all' | 'rejected' | 'aborted'`。
`decisionSource` 取值 `'user'`（用户点的）、`'approved_all_auto'`（本 run 开了全部允许后自动放行，此时 `status='approved_all'`，这条只作审计轨迹）、`'abort'`（运行被中止；关服 SIGINT / SIGTERM 结算残留挂起也用这个值）、`'restart'`（服务重启收口）。
中止或重启结算时 `status='aborted'`、`decision='aborted'`。

### 3.5 `tool_interactive`（结算前后）

挂起时（`status='pending'`）：

```json
{
  "toolCallId": "toolu_01H8k3xP",
  "toolName": "AskUserQuestion",
  "questions": [
    {
      "header": "格式",
      "question": "要处理什么格式？",
      "options": [
        { "label": "JSON", "description": "结构化输入" },
        { "label": "CSV" }
      ],
      "multiSelect": false
    }
  ]
}
```

应答后（`status='answered'`）：追加 `answers`。

```json
{
  "toolCallId": "toolu_01H8k3xP",
  "toolName": "AskUserQuestion",
  "questions": [
    {
      "header": "格式",
      "question": "要处理什么格式？",
      "options": [
        { "label": "JSON", "description": "结构化输入" },
        { "label": "CSV" }
      ],
      "multiSelect": false
    }
  ],
  "answers": { "要处理什么格式？": ["CSV"] }
}
```

`toolCallId` 是该次提问的 SDK `toolUseID`；AskUserQuestion 的 `tool_use` 不落库（提问本身由本条承载），前端不必去找对应的工具条目。
`answers` 的 key 是 `questions[].question` 的**原文**（与 SDK 的 `AskUserQuestion` 一致），value 是选中项 `label` 的数组（多选时多个）；对外的形状恒为 `Record<string, string[]>`，`{}` 表示用户未作答。
提交给 SDK 前会以**被问的问题**为权威归一：未被问到的 key 直接丢弃，多选答案按 `', '` 拼接（SDK 契约是 `{ [问题原文]: string }`）；归一只影响交给 SDK 的载荷，不改变上面这个对外形状。
被中止或重启结算时（`status='aborted'`）只有 `decisionSource`，没有 `answers`。

### 3.6 `error` / `status`

```json
{ "message": "模型调用未成功：error_during_execution" }
```

```json
{ "code": "SLOW_CONSUMER", "message": "…" }
```

`error` 的 `code` 与 `status` 的整个形状都是预留位，当前实现只写 `message`，前端按「有则展示」处理。

## 4. 获取消息列表

```text
GET /api/smart-factory/v1/messages/list
```

Query 参数：

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `sessionId` | string | 二选一 | 会话消息流：该会话的全部消息 |
| `runId` | string | 二选一 | 单次运行的消息流：只含本次 run 产出的消息（user 消息的 `runId` 为 `null`，不在其中） |
| `beforeSeq` | number | 否 | 向上翻页游标：返回 `seq` **严格小于**它的消息 |
| `afterSeq` | number | 否 | 向下增量游标：返回 `seq` **严格大于**它的消息 |
| `limit` | number | 否 | 条数上限，缺省 50，上限 200（超出按 200 截断） |
| `status` | string | 否 | 按消息状态过滤，取值同 [`Message.status`](#2-message-全字段表)；不在枚举内即 `400` |

`sessionId` 与 `runId` 必须**给且只给一个**，都缺或都给返回 `400`。
`beforeSeq` 与 `afterSeq` 同时给返回 `400`。
非法数字（非整数、负数）按未传处理。

### 4.1 取数窗口

三种模式，返回的 `items` **一律 `seq` 升序**：

| 请求 | 取哪一段 | 用途 |
|---|---|---|
| 不带游标 | `seq` 最大的 `limit` 条（最近 `limit` 条） | 进会话首屏：先拿最新一屏，不关心上面还有多少 |
| 只带 `beforeSeq=N` | `seq < N` 中最大的 `limit` 条 | 向上翻页（加载更早） |
| 只带 `afterSeq=N` | `seq > N` 中最小的 `limit` 条 | 增量续拉、轮询新消息 |

向上翻页的下一页游标用 `items[0].seq`（本页最小 `seq`）继续作 `beforeSeq`，直到 `items` 为空或条数不足 `limit`。
向下续拉用响应的 `nextAfterSeq` 继续作 `afterSeq`。

### 4.2 `nextAfterSeq`

规则：`items` 非空且条数**等于** `limit` 时为最后一条的 `seq`，否则为 `null`。

- 用「最近 `limit` 条」首屏时，把它当作后续增量拉取的起点：下一次 `afterSeq=nextAfterSeq` 就只拿到新到达的消息。
- 它表达的是「这个方向上可能还有更多」，不是「总共有多少条」。

请求实例（首屏）：

```bash
curl -s 'http://localhost:4100/api/smart-factory/v1/messages/list?sessionId=sess_9c1d4b7a&limit=50'
```

请求实例（向上翻页）：

```bash
curl -s 'http://localhost:4100/api/smart-factory/v1/messages/list?sessionId=sess_9c1d4b7a&beforeSeq=3&limit=50'
```

请求实例（取未结算的挂起，刷新后恢复弹窗的入口）：

```bash
curl -s 'http://localhost:4100/api/smart-factory/v1/messages/list?sessionId=sess_9c1d4b7a&status=pending'
```

响应实例 `200`：


### 4.3 刷新后怎么把画面拼回来

浏览器的内存状态丢了，服务端与数据库都没变，按三步重建：

1. `messages/list?sessionId=<id>&limit=50` 拉最近一屏历史。
2. `messages/list?sessionId=<id>&status=pending` 拉所有还没结算的审批与交互，把它们渲染成可操作弹窗。
3. 重新订阅会话，之后的实时事件继续到达；断线期间丢掉的流式增量不会重放，所以第 1、2 步是补历史与补挂起的权威手段（订阅时会补发什么，见 [`4.06 实时通道`](./4.06-实时通道.md)）。

注意 `messages` 不是 append-only 表：`status` 与 `content` 会变（审批从挂起变成已批准），所以**不能只按 `afterSeq` 增量续拉**，重连后必须重拉当前页或至少重拉一次 `?status=pending`。

## 5. 发送消息

```text
POST /api/smart-factory/v1/messages/send
```

请求体：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `sessionId` | string | 三选一（至多） | 续聊目标会话；与 `agentId` 至多给一个 |
| `agentId` | string | 三选一（至多） | 新建 runtime 会话的智能体；与 `sessionId` 至多给一个，每次调用都新建会话 |
| `modelId` | string | 新建会话时必填 | 新会话的框架模型 uuid，非空且可运行；`agentId` 与自由对话（两者都不给）都必填；给 `sessionId` 时禁止出现 |
| `mode` | string | 否 | 新会话审批模式，缺省 `workspace_write`；仅新建会话时接受，给 `sessionId` 时禁止出现 |
| `effort` | string | 否 | 新会话推理强度，缺省 `high`；仅新建会话时接受，给 `sessionId` 时禁止出现 |
| `prompt` | string | 条件必填 | 用户输入正文；**只有带了非空 `attachments` 时允许为空串**，两者都为空回 `400` |
| `attachments` | `Array<{ path: string }>` | 否 | 用户指定的**本机文件绝对路径**，最多 20 项（裸字符串也接受）。端侧形态下没有上传，路径就是全部内容；三种形态都接受 |

语义要点：

- **定位方式至多给一个**：`sessionId` 与 `agentId` 都给返回 `400`；**都不给 = 自由对话**（不选智能体）。
- `send { sessionId, prompt }`：续聊已有会话，使用该会话的 `modelId` / `approvalMode` / `effort`。
  请求里出现 `modelId` / `mode` / `effort` 任一字段返回 `400`。
- `send { modelId, mode?, effort?, prompt }`（两者都不给）：**自由对话**，每次新建一条目录会话（`agentId=null`、`stage='runtime'`）。
  cwd 取框架当前生效工作区的目录；没有生效工作区时落到 `{COSIGHT_HOME}/smart-factory/chat`（不存在则创建）；工作区存在但未绑目录 / 框架不可达返回 `502`，不悄悄换目录。
  目录实例是实例级仲裁：同一 cwd 同时只能有一个活跃顶层 run，第二个 `send` 返回 `409`。
- `send { agentId, modelId, mode?, effort?, prompt }`：**每次新建一条 `runtime` 会话**，不复用任何已有会话。
  `modelId` 必填、非空且可运行（不存在 / 协议不符 / 无密钥 `400`，框架不可达 `502`）；`mode` 缺省 `workspace_write`、`effort` 缺省 `high`，取值非法 `400`。
  三个字段都持久化到新会话，首轮 run 使用它们，`resumeSessionId` 为 `null`。
- **失败清理**：模型可运行性校验失败时不建会话；建会话后模型详情解析失败返回 `400` / `502`，产物门禁失败按下文返回 `404` / `409`。
  并发首帧互不挤占名额（见 [`02-data-model.md`](../03-architecture/02-data-model.md) §6）。
  上述失败都会删除刚建的会话，不留空会话；给 `sessionId` 时解析失败不创建任何会话。
- 一次 `send` 依次完成：**校验正文与附件** → 解析发送目标（取已有会话或新建会话）→ **在建 run 前**解析起跑条件（引擎适配器、工作区 / 阶段 cwd、模型）→ 以 `running` 建 run 并抢 session 级与非 `runtime` 的实例级仲裁 → 落一条 user 消息（`role='user'`、`type='text'`、`content` 见下、`runId=null`）→ 置会话 `in_progress` → 广播 `run.started` → 返回。
  任一步失败时直接返回错误，**不建会话、不建 run、不落用户消息、不改会话状态**。
- **附件只以路径的形式存在**（端侧服务与 Claude Code 同机，没有上传）：
  - 落库：`content = { text: prompt, files: [{ id, name }] }`，`name` 是解析后的**真实绝对路径**，`id` 由服务端按顺序生成（`file-1`…）。不带附件时仍是 `{ text: prompt }`，形状不变。
  - 进引擎：服务端把附件展开成一段文本接到 `prompt` 末尾（「以下是用户指定的本机文件，请直接用 Read 工具读取：- /abs/path」），**落库的正文保持用户原话**。引擎用 Read 工具自己读文件，服务端不读、不转码、不截断。
  - 校验与文件选择器同源：必须是绝对路径、存在、是文件（**浏览范围不设限**，整机任意位置都能选）；不满足回 `400` / `404`（见 4.07 §1）。同一路径重复出现只保留一份。
- 用户消息**不带 `runId`**（`runId: null`），按 `runId` 查消息列表不会返回它 —— 取这一轮的用户输入请按 `sessionId` 查。
- 返回的 `run.status` 恒为 `'running'`，`startedAt` 已落值（建 run 时写入），`finishedAt` / `error` 为 `null`，`waiting` 为 `null`。
  顶层 `status` 同为 `'running'`；`effort` / `modelId` / `modelName` / `modelFellBack`（恒 `false`）随响应返回，客户端不必再查会话列表；响应**没有** `created` 字段。
- `run.started` 在响应之前广播，且仅当广播时 run 仍为 `running`；期间被并发中止时跳过 `run.started` 与引擎启动，由 `closeRun` 收口，终态 run 永不补发起跑事件。
- 该会话处于 `completed` 时自动复活为 `in_progress`，`not_started` 同样进入 `in_progress`；状态变化会经 WS 的 `session.status` 广播。
- **活跃顶层 run 冲突**：`send { sessionId }` 在该会话已有活跃顶层 run 时返回 `409`；非 `runtime` 阶段同 agent 同 stage 的**其它会话**正在跑同样会挡住本次发送，前端应提示「该智能体正在运行」；`development` 起 run 时同 agent 有活跃 runtime run 也返回 `409`。
  `send { agentId }` 的并发首帧各自新建会话，不互相挤占名额；完整不变量见 [`02-data-model.md`](../03-architecture/02-data-model.md) §6。
  冲突时**不落任何消息、不起 run**。
- **建 run 前解析 cwd 与模型**：`runtime` 取最新 `vN` 产物目录（原地）；`preview` / `evaluation` 每次 send 时 ensure 一次（源 mtime 未变则跳过）；服务端调框架详情 `GET /api/framework/v1/models/{id}`，要求详情存在、`protocol='anthropic'`、`apiKey` 与 `modelName` 非空。
  模型不存在 / 协议不符 / 缺密钥 / 缺 `modelName` 返回 `400`，框架不可达或 5xx 返回 `502`，**不回退到工作区默认模型、框架生效模型或本机配置**。
  引擎启动后的运行期异常才落在 `run.status='failed'` 与 `type='error'` 的消息上。
- 引擎在响应之后异步启动，只使用已解析的适配器 / cwd / 模型，不重复解析、不重复置 running；本请求不等它结束，后续消息与状态变化走 WS。
- WS 上的 `send` 是同一服务路径的另一入口，见 [`4.06 实时通道`](./4.06-实时通道.md) §4.3。

## 6. 结算审批与交互

```text
POST /api/smart-factory/v1/messages/respond
```

**只有这一个结算端点**，因为审批与交互是同一个机制，传什么由目标消息的 `type` 决定：

| 目标消息 `type` | 请求体 | 结算后 `status` |
|---|---|---|
| `approval` | `{ messageId, decision: 'approved' \| 'approved_all' \| 'rejected' }` | 与 `decision` 同值 |
| `tool_interactive` | `{ messageId, answers: { "<问题原文>": ["<选项 label>", …] } }` | `'answered'` |

语义要点：

- 载荷与消息 `type` 不匹配返回 `400`；消息不存在、或 `type` 不是 `approval` / `tool_interactive` 返回 `404`；消息已结算返回 `409`。
- `decision` 只接受三个值，`'aborted'` 是服务端内部值，不接受客户端传入。
- `decision='approved_all'` 时，服务端在赢下结算仲裁之后、放行引擎之前把会话置为 `approvalMode='full_access'`、`approvedAll=true`；本 run 后续审批与之后的新 run 都不再挂起（仍会落一条审计消息，`status='approved_all'`、`decisionSource='approved_all_auto'`）。该开关是会话级的，经 `mode.switch` 切到非 `full_access` 才复位，没有单独的重置端点。
- `answers` 必须是对象且**每个 value 都是字符串数组**，否则 `400`；key 本身不校验（约定用 `questions[].question` 原文，未被问到的 key 提交后会被丢弃），`{}` 表示未作答。
- 仲裁由数据库条件更新完成（`WHERE id=? AND status='pending'`），并发或重复应答只有一个成功，其余拿 `409`。
- 结算成功会经 WS 广播更新后的这条 `message`，前端按 `id` 覆盖渲染即可。
- WS 上的 `message.respond` 是同一服务路径的另一入口，响应包在 `payload.message` 里。

## 7. 实时增量与落库的关系

- `chat.delta` 是 WS 事件，载荷 `{ sessionId, runId, parentRunId, messageType: 'text', delta }`，**只承载正文**。
- 思考增量走 `chat.thinking`，载荷 `{ sessionId, runId, parentRunId, phase: 'start' | 'delta' | 'stop', text?, at }`；`text` 仅 `phase='delta'` 出现，`start` / `stop` 只表示思考块边界。旧的 `chat.thinking.delta` 已删除。
- 两者都是**瞬态的、不落库**：断线即丢，也可能因为背压断开而整段丢失，所以只能用于流式渲染，不能当可靠信道。
- 同一 `runId` 的 `chat.delta` 是同一段正文的累加；同一 `runId` 的 `chat.thinking` `delta` 是同一段思考的累加。前端分别追加到正文 / 思考缓冲，不能混在一起。
- 落库的 `message`（`type='text'` 或 `'thinking'`）是该段的**整体值**：收到就用 `content.text` 整体覆盖本地缓冲，并开始等待下一段。
  会话里的 `text` 段可能有多条（引擎产出多个文本块），每次收到落库消息都意味着「上一段定稿、下一段另起」。
- `chat.final` / `chat.error` / `chat.aborted` / `chat.retry` 是收尾或重试通知，不是内容增量；`chat.retry` 表示 run 仍在继续。
- run 中途结束（含被中止）时，已经流出但还没有终稿的那一段会以累积值补落一条消息，前端同样按整体值覆盖，因此刷新后不会丢内容。
- 断线期间丢失的 `chat.delta` / `chat.thinking` 不会重放，终稿由落库的 `message` 补齐。
- `tool_use` / `tool_result` / `approval` / `tool_interactive` / `error` **只有落库的 `message`，没有 delta**。
- 挂起与结算是同一条消息的两次 `message` 事件（upsert 语义）：前端按 `id` 覆盖，不要追加。
- 因此「刷新后把画面拼回来」= 拉最近 N 条 + 拉 `?status=pending` + 重新订阅（见 §4.3）；实时通道的订阅语义、无回放边界与事件清单见 [`4.06 实时通道`](./4.06-实时通道.md)。

## 8. 错误码汇总

| HTTP | `error` | 出现在 |
|---|---|---|
| 400 | `BAD_REQUEST` | `messages/list` 的 `sessionId` / `runId` 传递不合法、两个游标同时给、`status` 非法；`messages/send` 的 `sessionId` 与 `agentId` 同时给、`prompt` 缺失或为空且无附件、`attachments` 形状或路径不合法、`send { sessionId }` 携带 `modelId` / `mode` / `effort`、新建会话（`agentId` / 自由对话）缺 `modelId`、`mode` / `effort` 非法、模型不可用、引擎适配器未知；`messages/respond` 的 `messageId` 缺失、载荷与消息 `type` 不匹配 |
| 404 | `NOT_FOUND` | `messages/send` 的会话或智能体不存在，或 development 目录 / 运行产物缺失；`messages/respond` 的目标消息不存在或不是交互类；未匹配到任何路由 |
| 409 | `CONFLICT` | `messages/send` 面对已有活跃 run 的会话（`send { sessionId }`），或非 `runtime` 阶段面对已有活跃 run 的实例，或 `development` 起 run 遇到同 agent 的活跃 runtime run；产物生产状态未完成 / 候选歧义 / 没有版本目录；`messages/respond` 面对已结算的消息 |
| 502 | `BAD_GATEWAY` / `FRAMEWORK_UNAVAILABLE` | `messages/send` 的工作区解析失败，或模型详情解析时框架网络异常 / 5xx（建 run 之前；不建 run、不落消息、不改会话状态） |

错误响应体统一为 `{ "error": "<码>", "message": "<中文兜底>", "messageKey": "<i18n 键>", "params": { ... } | null }`，由错误中间件产出；`messageKey` / `params` 的含义与降级规则见 [`4.02-通用规范.md`](./4.02-通用规范.md) §10.1。

**解析失败发生在建 run 之前**：引擎适配器、工作区目录、阶段 cwd、预览 / 评估物化、模型任一步失败，`messages/send` 直接返回上表的错误，不建 run、不落用户消息、不改会话状态。
**只有引擎启动后的运行期异常才算 run 内失败**：落在 `run.status='failed'` 与 `type='error'` 的消息上，此时 `messages/send` 已返回 `200`。前端不要把解析失败当成 run 失败去等 `run.status`。
