# 通用规范

> 状态：**已定稿**。本文定义所有接口共用的请求与响应规范：前缀、方法、id 传法、分页与游标、校验口径、错误码与鉴权。
> 代码落点：`server/src/app.ts`（路由装配）、`server/src/middleware/error-handler.ts`、`server/src/shared/validate.ts`、`server/src/shared/errors.ts`、`server/src/shared/ids.ts`、`server/src/shared/live/envelope.ts`。
> 验收测试：`server/tests/api-contract.test.ts`（契约边界）、`server/tests/session-api.test.ts`、`server/tests/ws.test.ts`。

本文按「约定 → 确切值 → 违反的后果」组织，每条都给可直接照着写的实例。
基址与端点清单见 [`./4.01-接口总览.md`](./4.01-接口总览.md)，各资源的字段形状见 [`./4.03-会话.md`](./4.03-会话.md)、[`./4.04-消息.md`](./4.04-消息.md)、[`./4.05-运行.md`](./4.05-运行.md)、[`./4.06-实时通道.md`](./4.06-实时通道.md)。

## 1. 前缀与版本

**约定**：所有路径（含 WebSocket）统一前缀 `/api/smart-factory/v1`，前缀里不进 id、不进资源名之外的段。

**确切值**：REST 基址 `http://{host}:{port}/api/smart-factory/v1`，WS 入口唯一 `ws://{host}:{port}/api/smart-factory/v1/ws`；`port` 来自 `PORT`，缺省 `4100`。

```bash
# REST
curl -s http://localhost:4100/api/smart-factory/v1/health

# WebSocket（路径写死在 config.wsPath，与 REST 同端口）
# ws://localhost:4100/api/smart-factory/v1/ws
```

**违反的后果**：前缀写错（多一段、少一段、换版本号）不匹配任何路由，返回 `404 NOT_FOUND`，响应体带实际收到的路径：

```json
{ "error": "NOT_FOUND", "message": "无匹配路由：GET /api/smart-factory/health",
  "messageKey": "error.not_found.route", "params": null }
```

前端开发态只写相对路径 `/api/smart-factory/v1/...`，由 vite 代理转发；写成绝对地址会让开发与部署两套地址分叉。
WS 的代理条目必须带 `ws: true`，否则握手按普通 HTTP 转发、连接永远建不起来。

## 2. HTTP 方法

**约定**：只许 `GET` 与 `POST`。读用 `GET`，写一律 `POST`，写操作的语义靠路径末段的动作词表达。

**确切值**：`DELETE` / `PUT` / `PATCH` 一律禁用，一个都没注册。

```bash
# 对：删除走 POST + 动作词
curl -s -X POST http://localhost:4100/api/smart-factory/v1/sessions/delete \
  -H 'Content-Type: application/json' -d '{"sessionId":"sess_1f0a..."}'

# 错：DELETE 不是本接口的方法，换成任何路径也一样
curl -s -X DELETE http://localhost:4100/api/smart-factory/v1/sessions/delete
```

**违反的后果**：方法不在注册表里就匹配不到路由，返回 `404 NOT_FOUND`（不是 `405`）：

```json
{ "error": "NOT_FOUND", "message": "无匹配路由：DELETE /api/smart-factory/v1/sessions/delete",
  "messageKey": "error.not_found.route", "params": null }
```

`PUT` / `DELETE` / `PATCH` 的方法级语义（替换 / 删除）与「中止」「结算」这类业务动作对不上，所以写操作收敛成「`POST` + 动作词」单一形态。

## 3. 动作词白名单

**约定**：路径末段只能是十一个动作词之一，资源名固定，两者都不许现造。
`05-openapi/` 覆盖的 agents 域除外：无动作词路径（`GET/POST /agents`、`GET /agents/{agentId}`）的语义由 HTTP 方法表达（GET 取、POST 建），动作词只出现在个体写路径末段（`/agents/{agentId}/update`）。

**确切值**：`list` / `detail` / `create` / `update` / `delete` / `rename` / `abort` / `send` / `respond` / `file` / `download`。
本期端点用到其中十个（`list`、`detail`、`create`、`update`、`delete`、`abort`、`send`、`respond`、`file`、`download`），`rename` 是预留位：将来加写端点时用它，不许发明新动词。

```bash
curl -s http://localhost:4100/api/smart-factory/v1/sessions/list
curl -s http://localhost:4100/api/smart-factory/v1/sessions/detail?sessionId=sess_1f0a...
```

**违反的后果**：不在白名单里的末段（如 `/sessions/query`、`/sessions/remove`）返回 `404 NOT_FOUND`，与「资源不存在」同一个码，靠 `message` 里的路径区分。

## 4. id 的位置：集合路径不带 id，个体与父子路径 id 进路径

**约定**：路径表达资源层级。集合级端点（列表、创建这类对整个集合的操作）路径只表达「哪个资源 + 哪个动作」，id 不出现；定位到具体资源的端点（个体操作、某资源下的子资源，如「某 agent 下的版本」）把 id 放进路径。本期 sessions / messages / runs 各端点均为集合级形态，agents 域（`05-openapi/`）按个体规则实现。

**确切值**：
- 集合级·查询：id 进 query 参数 - `GET .../sessions/detail?sessionId=sess_...`、`GET .../runs/detail?runId=run_...`
- 集合级·写：id 进请求体 - `POST .../sessions/delete` 请求体 `{"sessionId":"sess_..."}`、`POST .../messages/respond` 请求体 `{"messageId":"msg_..."}`
- 个体/父子级：id 进路径 - `GET /agents/{agentId}`；将来「某 agent 下的版本」即 `GET /agents/{agentId}/versions` 形态
- 无论 id 在 query、请求体还是路径，必填而缺失（或传空串、纯空白、路径段缺位）返回 `400 BAD_REQUEST`。

```bash
# 对：集合级查询 id 走 query
curl -s 'http://localhost:4100/api/smart-factory/v1/sessions/detail?sessionId=sess_1f0a...'

# 对：集合级写操作 id 走请求体
curl -s -X POST http://localhost:4100/api/smart-factory/v1/sessions/delete \
  -H 'Content-Type: application/json' -d '{"sessionId":"sess_1f0a..."}'

# 对：个体资源 id 走路径（agents 域）
curl -s http://localhost:4100/api/smart-factory/v1/agents/agt_9f8c1e2a-3b4d-4e5f-8a90-1b2c3d4e5f60
```

**违反的后果**：
- 集合级端点的路径里塞 id → `404 NOT_FOUND`，`message` 是 `无匹配路由：GET /api/smart-factory/v1/sessions/sess_1f0a.../detail`（sessions / messages / runs 的路由表是固定字符串，没有 id 段）。
- id 缺失或为空串 → `400 BAD_REQUEST`，`message` 是 `"<字段名> 必填"`：

```json
{ "error": "BAD_REQUEST", "message": "sessionId 必填",
  "messageKey": "error.bad_request.required", "params": { "name": "sessionId" } }
```

- id 形态合法但资源不存在 → `404 NOT_FOUND`，`message` 形如 `会话 sess_missing 不存在`。
两者的分界见 §11。

副作用：集合级端点路径里没有 id，日志与监控无法靠路径区分资源，所以服务端在每条日志里显式记录 id；个体/父子端点 id 已在路径上，日志同样显式记录 id，前后端口径一致；前端做埋点时也带上 id，不要只记路径。

## 5. 内容类型、时间与 id 前缀

**约定**：请求与响应都是 UTF-8 的 JSON；时间一律 ISO 8601；实体 id 带可读前缀。

**确切值**：
- 请求头 `Content-Type: application/json; charset=utf-8`；`charset` 缺省即 UTF-8，可以不写。
- 时间形如 `2026-10-14T09:56:00.000Z`（UTC、`T` 分隔、毫秒三位、`Z` 结尾），由服务端生成，客户端只解析不拼装。
- 服务端实体前缀：`agt_`（智能体）、`inst_`（实例）、`sess_`（会话）、`run_`（运行）、`msg_`（消息），格式 `<前缀>_<uuid>`；收养来的历史智能体保留原目录名、不带前缀（见 [`08-agent.md`](../03-architecture/08-agent.md) §1）。
- 实时通道前缀：`evt_<毫秒时间戳>_<序号>`（服务端事件 id）、`conn_<序号>`（连接 id），见 [`4.06-实时通道.md`](./4.06-实时通道.md)。
- 客户端上行请求 id 建议用 `req_<自增序号>`，服务端不校验其格式、原样回持，只要求它是字符串。

```bash
curl -s -X POST http://localhost:4100/api/smart-factory/v1/sessions/create \
  -H 'Content-Type: application/json; charset=utf-8' \
  -d '{"agentId":"my-agent","stage":"development","modelId":"a7cf0154-020b-4f97-b2bc-5ab8eb3bf0b5"}'
```

```json
{
  "id": "sess_3c9d2b1a-6f5e-4c7d-8a90-1b2c3d4e5f60",
  "instanceId": "inst_7b1c0d9e-2a3f-4b5c-9d8e-7f6a5b4c3d2e",
  "name": "",
  "status": "not_started",
  "modelId": "a7cf0154-020b-4f97-b2bc-5ab8eb3bf0b5",
  "resumeSessionId": null,
  "approvalMode": "workspace_write",
  "approvedAll": false,
  "effort": "high",
  "messageCount": 0,
  "lastMessage": null,
  "firstUserMessage": null,
  "instance": {
    "id": "inst_7b1c0d9e-2a3f-4b5c-9d8e-7f6a5b4c3d2e",
    "agentId": "my-agent",
    "stage": "development",
    "engine": "claude-cli",
    "createdAt": "2026-10-14T09:56:00.000Z",
    "updatedAt": "2026-10-14T09:56:00.000Z"
  },
  "createdAt": "2026-10-14T09:56:00.000Z",
  "updatedAt": "2026-10-14T09:56:00.000Z"
}
```

**违反的后果**：
- 不给 `Content-Type: application/json` 时请求体不被解析，后端看到的 `body` 为空，必填字段按缺失处理 → `400 BAD_REQUEST`。
- JSON 语法错误的请求体由解析层抛出，属客户端错误，按 `400 BAD_REQUEST` 回，`message` 是解析器原文，此时不要重试。
- 时间字段是服务端产出，客户端自己拼 `2026-10-14 09:56` 这类格式会在比较与排序时出错；`Date.parse` 可直接解析上例。

## 6. 分页

**约定**：列表接口统一 `?page=&pageSize=`，响应用 `PageResult<T>`。

**确切值**：
- 请求参数 `page`（缺省 `1`，只要求正整数、无上限）、`pageSize`（缺省 `20`，上限 `200`，超上限按 `200` 截断）。
- 响应 `PageResult<T> = { items: T[], total: number, page: number, pageSize: number }`，`total` 是过滤后的全量条数，不是本页条数。
- `page` 与 `pageSize` 回显**校验后**的请求值：缺省、非法回落与超上限截断之后的实际取值，前端不必自己保存请求参数。
- 排序：`sessions/list` 按 `updatedAt` **降序**（最近有活动的在前；改名 / 状态变更都会刷新它），`runs/list` 按 `createdAt` 降序；`messages/list` 例外，按 `seq` 升序且不用这套分页，见 §7。
- `/artifacts/list` 的目录列表**不分页**，信封仍是 `{ items, total }`，没有 `page` / `pageSize`。

```bash
curl -s 'http://localhost:4100/api/smart-factory/v1/sessions/list?agentId=my-agent&stage=runtime&page=2&pageSize=20'
```

```json
// 示例省略了同页其余 19 条
{
  "items": [ { "id": "sess_3c9d2b1a-...", "status": "completed", "...": "..." } ],
  "total": 221,
  "page": 2,
  "pageSize": 20
}
```

**违反的后果**：翻过尾页不报错，返回 `items: []` 且 `total` 不变，前端按空数组处理即可。
`pageSize` 超上限被截断成 200 而不报错，所以不要用「返回条数少于 `pageSize`」判断是否最后一页，用 `page * pageSize >= total` 判断。

## 7. 消息游标

**约定**：`messages/list` 不用 §6 的 page 分页，用基于 `seq` 的游标；`seq` 是会话内单调递增的排序权威键，不会因消息更新而变。

**确切值**（`?sessionId=` 或 `?runId=` 二选一必给）：

| 参数 | 取值 | 返回 |
|---|---|---|
| 不带游标 | - | 最新的 `limit` 条（`seq` 升序），首屏用它 |
| `afterSeq=N` | 非负整数 | `seq` 严格大于 `N` 的前 `limit` 条（`seq` 升序），续拉新消息用它 |
| `beforeSeq=N` | 非负整数 | `seq` 严格小于 `N` 的最新 `limit` 条（`seq` 升序），向上翻历史用它 |
| `limit` | 缺省 `50`，上限 `200` | 单次返回条数上限 |

- `afterSeq` 与 `beforeSeq` 同时给 → `400 BAD_REQUEST`。
- 响应固定 `MessagePage = { items: Message[], nextAfterSeq: number | null }`；返回条数等于 `limit` 时 `nextAfterSeq` 是最后一条的 `seq`，否则为 `null`。
- 首次进入会话用不带游标的取数拿最新一屏；向上翻历史用 `beforeSeq=` 当前首条的 `seq`；漏收事件后用 `afterSeq=nextAfterSeq` 续拉。

```bash
# 首屏：最近 50 条
curl -s 'http://localhost:4100/api/smart-factory/v1/messages/list?sessionId=sess_1f0a...'

# 向上翻一页历史
curl -s 'http://localhost:4100/api/smart-factory/v1/messages/list?sessionId=sess_1f0a...&beforeSeq=51&limit=50'

# 续拉新消息
curl -s 'http://localhost:4100/api/smart-factory/v1/messages/list?sessionId=sess_1f0a...&afterSeq=100'
```

```json
// 示例省略了同页其余 49 条（真实返回 50 条时 nextAfterSeq 才是非 null）
{
  "items": [ { "id": "msg_9a8b...", "seq": 51, "type": "text", "...": "..." } ],
  "nextAfterSeq": 100
}
```

**违反的后果**：两个游标同时给 → `400 BAD_REQUEST`，`message` 为 `afterSeq 与 beforeSeq 只能给一个`。
`limit` 非数值或非正数按 §8 静默回落 50；`limit` 超 200 按 200 截断。
只按 `afterSeq` 增量续拉会漏掉「已存在但状态变了」的消息（`status` 会从 `pending` 变成 `approved` 等），刷新与重连时必须重拉当前页或用 `?status=pending` 复查，见 [`4.04-消息.md`](./4.04-消息.md)。

## 8. 参数校验口径

**约定**：数值型参数的非法值**静默回落缺省**，不报错；只有「必填缺失」与「形态非法」才 `400`。前端据此决定本地校验做到什么程度。

**确切值**：

| 传参 | 实际取值 | 是否报错 |
|---|---|---|
| `?limit=abc` | `50`（回落缺省） | 否 |
| `?limit=-1` / `?limit=0` / `?limit=1.5` | `50` | 否 |
| `?limit=500` | `200`（截断） | 否 |
| `?page=-1` / `?page=abc` | `1` | 否 |
| `?pageSize=0` / `?pageSize=abc` | `20` | 否 |
| `?pageSize=500` | `200` | 否 |
| `?afterSeq=abc` / `?afterSeq=-1` | 忽略该参数，等同不传 | 否 |
| `?status=`（空串） | 不过滤 | 否 |
| `?status=foo` | - | 是，`400 BAD_REQUEST` |
| `?stage=foo` | - | 是，`400 BAD_REQUEST` |
| 缺 `sessionId` / `messageId` / `prompt` 等必填项 | - | 是，`400 BAD_REQUEST` |

结论：**前端可以省掉数值与分页的本地校验**（后端会兜住），但枚举类参数（`stage` / `status` / `type` / `subjectType` / `decision`）的取值必须自己保证，写错直接 400。

```bash
# 静默回落：limit 非法，服务端按 50 返回，HTTP 200
curl -s -o /dev/null -w '%{http_code}\n' \
  'http://localhost:4100/api/smart-factory/v1/messages/list?sessionId=sess_1f0a...&limit=abc'
# 200

# 形态非法：枚举取值不在表内，HTTP 400
curl -s 'http://localhost:4100/api/smart-factory/v1/sessions/list?stage=nope'
# {"error":"BAD_REQUEST","message":"stage 取值非法：\"nope\"（可选：development / preview / runtime / evaluation）",
#  "messageKey":"error.bad_request.invalid_value","params":{"name":"stage","value":"\"nope\"","allowed":"development / preview / runtime / evaluation"}}
```

**违反的后果**：把回落当报错处理（例如前端拦下 `limit=abc` 并提示用户）会与后端行为不一致，产生前端能拦、curl 与脚本却能过的分叉；反过来把枚举 400 当「可忽略」会在页面上静默丢数据。

## 9. 幂等与去重

**约定**：同一条消息可能在多个入口重复到达，前端一律按 `id` upsert；重复的写操作由服务端仲裁。

**确切值**：
- `messages/send`（REST）与 WS `send` 的响应里的 `message`，与随后到达的 `message` 事件是**同一条消息**（同 `id`、同 `seq`）。
事件可能先于响应到达，两个入口都要按 `id` 覆盖，不要 append。
- `messages/respond` 对同一条消息重复调用，第二次返回 `409 CONFLICT`，不发第二个裁决。
- `message` 事件的语义是 upsert：新建、内容更新（`chat.delta` 累计后的整段文本）与审批结算都走它。

```json
// REST 响应
{ "sessionId": "sess_1f0a...", "runId": "run_4d5e...", "instanceId": "inst_2f6a...",
  "status": "running", "effort": "high", "modelId": "a7cf0154-020b-4f97-b2bc-5ab8eb3bf0b5", "modelName": "claude-sonnet-4-5", "modelFellBack": false,
  "message": { "id": "msg_9a8b...", "seq": 12, "type": "text", "content": { "text": "你好" } },
  "run": { "id": "run_4d5e...", "status": "running", "startedAt": "2026-10-15T02:20:31.004Z", "finishedAt": null } }
```

```json
// 同一条消息随后（或先）以 WS 事件到达，id 相同
{ "id": "evt_1760000000000_7", "type": "event", "method": "message", "timestamp": 1760000000000,
  "payload": { "id": "msg_9a8b...", "seq": 12, "type": "text", "content": { "text": "你好" } } }
```

**违反的后果**：按到达顺序 append 会在消息列表里出现两条一样的消息（一条来自响应、一条来自事件）；按 `id` 去重后覆盖，两条路径合成一条。
在 Vue / React 里用 `id` 作 key 并整体替换该条目即可，不需要额外的去重表。

## 10. 错误响应形状

**约定**：REST 与 WS 的错误都带机器可读的 `code` 与人可读的 `message`，但**字段名不同**，两端必须各写一个解析器。

**确切值**：
- REST：HTTP 状态码 + `{ error, message, messageKey, params }`：
  - `error` 是枚举（见 §11），用于分支判断；
  - `messageKey` 是 i18n 键，形如 `error.not_found.agent`，由调用方按当前语言查自己的词表；
  - `params` 是插值参数（对象或 `null`），用于填 `{name}` / `{max}` 这类占位符；
  - `message` 是服务端已渲染的**中文兜底**，旧客户端、日志，以及词表里没有该 key 时用它。
- WS 请求失败：`type='response'`，`id` 与请求相同，`error: { code, message, messageKey?, params? }` 非空。
- WS 连接级错误：`type='event'`、`method='error'`，`code` 与 `message` 在 `payload` 里，没有 `error` 字段。

```bash
# REST 错误
curl -s 'http://localhost:4100/api/smart-factory/v1/runs/detail?runId=run_missing'
```

```json
{ "error": "NOT_FOUND", "message": "运行 run_missing 不存在",
  "messageKey": "error.not_found.run", "params": { "runId": "run_missing" } }
```

```json
// WS 请求失败（响应信封）
{ "id": "req_7", "type": "response", "method": "subscribe.result", "timestamp": 1760000000000,
  "error": { "code": "NOT_FOUND", "message": "会话 sess_missing 不存在",
             "messageKey": "error.not_found.session", "params": { "sessionId": "sess_missing" } } }
```

```json
// WS 连接级错误（事件信封）
{ "id": "evt_1760000000000_9", "type": "event", "method": "error", "timestamp": 1760000000000,
  "payload": { "code": "SLOW_CONSUMER", "message": "客户端消费过慢，连接将被断开" } }
```

**违反的后果**：用一个 `error.code` 解析器读 REST 响应会读到 `undefined`（REST 的机器可读字段叫 `error`，类型是字符串）；反之用 `error` 字符串解析 WS 会拿到一个对象。
REST 的 `error` 取值来自 §11 的七个枚举；WS 的 `error.code` 只有 `VALIDATION` / `NOT_FOUND` / `CONFLICT` / `INTERNAL` 四个（REST 细分码在 WS 边界收敛，见 [`4.06-实时通道.md`](./4.06-实时通道.md) §3），因此读字段与取值映射两边都要分开写。
WS 上行信封格式非法（不是 JSON、或缺 `id` / `method`）时返回 `id:""`、`method:"error"`、`error.code:"VALIDATION"`；未知 method 回显请求 id，响应 method 为 `"error"`、`error.code` 为 `"VALIDATION"`。WS 错误码与响应 method 规则见 [`4.06-实时通道.md`](./4.06-实时通道.md) §3。

### 10.1 `messageKey` 与降级规则

**约定**：服务端**不出词典**，只给 key；中文与英文词条都在调用方。同一条错误在不同语言下 `error` / `messageKey` / `params` 不变，只有最终展示的句子变 —— 切语言不需要重新请求。

**确切值**：`messageKey` 的形状是 `error.<分组>.<细节>`，例如：

| `error` | `messageKey` | `params` |
|---|---|---|
| `NOT_FOUND` | `error.not_found.agent` | `{ "agentId": "agt_…" }` |
| `BAD_REQUEST` | `error.bad_request.required` | `{ "name": "sessionId" }` |
| `CONFLICT` | `error.conflict.agent_name` | `{ "name": "天气智能体" }` |
| `PAYLOAD_TOO_LARGE` | `error.payload_too_large.file` | `{ "max": "10MB" }` |
| `BAD_GATEWAY` | `error.bad_gateway.workspace_unbound` | `{ "workspaceId": "8b1f…" }` |

调用方按下面的顺序取值：

1. 精确 key：`error.not_found.agent`；
2. 逐段截短：`error.not_found.agent.xxx` → `error.not_found.agent`；
3. 分组的 `default`：`error.not_found.<新增资源>` → `error.not_found.default`；
4. 都没有 → 用服务端的 `message`（中文兜底）；
5. 再没有 → 通用 `error.internal`。

第 3 条是必需的：服务端新增一个资源类型、调用方词表还没跟上时，也不会把「未找到某资源」说成「服务内部错误」。

**违反的后果**：按 `message` 文本做分支，切语言后判断全部失效；只认 `messageKey` 而不保留 `message` 兜底，词表缺 key 时界面上会出现键名。

**兼容性**：`messageKey` / `params` 是**增量字段**。只读 `error` 与 `message` 的旧客户端不受影响；`message` 的中文口径保持不变。

## 11. 错误码表

**约定**：REST 的 `error` 只有七个取值，判断逻辑按它分，不要按 `message` 文本分；WS 的 `error.code` 只有四个取值，见 [`4.06-实时通道.md`](./4.06-实时通道.md) §3。

| HTTP | `error` / `code` | 触发条件 |
|---|---|---|
| 400 | `BAD_REQUEST` | id 必填而缺失或为空串（`sessionId` / `runId` / `messageId` / `prompt` / `modelId`）；`agentId` 形态非法（须全小写并匹配 `^[a-z0-9][a-z0-9._-]{0,63}$`，且非 Windows 保留名、不以点结尾，细则见 [`4.03-会话.md`](./4.03-会话.md)）；`stage` / `status` / `decision` / `mode` / `effort` 不在枚举内；`sessions/create` 的 `modelId` 缺失、空串或不是字符串；`sessions/:sessionId/update` 与 WS `model.switch` 的 `modelId` 空串或不是字符串；`sessions/list` 的 `type` / `subjectType` 不在枚举内、`type` 与 `stage` 冲突、`subjectId` 与 `agentId` 不一致、`createdFrom` / `createdTo` 不是 ISO 日期时间；`messages/list` 的 `sessionId` 与 `runId` 未「给且只给一个」；`messages/send` 的 `sessionId` 与 `agentId` 同时给、`send { sessionId }` 携带 `modelId` / `mode` / `effort`、新建会话（`agentId` / 自由对话）缺 `modelId` 或为空串；模型详情 404/422、`protocol` 不是 `anthropic`、`apiKey` 或 `modelName` 为空（建 run 前，直接 400）；`afterSeq` 与 `beforeSeq` 同时给；`messages/respond` 的载荷与消息 `type` 不匹配（`approval` 缺 `decision`、`tool_interactive` 缺 `answers`、`answers` 不是对象或含非字符串数组的值）；`/artifacts/*` 的 `stage` 不在枚举、`agentId` 形态非法；`/artifacts/file` 与 `/artifacts/download` 的 `path` 缺失、任一 artifacts 端点的 `path` 含逃逸段（绝对路径、`..`、反斜杠、NUL 等，见 [`../03-architecture/07-artifact.md`](../03-architecture/07-artifact.md) §4）；`agents/*` 的 `workspaceId` 缺失或不是 uuid、`name` 缺失或 trim 后为空、`name` / `description` / `icon` 超出长度上限、`tags` 形态非法、`agents/update` 的可改字段一个都没给（见 [`5.01-agent-openapi.yaml`](../05-openapi/5.01-agent-openapi.yaml)）；`/files` 上传的 multipart 缺 `file` 字段、字段名不对或报文非法，`/files/{fileId}` 的存储名形态非法（不匹配 `fil_<uuid>[.ext]`，见 [`../03-architecture/09-file.md`](../03-architecture/09-file.md) §4）；请求体不是合法 JSON、或超过 2mb 上限（解析层客户端错误，一律按 400 回） |
| 404 | `NOT_FOUND` | 路径 / 方法 / 动作词写错等未匹配到任何路由；id 形态合法但资源不存在（会话 / 运行 / 消息）；`/artifacts/*` 的目录或文件不存在；`/files/{fileId}` 的存储名合法但文件不存在；`messages/respond` 的目标消息不是 `approval` / `tool_interactive`；`agents/*` 的目标智能体不存在；WS `subscribe` 的会话不存在；`instances/*` 等未开放路径 |
| 409 | `CONFLICT` | 活跃顶层 run 冲突：`send { sessionId }` 面对该会话已有活跃 run；`sessions/create` 与非 `runtime` 阶段的 `send` 面对同 agent 同 stage 已有活跃 run；`development` 起 run 面对同 agent 的活跃 runtime run（完整不变量见 [`../03-architecture/02-data-model.md`](../03-architecture/02-data-model.md) §6）；删除仍有活跃 run 的会话；无活跃 run 却调 `sessions/abort`；`runs/abort` 的目标 run 已终态；`messages/respond` 的目标消息已结算；同一工作区内智能体重名（`agents/create` / `agents/update`）；删除内置智能体（`agents/{agentId}/delete`；该端点会先停掉活跃 run 再删，不因此返回 409）；`/artifacts/*` 的 runtime 候选目录歧义（同一候选下多个子目录，或没有 `v*` 版本目录，见 [`../03-architecture/07-artifact.md`](../03-architecture/07-artifact.md) §3） |
| 413 | `PAYLOAD_TOO_LARGE` | `/artifacts/file` 读的文本文件超过大小上限（`ARTIFACT_MAX_FILE_BYTES`，默认 2 MiB）；`/artifacts/download` 不受该上限约束；`/files` 上传单文件超过上限（`FILES_MAX_FILE_BYTES`，默认 10 MB） |
| 500 | `INTERNAL_ERROR` | 未预期错误。引擎取值在启动时校验，不合法即拒绝启动，运行期不因此报此码 |
| 502 | `BAD_GATEWAY` | 框架模块面不可达、模块令牌缺失或无效、上游返回非 2xx（`/workspaces/list` 代理，依赖工作区目录解析的 `agents/*`、`/artifacts/*`，以及模型详情解析时的网络异常 / 5xx）；不降级、不猜路径 |
| 502 | `FRAMEWORK_UNAVAILABLE` | `/models/list` 的框架代理失败：框架不可达、令牌缺失或无效、上游非 2xx、响应不合法；`message` 是可直接展示的中文排障提示 |

分界口径：**形态非法判 400，形态合法但查不到判 404**。
`stage=nope` 是 400，`sessionId=sess_missing` 是 404，两者不要混。
`409` 全部是「当前状态不允许这次操作」，且都不是重试能自愈的：活跃 run 冲突要等它跑完或先 `abort`；已结算 / 已终态是重复提交，前端应直接以库里的最新状态刷新界面。

```bash
# 409：development 实例上已有活跃 run，同 stage 换个会话发消息同样被挡；runtime 的不同会话可并发
curl -s -X POST http://localhost:4100/api/smart-factory/v1/messages/send \
  -H 'Content-Type: application/json' \
  -d '{"sessionId":"sess_1f0a...","prompt":"再跑一次"}'
```

```json
{ "error": "CONFLICT", "message": "实例 inst_7b1c... 已有活跃 run",
  "messageKey": "error.conflict.active_run", "params": { "instanceId": "inst_7b1c..." } }
```

`runs/abort` 的 `409` 只表示「该 run 已终态」：run 行存在但驱动链已经收口（`succeeded` / `failed` / `aborted`），没有可中止的执行；前端据此把按钮置灰并刷新 `runs/detail`。

## 12. 鉴权

**约定**：没有鉴权。端侧本地单用户假设，服务不校验任何身份。

**确切值**：
- 不需要任何请求头、Cookie 或 token；服务端只 `json` 解析请求体，不读身份信息。
- 不会有 `401` / `403`：错误码只有 §11 的六个。
- CORS 缺省 `Access-Control-Allow-Origin: *`（`CORS_ORIGIN` 可覆盖），开发态经 vite 代理转发时连 CORS 也不涉及。

```bash
# 直接调，不带任何身份信息
curl -s http://localhost:4100/api/smart-factory/v1/sessions/list
```

**违反的后果**：前端不要写登录跳转、token 注入或 401 拦截分支，这些代码永远不会被触发。
反过来，服务无鉴权，任何能连到端口的人都能读写所有会话、列出主目录（`/fs/*`）；只应部署在可信网络，不要把服务暴露到公网。需要访问控制时靠网络层（防火墙）隔离，不要在应用层补鉴权。
