> 状态：**已定稿**。本文定义 `GET /agents/{agentId}/production`：读 AgentGenesis 的生产过程状态与交付门禁，回答「智能体生成完了没有、能不能进入预览 / 评估」。

## 1. 定位

智能体的生成由 AgentGenesis（`harness-create` 技能）在 `development` 阶段完成，产物直接写在 `development/output/agents/{name}/{vN}/`。**产物目录存在不代表生成结束**：可能正在写文件、可能停在人审、可能门禁失败。

本端点把技能自己的完成信号收敛成一个只读视图：

- `status`：`not_started` / `building` / `blocked` / `failed` / `completed`；
- `ready`：`status === 'completed'` 的派生布尔；
- `reasons`：不能进入预览 / 评估时的用户语义原因。

**只有 `ready === true` 才允许进入预览与评估阶段。** 这条规则在服务端由 `messages/send` 的起跑门禁兜底（§5），前端用 `ready` 控制页签，两层同一口径。

`GET /agents` 与 `GET /agents/{id}` 返回的 `Agent.status` 对普通智能体与本端点的 `status` **同源**（同一个 `readProductionStatus`），只是不带 `reasons` / `pipeline` / `delivery` / `product` 明细。内置智能体没有生产流程（`/production` 对它们返回 409），但随产品提供、开箱即用，`Agent.status` 恒为 `completed` —— 列表与卡片据此和普通智能体共用同一套「就绪才能使用」的判断。

## 2. 完成判定口径

### 2.1 读哪些文件

以 `<agentRoot>/development/` 为基准：

| 信号 | 路径 | 用途 |
|---|---|---|
| 过程状态 | `.agent-genesis/work/{name}/orchestrator-state.yaml` | `pipeline` / `pipeline_status` / `current_step` / `steps[]` / 重试计数 |
| 启动痕迹 | `.agent-genesis/work/*/`（最早落盘的是 `env-readiness.yaml`） | 区分「开过工但被中断」与「从未开始」；只影响 `not_started` / `failed` 的分支 |
| 交付门禁 | `.agent-genesis/work/{name}/gate-results/*.json` | `verdict` ∈ `PASS` / `CONCERNS` / `FAIL` |
| 产物 | `output/agents/{name}/{vN}/` | 恰好一个 `name`，取最新 `vN` |

门禁文件的读取顺序：

1. `current_step` 对应的 `gate-results/<step_id>.json`（技能统一按 step_id 落盘）；
2. `g028-exit-sanity.json`（技能文档口径，未来版本兼容）；
3. full 车道：`step-4-implementation.json`（executor 收尾的合并 verdict）；
4. fast 车道：`step-f1-fast-build.json`（create）/ `step-f2-fast-optimize.json`（optimize）。

只认**第一个存在**的文件，不合并多份 verdict。车道优先取 `orchestrator-state.yaml` 的 `pipeline`（`agent-creation` = full，`agent-creation-fast` = fast）；状态缺失时按实际存在的门禁文件反推。

### 2.2 完成条件

```
completed := 产物布局完整
          && 门禁 verdict ∈ {PASS, CONCERNS}
          && 流程已收尾
          && development 没有 pending / running 的 run
```

「流程已收尾」分车道：

- **full**：`pipeline_status === COMPLETED`（技能在 pipeline 收尾时显式写）；
- **fast**：`current_step ∈ {step-f1-fast-build（create）, step-f2-fast-optimize（optimize）}`（fast 驱动**通常不写** `COMPLETED`；写了也认，否则看收尾步）。

`CONCERNS` 是技能里程碑允许的交付结果，因此也放行；`FAIL` 一律不放行。

### 2.3 状态推导（按序短路）

| 顺序 | 条件 | `status` | `reasons` |
|---|---|---|---|
| 1 | development 有活跃 run | `building` | 智能体正在生成中，请等待本次运行结束 |
| 2 | 无状态、无产物、无门禁，且 `.agent-genesis/work/` 下**没有**工作目录 | `not_started` | 尚未开始生成智能体 |
| 2b | 无状态、无产物、无门禁，但 `.agent-genesis/work/` 下**已有**工作目录 | `failed` | 生成流程已开始但未完成，请重新发起生成 |
| 3 | `pipeline_status = BLOCKED` | `blocked` | 生成流程已暂停，等待处理 |
| 4 | `pipeline_status = FAILED`，或门禁 `FAIL` | `failed` | 生成流程失败 / 生成产物未通过质量门禁 |
| 5 | 产物布局不完整 | `failed` | 具体布局原因（空目录、多个智能体目录、无 `v*`） |
| 6 | 有产物但缺状态、或状态文件不唯一 | `failed` | 缺少生成过程状态 / 生产状态不唯一 |
| 7 | §2.2 完成条件成立 | `completed` | `[]` |
| 8 | 其余 | `building` | 智能体正在生成中 |

**活跃 run 压过一切**：用户重新发起生成时，旧状态可能仍写着 `COMPLETED`、旧产物也还在；此时按 `building` 处理，避免预览 / 评估抢跑。

**「开过工」与「没开工」分开判**：技能一启动就会建 `.agent-genesis/work/{name}/` 并先落 `env-readiness.yaml`，`orchestrator-state.yaml` 要晚得多。服务重启会把在途 run 收口成 `failed`（`error: 服务重启`）；如果此时状态文件还没写，只剩工作目录与早期文件。**只要 `work/` 下有工作目录就按 2b 报 `failed`**，不能退回 `not_started` —— 那会让用户以为自己的需求从未开始处理。状态文件缺失但已有工作痕迹，也一律 fail-closed。

## 3. 端点

### `GET /agents/{agentId}/production`

- 无请求体、无查询参数；
- 成功恒 `200`（**尚未开始也返回 200**，用 `status=not_started` 表达）；
- 未知智能体 `404 NOT_FOUND`；`agentId` 形态非法 `400 BAD_REQUEST`；工作区不可解析 `502 BAD_GATEWAY`；
- 只读：不建实例、不建会话、不触发物化；`development` 实例用只读查询，不 `getOrCreate`。

响应：

```json
{
  "agentId": "agt_7f3c...",
  "status": "completed",
  "ready": true,
  "lane": "full",
  "pipeline": {
    "status": "COMPLETED",
    "currentStep": "step-5-readiness-verification",
    "completedSteps": 6,
    "lastUpdate": "2026-10-20T09:12:31Z",
    "retryCount": 0,
    "retryBudget": 5
  },
  "delivery": {
    "verdict": "PASS",
    "source": "step-4-implementation.json",
    "concerns": []
  },
  "product": {
    "name": "weekly-report",
    "version": "v1",
    "path": "output/agents/weekly-report/v1",
    "updatedAt": "2026-10-20T09:10:02Z"
  },
  "reasons": []
}
```

未开始时：

```json
{
  "agentId": "agt_7f3c...",
  "status": "not_started",
  "ready": false,
  "lane": null,
  "pipeline": null,
  "delivery": null,
  "product": null,
  "reasons": ["尚未开始生成智能体"]
}
```

字段口径：

| 字段 | 说明 |
|---|---|
| `status` | 派生状态；前端只看它和 `ready` |
| `ready` | 是否允许进入预览 / 评估 |
| `lane` | `full` / `fast`；无法判断为 `null` |
| `pipeline.status` | 原始 `pipeline_status`，排障用，不要用它替代 `status` |
| `pipeline.currentStep` | 原始 step id；用户面展示应转语义，不直接显示 |
| `pipeline.completedSteps` | `steps[]` 去重后的 step 数（重试会重复追加同一步） |
| `delivery.source` | 门禁证据文件名，不含路径 |
| `delivery.concerns` | 门禁 concerns，**内部诊断信息**，不建议原样展示 |
| `product.path` | 相对 development 目录，**不下发绝对路径** |
| `reasons` | 用户语义原因，不含 gate / step 编号 |

## 4. 前端接入

- 进入预览 / 评估页签前读一次；`ready === false` 时禁用页签，展示 `reasons`。
- 生成中轮询 3–5 秒；收到 WS `run.status` 终态事件后立即重拉一次。
- 从 `development` 切到 `preview` / `evaluation` 时再校验一次，防止停留在旧状态。
- 本端点不新增 WS 事件：生产状态不是引擎事件，按需拉取即可。

## 5. 服务端门禁

`messages/send` 的目标阶段为 `preview` / `evaluation` / `runtime` 时，建 run 前：

1. `development` 有活跃 run → `409 CONFLICT`（重建期产物可能正在改写）；
2. `resolveStageCwd` 调 `locateProducedAgent`：布局缺失 `404`、流程未收尾或门禁未过 `409`；
3. 失败时**不建 run、不落用户消息、不改会话状态**。

`POST /sessions/create` 不拦：它按契约不碰磁盘、不建 run；「进入阶段」由前端用 `ready` 控制。

`GET /artifacts/list?stage=runtime` 的根定位与物化门禁同源，未完成时同样报错。

## 6. 边界

- **不落库**：状态每次从磁盘现算，没有新表、没有缓存。
- **不猜测**：产物目录必须恰好一个 `name`、有 `v*`；状态文件必须唯一或按 `name` 精确匹配；否则 `failed` + 原因，不挑一个凑合。
- **work 目录是过程产物**（技能约定临时保留 30 天）：被清理后即使 `output/` 还在，也无法确认交付门禁，按 `failed` 处理（fail-closed）。
