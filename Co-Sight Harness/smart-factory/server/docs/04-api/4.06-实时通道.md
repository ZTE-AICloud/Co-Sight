# 实时通道

> 状态：**已定稿**。本文定义实时通道的连接、信封、上下行与方法语义、时序与断线恢复。
> 代码落点：`server/src/shared/live/*`、`server/src/modules/session/session.service.ts`、`server/src/shared/engine/claude-adapter.ts`、`server/src/index.ts`
> 验收测试：`server/tests/{ws,ws-gateway,session-compat,approval,live-hub}.test.ts`、`server/tests/e2e/session-flow.mjs`
> 相关篇：[4.02 通用规范](./4.02-通用规范.md) / [4.04 消息](./4.04-消息.md)

本文是实时通道的唯一权威：前端照此可实现，不需要读 `server/src`。
本次协议对齐只改服务端与文档，`web/` 与 cosight-viewer 代码均未修改；viewer 需自行把首帧 `send` 的 `versionId` 改为 `agentId`（选了智能体才发，不选即自由对话），并带上必填的 `modelId`（可选 `mode` / `effort`），续聊改发 `sessionId`；思考展示按需消费 `chat.thinking`。

REST 与 WS 的分工：**WS 以实时为主**（上行动作 + 下行事件），另保留只读的 `history` 方法供商用客户端取历史；**历史与查询仍以 REST 为权威**，WS 不回放。
协议分两层：**原生方法 / 事件**是智能体运行时的稳定契约，**兼容方法 / 事件**是为商用客户端补齐的别名与附加事件；两层同时存在，兼容层不替换原生层。

## 1. 连接

| 项 | 值 |
|---|---|
| 路径 | `/api/smart-factory/v1/ws` |
| 协议 | 明文 `ws://`（端侧本地单用户，无 TLS、无鉴权） |
| 端口 | 与 REST 同端口（默认 4100），前缀也相同 |
| 编码 | 文本帧，payload 为 UTF-8 JSON |

- 路径与 REST 同端口同前缀，服务端用 `http.createServer` 让 WS 与 Express 共享监听。
- 开发态前端走 vite 代理，**必须给 `/api` 代理条目加 `ws: true`**，否则握手被当普通 HTTP 处理，连接直接失败（见 [4.07 待前端对齐](./4.07-待前端对齐.md)）。
- 连接建立后，服务端**立刻**推一条 `connection.ready` 事件，前端应先等到它再发任何请求。
- 一条连接可以同时订阅任意多个会话；一个会话的事件会推给所有订阅它的连接（多端查看同一会话靠这个）。

```json
{
  "id": "evt_1785715200010_1",
  "type": "event",
  "method": "connection.ready",
  "timestamp": 1785715200010,
  "payload": { "connectionId": "conn_1", "restored": false, "sessionId": null }
}
```

- `connectionId` 是连接级标识，形如 `conn_1`，断开即失效；重连后是新值。
- `restored` 恒为 `false`：本服务没有连接恢复能力，也不下发 `connectionToken`。
- `sessionId` 恒为 `null`：连接不带鉴权、不绑定会话，订阅关系只由 `subscribe` 建立。
- 把 `connectionId` 只用于日志与排查，业务逻辑不要依赖它。

## 2. 心跳

**心跳由客户端驱动**：客户端每 `WS_HEARTBEAT_MS`（默认 30000ms）发一条 `{method:'ping'}` 请求帧，服务端回一条 `pong` 响应帧。

服务端另一侧独立巡检：每 30s 扫一次空闲连接，**距上次收到该连接的任何一个帧超过 60s（2 倍间隔）**的，在下一拍巡检断开（关闭码 `1000`，reason 为「心跳超时」），并清理它的全部订阅；因此实际断开时刻在 60s 之后，最迟约 90s。

- **前端必须自己起心跳定时器**：不起、或间隔大于 60s，连接会在空闲超过 60s 后的下一拍巡检被服务端断开（最迟约 90s）。
- 服务端**不主动发协议层 ping**，`onping` 之类的事件不会出现，前端不要等它。
- **任何上行帧都算活跃**：`send` / `history` / `message.respond` / `approval.respond` / `tool.respond` / `model.switch` / `mode.switch` / `effort.switch` / `run.abort` / `subscribe` / `unsubscribe` 都会刷新活跃时间，ping 不是唯一手段，但只要有超过 60s 的空闲就会被判超时，定时器仍是最省心的做法。
- 被断开时前端会收到 `close` 事件（`code === 1000`、`reason === '心跳超时'`），此时该连接的所有订阅已在服务端清理，必须走第 7 节的「断线重连」流程。

请求帧：

```json
{
  "id": "req_ping_1",
  "type": "request",
  "method": "ping",
  "timestamp": 1785715230000,
  "payload": {}
}
```

响应帧：

```json
{
  "id": "req_ping_1",
  "type": "response",
  "method": "pong",
  "timestamp": 1785715230012,
  "payload": { "serverTime": 1785715230012 },
  "error": null
}
```

`ping` 的响应 `method` 固定为 `pong`，载荷是 `{ serverTime }`（毫秒时间戳数字）；其余方法的响应 `method` 都是 `<请求 method>.result`（见 §3）。

### 2.1 行为与后果

| 客户端行为 | 服务端行为 | 前端看到什么 | 该做什么 |
|---|---|---|---|
| 每 30s 发一条 `ping` | 回 `pong`，刷新活跃时间 | 连接保持 | 什么都不做 |
| 不发心跳 | 空闲超 60s 判超时，下一拍巡检断开、清订阅（最迟约 90s） | `close`，`code=1000`，`reason='心跳超时'` | 按第 7 节重连 + 重订阅 + 重拉 |
| 心跳间隔大于 60s | 同上（两次巡检之间就超时） | 同上 | 把定时器间隔收敛到 30s |
| 只发业务帧、不发 ping | 照样算活跃，连接保持 | 连接保持 | 空闲期仍要 ping，否则照样被断 |
| 网络半开（网线拔掉、无 `close`） | 空闲超 60s 后，下一拍巡检断开 | 客户端可能迟迟收不到 `close` | 用「发 ping 后 N 秒内没收到 pong」自行判死并重连 |

## 3. 信封

三种帧共用同一个信封：

```ts
interface Envelope<T = unknown> {
  id: string;
  type: 'request' | 'response' | 'event';
  method: string;
  timestamp: number;
  payload?: T;
  error?: { code: string; message: string } | null;
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | 是 | 请求由客户端生成、服务端原样回显；事件由服务端生成，形如 `evt_<毫秒时间戳>_<自增序号>` |
| `type` | string | 是 | `request`（客户端上行）/ `response`（服务端对某个请求的回执）/ `event`（服务端主动推送） |
| `method` | string | 是 | 请求方法名或事件名；**除 `ping`、解析失败与未知方法外，成功与错误响应的 `method` 为 `<请求 method>.result`**；`ping` 的响应为 `pong`；信封解析失败的响应 `id` 为 `""`、`method` 为 `error`；未知方法的响应 `method` 也是 `error` |
| `timestamp` | number | 是 | 毫秒级整数时间戳（`Date.now()`），仅用于排查，不参与业务判断 |
| `payload` | object | 否 | 方法 / 事件的载荷，形状由 `method` 决定 |
| `error` | object | 否 | 仅错误响应出现，成功响应为 `null`；形状 `{ code, message, messageKey?, params? }` |

五条硬规则：

1. **每个请求必须带 `id`**，`id` 由客户端生成（建议 `req_` 前缀 + 自增或随机串）。
   服务端只回显，不校验唯一性，也不去重。
2. **信封解析失败时，服务端返回 `id: ""`、`method: "error"`、`error.code: "VALIDATION"`**，请求 `id` 无法回显。
   所以前端不传 `id` 的请求，其 Promise 永远拿不到回执，会造成静默挂死。
3. **未知 `method` 回显请求 `id`，但响应 `method` 固定为 `error`，`error.code` 为 `VALIDATION`**（不是 `<method>.result`）。
4. **WS 的错误形状与 REST 不同**：REST 是 `{ error, message, messageKey, params }`，WS 是 `error: { code, message, messageKey?, params? }`。
   两边的解析器不能共用，WS 侧要单独写。
   `messageKey` / `params` 的含义与降级规则和 REST 完全一致（见 [`4.02-通用规范.md`](./4.02-通用规范.md) §10.1）；
   `message` 仍是中文兜底。
5. **WS 错误码只有四个**：`VALIDATION` / `NOT_FOUND` / `CONFLICT` / `INTERNAL`。
   REST 侧细分码在 WS 边界收敛：`BAD_REQUEST` → `VALIDATION`，`INTERNAL_ERROR` / `FRAMEWORK_UNAVAILABLE` → `INTERNAL`，`NOT_FOUND` / `CONFLICT` 原样保留。
   `SLOW_CONSUMER` **不是**响应错误码，只出现在连接级 `error` 事件的 payload 里（见 §5.7、§8）。

请求帧：

```json
{
  "id": "req_7f3a1c",
  "type": "request",
  "method": "subscribe",
  "timestamp": 1785715200100,
  "payload": { "sessionId": "sess_4f2a9c" }
}
```

成功响应帧：

```json
{
  "id": "req_7f3a1c",
  "type": "response",
  "method": "subscribe.result",
  "timestamp": 1785715200118,
  "payload": { "sessionId": "sess_4f2a9c", "subscribed": true, "status": "in_progress" },
  "error": null
}
```

错误响应帧（**没有 `payload` 字段**）：

```json
{
  "id": "req_7f3a1c",
  "type": "response",
  "method": "subscribe.result",
  "timestamp": 1785715200118,
  "error": { "code": "NOT_FOUND", "message": "会话 sess_4f2a9c 不存在",
             "messageKey": "error.not_found.session", "params": { "sessionId": "sess_4f2a9c" } }
}
```

信封解析失败与未知方法的响应帧：

```json
{
  "id": "",
  "type": "response",
  "method": "error",
  "timestamp": 1785715200118,
  "error": { "code": "VALIDATION", "message": "信封格式非法",
             "messageKey": "error.validation_failed", "params": null }
}
```

```json
{
  "id": "req_7f3a1c",
  "type": "response",
  "method": "error",
  "timestamp": 1785715200118,
  "error": { "code": "VALIDATION", "message": "未知方法：foo",
             "messageKey": "error.bad_request.unknown_method", "params": { "method": "foo" } }
}
```

## 4. 上行方法

一共十二个：原生六个 - `subscribe` / `unsubscribe` / `send` / `message.respond` / `run.abort` / `ping`；兼容六个 - `history` / `approval.respond` / `tool.respond` / `model.switch` / `mode.switch` / `effort.switch`。
除 `ping`、信封解析失败与未知方法外，成功与错误响应的 `method` 都是 `<请求 method>.result`；`ping` 的响应 `method` 为 `pong`。
未知 `method` 的响应 `method` 固定为 `error`、回显请求 `id`，`error.code` 为 `VALIDATION`（`message` 为「未知方法：xxx」）。

| method | 层 | payload | 成功响应 method | 成功响应 payload | 错误响应可能取值 |
|---|---|---|---|---|---|
| `subscribe` | 原生 | `{ sessionId }` | `subscribe.result` | `{ sessionId, subscribed: true, status }` | `VALIDATION` / `NOT_FOUND` |
| `unsubscribe` | 原生 | `{ sessionId }` | `unsubscribe.result` | `{ sessionId, unsubscribed: true }` | `VALIDATION` |
| `send` | 原生 | `{ sessionId, prompt, attachments? }` 或 `{ agentId, modelId, mode?, effort?, prompt, attachments? }` 或 `{ modelId, mode?, effort?, prompt, attachments? }`（自由对话） | `send.result` | `{ sessionId, runId, instanceId, status: "running", effort, modelId, modelName, modelFellBack: false, message: Message, run: Run }` | `VALIDATION` / `NOT_FOUND` / `CONFLICT` / `INTERNAL` |
| `history` | 兼容 | `{ sessionId, limit?, offset?, includeTelemetry? }` | `history.result` | `{ sessionId, messages: HistoryMessage[], total }` | `VALIDATION` / `NOT_FOUND` / `INTERNAL` |
| `approval.respond` | 兼容 | `{ approvalId, decision }` | `approval.respond.result` | `{ approvalId, decision, resolved: true }` | `VALIDATION` / `NOT_FOUND` / `CONFLICT` |
| `tool.respond` | 兼容 | `{ toolCallId, answers }` | `tool.respond.result` | `{ toolCallId, received: true }` | `VALIDATION` / `NOT_FOUND` / `CONFLICT` |
| `model.switch` | 兼容 | `{ sessionId, modelId }` | `model.switch.result` | `{ sessionId, modelId, appliesTo: "nextRun" }` | `VALIDATION` / `NOT_FOUND` |
| `mode.switch` | 兼容 | `{ sessionId, mode }` | `mode.switch.result` | `{ sessionId, mode }` | `VALIDATION` / `NOT_FOUND` |
| `effort.switch` | 兼容 | `{ sessionId, effort }` | `effort.switch.result` | `{ sessionId, effort }` | `VALIDATION` / `NOT_FOUND` |
| `message.respond` | 原生 | `{ messageId, decision? }` 或 `{ messageId, answers? }` | `message.respond.result` | `{ message: Message }` | `VALIDATION` / `NOT_FOUND` / `CONFLICT` |
| `run.abort` | 原生 | `{ runId }` | `run.abort.result` | `{ runId, aborted: true }` | `VALIDATION` / `NOT_FOUND` / `CONFLICT` |
| `ping` | 原生 | 省略或 `{}` | `pong` | `{ serverTime }` | 无 |

### 4.1 `subscribe`

订阅一个会话的实时事件。
**什么时候用**：打开一个会话页（首屏或重连后）时调一次；另一个连接想旁观同一会话也要各自订阅。

请求：

```json
{
  "id": "req_7f3a1c",
  "type": "request",
  "method": "subscribe",
  "timestamp": 1785715200100,
  "payload": { "sessionId": "sess_4f2a9c" }
}
```

成功响应：

```json
{
  "id": "req_7f3a1c",
  "type": "response",
  "method": "subscribe.result",
  "timestamp": 1785715200118,
  "payload": { "sessionId": "sess_4f2a9c", "subscribed": true, "status": "in_progress" },
  "error": null
}
```

- `status` 是**订阅那一刻**的会话状态快照，取值 `not_started` / `in_progress` / `completed`。
  它是快照不是订阅：后续变化仍靠 `session.status` 事件。
- **响应之后**，服务端会向该连接**逐条补发**这个会话当前所有 `status='pending'` 的 `approval` / `tool_interactive` 消息，以 `approval.request` / `tool.interactive` 兼容事件帧发出（形状见 §5.10.6 / §5.10.7）。
  补发是幂等的：前端按 `approvalId` / `toolCallId` upsert，同一张卡不能弹两次。
- **只补发挂起的审批与交互，不补发其它历史**（没有回放）。
  补发不使用 `message` 事件，而是 `approval.request` / `tool.interactive` 兼容帧；它们与实时兼容事件由同一构造函数产出，形状完全一致，前端用同一套 handler 处理。
  对话正文、工具调用、流式内容要走 REST（或兼容 `history`）拉取，见 §7。
- 重复订阅同一会话是幂等的，不会收到重复补发之外的副作用。

会话不存在时的错误响应：

```json
{
  "id": "req_7f3a1c",
  "type": "response",
  "method": "subscribe.result",
  "timestamp": 1785715200118,
  "error": { "code": "NOT_FOUND", "message": "会话 sess_4f2a9c 不存在",
             "messageKey": "error.not_found.session", "params": { "sessionId": "sess_4f2a9c" } }
}
```

缺 `sessionId` 或为空串回 `VALIDATION`（`message` 为「sessionId 必填」）。

补发帧（一条挂起的审批，紧跟在上面的成功响应之后）：

```json
{
  "id": "evt_1785715200120_9",
  "type": "event",
  "method": "approval.request",
  "timestamp": 1785715200120,
  "payload": {
    "approvalId": "msg_9de1f0",
    "sessionId": "sess_4f2a9c",
    "runId": "run_8ab31d",
    "parentRunId": null,
    "toolCallId": "toolu_01AbCd",
    "toolName": "Bash",
    "title": "允许执行 Bash？",
    "description": "npm test",
    "input": { "command": "npm test" },
    "options": [
      { "value": "approved", "label": "允许", "enLabel": "Allow" },
      { "value": "approved_all", "label": "本会话全部允许", "enLabel": "Allow all" },
      { "value": "rejected", "label": "拒绝", "enLabel": "Reject" }
    ]
  }
}
```

### 4.2 `unsubscribe`

取消订阅一个会话，之后不再收到它的事件。
**什么时候用**：离开会话页、或该标签页主动释放资源时。

请求：

```json
{
  "id": "req_9c02de",
  "type": "request",
  "method": "unsubscribe",
  "timestamp": 1785715200900,
  "payload": { "sessionId": "sess_4f2a9c" }
}
```

成功响应：

```json
{
  "id": "req_9c02de",
  "type": "response",
  "method": "unsubscribe.result",
  "timestamp": 1785715200912,
  "payload": { "sessionId": "sess_4f2a9c", "unsubscribed": true },
  "error": null
}
```

- 取消一个没订阅过的会话也返回成功，幂等，不报错。
- 缺 `sessionId` 回 `VALIDATION`。
- 连接断开时服务端会自动清理该连接的全部订阅，前端不必在 `close` 前抢救着 `unsubscribe`。

### 4.3 `send`

发一条用户消息并起一个 run。
**什么时候用**：用户在发送框里提交时；`send { sessionId }` 续聊，`send { agentId }` 开一条新对话，两者都不给则是自由对话（不选智能体，落当前工作区目录）。

请求（续聊，已有会话）：

```json
{
  "id": "req_2c9d41",
  "type": "request",
  "method": "send",
  "timestamp": 1785715200200,
  "payload": { "sessionId": "sess_4f2a9c", "prompt": "给 weather-agent 补一个单元测试" }
}
```

请求（首帧，按智能体新建会话）：

```json
{
  "id": "req_2c9d42",
  "type": "request",
  "method": "send",
  "timestamp": 1785715200200,
  "payload": {
    "agentId": "weather-agent",
    "modelId": "a7cf0154-020b-4f97-b2bc-5ab8eb3bf0b5",
    "mode": "workspace_write",
    "effort": "high",
    "prompt": "你好"
  }
}
```

请求（首帧，自由对话 —— 不选智能体，每次新建一条目录会话）：

```json
{
  "id": "req_2c9d43",
  "type": "request",
  "method": "send",
  "timestamp": 1785715200200,
  "payload": {
    "modelId": "a7cf0154-020b-4f97-b2bc-5ab8eb3bf0b5",
    "mode": "workspace_write",
    "effort": "high",
    "prompt": "你好"
  }
}
```

- `sessionId` 与 `agentId` **至多给一个**：两个都给回 `VALIDATION`；**都不给 = 自由对话**（不选智能体），每次新建一条目录会话。
  `prompt` 必填 —— 例外是带了非空 `attachments`（本机文件路径列表），此时正文可以为空串。
- `attachments` 与 REST `messages/send` 同形同规则（`[{ path }]`，最多 20 项，接受本机任意存在的绝对路径）。落库写进 user 消息的 `content.files`，进引擎时展开成一段路径清单接到 `prompt` 末尾；详见 [`4.04 消息`](./4.04-消息.md) §5。
  响应里的 `message.content.files` 就是这一轮的附件，客户端渲染 chip 直接用它，不必在本地另存。
- `send { sessionId }`：续聊已有会话，使用该会话的 `modelId` / `approvalMode` / `effort`。
  请求里出现 `modelId` / `mode` / `effort` 任一字段回 `VALIDATION`。
- `send { agentId, modelId, mode?, effort? }`：**每次都新建一条 `runtime` 会话**，不复用任何已有会话。
  `modelId` 必填、非空且可运行（缺失 / 空串 / 非字符串 / 模型不存在 / 协议不符 / 缺密钥回 `VALIDATION`，框架不可达回 `INTERNAL`）；`mode` 缺省 `workspace_write`、`effort` 缺省 `high`，取值非法 `VALIDATION`。
  三个字段都持久化到新会话，首轮 run 使用它们，`resumeSessionId` 为 `null`。
- `send { modelId, mode?, effort? }`（无 `sessionId` / `agentId`）：**自由对话**，每次都新建一条目录会话（`agentId=null`、`stage='runtime'`）。
  cwd 取框架**当前生效工作区的目录**；框架没有生效工作区时落到 `{COSIGHT_HOME}/smart-factory/chat`（不存在则创建）。工作区存在但未绑目录、或框架不可达按 `INTERNAL` 返回，不悄悄换目录。
  `modelId` / `mode` / `effort` 的规则与 `agentId` 首帧完全一致；会话建好之后的事件、审批、三个 switch、history 与智能体会话共用同一条链路。
  目录实例是**实例级**仲裁：同一工作区（或兜底目录）同时只能有一个活跃顶层 run，第二个 `send` 回 `CONFLICT`。
- `agentId` 先查 `agents` 表；智能体不存在时直接返回 404 `NOT_FOUND`，不创建实例、会话或 run。
- **失败清理**：模型可运行性校验失败时不建会话；建会话后模型详情解析失败返回 `VALIDATION`（模型不存在 / 协议不符 / 缺密钥 / 缺 `modelName`）或 `INTERNAL`（框架不可达 / 5xx）；产物门禁失败按 [`4.10`](./4.10-智能体产物状态.md) 返回 `NOT_FOUND` / `CONFLICT`。
  并发首帧互不挤占名额（见 [`02-data-model.md`](../03-architecture/02-data-model.md) §6）。
  `send { agentId }` / 自由对话遇到上述失败都会删除刚建的会话，不留空会话。
- **解析先于建 run**：服务端在建 run 前解析引擎适配器、工作区目录 / 阶段 cwd（预览 / 评估在此完成物化）与模型。任一步失败直接返回错误，**不建 run、不落用户消息、不改会话状态**。
- 响应里的 `modelId` 已是本次 run 使用的会话模型 id，恒非空。

成功响应：

- **顶层 `sessionId` / `runId` / `instanceId` / `status` 是兼容字段**：商用客户端直接读 `payload.runId` 即可；原生客户端仍可读 `message` 与 `run`。
- `status` 恒为 `"running"`，与 `run.status` 同值；客户端收到响应即可进入运行态，不需要再等 `run.started` 才认为已起跑。
- `effort` 是会话当前推理强度；`modelId` 是本次 run 使用的会话模型 id，恒非空；`modelName` 是下发引擎的模型名；`modelFellBack` 恒为 `false`，本服务不实现模型回退。响应没有 `created` 字段。
- 响应里的 `run.status` 是 `running`，`startedAt` 已落值：run 在建行时就是 `running`，引擎随后异步启动。`run.started` 也在响应之前广播（见 §5.3 / §6），响应的 `status` + `run.status` 与事件表达的是同一个运行态。
- **隐式订阅**：发起 `send` 的那条连接会自动订阅目标会话（新建会话的两条分支 —— `agentId` 与自由对话 —— 在活跃 run 建行成功之后、用户消息落库之前订阅），前端**不需要**「先 `subscribe` 再 `send`」，也不会漏掉这个 run 的任何事件。
  显式 `subscribe` 的用途是另一个连接查看同一会话，或者你先订阅、后由别处发起运行。
- **`send` 与 `subscribe` 之间不要假设任何顺序**：先发后订、先订后发都能收到事件。
- 响应里的 `message`（user）与响应前到达的 `message` 事件（见 §5.5）是**同一条**，按 `id` upsert 即可，不要追加两条。
- **中止竞态**：中止句柄在响应返回前已注册。若 run 在 `run.started` 广播前被并发中止，则跳过 `run.started` 与引擎启动，由 `closeRun` 收口；此时响应里的 `run` 仍是建行时的 `running` 快照，终态以随后的 `run.status` 事件为准。终态 run 永不补发 `run.started`。
- 会话处于 `completed` 时，`send` 会把它复活为 `in_progress`，`session.status` 事件在响应前广播。
- 前端要在收到响应或 `CONFLICT` 之前就禁用发送按钮，避免用户连点。

错误响应取值：

| code | 何时 | 前端表现 |
|---|---|---|
| `VALIDATION` | `sessionId` 与 `agentId` 同时给、参数缺失 / 非法、`send { sessionId }` 携带 `modelId` / `mode` / `effort`、新建会话（`agentId` / 自由对话）缺 `modelId`、`mode` / `effort` 非法、模型不存在 / 协议不符 / 缺密钥 / 缺 `modelName`，或引擎适配器取值未知（REST 400） | 提示参数错误，不重试；模型问题提示重新选择模型 |
| `NOT_FOUND` | 会话（或它的实例）不存在，`agentId` 对应的智能体不存在，或 development 目录 / 运行产物缺失（REST 404） | 提示目标不存在 |
| `CONFLICT` | 该会话已有活跃 run（`send { sessionId }`），或非 `runtime` 阶段该实例已有活跃 run（含自由对话的目录实例），或 `development` 起 run 遇到同 agent 的活跃 runtime run，或产物生产状态未完成 / 候选歧义 / 没有版本目录（REST 409）。新建会话（`agentId` / 自由对话）遇到上述冲突时新建的会话会被删除 | 会话级冲突提示「本会话正在运行」；非 `runtime` 实例冲突提示「该智能体正在运行」；产物问题提示修正产物后重试 |
| `INTERNAL` | 工作区解析失败或模型详情解析时框架不可达 / 5xx（`FRAMEWORK_UNAVAILABLE`），或落 user 消息失败等未预期错误（REST 502 等） | 通用错误提示；解析失败时服务端**不建 run、不落用户消息、不改会话状态**，修正配置后可重试 |

`CONFLICT` 的边界：`send { sessionId }` 撞上该会话的活跃顶层 run 即冲突；非 `runtime` 阶段**同 agent 同 stage 的其它会话**正在跑也会挡住发送，提示文案应是「该智能体正在运行」而不是「本会话正在运行」。
`runtime` 没有实例级约束，`send { agentId }` 的并发首帧都能成功；完整不变量见 [`02-data-model.md`](../03-architecture/02-data-model.md) §6。
模型解析与活跃 run 判定都发生在建 run 之前；任一失败都不留 run，`send { agentId }` 还会删除新建的会话。

```json
{
  "id": "req_2c9d41",
  "type": "response",
  "method": "send.result",
  "timestamp": 1785715200233,
  "error": { "code": "CONFLICT", "message": "会话 sess_4f2a9c 已有活跃 run",
             "messageKey": "error.conflict.active_run", "params": { "sessionId": "sess_4f2a9c" } }
}
```

### 4.4 `history`

取一段历史消息，供商用客户端沿用其原来的 `history` 调用。
**什么时候用**：商用客户端建连后拉历史；新前端仍推荐用 REST [`messages/list`](./4.04-消息.md)，两者数据同源。

请求：

```json
{
  "id": "req_hist_1",
  "type": "request",
  "method": "history",
  "timestamp": 1785715201000,
  "payload": { "sessionId": "sess_4f2a9c", "limit": 50, "offset": 0, "includeTelemetry": false }
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `sessionId` | string | 是 | 会话 id |
| `limit` | number | 否 | 返回条数，缺省 50，上限 200（超出按 200 截断） |
| `offset` | number | 否 | 从**最新一条往前**跳过的条数，缺省 0；越界返回空数组 |
| `includeTelemetry` | boolean | 否 | **接收但忽略**：当前没有遥测消息，传什么值都不影响结果 |

成功响应（`method` 为 `history.result`，符合 `<请求 method>.result` 的统一规则）：

```json
{
  "id": "req_hist_1",
  "type": "response",
  "method": "history.result",
  "timestamp": 1785715201018,
  "payload": {
    "sessionId": "sess_4f2a9c",
    "total": 1,
    "messages": [
      {
        "id": "msg_1a77c0",
        "sessionId": "sess_4f2a9c",
        "runId": null,
        "role": "user",
        "type": "text",
        "content": "给 weather-agent 补一个单元测试",
        "createdAt": "2026-10-15T06:40:00.200Z"
      }
    ]
  },
  "error": null
}
```

- `messages` **按 `seq` 升序**；`offset` 的作用是「最近 `limit` 条里跳过最新 `offset` 条」，返回值仍按升序。
- `total` 是该会话的**全部消息条数**，与 `limit` / `offset` 无关；`messages` 只是本次窗口。前端用它判断还有多少历史可翻。
- **`content` 恒为字符串**，与 REST 的对象形状不同；拍平规则：

  | `type` | `content` |
  |---|---|
  | `text` / `thinking` | `content.text` |
  | `tool_use` | `JSON.stringify(content.input ?? content)` |
  | `tool_result` | `content.output`（字符串）否则 `JSON.stringify(content.output ?? '')` |
  | `approval` | `content.title`（字符串）否则 `JSON.stringify(content)` |
  | `tool_interactive` | `JSON.stringify(content.questions ?? content)` |
  | 其它 | `JSON.stringify(content)` |

- `runId` 可为 `null`（例如 `send` 落的用户消息不挂 run）。
- 缺 `sessionId` 回 `VALIDATION`；会话不存在回 `NOT_FOUND`；其它未预期错误回 `INTERNAL`。
- 这是 WS 上唯一的只读方法；它不回放实时事件，也不替代 REST 的游标分页。

### 4.5 `approval.respond`

兼容审批应答。`approvalId` 就是审批消息的 `message.id`（与 `approval.request` 事件里的 `approvalId` 同值），校验与结算走与 `message.respond` 同一条服务路径。

```json
{
  "id": "req_5b7e02",
  "type": "request",
  "method": "approval.respond",
  "timestamp": 1785715205000,
  "payload": { "approvalId": "msg_9de1f0", "decision": "approved" }
}
```

- `decision` 取值：`approved` / `approved_all` / `rejected`。
- `decision='approved_all'` 时，服务端在抢到结算仲裁之后、放行引擎之前把会话置为 `approvalMode='full_access'`、`approvedAll=true`；本 run 的下一条审批与之后的新 run 都读这个会话级开关，不再挂起。
- 成功响应：`{ approvalId, decision, resolved: true }`；结算后的消息通过 `message` 事件广播（同 `id` 更新），响应本身不再携带 `Message`。
- 错误：`VALIDATION`（`approvalId` 缺失、`decision` 非法）、`NOT_FOUND`（消息不存在或不是审批消息）、`CONFLICT`（已结算）。

### 4.6 `tool.respond`

兼容交互应答。服务端按 `toolCallId` 找到 `status='pending'` 的 `tool_interactive` 消息，再把 `answers` 归一为 `{ 问题原文: [选项] }` 后结算。

```json
{
  "id": "req_6a12ff",
  "type": "request",
  "method": "tool.respond",
  "timestamp": 1785715210000,
  "payload": {
    "toolCallId": "toolu_01AbCd",
    "answers": [ { "question": "要处理什么格式？", "answer": "CSV" } ]
  }
}
```

- `answers` 支持两种形态：数组 `[{ question, answer }]`（`answer` 为字符串或字符串数组），或对象 `{ 问题原文: 字符串或字符串数组 }`。
- 成功响应：`{ toolCallId, received: true }`；结算后的消息通过 `message` 事件广播，响应本身不再携带 `Message`。
- 错误：`VALIDATION`（`toolCallId` 缺失、`answers` 格式非法）、`NOT_FOUND`（没有与该 `toolCallId` 匹配的待应答交互）、`CONFLICT`（已结算）。

### 4.7 `model.switch`

切换会话模型，**下个 run 生效**。
**活跃 run 不受影响，也不会被中断，本方法不返回 `CONFLICT`**。

```json
{
  "id": "req_sw_model",
  "type": "request",
  "method": "model.switch",
  "timestamp": 1785715220000,
  "payload": { "sessionId": "sess_4f2a9c", "modelId": "f3b2a1c0-9d8e-4f7a-8b6c-5d4e3f2a1b0c" }
}
```

- `modelId` 是框架模型 uuid，**必须是非空字符串且可运行**；空串、非字符串或缺失回 `VALIDATION`，不支持清空模型。
  切换时校验模型可运行：模型不存在、协议不是 `anthropic` 或没有配置 API 密钥回 `VALIDATION`，框架不可达 / 5xx 回 `INTERNAL`，失败不改动会话。
- 成功响应：`{ sessionId, modelId, appliesTo: "nextRun" }`。
- 其它订阅端会收到 `settings.changed` 事件（见 §5.10.10）。
- 错误：`VALIDATION`（`sessionId` / `modelId` 缺失或非法）、`NOT_FOUND`（会话不存在）。

### 4.8 `mode.switch`

切换会话审批模式，**下个 run 生效**；活跃 run 不受影响，不返回 `CONFLICT`。

```json
{
  "id": "req_sw_mode",
  "type": "request",
  "method": "mode.switch",
  "timestamp": 1785715220000,
  "payload": { "sessionId": "sess_4f2a9c", "mode": "full_access" }
}
```

- `mode` 取值：`read_only` / `workspace_write` / `full_access`，新建会话缺省 `workspace_write`。
- 线路字段名仍是 `mode`，它改的是 Session 的 `approvalMode`（DTO 字段名）。切到任何非 `full_access` 的值会把 `Session.approvedAll` 复位为 `false`；切到 `full_access` 不会自动置真。
- 成功响应：`{ sessionId, mode }`。
- 其它订阅端会收到 `settings.changed` 事件（见 §5.10.10）。
- 错误：`VALIDATION`（`sessionId` 缺失、`mode` 不在枚举内）、`NOT_FOUND`（会话不存在）。

### 4.9 `effort.switch`

切换会话推理强度，**下个 run 生效**；活跃 run 不受影响，不返回 `CONFLICT`。

```json
{
  "id": "req_sw_effort",
  "type": "request",
  "method": "effort.switch",
  "timestamp": 1785715220000,
  "payload": { "sessionId": "sess_4f2a9c", "effort": "max" }
}
```

- `effort` 取值：`low` / `medium` / `high` / `xhigh` / `max`，新建会话缺省 `high`。
- 成功响应：`{ sessionId, effort }`。
- 其它订阅端会收到 `settings.changed` 事件（见 §5.10.10）。
- 错误：`VALIDATION`（`sessionId` 缺失、`effort` 不在枚举内）、`NOT_FOUND`（会话不存在）。

### 4.10 `message.respond`

结算一条挂起的审批或交互。
**什么时候用**：用户点了审批卡上的按钮、或提交了提问卡的回答。

原生结算接口只有这一个，因为审批与交互是同一个机制，传什么由目标消息的 `type` 决定；`approval.respond` 与 `tool.respond` 是它的兼容别名。

审批（`type='approval'`）请求：

```json
{
  "id": "req_5b7e02",
  "type": "request",
  "method": "message.respond",
  "timestamp": 1785715205000,
  "payload": { "messageId": "msg_9de1f0", "decision": "approved" }
}
```

`decision` 取值：`approved`（允许这一次）/ `approved_all`（允许，并把会话切到全权模式：`approvalMode='full_access'`、`approvedAll=true`；本 run 后续审批与之后的新 run 都不再挂起）/ `rejected`（拒绝）。

交互（`type='tool_interactive'`）请求：

```json
{
  "id": "req_6a12ff",
  "type": "request",
  "method": "message.respond",
  "timestamp": 1785715210000,
  "payload": { "messageId": "msg_77c3a1", "answers": { "要处理什么格式？": ["CSV"] } }
}
```

`answers` 的 key 是 `content.questions[].question` 的**原文**，value 是选中的 option 文案数组（与 Claude SDK 的 `AskUserQuestion` 一致）。

成功响应（结算后的完整消息，`status` 已不是 `pending`）：

```json
{
  "id": "req_5b7e02",
  "type": "response",
  "method": "message.respond.result",
  "timestamp": 1785715205014,
  "payload": {
    "message": {
      "id": "msg_9de1f0",
      "sessionId": "sess_4f2a9c",
      "runId": "run_8ab31d",
      "seq": 10,
      "role": "assistant",
      "type": "approval",
      "status": "approved",
      "content": {
        "toolCallId": "toolu_01AbCd",
        "toolName": "Bash",
        "title": "允许执行 Bash？",
        "description": "npm test",
        "input": { "command": "npm test" },
        "decision": "approved",
        "decisionSource": "user"
      },
      "createdAt": "2026-10-15T06:40:02.400Z"
    }
  },
  "error": null
}
```

错误响应取值：

| code | 何时 |
|---|---|
| `VALIDATION` | 载荷与消息 `type` 不匹配：`approval` 不给 `decision`（或取值非法）、`tool_interactive` 不给 `answers`（或 `answers` 不是「字符串数组的对象」） |
| `NOT_FOUND` | 消息不存在，或该消息不是 `approval` / `tool_interactive`（例如对一条普通 text 消息应答） |
| `CONFLICT` | 消息已结算（重复点击、两个端同时应答） |

```json
{
  "id": "req_5b7e02",
  "type": "response",
  "method": "message.respond.result",
  "timestamp": 1785715205014,
  "error": { "code": "CONFLICT", "message": "消息 msg_9de1f0 已结算",
             "messageKey": "error.conflict.message_settled", "params": { "messageId": "msg_9de1f0" } }
}
```

- `CONFLICT` 不是失败：说明别的路径已经结算了，前端按 `id` upsert 收到的那条 `message` 事件即可，不要弹错误。
- `approved_all` 的会话更新发生在抢到结算仲裁之后、`liveHub.settle` 放行引擎之前，因此同一 run 的下一条审批能立即看到新的 `approvedAll`；并发失败的一方只拿 `CONFLICT`，不写会话。
- 会话更新落库失败只记日志、不让本次响应失败（与 agent-runtime 一致），但以库里的最新会话状态为准。
- 结算成功后引擎被放行，同一 `id` 的 `message` 事件会广播给该会话的所有订阅端（多端同步靠它）。
- 同一条消息**没有超时**：挂起多久应答都有效，见 §10。

### 4.11 `run.abort`

中止一个正在跑的 run。
**什么时候用**：用户点「停止」，或界面上要放弃这次运行。

请求：

```json
{
  "id": "req_3e8811",
  "type": "request",
  "method": "run.abort",
  "timestamp": 1785715215000,
  "payload": { "runId": "run_8ab31d" }
}
```

成功响应：

```json
{
  "id": "req_3e8811",
  "type": "response",
  "method": "run.abort.result",
  "timestamp": 1785715215021,
  "payload": { "runId": "run_8ab31d", "aborted": true },
  "error": null
}
```

- 响应不再返回完整 `Run`；`runId` 是**向上解析后的顶层 run id**（传子 run id 时也是顶层 run）。
- 终态细节通过随后广播的 `run.status` 与 `message` 事件获取，字段定义见 [4.05 §2](./4.05-运行.md#2-run-字段表)。

错误响应取值：

| code | 何时 | 前端表现 |
|---|---|---|
| `VALIDATION` | `runId` 缺失 | 参数错误，不重试 |
| `NOT_FOUND` | run 不存在 | 刷新会话状态 |
| `CONFLICT` | **该 run（或其向上解析到的顶层 run）已经落终态**（`succeeded` / `failed` / `aborted`） | 不是失败，按已收尾处理，刷新局面即可 |

```json
{
  "id": "req_3e8811",
  "type": "response",
  "method": "run.abort.result",
  "timestamp": 1785715215021,
  "error": { "code": "CONFLICT", "message": "运行 run_8ab31d 已终态",
             "messageKey": "error.conflict.run_terminal", "params": { "runId": "run_8ab31d" } }
}
```

`CONFLICT` 只有这一个含义：**该 run（或子 run 向上解析到的顶层 run）已经是终态**，不要把它当成「服务端忙」去重试。

传子 run id 时向上解析到顶层 run，按顶层 run 中止，响应返回顶层 run。

中止的连带效果（前端看到的完整结果，顺序固定）：

1. 该 run 树（顶层 run 及其全部子 run）下所有 `status='pending'` 的审批 / 交互被置 `aborted`，并以 `message` 事件广播（`content.decisionSource` 为 `'abort'`）。
2. 顶层 run 落 `aborted`，该 run 血缘下的活跃子 run 批量落 `aborted`；每个被收敛的子 run 补发 `task.notified`（wire `status='stopped'`）。子 run 不发 `chat.final` / `chat.error` / `chat.aborted`。
3. 顶层 run 广播 `run.status` / `chat.aborted`，最后广播 `session.status`（通常为 `completed`）。
   中止在 `abortRun` 内立即广播，不等引擎返回；`closeRun` 幂等去重。

会话粒度的等价入口是 REST `POST /sessions/abort { sessionId }`，它只是「中止该会话当前活跃 run」的另一入口。

## 5. 下行事件

原生十个：`connection.ready` / `session.status` / `session.named` / `run.started` / `run.status` / `message` / `chat.delta` / `error` / `task.started` / `task.notified`。
兼容十个：`chat.thinking` / `chat.retry` / `chat.final` / `chat.error` / `chat.aborted` / `approval.request` / `tool.interactive` / `tool.executing` / `tool.executed` / `settings.changed`。

两层的关系是**叠加**，不是替代：

- **原生事件仍是内容真相**：正文终稿、工具调用、审批与交互都以 `message` 的 upsert 为准；顶层 run 成败以 `run.status` 为准。
- **兼容事件是附加通知**：商用客户端可以只消费兼容事件，原生客户端可以完全忽略它们；两条流会同时到达同一订阅者。
- **`chat.delta` 只承载正文增量**，思考走 `chat.thinking` 的 `start` / `delta` / `stop` 三阶段，不会再混进正文；旧的 `chat.thinking.delta` 已删除。
- **`chat.retry` 是重试通知**：引擎发生 API 重试时发送，run 仍在继续，不是终态事件。
- **`run.started` / `run.status` 只表示顶层 run**；子 agent 任务用 `task.started` / `task.notified`，不影响顶层 run 的状态。
- **内容类兼容事件（`chat.*` / `tool.*` / `approval.request`）都带 `runId` 与 `parentRunId`**：子 run 的 `parentRunId` 是父 run id，顶层 run 为 `null`；原生 `message` 只带 `runId`，父 run 关系用 `task.started`（断线后配合 `runs/children`）建立的映射定位。`settings.changed` 没有 run 维度，只带 `sessionId`。
- **`task.*` 是新增原生事件**：cosight-viewer 未注册，会自然忽略；现有原生事件不变，兼容事件按 §5.10 发送。
- **`settings.changed` 用于多端同步**：WS 三个 switch 与 REST 会话设置更新都会广播，`changedBy.channel` 区分 `ws` / `http`。
- **`interactive.timeout` 刻意不实现**：审批与交互没有超时，服务端永远不会发出该事件；出口只有用户应答、中止、服务重启或进程被杀。

| method | 层 | 何时发 | 前端该做什么 |
|---|---|---|---|
| `connection.ready` | 原生 | 连接建立后立即 | 记录 `connectionId`，启动心跳定时器；`restored` 恒 `false`、`sessionId` 恒 `null`，重连场景下重新订阅 |
| `session.status` | 原生 | 会话状态变化（起 run 置 `in_progress`、run 收尾重算） | 更新会话头状态 |
| `session.named` | 原生 | 会话名为空、run 收口后由引擎标题补上 | 更新会话名展示；普通列表下次拉取也会带出新名字 |
| `run.started` | 原生 | 顶层 run 以 `running` 建行后、`send` 响应前（仅当 run 仍为 `running`） | 进入「运行中」态，禁用发送、显示停止按钮 |
| `run.status` | 原生 | 顶层 run 落终态（成功 / 失败 / 中止） | 收尾：解除忙碌态，刷新 `runs/detail` 与挂起状态 |
| `message` | 原生 | 一条消息落库（新建或更新） | 按 `id` upsert 渲染 |
| `chat.delta` | 原生 | 正文流式产出 | 仅用于流式渲染，瞬时内容 |
| `chat.thinking` | 兼容 | 思考块开始 / 增量 / 结束 | 按 `phase` 建、累加、收掉思考占位；瞬时内容 |
| `chat.retry` | 兼容 | 引擎发生 API 重试 | 展示重试进度；run 未终止 |
| `chat.final` | 兼容 | 成功顶层 run 收尾 | 取 `content` 作为本轮终稿，按 `messageId` 去重（为 `null` 时跳过），结束流式占位 |
| `chat.error` | 兼容 | 失败顶层 run 收尾 | 展示 `message`（`code` 恒 `RUN_ERROR`），结束一轮 |
| `chat.aborted` | 兼容 | 中止顶层 run 收尾 | 清流式，展示 `reason`，结束一轮 |
| `approval.request` | 兼容 | 审批消息以 `pending` 落库 | 弹审批卡；`approvalId` 用于 `approval.respond` |
| `tool.interactive` | 兼容 | 交互消息以 `pending` 落库 | 弹提问卡；`toolCallId` 用于 `tool.respond` |
| `tool.executing` | 兼容 | `tool_use` 消息落库 | 显示工具开始执行 |
| `tool.executed` | 兼容 | `tool_result` 消息落库 | 显示工具结果 |
| `settings.changed` | 兼容 | 会话设置经 WS switch 或 REST 更新 | 同步设置 UI；调用方自己的响应已确认，处理需幂等 |
| `error` | 原生 | 连接级错误（当前仅 `SLOW_CONSUMER`） | 立即准备重连 + 重订阅 + 重拉 |
| `task.started` | 原生 | 子 agent 任务开始（`task_started`） | 按 `runId` 建子 agent 块，按 `parentRunId` 挂到父块下 |
| `task.notified` | 原生 | 子 agent 任务结束（`task_notification`） | 按 `runId` 收敛子 agent 块状态 |

事件只推给**订阅了该会话**的连接（`connection.ready` 与 `error` 是连接级的，只推给本连接）。

### 5.1 `connection.ready`

何时发：WS 握手成功后立即，早于任何其它事件。

```json
{
  "id": "evt_1785715200010_1",
  "type": "event",
  "method": "connection.ready",
  "timestamp": 1785715200010,
  "payload": { "connectionId": "conn_1", "restored": false, "sessionId": null }
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `connectionId` | string | 连接级标识，形如 `conn_1`，进程内自增，断开即失效 |
| `restored` | boolean | 恒为 `false`：服务端没有连接恢复能力，也不下发 `connectionToken` |
| `sessionId` | null | 恒为 `null`：连接不带鉴权、不绑定会话 |

前端：收到它才算连接可用；重连场景下，在这一步之后开始第 7 节的重订阅与重拉。
不要等待 `connectionToken` 或任何鉴权字段：本服务端侧本地单用户，没有这些概念。

### 5.2 `session.status`

何时发：会话状态发生变化时。
当前只有两个触发点 - 起 run 时置 `in_progress`、run 收尾后重算为 `completed`。

```json
{
  "id": "evt_1785715200240_11",
  "type": "event",
  "method": "session.status",
  "timestamp": 1785715200240,
  "payload": { "sessionId": "sess_4f2a9c", "status": "in_progress" }
}
```

```json
{
  "id": "evt_1785715212100_41",
  "type": "event",
  "method": "session.status",
  "timestamp": 1785715212100,
  "payload": { "sessionId": "sess_4f2a9c", "status": "completed" }
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `sessionId` | string | 会话 ID |
| `status` | string | `not_started` / `in_progress` / `completed` |

- `not_started` 只会在 `subscribe` 的响应快照里出现，不会有对应的事件。
- 会话状态是粗粒度的：`completed` 只代表「没有活跃 run」，不代表这次运行成功，run 的成败看 `run.status`。
- 前端：只用来更新会话头的状态标签，不要用它驱动消息流。

### 5.2.1 `session.named`

何时发：会话名为空（`name === ''`）且本轮 run 已收口时，服务端从引擎读到的会话标题补名成功之后。
引擎不提供标题、会话文件不存在或标题仍为空时不发；已有名字（含工坊按首条正文起的名字）不会被覆盖。

```json
{
  "id": "evt_1785715212400_42",
  "type": "event",
  "method": "session.named",
  "timestamp": 1785715212400,
  "payload": { "sessionId": "sess_4f2a9c", "name": "会话 name 处理逻辑" }
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `sessionId` | string | 会话 ID |
| `name` | string | 补上的会话名；长度超过 60 字时截断并补 `…` |

- 只在空名时补：调用方/用户给过名字的会话不会被引擎标题覆盖。
- 补名是幂等的：同一会话只会发一次；没发出来（标题还没生成）时下一轮 run 收口会再试。
- 前端：更新会话名即可；漏收也不影响数据，`sessions/list` 下次拉取会带出新名字。

### 5.3 `run.started`

何时发：顶层 run 以 `running` 建行之后、`send` 响应返回之前；引擎在响应后异步启动。

**只表示顶层 run**：子 run 的启动走 `task.started`（见 §5.8），不会发本事件。

**到达时 `payload.status` 已经是 `running`** - 顶层 run 建行即 `running` 并写 `startedAt`，不存在 `pending` 阶段，也没有对应的 `pending` 事件。`send` 响应同样带 `status:'running'` 与 `run.status='running'`，本事件不是运行态的唯一确认。

**只在 run 仍为 `running` 时发**：若 `send` 返回前 run 已被并发中止或结算，跳过本事件，也不启动引擎；`closeRun` 收口并广播 `run.status`。终态 run 永不补发 `run.started`。引擎启动前若收到中止信号，同样不调用适配器。

载荷是完整 `Run`，字段定义见 [4.05 §2](./4.05-运行.md#2-run-字段表)；顶层 run 的 `parentRunId` / `parentToolUseId` / `subagentType` / `taskId` 恒为 `null`，`delegationDepth` 恒为 `0`。

```json
{
  "id": "evt_1785715200260_12",
  "type": "event",
  "method": "run.started",
  "timestamp": 1785715200260,
  "payload": {
    "id": "run_8ab31d",
    "sessionId": "sess_4f2a9c",
    "instanceId": "inst_55b2",
    "parentRunId": null,
    "parentToolUseId": null,
    "subagentType": null,
    "delegationDepth": 0,
    "taskId": null,
    "status": "running",
    "error": null,
    "startedAt": "2026-10-15T06:40:00.255Z",
    "finishedAt": null,
    "createdAt": "2026-10-15T06:40:00.210Z",
    "waiting": null
  }
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | run ID，后续 `run.abort`、`runs/detail` 都用它 |
| `sessionId` | string | 所属会话 |
| `instanceId` | string | 所属实例（同 agent 同 stage） |
| `parentRunId` | `null` | 本事件只表示顶层 run |
| `parentToolUseId` | `null` | 同上 |
| `subagentType` | `null` | 同上 |
| `delegationDepth` | `0` | 顶层 run 恒为 `0` |
| `taskId` | `null` | 同上 |
| `status` | string | 本事件恒为 `running` |
| `error` | string \| null | 失败原因，本事件恒为 `null` |
| `startedAt` | string \| null | ISO 时间字符串，本事件已非空 |
| `finishedAt` | string \| null | ISO 时间字符串，本事件恒为 `null` |
| `createdAt` | string | run 创建时间 |
| `waiting` | object \| null | 派生字段：该 run 挂起中的审批 / 交互数量与最早一条的时间；无挂起为 `null` |

前端：用 `payload.id` 记住当前 runId（`run.abort` 要用），把界面切到「运行中」。

### 5.4 `run.status`

何时发：顶层 run 落终态时发一次，只此一次。
没有中间进度事件，进度感靠 `chat.delta` / `chat.thinking` 与 `message`。

**只表示顶层 run**：子 run 的终态走 `task.notified`（见 §5.9）。
顶层 run 收尾时若仍有活跃子 run，`closeRun` 会把它们收敛为 `aborted` 并补发 `task.notified`。

失败的 run（此时会先收到一条 `type='error'` 的 `message` 事件，再收到本事件）：

| 字段 | 类型 | 说明 |

| `startedAt` | string \| null | 起跑时间；终态时非空 |

### 5.5 `message`

何时发：**一条消息落库时**（新建或更新都发）。

这是**落库快照的 upsert**，不是增量：载荷就是那条消息在库里的完整一行，前端按 `id` 覆盖渲染。

`payload.runId` 可能是子 run id：子 agent 的产出与顶层 run 的产出共用同一条会话消息流，按 `runId` 归属。

```ts
interface Message {
  id: string;
  sessionId: string;
  runId: string | null;
  seq: number;                    // 会话内单调递增，排序权威键
  role: 'user' | 'assistant' | 'system';
  type: 'text' | 'thinking' | 'tool_use' | 'tool_result' | 'approval' | 'tool_interactive' | 'error' | 'status';
  status: 'pending' | 'approved' | 'approved_all' | 'rejected' | 'answered' | 'aborted' | null;
  content: object;                // 形状由 type 决定，权威定义见 4.04
  createdAt: string;
}
```

覆盖规则：

- `id` 已存在 → **整行替换**（`status` 与 `content` 都可能变）；
- `id` 不存在 → 插入，按 `seq` 排序，**不要用 `createdAt` 排序**（更新不刷新 `createdAt`，同一 `id` 的 `createdAt` 恒为首次落库时间）。
- 重复收到同一条（例如 `send` 响应里的 user 消息 + 响应前到达的 `message` 事件）不会出问题，这正是 upsert 的意义。

前端按 `seq` 去重/排序，按 `id` 覆盖，两条规则合起来就是一份幂等的消息表。

**实例一：新建一条 assistant 文本**（`type='text'`，`status` 恒为 `null`）。

```json
{
  "id": "evt_1785715201875_18",
  "type": "event",
  "method": "message",
  "timestamp": 1785715201875,
  "payload": {
    "id": "msg_3c81be",
    "sessionId": "sess_4f2a9c",
    "runId": "run_8ab31d",
    "seq": 9,
    "role": "assistant",
    "type": "text",
    "status": null,
    "content": { "text": "已补上 weather-agent 的单元测试，覆盖了缓存命中与超时两条分支。" },
    "createdAt": "2026-10-15T06:40:01.875Z"
  }
}
```

**实例二：同一条审批的结算更新**（`id` / `seq` / `createdAt` 不变，`status` 与 `content` 变）。

```json
{
  "id": "evt_1785715205200_24",
  "type": "event",
  "method": "message",
  "timestamp": 1785715205200,
  "payload": {
    "id": "msg_9de1f0",
    "sessionId": "sess_4f2a9c",
    "runId": "run_8ab31d",
    "seq": 10,
    "role": "assistant",
    "type": "approval",
    "status": "approved",
    "content": {
      "toolCallId": "toolu_01AbCd",
      "toolName": "Bash",
      "title": "允许执行 Bash？",
      "description": "npm test",
      "input": { "command": "npm test" },
      "decision": "approved",
      "decisionSource": "user"
    },
    "createdAt": "2026-10-15T06:40:02.400Z"
  }
}
```

`status != 'pending'` 就是个信号：这条审批/交互已经出结果，前端**必须**把弹卡收掉（哪怕是被别的端或中止结算的）。

**哪些消息会以本事件出现**：全部落库的消息。

| `type` | 何时出现 | 前端渲染 |
|---|---|---|
| `text` | 每个 assistant 文本块一条（工具调用后模型再生成，就是**再一条**） | 正文气泡 |
| `thinking` | 每个 assistant 思考块一条 | 思考折叠区 |
| `tool_use` | 每个工具调用一条（`content` 含 `toolCallId` / `toolName` / `input`） | 工具调用条目 |
| `tool_result` | 每个工具结果一条（`content` 含 `toolCallId` / `output` / `isError`） | 挂在对应 `toolCallId` 的调用条目下 |
| `approval` | 审批挂起时落一条 `status='pending'`，结算时同 `id` 再更新一条 | 审批卡，`pending` 时弹 |
| `tool_interactive` | 交互挂起同上（`AskUserQuestion` 走它，不走 `tool_use`） | 提问卡 |
| `error` | run 失败时补一条 system 消息（`content.message` 是原因） | 错误提示 |
| `status` | 预留，当前实现不产出 | 可忽略 |

`content` 各形状的权威定义在 [4.04 消息](./4.04-消息.md)，本文只给帧实例。

### 5.6 `chat.delta`

何时发：引擎流式产出时，高频。

```json
{
  "id": "evt_1785715201600_16",
  "type": "event",
  "method": "chat.delta",
  "timestamp": 1785715201600,
  "payload": {
    "sessionId": "sess_4f2a9c",
    "runId": "run_8ab31d",
    "parentRunId": null,
    "messageType": "text",
    "delta": "已补上 weather-agent"
  }
}
```

思考增量**不走**本事件，走 `chat.thinking` 的 `phase='delta'`（见 §5.10.1）；`chat.delta` 恒为正文，`messageType` 字段保留为 `'text'` 以兼容旧客户端。

| 字段 | 类型 | 说明 |
|---|---|---|
| `sessionId` | string | 会话 ID |
| `runId` | string | 产出该段正文的 run；可能是子 run |
| `parentRunId` | string \| null | 父 run id；顶层 run 为 `null`，子 run 为父 run id |
| `messageType` | string | 恒为 `'text'` |
| `delta` | string | 本次增量片段，**不是**完整内容 |

四条语义，缺一条就会写错：

1. **瞬态、不落库、断线即丢**。
   它只是观感，不是内容真相。
2. **同一 `(runId, 'text')` 的增量是同一段正文的累加**：客户端应 `buffer += delta` 流式渲染。
   思考内容走 `chat.thinking` 的同一 `runId` 增量，单独累加到思考缓冲，不能拼进正文。
3. **落库的 `message`（`type='text'` / `'thinking'`）是该段的整体值**：前端收到它时**覆盖**本地缓冲（`buffer = content.text`），**不是 `+=`**。
   写成追加就会看到内容翻倍。
4. **一个 run 里可能有多个文本段**：模型调用工具之后会再生成一段（新的 `chat.delta` 段、新的 `message`）。
   delta 段与 message 段的对应关系**靠到达顺序，不靠 id** - `chat.delta` 不带消息 id。

推荐的客户端算法（三段式）：

1. 收到 `chat.delta` / `chat.thinking`（`phase='delta'`）→ 分别计入正文 / 思考的当前段缓冲，流式渲染。
2. 收到 `type='text'` / `'thinking'` 的 `message` → 用整条消息**替换**对应段的流式占位，并**结束当前段**。
3. 该段之后的增量事件开启新的一段，重复第 1 步。

### 5.7 `error`

何时发：连接级错误。
当前只有一种：慢消费者（见 §8）。

```json
{
  "id": "evt_1785715230000_77",
  "type": "event",
  "method": "error",
  "timestamp": 1785715230000,
  "payload": { "code": "SLOW_CONSUMER", "message": "客户端消费过慢，连接将被断开" }
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | string | 错误码，当前仅 `SLOW_CONSUMER` |
| `message` | string | 可展示的原因描述 |

- 这是**事件**（`type='event'`），不是某个请求的回执，`id` 是 `evt_` 前缀。
- 收到它意味着服务端**马上会断开这条连接**，前端必须走第 7 节的重连流程（重连 + 重订阅 + 重拉），只弹个提示不够。

### 5.8 `task.started`

何时发：引擎上报 `task_started`，且任务类型为 `local_agent` 或带 `subagent_type` 时。
服务端先创建子 run（`status='running'`），再广播本事件；其它任务类型不建子 run，也不发本事件。

```json
{
  "id": "evt_1785715203120_15",
  "type": "event",
  "method": "task.started",
  "timestamp": 1785715203120,
  "payload": {
    "sessionId": "sess_4f2a9c",
    "runId": "run_c41e7a92",
    "parentRunId": "run_8ab31d",
    "taskId": "task_7f21",
    "toolCallId": "toolu_01AbCd",
    "subagentType": "general-purpose",
    "delegationDepth": 1,
    "description": "补齐 weather-agent 的单元测试"
  }
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `sessionId` | string | 会话 ID |
| `runId` | string | 新建子 run 的 id |
| `parentRunId` | string | 父 run id；引擎未给 `parent_task_id` 时为顶层 run |
| `taskId` | string | 引擎任务 id（`task_id`） |
| `toolCallId` | string \| null | 触发该任务的父级工具调用 id（SDK `tool_use_id`）；**wire 字段名是 `toolCallId`** |
| `subagentType` | string \| null | 子 agent 类型 |
| `delegationDepth` | number | 委派深度；优先取引擎上报的 `spawn_depth`（大于 `0` 时），缺失或为 `0` 时为父 run 深度 + 1（顶层子 run 为 `1`） |
| `description` | string | 可选附加字段：任务描述，可能为空串；客户端可忽略 |

- 子 run 的 `sessionId` / `instanceId` 继承父 run，不占用活跃顶层 run 名额，也不发 `run.started`。
- **resume**：同一 `task_id` 在旧子 run 已终态后再次收到 `task_started`（SDK 恢复后 `task_id` 不变、`run_id` 变）时新建一条子 run；恢复后的内容与终态都归新 run。
- **内容归位**：消息的 `runId` 归属依次尝试 `agent_id`（等于 `task_id`）→ `parent_tool_use_id` → 父 run；前两级能对上子 run 的落在子 run，都对不上时落在父 run。
- **审批**：`CanUseTool` 的 `agentID` 等于 `task_id`，`InputRequest` 带 `agentId`；子 agent 的审批消息落在子 run；是否自动放行读会话的 `Session.approvedAll`，顶层 run 与子 run 同源。
- **wire 与 DTO 的字段名不同**：本事件的 `toolCallId` 在 REST `Run` DTO 里叫 `parentToolUseId`（见 [4.05 §2](./4.05-运行.md#2-run-字段表)），两者同值。
- 不显式设置 `forwardSubagentText`；SDK 0.3.300 默认 `false`，子 agent 正文不保证进入主流，前端不要假设每个子 run 都有正文消息。

### 5.9 `task.notified`

何时发：引擎上报 `task_notification`，服务端把对应子 run 条件更新到终态后广播。
本事件只表示子 run，不表示顶层 run。

```json
{
  "id": "evt_1785715210480_26",
  "type": "event",
  "method": "task.notified",
  "timestamp": 1785715210480,
  "payload": {
    "sessionId": "sess_4f2a9c",
    "runId": "run_c41e7a92",
    "parentRunId": "run_8ab31d",
    "taskId": "task_7f21",
    "status": "completed",
    "subagentType": "general-purpose",
    "error": null,
    "summary": "已补齐 6 个用例，全部通过"
  }
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `sessionId` | string | 会话 ID |
| `runId` | string | 子 run id |
| `parentRunId` | string | 父 run id |
| `taskId` | string | 引擎任务 id（`task_id`） |
| `status` | `'completed'` \| `'failed'` \| `'stopped'` | **wire 使用 SDK 原值**：`completed` / `failed` / `stopped`；DB 的 Run 状态映射为 `succeeded` / `failed` / `aborted` |
| `subagentType` | string \| null | 子 agent 类型 |
| `error` | string \| null | 可选附加字段；仅 `failed` 非空，可直接展示 |
| `summary` | string \| null | 可选附加字段；引擎给出的任务摘要 |

- **wire 与 DB 的状态值不同**：本事件 `status` 用 SDK 值 `completed` / `failed` / `stopped`；DB 与 REST `Run` DTO 仍是 `succeeded` / `failed` / `aborted`。前端渲染子 agent 块时直接用 wire 值，需要与 REST 对齐时按上表映射。
- 终态走条件更新：子 run 已终态则不再重复广播。
- 子 run 的 `finishedAt` 随终态落值；`failed` 时 `error` 非空。
- 顶层 run 不因单个子 run 结束而变化，`run.status` 只在顶层 run 收尾时发一次。
- 中止与正常收尾时残留子 run 的收敛顺序见 §6.1。

### 5.10 兼容事件

兼容事件为商用客户端补发，全部推给**订阅了该会话**的连接；原生 `message` / `run.status` 事件照常同时发送。
`task.*` 是原生事件，不属于兼容层；cosight-viewer 未注册，忽略即可。兼容事件的形状以本节为准。

**`interactive.timeout` 刻意不实现**：审批与交互没有超时，服务端不会发出该事件，客户端不要等待它。

#### 5.10.1 `chat.thinking`

思考块的阶段事件，替代已删除的 `chat.thinking.delta`。语义与 `chat.delta` 相同：瞬态、不落库、断线即丢。

```json
{
  "id": "evt_1785715201400_14",
  "type": "event",
  "method": "chat.thinking",
  "timestamp": 1785715201400,
  "payload": {
    "sessionId": "sess_4f2a9c",
    "runId": "run_8ab31d",
    "parentRunId": null,
    "phase": "delta",
    "text": "先看一下现有测试文件的结构",
    "at": "2026-10-15T06:40:01.400Z"
  }
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `sessionId` | string | 会话 ID |
| `runId` | string | 产出该段思考的 run；可能是子 run |
| `parentRunId` | string \| null | 父 run id；顶层 run 为 `null` |
| `phase` | `'start'` \| `'delta'` \| `'stop'` | 思考块阶段 |
| `text` | string | **仅 `phase='delta'` 出现**：本次思考增量，**不是**完整内容 |
| `at` | string | 该阶段的发生时刻，ISO 8601 |

- `start` / `stop` 只表示思考块的边界，不带 `text`；客户端收到 `start` 建思考占位，收到 `stop` 收掉流式态。
- 同一 `runId` 的 `delta` 是同一段思考的累加；落库的 `type='thinking'` `message` 是整体值，收到后用 `content.text` 覆盖缓冲。
- `chat.thinking.delta` 已删除，服务端不再发送；只想展示正文的客户端可以完全忽略本事件。

#### 5.10.2 `chat.retry`

引擎上报 API 重试时发送。它不是终态事件，run 仍在继续。

```json
{
  "id": "evt_1785715201300_13",
  "type": "event",
  "method": "chat.retry",
  "timestamp": 1785715201300,
  "payload": {
    "sessionId": "sess_4f2a9c",
    "runId": "run_8ab31d",
    "parentRunId": null,
    "attempt": 1,
    "maxRetries": 3,
    "errorStatus": 529,
    "error": "overloaded_error"
  }
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `sessionId` | string | 会话 ID |
| `runId` | string | 发生重试的顶层 run |
| `parentRunId` | null | 本事件只表示顶层 run，恒为 `null` |
| `attempt` | number | 第几次重试，从 1 起 |
| `maxRetries` | number | 最大重试次数 |
| `errorStatus` | number \| null | 上游 HTTP 状态码；无则为 `null` |
| `error` | string \| null | 上游错误文本；无则为 `null` |

- 前端可展示「正在重试（`attempt` / `maxRetries`）」；最终成败仍以 `run.status` 与 `chat.final` / `chat.error` 为准。
- 重试事件是通知，不改变 run 状态，也不要求客户端重发消息。

#### 5.10.3 `chat.final`

成功顶层 run 收尾时**恰好发一次**。子 run 收尾不发本事件，只发 `task.notified`。

```json
{
  "id": "evt_1785715212001_42",
  "type": "event",
  "method": "chat.final",
  "timestamp": 1785715212001,
  "payload": {
    "sessionId": "sess_4f2a9c",
    "runId": "run_8ab31d",
    "parentRunId": null,
    "content": "已补上 weather-agent 的单元测试。",
    "messageId": "msg_3c81be"
  }
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `sessionId` | string | 会话 ID |
| `runId` | string | 收尾的顶层 run |
| `parentRunId` | `null` | 恒为 `null`；本事件只表示顶层 run |
| `content` | string | 本轮终稿 |
| `messageId` | string \| null | 终稿对应的落库消息 id；客户端据此按 `id` 覆盖，不要追加正文。本次 run 没有产生助手文本消息时（如纯工具回合）为 `null`，此时跳过按 id 覆盖即可 |

- `content` 优先取适配器终稿；终稿为空时退回本 run 累积的正文增量，再退回已落库的助手文本。
- 与原生事件的顺序：`run.status`（`succeeded`）→ `chat.final` → `session.status`（`completed`）。

#### 5.10.4 `chat.error`

失败顶层 run 收尾时发一次。子 run 收尾不发本事件，只发 `task.notified`。

```json
{
  "id": "evt_1785715212001_43",
  "type": "event",
  "method": "chat.error",
  "timestamp": 1785715212001,
  "payload": {
    "sessionId": "sess_4f2a9c",
    "runId": "run_8ab31d",
    "parentRunId": null,
    "code": "RUN_ERROR",
    "message": "模型调用未成功：error_during_execution"
  }

```

| 字段 | 类型 | 说明 |
|---|---|---|
| `sessionId` / `runId` | string | 会话与收尾的顶层 run |
| `parentRunId` | `null` | 恒为 `null`；本事件只表示顶层 run |
| `code` | string | 恒为 `RUN_ERROR` |
| `message` | string | 与 `run.status` 事件里的 `error` 同值，可直接展示 |

#### 5.10.5 `chat.aborted`

中止顶层 run 收尾时发一次。子 run 收尾不发本事件，只发 `task.notified`。

```json
{
  "id": "evt_1785715212001_44",
  "type": "event",
  "method": "chat.aborted",
  "timestamp": 1785715212001,
  "payload": {
    "sessionId": "sess_4f2a9c",
```

| `reason` | string | 取 `run.error`，没有时用「用户中止」 |

#### 5.10.6 `approval.request`

审批消息以 `status='pending'` 落库后发送（紧跟在同一条 `message` 事件之后）。

```json
{
  "id": "evt_1785715202400_12",
  "type": "event",
  "method": "approval.request",
  "timestamp": 1785715202400,
  "payload": {
    "approvalId": "msg_9de1f0",
    "sessionId": "sess_4f2a9c",
    "runId": "run_8ab31d",
    "parentRunId": null,
    "toolCallId": "toolu_01AbCd",
    "toolName": "Bash",
    "title": "允许执行 Bash？",
    "description": "npm test",
    "input": { "command": "npm test" },
    "options": [
      { "value": "approved", "label": "允许", "enLabel": "Allow" },
      { "value": "approved_all", "label": "本会话全部允许", "enLabel": "Allow all" },
      { "value": "rejected", "label": "拒绝", "enLabel": "Reject" }
    ]
  }
}
```

- `approvalId` 就是审批消息的 `message.id`，原样回传给 `approval.respond`。
- `toolCallId` 是对应的工具调用 id；审批消息自身没有该字段时可为 `null`。
- `agentId` 是**可选**字段：审批来自子 agent 时携带，顶层 run 的审批不带；客户端可忽略。
- `runId` 是产出该审批的 run（可能是子 run），`parentRunId` 是它所属的父 run；顶层 run 的审批 `parentRunId` 为 `null`。
- `options` 的 `value` 就是 `approval.respond` 的 `decision`；引擎明确禁止「本会话全部允许」时（消息 `content.allowAll === false`）不提供 `approved_all`。
- 用户选 `approved_all` 后，服务端把会话置为 `approvalMode='full_access'`、`approvedAll=true`，再放行引擎；之后的新 run 继承该会话状态，直到 `mode.switch` 切到非 `full_access` 才复位。
- **不带 `expiresAt`，也没有任何超时字段**：审批没有超时。
- 只在 `pending` 时发送；结算走原生 `message` 事件（同 `id` 更新）。

#### 5.10.7 `tool.interactive`

交互消息以 `status='pending'` 落库后发送（紧跟在同一条 `message` 事件之后）。

```json
{
  "id": "evt_1785715210400_20",
  "type": "event",
  "method": "tool.interactive",
  "timestamp": 1785715210400,

    "toolName": "AskUserQuestion",
    "input": { "questions": [ { "header": "格式", "question": "要处理什么格式？", "options": [ { "label": "CSV" } ] } ] }
```

- `toolCallId` 原样回传给 `tool.respond`。
- `runId` 是产出该交互的 run（可能是子 run），`parentRunId` 是它所属的父 run；顶层 run 的交互 `parentRunId` 为 `null`。
- **没有 `timeout` 字段，也没有超时语义**：交互挂起多久应答都有效。

#### 5.10.9 `tool.executed`

`tool_result` 消息落库后发送（紧跟在同一条 `message` 事件之后）。

```json
{
  "id": "evt_1785715204500_18",
  "type": "event",
  "method": "tool.executed",
  "timestamp": 1785715204500,
  "payload": {
    "sessionId": "sess_4f2a9c",
    "runId": "run_c41e7a92",
    "parentRunId": "run_8ab31d",
    "toolCallId": "toolu_01AbCd",

```

- `toolName` / `input` 从同一 run 内对应的 `tool_use` 消息回填；找不到对应调用时使用结果消息自身的字段。
- `isError` 恒为布尔值。
- `runId` / `parentRunId` 取值语义同 §5.10.6；客户端可忽略。

#### 5.10.10 `settings.changed`

会话设置发生变化时发送，用于多端同步。WS 的 `model.switch` / `mode.switch` / `effort.switch` 与 REST 的会话设置更新都会触发。

```json
{
  "id": "evt_1785715220100_30",
  "type": "event",
  "method": "settings.changed",
  "timestamp": 1785715220100,
  "payload": {
    "sessionId": "sess_4f2a9c",
    "settings": { "mode": "workspace_write", "effort": "high", "modelId": "f3b2a1c0-9d8e-4f7a-8b6c-5d4e3f2a1b0c" },
    "changedBy": { "channel": "ws", "actorId": "" },
    "appliesTo": "nextRun",
    "at": "2026-10-19T06:40:20.100Z"
  }
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `sessionId` | string | 会话 ID |
| `settings` | object | 变更后的会话设置：`mode`、`effort`、`modelId`（恒非空）。`mode` 是线路快照字段名，对应 Session DTO 的 `approvalMode`（agent-runtime 口径） |
| `changedBy.channel` | `'ws'` \| `'http'` | 变更来源：WS switch 或 REST 更新 |
| `changedBy.actorId` | string | 恒为 `""`：本服务没有鉴权，无法识别操作者 |
| `appliesTo` | `'nextRun'`（可选） | 出现时表示设置从下个 run 生效；当前三个 switch 均为该语义 |
| `at` | string | 变更时刻，ISO 8601 |

- 事件是广播通知，调用方自己的请求响应（如 `model.switch.result`）已经确认结果；处理本事件要幂等。
- 快照只含 `mode` / `effort` / `modelId`，不含 `approvedAll`；Session 详情（REST `sessions/detail`）用 `approvalMode` 与 `approvedAll` 暴露完整状态。
- `mode` 切到非 `full_access` 会复位 `approvedAll=false`；需要同步该字段的客户端在收到本事件后重拉一次会话详情。
- 只表示设置变更，不改变 run 状态；活跃 run 不受影响。

## 6. 一次运行的完整时序

以一个 run 从发起到收尾为例，事件到达顺序如下（同一连接上的顺序是确定的）。

| # | 帧 | 说明 |
|---|---|---|
| 0 | （无帧）解析阶段 | 建 run 前解析引擎适配器、工作区 / 阶段 cwd（含物化）与模型；失败则直接回 `send.result` 错误，后续帧都不出现 |
| 1 | `message`（user, `type='text'`） | 用户消息落库即广播 |
| 2 | `session.status`（`in_progress`） | 会话被置为进行中 |
| 3 | `run.started`（`status='running'`） | run 建行即 `running`；仍在运行时于响应前广播 |
| 4 | `send` 的 `response` | 响应帧在 `message` / `session.status` / `run.started` **之后**返回，`run.status` 与顶层 `status` 均为 `running` |
| 5 | `chat.thinking`（`start` → `delta` × N → `stop`） | 思考块阶段（模型支持思考时）；`delta` 带 `text` |
| 6 | `message`（`thinking`） | 思考段终稿（整体值） |
| 7 | `chat.delta`（text）× N | 正文流式 |
| 8 | `message`（`text`） | 正文段终稿（整体值） |
| 9 | `message`（`tool_use`）+ `tool.executing` | 工具调用落库，随后补一条兼容事件 |
| 10 | `message`（`approval`, `status='pending'`）+ `approval.request` | 需要审批时挂起，引擎阻塞；**没有配套的 run 事件**，`waiting` 只在 REST `runs/detail` 上可见 |
| 11 | `message`（同 `id`，`status='approved'`） | 用户应答后结算更新 |
| 12 | `message`（`tool_result`）+ `tool.executed` | 工具结果落库，随后补一条兼容事件 |
| 13 | `chat.delta`（text）× N → `message`（`text`） | 工具之后再生成一段正文 |
| 14 | `run.status`（`succeeded` / `failed` / `aborted`） | run 落终态 |

两点必须理解到位：

1. **发消息的时刻与订阅的时刻无关**：`message` 事件对 user 消息也照发。
   如果你用 REST `messages/send` 发起运行、之后才订阅，那么第 1 帧你**永远收不到**，它只能从 REST 历史里拿。
   这也是「先订阅再拉取、按 id 合并」的理由（见 §7）。
2. **顺序是「事件在前、响应在后」**：第 4 帧的 `send` 响应晚于第 1-3 帧（`message`、`session.status`、`run.started` 都是先广播再返回）。
   所以前端不能用「等 `send` 返回了才开始收事件」的写法去维护顺序，按 id upsert 才是稳定的做法。
3. **解析失败没有后续帧**：工作区 / cwd / 物化 / 模型解析失败时，服务端只回 `send.result` 错误，不建 run、不落用户消息、不改会话状态，第 1 帧起的任何事件都不会出现。

### 6.1 子 agent 任务时序

顶层 run 运行期间，引擎可在任意时刻上报任务；子 agent 的事件与顶层内容事件交错到达，同一连接上的顺序确定。

| # | 帧 | 说明 |
|---|---|---|
| 1 | `task.started` | 子 run 以 `running` 落库并广播，前端建子 agent 块 |
| 2 | 子 run 的 `message` / `chat.delta` / `chat.thinking` | 内容事件带子 `runId`；`chat.*` 另带 `parentRunId` |
| 3 | 子 run 的 `tool.executing` / `tool.interactive` / `approval.request` | 额外带 `parentRunId`，前端据此挂到父块下 |
| 4 | `task.notified` | 子 run 落终态，前端收敛子 agent 块 |

- 多个子 run 可同时活跃；它们的 `task.*` 与内容事件按 `runId` 区分，不要按到达顺序猜测归属。
- 子 run 不发 `run.started` / `run.status`；顶层 run 不因单个子 run 结束而收尾。
- 顶层 run 收尾时若仍有活跃子 run，`closeRun` 把它们收敛为 `aborted` 并补发 `task.notified`。
- **中止时序（可观测事件）**：中止信号 → 该 run 树内 pending 审批与交互结算并广播 → 子 run `task.notified` → 顶层 `run.status` / `chat.aborted` → `session.status`。
  中止在 `abortRun` 内立即广播，不等引擎返回；`closeRun` 幂等去重。

## 7. 进入会话与断线重连

### 7.1 进入一个会话

1. WS 发 `subscribe { sessionId }`，拿到 `{ sessionId, subscribed: true, status }`，用 `status` 初始化会话头。
2. **接着会收到补发的 `approval.request` / `tool.interactive` 事件**：该会话当前所有 `status='pending'` 的审批与交互，逐条送达。
   按 `id` upsert，重复的不重复弹卡。
3. REST 拉最近一页对话：`GET /api/smart-factory/v1/messages/list?sessionId=<id>&limit=50`（最近 50 条）。
   商用客户端也可用 WS `history { sessionId, limit: 50, offset: 0 }`（`content` 为字符串）；新前端推荐 REST，因为 REST 的游标分页更适合向上翻页。
4. 把第 2 步的补发与第 3 步的列表**按 `id` 合并去重**，再按 `seq` 排序渲染。
5. 需要更早的历史：用 `beforeSeq` 向上翻页，直到 `seq` 回到 1 或用户停下（参数与响应形状见 [4.04 消息](./4.04-消息.md)）。
6. 需要知道「现在有没有在跑」：拉 `GET /runs/list?sessionId=<id>&pageSize=1` 或 `GET /runs/detail?runId=<id>`，用 `status` 与 `waiting` 决定界面是否忙碌。

**顺序不能反**：先 `GET` 再 `subscribe` 会丢掉「拉取完成」与「订阅生效」之间那个窗口里产生的事件，那个窗口里的正文与挂起消息就再也补不回来（WS 不回放）。
所以必须**先订阅、再拉取、最后按 id 合并**。

### 7.2 断线重连

断开的原因可以是：服务端心跳超时（§2）、慢消费者断流（§8）、服务重启、网络抖动、标签页休眠。

**订阅随连接消失**：重连是一条全新的连接，服务端不会记得你之前订阅过什么。

重连后的完整步骤：

1. 建新连接，等 `connection.ready`，重启心跳定时器。
2. **重新 `subscribe` 每个打开的会话**（每个 `sessionId` 各一次）。
3. **重新拉一次消息**：`GET messages/list?sessionId=&limit=50` 按 id 合并；至少也要拉一次 `GET messages/list?sessionId=&status=pending` 把挂起对齐。
4. **重新拉会话与运行状态**：`GET sessions/detail?sessionId=`、`GET runs/detail?runId=`（或 `runs/list?sessionId=`）。
   需要展示子 agent 时，再对每个顶层 run 调 `GET runs/children?runId=&page=&pageSize=` 对齐子 run 状态与 `waiting`。
5. 用第 4 步的结果覆盖界面状态，再恢复实时渲染。

第 4 步不能省，原因是**服务重启时没有连接，状态变化不会广播**：

- 重启会把所有活跃 run 置 `failed`，`error` 为「服务重启」；
- 重启会把所有残留的 `status='pending'` 审批 / 交互置 `aborted`（`decisionSource` 为 `'restart'`）；
- 这两类变化发生时服务端还没有任何连接，`run.status` / `message` 事件都不会有人收到，只能靠重连后重拉。

同理，关闭进程（SIGINT / SIGTERM）时也是先把挂起置 `aborted` 再断开连接，客户端可能来不及处理，重连后重拉一样能对齐。

### 7.3 REST 拉取与 WS 事件的合并

两条流会交叠（拉取期间的实时事件也在到达），所以合并规则要固定：

- **以 `id` 为准 upsert**，后到的覆盖先到的；
- **以 `seq` 为准排序**，不用 `createdAt`；
- 重拉时可以整段替换「不在挂起集合里、且 `seq` 在拉取范围内」的本地副本，但**不要**丢掉比拉取范围更新的 `id`（那部分是 WS 实时来的）。

## 8. 慢消费者（`SLOW_CONSUMER`）

服务端每次下发前检查该连接的写缓冲，堆积超过 `WS_MAX_BUFFERED_BYTES`（默认 4MB）时：

1. 先发一条 `error` **事件**（`method='error'`，`payload.code='SLOW_CONSUMER'`，见 §5.7）；
2. 随即断开该连接。

```json
{
  "id": "evt_1785715230000_77",
  "type": "event",
  "method": "error",
  "timestamp": 1785715230000,
  "payload": { "code": "SLOW_CONSUMER", "message": "客户端消费过慢，连接将被断开" }
}
```

前端收到后**必须**做的事（三件都要做，缺一件用户就会看到「卡住的界面」）：

1. 准备重连（退避重试）；
2. 重连后重新 `subscribe` 全部打开的会话；
3. 重拉 `messages/list` 与 `runs/detail` 对齐期间的内容。

断流不丢数据：正文、思考与审批都有落库消息兜底，丢掉的只是瞬态的 `chat.delta` / `chat.thinking`。

## 9. 客户端必须遵守的规则

1. **自己起心跳定时器**，每 30s 发一条 `ping`。
   违反后果：空闲超过 60s 后被服务端断开（下一拍巡检，最迟约 90s），界面「假在线」。
2. **不能只按 `afterSeq` 增量续拉**。
   `messages.status` 会变（挂起会变结算），增量拉取会拿到旧行。
   违反后果：界面永远显示「等待审批」。
3. **先 `subscribe` 再拉取**，拉完按 `id` 合并。
   违反后果：丢掉窗口内的实时事件，且无法找回。
4. **`chat.delta` / `chat.thinking` 只用于流式渲染**。
   它们是瞬态内容、断线即丢，终稿一律以 `message` 为准；思考增量不能拼进正文。
   兼容事件（`chat.final` 等）是附加通知，消费它们时不要与 `message` 重复追加同一条正文。
5. **收到 `type='text'` / `'thinking'` 的 `message` 要整体覆盖，不是追加**。
   违反后果：正文内容翻倍。
6. **挂起状态以 REST 为准**：任何时候 `GET messages/list?sessionId=&status=pending` 都能问出「现在还有什么在等我」。
   WS 是便利通道，不是真相来源。
7. **每个请求都必须带 `id`**。
   违反后果：信封解析失败时服务端回 `id=""`，Promise 无法归属（静默挂死）。
8. **`send` 与 `subscribe` 之间不要假设任何顺序**：`send` 会隐式订阅，先发后订也能收全事件。
9. **收到 `error` 事件（`SLOW_CONSUMER`）要准备重连 + 重订阅 + 重拉**，不能只弹提示。
10. **重连后必须重订阅并重拉**：订阅随连接消失，服务端不记得你之前订过什么。
11. **子 agent 的状态只信 `task.started` / `task.notified` 与 `runs/children`**。
    `run.started` / `run.status` 只表示顶层 run；内容事件按 `runId` 归属。`chat.delta` / `chat.thinking` / `tool.*` / `approval.request` / `tool.interactive` 直接带 `parentRunId`；`chat.final` / `chat.error` / `chat.aborted` 只表示顶层 run。原生 `message` 只带 `runId`，父 run 关系用 `task.started`（断线后配合 `runs/children`）建立的 `runId → parentRunId` 映射定位。

## 10. 刻意不做

| 不做 | 理由 | 替代 |
|---|---|---|
| **历史回放** | 服务端不为断线连接缓冲事件，内存与会话数线性、与事件总量无关 | 订阅只补发挂起的审批 / 交互；其余历史走 REST |
| **`interactive.timeout` 事件** | 刻意不实现：审批与交互没有超时，挂起多久应答都有效 | 前端把 `waiting` 渲染成「等待审批中，已等 X 秒」并提供中止按钮；不要等待该事件 |
| **消息级断线续传** | 没有 `seq` 游标续传，`chat.delta` / `chat.thinking` 不保证必达 | 重连后重拉 + 按 `id` 合并 |
| **审批超时** | 是设计决策而不是遗漏：挂起的出口只有四个 - 用户应答、用户中止（`run.abort` / `sessions/abort`）、服务重启、进程被杀 | 前端把 `waiting` 渲染成「等待审批中，已等 X 秒」并提供中止按钮 |
| **`versionId` / 版本号** | 本服务用 `agentId` 定位智能体，没有版本概念 | 客户端发 `send { agentId?, modelId, mode?, effort?, prompt }`；`versionId` 必须去掉，选了智能体发 `agentId`、不选就是自由对话；`modelId` 两种情况都必填 |
| **连接恢复 token** | 没有 `connectionToken`，也没有连接级会话恢复；`connection.ready.restored` 恒 `false`、`sessionId` 恒 `null` | 重连后重新 `subscribe` 并重拉 |
| **模型回退（model fallback）** | 本服务不实现模型回退，`send.result.modelFellBack` 恒为 `false` | 模型解析失败直接返回 `send` 错误，不建 run；不在多个模型间自动切换 |
| **鉴权** | 端侧本地单用户，无鉴权 | 无（部署侧不要把它暴露到公网） |
| **协议层 ping/pong** | 心跳统一走应用层信封，浏览器与脚本一套行为 | §2 的 `{method:'ping'}` / `pong {serverTime}` |
