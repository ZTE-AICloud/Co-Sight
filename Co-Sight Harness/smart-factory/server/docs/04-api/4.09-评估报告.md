## 1. 定位与结论

评估阶段左栏是真实的 `stage = 'evaluation'` 会话；右栏要看的是这轮评估产出的**报告**，不是会话消息。报告由评估技能写在评估沙箱里（入口是 `agent-eval`，内部依次分派 `e2e-test-generator` / `e2e-test-runner` / `e2e-test-evaluator` / `traceaudit`），当前是一组目录和 JSON / JSONL / Markdown 文件。

右栏的交互与信息层级见设计预览 `web/demo.evaluate-report.html`（数据取自真实报告样例）；本文只定义它需要的后端数据形状。

**后端应新增一组归一化只读接口，而不是让前端直接读 `/artifacts/*` 自己拼。**

理由：

1. 一份报告横跨四个目录、十余个文件；前端要自己决定「哪份是最新的、什么算完成、平均值怎么算」。
2. 报告里有两套分：结果质量（runtime rubric，四个维度）与轨迹合规（traceaudit，五个维度）。两套分**不合成总分**，这个口径必须由服务端固定下来。
3. 文件是评估工具的内部格式，会随工具版本变化；前端只认稳定 DTO，工具换格式时改服务端适配层。
4. `artifacts/file` 只读文本且有 2 MiB 上限；报告解析需要读取多个文件并容忍写到一半的中间态。
5. 原始文件仍然可以看：报告 DTO 返回相对目录，`/artifacts/*` 用 `stage=evaluation` + 该目录继续浏览 / 下载。

**本方案不新增**：

- **开始评估**：仍然是往 `stage = 'evaluation'` 的会话发消息（`POST /messages/send` 或 WS `send`），不另造 `evaluations/create`。消息本身是一条 slash 命令 —— 调 `goldeval` 插件的 `agent-eval` 技能（`/goldeval:agent-eval --agent . --output ..`），四段流程与产物约定由技能维护。会话 cwd 是 `<evaluation>/agent/`，`--output` 传的是**父目录**（技能对 `e2e-test-*` 形态直接报错），`..` 即沙箱根，编排层在它下面新建 `<e2e-test-时间戳>/`，正是本文 §2.1 的落点。技能缺省父目录是 `outputs/`，服务端不认，所以必须显式传。
- **中止评估**：仍然是 `POST /runs/abort` 或 `POST /sessions/abort`。
- **原始文件浏览 / 下载**：复用 `/artifacts/list`、`/artifacts/file`、`/artifacts/download`。
- **数据库表**：报告不落库，文件目录就是真相，与 artifacts 的定位一致。

## 2. 数据来源与发现规则

### 2.1 目录

评估目录（已有）：`<agentRoot>/evaluation/`，其中 `agentRoot = <workspace.directory>/.smart-factory/agents/{agentId}`。

沙箱根下固定两项：被测副本 `agent/`（评估会话 cwd）与报告目录 `e2e-test-*`。副本必须收在子目录里——评估工具的 runner 要求报告目录在被测目录之外，否则每条例用的 workspace 副本会递归复制自己；因此 kick-off 是 `--agent . --output ..`（cwd = `agent/`，父目录 = 沙箱根）。扫描报告时忽略 `agent/`。

**报告的存留**：run 前的物化在源产物未变时跳过，旧报告原地保留（属于历史轮次，仍可按 `reportId` 读取）。「重新评估」是例外：建会话时带 `resetSandbox`（见 [`4.03-会话.md`](./4.03-会话.md) §2），服务端把整个沙箱目录连同旧报告一起删掉，再按最新产物重拷 —— 用户点这个按钮的语义就是「旧结论作废、重新来一轮」。同阶段已有活跃 run 时建会话本身 `409`，不会删到正在用的沙箱。

一次评估产出如下（以样例 `e2e-test-20261016-095720` 为准）。样例是打包成 zip 发给前端的，**线上工具直接把目录写在 `evaluation/` 下**，后端不需要解压；如果将来工具只产出 zip，需要另行约定解压落盘规则，不在本方案内。

```text
evaluation/
├── agent/                                 # 被测副本，评估会话 cwd（不是报告，不参与扫描）
└── e2e-test-20261016-095720/              # reportId = 目录名
    ├── generated_datasets/                # ① 生成测试集
    │   ├── manifest.json                  # 任务信息、工具版本、产物 sha
    │   ├── eval-plan.json                 # 覆盖计划：tier / 目标 / 六维分布 / 驳回
    │   ├── agent-profile.json             # 智能体画像：能力点、GWT 基线
    │   ├── seed.jsonl                     # 用例（此时还没有 eval 字段）
    │   └── report.md
    ├── run_datasets/                      # ② 执行测试
    │   ├── run-manifest.json              # agent sha、隔离方式
    │   ├── seed.jsonl                     # 回写 run 字段
    │   └── <caseId>/
    │       ├── result.json                # SDK result：耗时、轮数、费用、输出
    │       ├── timing.json                # elapsed_seconds / exit_code / timed_out
    │       ├── stdout.txt
    │       ├── stderr.txt
    │       ├── sessions/<uuid>.jsonl      # 轨迹原文（不解析）
    │       └── workspace/
    ├── eval_datasets/                     # ③ 结果评分（runtime rubric）
    │   ├── eval-manifest.json             # 阈值、权重、裁判模型、rubric sha
    │   ├── seed.jsonl                     # 回写 eval 字段：四维分、命中项、理由
    │   ├── judge.json
    │   └── report.md                      # 人读版报告
    └── eval_results/                      # ④ 轨迹审计（traceaudit）
        └── batch_20261016T020816Z/
            ├── batch-summary.json         # 五维审计均分、逐用例摘要
            ├── batch-summary.md
            └── cases/<caseId>/
                ├── rubric-scores.json     # 五维分 + 每项检查的通过/证据
                ├── trajectory-report.json
                └── trajectory-report.md
```

### 2.2 发现与排序

- 扫描 `evaluation/` 的**直接子目录**，只认目录名匹配 `^e2e-test-[A-Za-z0-9._-]+$` 的项。
  （评估工具固定用这个前缀；不是这个前缀的目录一律忽略，避免把用户随手建的文件当成报告。）
- `reportId` 就是目录名，稳定且唯一。
- 列表按 `reportId` **降序**。目录名后缀是 `YYYYMMDD-HHmmss`，字典序即时间序；这样列表排序不需要先解析每份报告的 JSON。若将来命名规则变化导致字典序不再等于时间序，再由服务端按目录 mtime 降序兜底。
- `createdAt` 取 `generated_datasets/manifest.json` 的 `created_at`（统一转成 UTC ISO）；缺失时取目录 `birthtime`，再缺失退 `mtime`。
- `updatedAt` 取报告目录内已知文件的最大 `mtime`。
- 同一份报告在评估运行中会不断变大：**只有 manifest / summary 文件存在且能解析，才把对应步骤算作完成**（见 §6）。
- 评估工具应在开始时就把报告目录建出来（哪怕还是空的）；`list` 只能看到已经存在的目录，看不到「将要产生」的报告。

### 2.3 字段映射（API ← 原始文件）

| API 字段 | 来源 |
|---|---|
| `title` | `generated_datasets/manifest.json.task_id`，缺失用 `reportId` |
| `tools.generate` | `generated_datasets/manifest.json.tool_version`（按 `name/version` 拆分） |
| `tools.evaluate` | `eval_datasets/eval-manifest.json.tool_version`（按 `name/version` 拆分） |
| `tools.audit` | `eval_results/batch-*/batch-summary.json.meta.skill` + `meta.evaluatorVersion` + `meta.rubricVersion` |
| `judge.model` | `eval_datasets/eval-manifest.json.judge.model` |
| `judge.mainAgentModel` | `eval_datasets/eval-manifest.json.judge.main_agent_model` |
| `thresholds` / `scores.weights` | `eval-manifest.json.thresholds` / `.dimension_weights` |
| 逐用例 `eval.*` | `eval_datasets/seed.jsonl` 每行的 `eval` 字段 |
| 覆盖计划 | `generated_datasets/eval-plan.json` |
| 审计汇总 | `eval_results/batch-*/batch-summary.json` |
| 逐用例审计分 / 检查项 | `eval_results/batch-*/cases/<caseId>/rubric-scores.json` |
| 用例运行元数据 | `run_datasets/<caseId>/timing.json` + `result.json` + `eval.attempts` |
| 环境信息 | `eval-manifest.json` + `run-manifest.json` + `generated_datasets/manifest.json` |

运行元数据的取法：

- `run.elapsedMs` = `timing.elapsed_seconds * 1000`（墙钟时间，与报告里的 `27.2s` 一致；不要用 `result.duration_ms`）
- `run.exitCode` = `timing.exit_code`；`timing.timed_out === true` 时 `run.status = 'timeout'`
- `run.turns` = `result.num_turns`
- `usage.inputTokens` / `outputTokens` / `costUsd` = `result.usage.input_tokens` / `output_tokens` / `result.total_cost_usd`
- `resultPreview` = `result.result`（超 4000 字符截断）
- `run.status`：`timing.timed_out === true` → `timeout`；否则 `result.is_error === true` → `error`；否则 `timing.exit_code !== 0` → `failed`；否则 `passed`。不依赖 seed 里的 `run.status` 字符串。

两条组装细节：

- `coverage.rejected[].reason` = `eval-plan.json.rejected[].errors` 用 `；` 连接；`sourceRef` = `source_ref`。
- `reportId` 与 `caseId` 是目录名，不是 `agt_` / `sess_` 那类带前缀的实体 id；不要对它们做前缀解析。

**不返回绝对路径**。原始 JSON 里的 `rubric_path`、`input_seed`、`agent_root` 都是宿主机绝对路径，DTO 只返回文件名或报告内相对路径。

## 3. 端点总表

路径相对基址 `/api/smart-factory/v1`。全部为 `GET`、成功 `200`。

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/evaluations/list` | 列出某个智能体的评估报告（摘要，分页） |
| GET | `/evaluations/detail` | 一份报告的概览：分数、流水线、覆盖、审计、环境 |
| GET | `/evaluations/cases/list` | 一份报告里的用例摘要（分页、可按结果/维度筛） |
| GET | `/evaluations/cases/detail` | 单条用例：期望项、裁判理由、运行元数据、审计检查项 |
| GET | `/evaluations/download` | **可选（二期）** 导出整份报告；v1 不做 |

路径末段仍是 `4.02 §3` 的动作词白名单（`list` / `detail` / `download`）；`cases` 是 `evaluations` 下的子资源，id 仍走 query，符合「集合级端点 id 不进路径」。

## 4. 公共参数与校验

| 参数 | 出现端点 | 必填 | 说明 |
|---|---|---|---|
| `agentId` | 全部 | 是 | 形态按 `4.02 §11` / `assertAgentId`；非法 `400`，智能体不存在 `404` |
| `reportId` | detail / cases / download（二期） | 是 | 报告目录名，匹配 `^e2e-test-[A-Za-z0-9._-]+$`；非法 `400` |
| `caseId` | cases/detail | 是 | 单段目录名，不接受 `/`、`\`、`..`、NUL；非法 `400` |
| `status` | list | 否 | 报告状态：`pending` / `running` / `completed` / `partial` / `failed` |
| `status` | cases/list | 否 | 用例结果：`passed` / `failed` / `invalid`；空串不过滤 |
| `dimension` | cases/list | 否 | `functional` / `boundary` / `tool_use` / `instruction` / `safety` / `failure` |
| `page` / `pageSize` | list / cases/list | 否 | 按 `4.02 §6`：缺省 1 / 20，`pageSize` 上限 200；响应回显校验后的 `page` / `pageSize` |

`status` 在两类端点上枚举不同：`/evaluations/list` 指报告状态，`/evaluations/cases/list` 指用例结果。后端按端点分别校验，前端不要混用。

校验口径与现有接口一致：

- 数值参数非法静默回落缺省；枚举非法 `400 BAD_REQUEST`。
- `agentId` / `reportId` / `caseId` 缺失或空串 `400`。
- `reportId` 形态合法但目录不存在、`caseId` 不在该报告里 → `404 NOT_FOUND`。
- `/evaluations/list` 在评估目录不存在、或还没有任何报告时返回 `200 { items: [], total: 0, page: 1, pageSize: 20 }`，不报 404；404 只用于 `detail` / `cases/*` 指定的报告不存在。
- 工作区目录解析失败（工作区没有目录、框架不可达）→ `502 BAD_GATEWAY`，与 `/artifacts/*` 同一口径。
- **路径安全**：`reportId` 与 `caseId` 都会拼进文件路径。除了上面的正则 / 单段校验，拼出的路径 `resolve` 后必须仍在 `agentRoot/evaluation` 之内（双保险）；违规一律 `400`，不区分「非法」与「逃逸」。

## 5. 响应 DTO

约定：字段名 camelCase（与现有 DTO 一致）；时间 ISO 8601 UTC；未知 / 缺失用 `null` 或空数组，不省略字段；分数为 0–5，平均分保留 2 位小数；`passRate` 是 0–1 的比例。

### 5.1 报告摘要

```ts
type EvaluationReportStatus = 'pending' | 'running' | 'completed' | 'partial' | 'failed';
type EvaluationStepState = 'pending' | 'running' | 'done' | 'failed';

interface EvaluationStep {
  state: EvaluationStepState;
  /** 该步骤完成 / 失败的时间；未完成或无法判断为 null */
  at: string | null;
}

interface EvaluationAuditSummary {
  /** 审计平均总分 0–5 */
  average: number | null;
  /** batch-summary 的等级，如 ACCEPTABLE */
  grade: string | null;
  /** 参与审计的用例数 */
  evaluated: number;
  /** 审计失败的用例数（meta.failed） */
  failed: number;
  /** 未通过检查的**去重 checkId 数**（不是出现次数） */
  failedChecks: number;
}

interface EvaluationReportSummary {
  reportId: string;
  agentId: string;
  title: string;
  status: EvaluationReportStatus;
  createdAt: string;
  updatedAt: string;
  /** 相对 evaluation 根的目录，直接喂给 /artifacts/* */
  dir: string;

  pipeline: {
    plan: EvaluationStep;   // 生成测试集
    run: EvaluationStep;    // 执行测试
    score: EvaluationStep;  // 结果评分
    audit: EvaluationStep;  // 轨迹审计
  };

  counts: {
    /** 当前可用 seed.jsonl 的总条数（含未评分 / 无效） */
    total: number;
    /** eval.status === 'ok' 的条数 */
    valid: number;
    /** 已评分但没评出结果（eval 存在且 eval.status !== 'ok'），前端显示为「解析失败」 */
    invalid: number;
    /** 还没评分：eval 字段缺失（生成 / 执行阶段）；完成态报告恒为 0 */
    pending: number;
    passed: number;
    failed: number;
    expectedTotal: number;
    expectedHit: number;
    expectedMiss: number;
  };

  scores: {
    /** 逐条加权分再取平均；口径见 5.3 */
    weightedAverage: number | null;
    /** passed / valid，0–1 */
    passRate: number | null;
    dimensions: {
      correctness: number | null;
      completeness: number | null;
      formatCompliance: number | null;
      actionability: number | null;
    };
    weights: {
      correctness: number;
      completeness: number;
      formatCompliance: number;
      actionability: number;
    };
  };

  thresholds: {
    weighted: number | null;
    correctness: number | null;
    completeness: number | null;
    /** 三项阈值是否全部达标；无法计算为 null */
    met: boolean | null;
  };

  audit: EvaluationAuditSummary | null;

  /** 报告生成后开发产物变过（run-manifest.matches === false） */
  stale: boolean | null;

  /** 非致命问题：缺文件、JSON 解析失败、画像 warning、用例 warning 等 */
  warnings: string[];
}
```

### 5.3 评分口径（服务端算，前端不再算）

- 只统计 `eval.status === 'ok'` 的用例。
- 逐条加权分：`correctness*0.4 + completeness*0.3 + format_compliance*0.15 + actionability*0.15`。直接取 `eval.weighted_score`；缺失才现算。
- `scores.weightedAverage` = 逐条 `weighted_score` 的算术平均。
- `scores.dimensions.*` = 各维度的算术平均。
- `passRate` = `passed / valid`。
- `thresholds.met` = `weightedAverage >= thresholds.weighted && correctnessAvg >= thresholds.correctness && completenessAvg >= thresholds.completeness`。
- **审计分不并入上述平均**。`audit.average` 直接取 `batch-summary.aggregate.averageTotalScore`，与结果质量分并列展示。
- `audit.grade`：`batch-summary` 只有逐用例 grade，没有总体 grade。取**总分最低**那条用例的 grade（同分取 `cases[]` 中靠前的一条），即「最差一条决定总体等级」。
- `audit.failed` 是**审计执行失败**的用例数（`batch-summary.meta.failed`），不是测试失败数；测试失败看 `counts.failed`。
- `audit.failedChecks` = `auditDetails.checks` 中 `passed === false` 的 `checkId` 去重数；不是行数（同一检查在 4 条用例上失败只算 1）。
- 平均分统一保留 2 位小数（如 `4.67`）；逐用例分是整数，不处理。
  实现用 `Number(value.toFixed(2))`，**不要用 `Math.round(value * 100) / 100`**：
  样例的 `18.7 / 4 = 4.675`，前者的结果是 `4.67`（与评测报告一致），后者会得到 `4.68`。

### 5.4 用例摘要

```ts
type EvaluationCaseStatus = 'passed' | 'failed' | 'invalid';

interface EvaluationCaseSummary {
  caseId: string;
  /** seed.jsonl 中的顺序，从 0 开始；列表按它升序 */
  index: number;
  dimension: string;
  dimensionLabel: string;
  capabilityRef: string | null;
  input: string;
  status: EvaluationCaseStatus;
  /** false = 还没评分（生成 / 执行阶段）；此时 status 也是 invalid，但语义是「等待」不是「失败」 */
  scored: boolean;
  /** 0–5；invalid 时为 null */
  weightedScore: number | null;
  scores: {
    correctness: number | null;
    completeness: number | null;
    formatCompliance: number | null;
    actionability: number | null;
  };
  expected: { total: number; hit: number; miss: number };
  run: {
    status: 'passed' | 'failed' | 'error' | 'timeout' | 'unknown' | null;
    elapsedMs: number | null;
    turns: number | null;
    exitCode: number | null;
    attempts: number;
  };
  audit: {
    totalScore: number | null;
    grade: string | null;
  } | null;
  warnings: string[];
}
```

注意：`case.run.status` 是**评估工具单条用例的执行结果**（`passed|failed|error|timeout|unknown`），不是服务端的 `Run.status`（`pending|running|succeeded|failed|aborted`）；两者不要混用。

`status` 判定：

- `eval.status !== 'ok'` → `invalid`；
- 否则 `eval.passed === true` → `passed`，`false` → `failed`。
- 注意：**`passed` 不代表所有期望项都命中**。样例里 `calculator_instruction_001` 有 1 项未命中，但加权 3.85 仍高于阈值，所以 `passed = true`；前端要同时看 `expected.miss`。
- `invalid` 用例：`eval` 字段缺失或 `eval.status !== 'ok'`。此时 `scores` / `weightedScore` / `expected` 全为 null 或 0，`expectedItems` 为空数组；`run` 元数据仍尽量返回（执行过但评分失败时也能看到耗时与输出）。
- `scored` 区分两种 `invalid`：`false` = 评估还没走到评分（生成 / 执行阶段，`run.status` 为 null 时连执行都没开始）；`true` = 评分跑过但没评出结果。前端据此显示「待执行 / 待评分」而不是红色的「评分失败」。
- 用例来源按阶段回退：`eval_datasets/seed.jsonl` → `run_datasets/seed.jsonl` → `generated_datasets/seed.jsonl`。评分阶段之前列表照样能看，解析失败（覆盖写半截）时也回退到上一份。计数与评分口径不变，仍只统计 `eval.status === 'ok'`。

## 6. 状态推断与中间态

报告状态是**流水线健康度**，不是用例通过率。用例失败仍然可以是 `completed`。

四个步骤的完成判据：

| 步骤 | done | failed |
|---|---|---|
| `plan` | `generated_datasets/manifest.json` 与 `eval-plan.json` 都存在且能解析 | 文件存在但 JSON 解析失败 |
| `run` | `run_datasets/run-manifest.json` 存在且每个 seed 用例都有 `timing.json` | `run-manifest.json` 存在但解析失败 |
| `score` | `eval_datasets/eval-manifest.json` 存在，且 `seed.jsonl` 每行都有 `eval` 字段 | `eval-manifest.json` 存在但解析失败 |
| `audit` | `eval_results/batch-*/batch-summary.json` 存在且能解析 | summary 存在但解析失败 |

整体状态（按顺序判定，先命中先返回）：

```text
1. 四步都 done                              → completed
2. 有步骤未 done，且评估会话有活跃 run       → running
3. 有步骤解析失败（且没有活跃 run）          → failed
4. 有步骤未 done，至少一步 done              → partial
5. 只有报告目录、一步都没 done               → pending
```

- 先判「活跃 run」再判「解析失败」：报告可能正写到一半，JSON 读失败是中间态，不是失败。
- 「评估会话有活跃 run」= `sessions/list?agentId=&stage=evaluation&pageSize=1` 取最近一场，再取它的最近一条 run；`status` 为 `pending` / `running` 即活跃。这是提示性的关联：报告目录与 run 没有强绑定，不能拿 runId 当报告主键。
- 报告目录可能刚创建、文件还没落盘：JSON 读失败但 run 仍活跃 → 该步骤记 `running`，报告整体 `running`，不报 500。
- 已完成报告里的可选文件缺失（如 `report.md`、某个 case 的 `stderr.txt`）只进 `warnings`，不改变状态。
- `stale`：`run-manifest.matches === false` 表示生成与执行时看到的产物 sha 不一致；报告仍可读，但前端应提示「产物已变化，建议重跑」。

## 8. 原始文件与前端接线

报告 DTO 里的 `dir` 与 `files.*` 都是**相对 `evaluation/` 根**的路径，直接拼给现有 artifacts 接口：

```bash
# 看报告根目录
curl -s 'http://localhost:4100/api/smart-factory/v1/artifacts/list?stage=evaluation&agentId=agt_...&path=e2e-test-20261016-095720'

# 读人读版报告
curl -s 'http://localhost:4100/api/smart-factory/v1/artifacts/file?stage=evaluation&agentId=agt_...&path=e2e-test-20261016-095720/eval_datasets/report.md'

# 下载单个文件
curl -s -OJ 'http://localhost:4100/api/smart-factory/v1/artifacts/download?stage=evaluation&agentId=agt_...&path=e2e-test-20261016-095720/eval_datasets/report.md'
```

前端推荐调用顺序：

1. 进入评估阶段 → `GET /evaluations/list?agentId=` → 取 `items[0]`（没有报告则显示空态）。
2. `GET /evaluations/detail?agentId=&reportId=` → 渲染结论、四维、覆盖、审计、环境。
3. `GET /evaluations/cases/list?...` → 渲染用例卡片；展开某条时再调 `cases/detail`。
4. 门禁：`detail.status === 'completed'` 才展示完整报告；`running` 展示进度骨架；`partial` / `failed` 展示已完成部分 + `warnings`。

实时性：

- v1 **不新增 WS 事件**。评估会话的 `run.status` 到终态（`succeeded` / `failed` / `aborted`）时，前端重拉 `list` 与 `detail`。
- **评估会话在跑时就要轮询**（每 2–5 秒）：一轮评估会在中途新建 `e2e-test-*` 目录，只等 run 终态会让右栏停在上一次报告（或空态）直到整轮结束。`status === 'running'` 的报告也要继续轮询。报告文件是幂等覆盖写，重复拉没有副作用。
- 二期若要免轮询，再加一条只读事件 `evaluation.updated`（见 §11），不要复用 `message` 事件。

## 9. 错误码

沿用 [`4.02 §11`](./4.02-通用规范.md) 的七个码，不新增：

| HTTP | error | 场景 |
|---|---|---|
| 400 | `BAD_REQUEST` | `agentId` / `reportId` / `caseId` 缺失或形态非法；`status` / `dimension` 不在枚举；`reportId` / `caseId` 含路径逃逸段 |
| 404 | `NOT_FOUND` | 智能体不存在；`detail` / `cases/*` 指定的报告目录不存在；`caseId` 不在该报告里。`list` 在从未评估过时返回空列表，不报 404 |
| 413 | `PAYLOAD_TOO_LARGE` | 必需 JSON / JSONL 超过 `EVALUATION_MAX_JSON_BYTES`（默认 5 MiB）；可选文件超限只进 `warnings` |
| 500 | `INTERNAL_ERROR` | 未预期错误 |
| 502 | `BAD_GATEWAY` | 工作区目录解析失败（工作区无目录、框架不可达） |

**格式错误不一定是 500**：必需文件存在但 JSON 解析失败且报告仍在运行 → 该步骤 `running`；已完成报告里的必需文件解析失败 → `status: 'failed'` + `warnings`，仍返回 200。只有「不该发生的异常」才 500。

## 11. 待决策

以下不阻塞 v1，但建议评审时定下来：

1. **导出整份报告**：是否要 `GET /evaluations/download?format=zip|markdown`？
   v1 建议不做：单文件下载走 `/artifacts/download` 已经够用；整目录打包需要引入 zip 依赖，且导出给谁看、要不要脱敏都还没定（对应 `web/docs/open-questions.md` 的「评估报告要不要导出」）。
2. **`hasMiss` 过滤**：样例里「通过但有未命中」是常见态。v1 让前端在已取回的列表里过滤；如果用例数会到几百条，再加 `hasMiss=true|false`。
3. **`evaluation.updated` 事件**：二期是否需要服务端监听文件变化并推 WS。v1 用「run 终态重拉 + running 轮询」。
4. **报告与 run 的强绑定**：v1 的 `reportId` 是目录名，报告与 run 没有映射字段；「评估会话有活跃 run」只用于推断 `running`。若将来一次 run 可能产出多份报告，或一份报告跨多次 run，需要工具写出 runId 映射文件，再升级契约。
5. **陈旧报告**：v1 只暴露 `run-manifest.matches`。是否要把「当前 development 产物 sha ≠ 报告 sha」也算 stale？那需要每次请求计算产物 sha，成本较高，建议二期。
