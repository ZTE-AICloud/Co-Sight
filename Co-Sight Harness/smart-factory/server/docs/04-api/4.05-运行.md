# 运行

> 状态：**已定稿**。运行（run）是一条用户消息触发的**一次执行**；子 agent 任务另起子 run，通过血缘字段挂到父 run 下。本篇给出 4 个运行端点的请求与响应全貌、状态机与挂起派生字段 `waiting` 的用法。
> 代码落点：`server/src/modules/run/*`、`server/src/modules/session/session.service.ts`、`server/src/shared/store/runs.repo.ts`。
> 验收测试：`server/tests/runs.test.ts`、`server/tests/session-api.test.ts`、`server/tests/approval.test.ts`、`server/tests/subagent-run.test.ts`。
> 相关篇：[4.02 通用规范](./4.02-通用规范.md)（前缀、id 传法、分页与错误体）、[4.03 会话](./4.03-会话.md)、[4.04 消息](./4.04-消息.md)、[4.06 实时通道](./4.06-实时通道.md)、[会话与运行](../03-architecture/03-session-run.md)。

## 1. 端点总表

| 方法 | 路径 | 请求 | 成功响应 |
|---|---|---|---|
| GET | `/api/smart-factory/v1/runs/list` | `?sessionId=&page=&pageSize=` | `200` `{ items: Run[], total: number, page: number, pageSize: number }` |
| GET | `/api/smart-factory/v1/runs/detail` | `?runId=` | `200` `Run` |
| GET | `/api/smart-factory/v1/runs/children` | `?runId=&page=&pageSize=` | `200` `{ items: Run[], total: number, page: number, pageSize: number }` |
| POST | `/api/smart-factory/v1/runs/abort` | `{ runId }` | `200` `Run` |

run 由 [`messages/send`](./4.04-消息.md) 创建，没有独立的创建端点；顶层 run 建行即 `running`（`startedAt` 同时落值），并在 `send` 响应前广播 `run.started`。子 run 由引擎的 `task_started` 创建，同样直接以 `running` 起步，没有独立的创建端点。
本文 curl 以 `http://localhost:4100` 为基址，端口取自 `PORT`（缺省 4100）。

## 2. Run 字段表

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 运行 id，形态 `run_<uuid>` |
| `sessionId` | string | 所属会话 |
| `instanceId` | string | 所属实例，从会话抄来的冗余字段；只与库内冗余列 `stage` 一起支撑非 `runtime` 的实例级部分唯一索引（`stage` 不下发 DTO）。session 级索引直接用 `session_id` |
| `parentRunId` | string \| null | 父 run id；顶层 run 为 `null` |
| `parentToolUseId` | string \| null | 触发子 run 的父级 task 工具调用 id；顶层 run 为 `null`。WS `task.started` 事件里同值字段的 wire 名是 `toolCallId` |
| `subagentType` | string \| null | 子 agent 类型；顶层 run 为 `null` |
| `delegationDepth` | number | 委派深度；顶层 run 为 `0`；子 run 优先取引擎上报的 `spawn_depth`（大于 `0` 时），缺失或为 `0` 时取父 run 深度 + 1（顶层子 run 为 `1`） |
| `taskId` | string \| null | 引擎任务 id；顶层 run 为 `null`，子 run 非空 |
| `status` | `'running'` \| `'succeeded'` \| `'failed'` \| `'aborted'` | 运行状态，见 §3；`pending` 仍保留在类型 / 库枚举中，但当前没有任何写入路径产生它 |
| `error` | string \| null | 失败原因，只有 `failed` 必然非 null，见 §4 |
| `startedAt` | string \| null | 建 run 时写入（顶层与子 run 都以 `running` 创建）；当前所有创建路径都写它，类型保留 `null` 只为枚举完整 |
| `finishedAt` | string \| null | 落终态的时刻；`running` 期间为 `null` |
| `createdAt` | string | 起 run 的时刻，ISO 8601 |
| `waiting` | `{ count: number, since: string } \| null` | **派生字段**，该 run 下等待应答的挂起消息情况，见 §6.1 |

「允许所有」已从 Run 移到 Session：Run 不再有 `approvedAll` 字段，审批是否自动放行读会话的 `Session.approvedAll`，见 [`4.03 会话`](./4.03-会话.md) §3.1 与 [`06-approval.md`](../03-architecture/06-approval.md) §3。
消息归属用 `Message.runId`，`Message` 表不改：子 run 的产出与父 run 同处该会话的消息流，靠 `runId` 区分。
子 run 与父 run 同 `sessionId`、同 `instanceId`，不占用活跃顶层 run 名额。

## 3. 状态机

```text
running --> succeeded | failed | aborted
```

| 状态 | 进入条件 |
|---|---|
| `running` | `messages/send` / WS `send` 建 run 行时写入，同时写 `startedAt`；引擎随后异步启动。子 run 同样以 `running` 创建 |
| `succeeded` | 引擎正常返回，且期间没有被中止 |
| `failed` | 引擎抛错或引擎启动异常（`error` 记原因），或服务重启收口（`error='服务重启'`） |
| `aborted` | 被 [`runs/abort`](#8-中止运行) 或 [`sessions/abort`](./4.03-会话.md#8-中止会话) 中止 |

- 终态是 `succeeded` / `failed` / `aborted` 三者，**不可逆**：落终态后所有写入走条件更新，受影响 0 行即放弃，因此重复中止、引擎后到的返回都改不动它。
- `pending` 仅作为 DTO / 库枚举的保留值，当前没有写入路径；因此不存在「已受理、未起跑」的中间态。工作区 / cwd / 物化 / 模型的解析失败发生在建 run 之前，走 `send` 错误，不产生 run。
- 顶层 run 建行后、`send` 返回前广播 `run.started`，且仅当广播时 run 仍为 `running`；若期间被并发中止，跳过 `run.started` 与引擎启动，由 `closeRun` 收口。
- 子 run 由 `task_started` 直接以 `running` 创建；终态由 `task_notification` 落定（`completed → succeeded`、`failed → failed`、`stopped → aborted`），同样走条件更新。
- **wire 与 DB 的状态值不同**：WS `task.notified` 的 `status` 用 SDK 原值 `completed` / `failed` / `stopped`；DB 与本文 `Run` DTO 用 `succeeded` / `failed` / `aborted`。前端展示子 agent 时按 wire 值收敛，与 REST 对齐时按上面的映射转换。
- `run.started` / `run.status` 只表示顶层 run；子 run 的状态经 `task.started` / `task.notified` 广播，见 [4.06 实时通道](./4.06-实时通道.md) §5.8 / §5.9。
- 会话状态随之派生：起 run 置 `in_progress`，该会话没有活跃 run（含子 run）时置 `completed`（见 [`4.03 会话`](./4.03-会话.md) §3.1）。

## 4. `error` 字段什么时候有值

| 状态 | `error` |
|---|---|
| `running` | `null` |
| `succeeded` | `null` |
| `aborted` | `null`（中止不是失败） |
| `failed` | **必然非 null**，取值是引擎异常消息、引擎启动异常原因，或被启动收口写成的 `服务重启` |

run 落 `failed` 时**至少有一条可读错误**：该 run 最后一条消息若是助手文本且与 `run.error` 同文（SDK 会把上游 API 错误当助手文本吐出），就复用它而不再补消息；否则在会话末尾补一条 `role='system'`、`type='error'` 的消息。两种情况下 `content` 里的错误文本都与 `run.error` 同源，前端展示哪一个都行（建议气泡里展示消息，状态栏展示 `run.status`）。

### 6.1 `waiting` 是怎么算出来的

`waiting` 是**派生字段，不是库里的列**，每次读取时现算：

- `count`：该 run 下 `status='pending'` 且 `type` 为 `approval` 或 `tool_interactive` 的消息条数。
- `since`：这些消息里 **`createdAt` 最早一条**的时刻（ISO 8601），也就是「这个 run 最早从什么时候开始等人」。
- 没有挂起时为 `null`。

由此可得：

- 只有 `running` 且正卡在审批或交互上的 run 才会非 null；终态必然为 `null`（run 建行即 `running`，没有未起跑的中间态）。
- 「已等多久」用 `since` 现算，不要用 `count` 或消息时间戳累加。

### 6.2 前端拿 `waiting` 做什么

- 渲染成**醒目的等待态**横幅，例如「等待审批中，已等 X 秒」，`since` 就是计时起点。
- 在同一处提供**中止按钮**，动作是 [`POST runs/abort`](#8-中止运行)；这是用户从「卡住的 run」里出来的唯一手段。
- 详情页与运行列表都用它做「这个 run 在等人」的判据，不要去逐条扫消息。

## 8. 中止运行

```text
POST /api/smart-factory/v1/runs/abort
```

请求体：`{ "runId": "run_5b8e2a41" }`。

语义要点：

- **传子 run id 时向上解析到顶层 run**，底层中止整个顶层 run 树（顶层 run 及其全部子 run），响应返回解析后的顶层 run；传顶层 run id 行为不变。
- 中止按下面的顺序推进：
  1. 顶层 run 条件更新为 `aborted`、写 `finishedAt`（该 run 占用的活跃顶层 run 名额随之释放；非 `runtime` 阶段还包括实例级名额）；
  2. 落中止信号、停引擎；
  3. 该 run 血缘下的活跃子 run 批量落 `aborted`；
  4. 把该 run 树下所有 `status='pending'` 的审批与交互置 `aborted`（`approval` 的 `content` 变成 `decision='aborted'`、`decisionSource='abort'`；`tool_interactive` 只有 `decisionSource='abort'`，不带 `answers`），并放行被阻塞的引擎；
  5. 每个被收敛的子 run 补发 `task.notified`（wire `status='stopped'`，DB 落 `aborted`），随后顶层 run 广播 `run.status` / `chat.aborted`，最后广播 `session.status`。
  终态与中止信号都先于放行引擎：引擎读到的必然是 `aborted`，后到的成功返回不会把终态改写成 `succeeded`。
- 中止在 `abortRun` 内立即广播，不等引擎返回；收尾的 `closeRun` 幂等去重。
- 正常收尾（`closeRun`）也会把残留的活跃子 run 收敛为 `aborted` 并补发 `task.notified`。
- 被结算的那几条消息与 `run.status` 会经 WS 广播，前端按 `id` 覆盖渲染。
- 落终态即摘掉运行句柄：**对同一个 run（含子 run 解析到的顶层 run）重复中止稳定返回 `409`**。
- 引擎后到的返回不改写终态，run 保持 `aborted`（`finishedAt` 非空）。
- 中止后该实例可以再 `send`、再 `create` 会话。

请求实例：

```bash
curl -s -X POST 'http://localhost:4100/api/smart-factory/v1/runs/abort' \
  -H 'Content-Type: application/json' \
  -d '{"runId":"run_5b8e2a41"}'
```

响应实例 `200`：

```json
{
  "id": "run_5b8e2a41",
  "sessionId": "sess_9c1d4b7a",
  "instanceId": "inst_2f6a1c8e",
  "parentRunId": null,
  "parentToolUseId": null,
  "subagentType": null,
  "delegationDepth": 0,
  "taskId": null,
  "status": "aborted",
  "error": null,
  "startedAt": "2026-10-15T02:20:31.004Z",
  "finishedAt": "2026-10-15T02:22:05.881Z",
  "createdAt": "2026-10-15T02:20:30.998Z",
  "waiting": null
}
```

错误：

| HTTP | `error` | 触发条件 | 响应体 `message` 示例 |
|---|---|---|---|
| 400 | `BAD_REQUEST` | `runId` 缺失或为空串 | `runId 必填` |
| 404 | `NOT_FOUND` | 运行不存在 | `运行 run_5b8e2a41 不存在` |
| 409 | `CONFLICT` | 该 run（或子 run 向上解析到的顶层 run）已终态（含重复中止） | `运行 run_5b8e2a41 已终态` |

`409` 只有一个含义：**该 run（或子 run 向上解析到的顶层 run）已经是终态**（`succeeded` / `failed` / `aborted`），没有别的分支。
想中止一个会话的当前活跃 run，也可以走 [`sessions/abort`](./4.03-会话.md#8-中止会话)，两者是同一条服务路径。

## 9. 活跃顶层 run 名额与「审批不超时」的语义后果

- **同一会话在任何 stage 至多一个活跃顶层 run**（`running` 且 `parentRunId` 为 `null`；`pending` 仅枚举保留值），由部分唯一索引 `uq_runs_one_active_top_per_session` 兜底 + 起 run 前的事务检查。
  `send { sessionId }` 面对该会话的活跃顶层 run 返回 `409`；子 run 不占名额，同一顶层 run 下可以有多个并发子 run。
  完整不变量见 [`02-data-model.md`](../03-architecture/02-data-model.md) §6。
- **非 `runtime` 阶段另有实例级名额**：`development` / `preview` / `evaluation` 下同一 `(agentId, stage)` 至多一个活跃顶层 run。
  `messages/send` 与 `sessions/create` 冲突时返回 `409`；不同会话也不能并发。
- **`runtime` 没有实例级名额**：同一 agent 的不同会话可以各有一个活跃顶层 run 并发执行。
  `send { agentId }` 的并发首帧都能成功建会话并起 run，`sessions/create` 也不因实例下已有活跃 run 返回 `409`。
  `send { agentId }` 会先建新会话；起跑条件解析或产物门禁失败会删除这条新会话，不留下空会话。
- **跨阶段守卫**：`development` 有活跃 run 时进入 `preview` / `runtime` / `evaluation` 返回 `409`；同 agent 有活跃 runtime run 时启动 `development` 同样返回 `409`（见 [`03-session-run.md`](../03-architecture/03-session-run.md) §1.4）。
- **共享 cwd 的写冲突边界**：见 [`02-data-model.md`](../03-architecture/02-data-model.md) §6。
- **审批不超时**：没有超时器、没有 `expiresAt`、没有自动拒绝。
  引擎一直等在挂起的那条 Promise 上，服务端也一直持有它。
- 两条合起来的后果：**一个无人应答的 run 会一直占着它的活跃顶层 run 名额**。
  `runtime` 只卡该会话，同 agent 的其它会话不受影响；非 `runtime` 阶段还卡住整个实例，该实例后续的 `send` 与 `create` 全部 `409`。
  出口只有四个：用户应答、用户中止、服务重启、进程被杀。
- 因此前端必须把 `waiting`（见 §6.2）渲染成醒目的等待态并提供中止按钮，不能指望它自己超时。
- **服务重启**：重启不续跑。
  启动时把所有活跃 run 置 `failed`（`error='服务重启'`、写 `finishedAt`），残留的 `status='pending'` 消息置 `aborted`（`decisionSource='restart'`），并按会话重算 `completed`。
  关闭（SIGINT / SIGTERM）时把残留挂起按 `decisionSource='abort'` 结算（与 `runs/abort` 同源，区别于启动收口的 `'restart'`）。

## 10. 错误码汇总

| HTTP | `error` | 出现在 |
|---|---|---|
| 400 | `BAD_REQUEST` | `runs/list` 的 `sessionId` 缺失；`runs/detail`、`runs/children` 的 `runId` 缺失；`runs/abort` 的 `runId` 缺失 |
| 404 | `NOT_FOUND` | `runs/list` 的会话不存在；`runs/detail`、`runs/children` 与 `runs/abort` 的运行不存在；未匹配到任何路由 |
| 409 | `CONFLICT` | `runs/abort` 面对已终态的 run；`messages/send` 面对已有活跃 run 的会话或非 `runtime` 阶段已有活跃 run 的实例；`sessions/create` 在非 `runtime` 阶段面对已有活跃 run 的实例；`development` 起 run 面对同 agent 的活跃 runtime run |

错误响应体统一为 `{ "error": "<码>", "message": "<中文兜底>", "messageKey": "<i18n 键>", "params": { ... } | null }`，由错误中间件产出；`messageKey` / `params` 的含义与降级规则见 [`4.02-通用规范.md`](./4.02-通用规范.md) §10.1。
