# ADR-0001：不采用 DDD 四层分层

> 状态：**已接受**（2026-10-14）。改动本决策需新开 ADR 取代本篇。

## 1. 背景与问题

同仓库的参考实现 `aimatrix_aim-nae_agent-runtime` 用 NestJS + DDD 四层（`domain` / `application` / `infrastructure` / `interface`）。本仓后端是否也按 DDD 分层组织代码，需要一次明确决策，否则每加一个域都要重新讨论文件该放哪。

## 2. 决策

**不采用 DDD 四层分层。** 后端用 `modules/<domain>/` 四件套（`routes` / `controller` / `service` / `index`）+ `shared/`，业务规则写在 `*.service.ts`（该域唯一业务承载），跨域只经 `service`，存储访问只经 `shared/store/*.repo.ts`。详见 [`../03-architecture/01-architecture.md`](../03-architecture/01-architecture.md) 第 2 节。

同时**不做「轻 DDD」的提前拆分**：不为 `domain/` / `*.domain.ts` / `*.rules.ts` 预留目录；规则膨胀时按 §5 的触发条件处理。

## 3. 理由

1. **域模型薄，技术复杂厚**：会话 / 实例 / 运行三域合计 4 张表，显式不变式 5 条；难点在实时推送、持久化与「不回放」语义，属技术复杂度，分四层不解决。
2. **DDD 最值钱的部分已在用**：契约先行（类型层）、存储隔离（repo）、入口校验。缺的只是 `domain/` 这一层显式目录，属形式而非能力。
3. **成本与收益不匹配**：每域 8–12 个文件 + 大量 DTO↔实体映射样板，而业务逻辑尚薄。
4. **一致性优先**：同仓库的 `harness-server` 用 `routes → services → repositories → db` 的轻量分层，同一仓库两套后端分层约定会长期制造认知负担。

## 4. 后果

- **正面**：每域文件数少、上手快；与 `harness-server` 约定一致；测试可直接整体替换容器，不必穿透四层。
- **负面**：`*.service.ts` 同时承担编排与规则两类职责，最容易膨胀成上帝文件；纯规则的单测要靠拆文件而非拆目录来保障。
- **缓解**：service 只保留「编排 + 落库」，纯规则一旦成规模就抽到同域独立文件，仍不建四层。

## 5. 重新评估的触发条件

出现下列任一情况时，新开 ADR 重新评估（优先考虑「同域抽规则文件」，而非直接跳到四层）：

- 同一域由 ≥2 个团队并行改动；
- 同一条业务规则在 ≥3 处重复实现；
- 一个 `*.service.ts` 超过约 300 行且拆文件已明显不够；
- 同一域需要支持多套存储或多种 runtime，且各自的业务规则**不同**（不仅是实现不同）；
- 出现与外部系统长期双向同步的复杂模型，或新增规则密集域。
