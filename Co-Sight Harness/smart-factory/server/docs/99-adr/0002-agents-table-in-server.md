# ADR-0002：智能体管理收进本仓后端，新增 agents 表

> 状态：**已提议**（2026-10-15）。本决策取代 [`../03-architecture/01-architecture.md`](../03-architecture/01-architecture.md) §1.1 减法清单里的「智能体管理」一项与 §2.2 的「`agent-create` 域整个删除」。
> 接口形状见 [`../05-openapi/5.01-agent-openapi.yaml`](../05-openapi/5.01-agent-openapi.yaml)。

## 1. 背景与问题

原设计**明确不做**智能体管理：无 agents 表、无列表与发布接口，理由是「页面与数据在别的组件里」；智能体的身份只是磁盘目录名 `agentId`，`instances.agent_id` 是一根指向目录的裸字符串（[`../03-architecture/02-data-model.md`](../03-architecture/02-data-model.md) §1 的链路起点写作「`agentId`（目录名，无表）」）。前端因此只能打 mock 中间件（`web/mock/agents-plugin.ts`），并把两边的行为差异逐条登记成待定项（`web/docs/contracts.md` 的偏差表）。

与其他模块对齐后发现：那份「别的组件」并不存在，智能体元数据（列表 / 创建 / 改名 / 删除）没有任何组件承接。而本仓后端已经握着它的产物目录、它的实例与它的全部会话，是唯一同时知道「这个智能体存在」和「它跑过什么」的一侧。继续留在别处，会让「删掉一个智能体」变成一次跨服务协调。

## 2. 决策

新增 `agents` 表（第五张表）+ `modules/agent/` 域 + `/agents/{list,detail,create,update,delete}` 五个端点。
（2026-10-19 追加只读 `GET /agents/tags`，用于标签筛选下拉；不改变本 ADR 的决策，接口形状以 5.01 为准。）要点：

- **`id` 用 `agt_<uuid>`，同时就是产物目录名**（`<workspace.directory>/.smart-factory/agents/{id}/`，工作区由 `agents.workspace_id` 经框架工作区接口解析）。`dir` 不入库，由 `dir-resolver` 现算。
- **表是智能体存在的唯一权威**：`sessions/create` 校验存在，未知 `agentId` 返回 `404`。
- **`delete` 库与盘都删**，顺序固定为**先删盘、后删库**；启动时按工作区**幂等收养** `<workspace.directory>/.smart-factory/agents/` 下的存量目录，`id` 保留原目录名不重发 uuid。
- **零外键照旧**：级联由应用层在同一事务显式完成，没有数据库级外键。
- **命名与身份传法**：模型与响应体的身份字段叫 `id`（与 `inst_` / `sess_` / `run_` / `msg_` 一致）；身份的值按**「集合路径不带 id，个体与父子路径 id 进路径」**传递（集合 `GET/POST /agents`，个体 `GET /agents/{agentId}`、`POST /agents/{agentId}/update|delete`），请求体只承载可变字段，与 [`../04-api/4.02-通用规范.md`](../04-api/4.02-通用规范.md) §4 一致。`instances.agent_id` 这根引用列的列名不动。

## 3. 理由

1. **谁拥有产物目录，谁就该拥有「这个智能体存在」的权威。** 目录、实例、会话三样都在本仓，只有元数据在外面，是所有权切错的形状。
2. **迁移成本被压到一行 base URL。** 前端已有一整套接口形状（mock，含分页 / 关键字 / 状态过滤与错误码），后端照着实现即可；`web/src/shared/api/agents.ts` 换掉 `VITE_AGENTS_API_BASE_URL` 就完成切换。
3. **`agentId` 这个名字已经失去依据。** 它原本的意思是「不是外键、指向目录的裸字符串」；有表之后它就是个主键，继续叫 `agentId` 只会让 `agents` 成为五张表里唯一主键不叫 `id` 的表。
4. **减法清单要减的是「不必要的能力」，不是「必须有人做但没人做」。** 智能体管理属于后者，`4.01` §5 把它记成「刻意不存在」是当时信息不足。

## 4. 后果

- **正面**：会话 / 运行与智能体之间从「约定」变成可校验的引用；`4.07` 里前端登记的偏差项（agentId 生成方、重名判定、`dir` 形态、状态机、分页、`update` / `rename` 是否存在）一次结清。
- **负面**：本仓第一次出现**删数据同时删盘**的破坏性端点；启动多一步收养；`sessions/create` 多一条前置校验，6 个测试文件里随手写的 `agentId` 要先建行。
- **缓解**：删除顺序固定为先盘后库，使「删盘失败」不会被下次启动的收养复活；收养只补登记、不重构存量 `id`，`instances.agent_id` 的字符串引用不会断；`agentId` 形态校验仍是路径拼接的唯一安全边界，uuid 使得它无需放宽（也就不引入 Unicode 归一与大小写文件系统的坑）。
## 5. 重新评估的触发条件

- 智能体元数据出现**第二写者**（别的组件也要改 `agents` 表），那时该重新切所有权，而不是加接口；
- 需要**版本 / 发布态 / 每智能体权限**（那是新 ADR 的题目，不是本表的字段扩张）；
- 删除需要**可恢复**（回收站）时，先盘后库的顺序与「不留软删除」的决定要一起重审；
- 出现**多用户 / 远端**形态，`boot 收养目录` 与「无鉴权、删盘即毁」的前提都不再成立。
