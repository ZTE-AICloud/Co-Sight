0. 结论摘要

核心结论：不能无缝运行。业务逻辑层可移植，强制层结构性不可移植。

drive 的编排循环（状态机、DAG、wave 调度、46 个 Python 脚本）在 dsh 上可以原样跑通，零改造。但 drive 的核心价值——由 harness 层强制执行的状态机不变量与 HITL 门禁——在 dsh 上有两处结构性缺失，不是配置能弥补的：allowed-tools 差分权限机制不存在，且三条 PreToolUse matcher 全部静默失效。

估算：约 70% 的代码可直接使用，约 30%（强制层）需要重新设计。且失败模式是静默的——不报错、不告警，workflow 照常产出结果，但零强制。

按使用场景的可行性

使用场景可行性说明
纯 auto 编排
只要产出，不要强制		可跑通drive 的 auto_mode=true 是贯穿 harness 与 CLI 两层的完整旁路，无需任何确认脚本。46 个 Python 脚本零 Claude 依赖，原样可用。
auto + 需要状态机不变量可跑但无强制守卫是唯一执行层，dsh 上全部不触发。CLI 层那道门兜底，但其 docstring 自陈「可能被绕过」。
HITL 模式
默认 auto_mode=false		不可用确认门禁依赖「权限弹窗即人工确认」机制，dsh 无差分权限能力，门禁无处安放。

一个反直觉的有利结论

auto_mode=true 的存在使最难的那个 gap 自动消失。dsh 缺失的「差分权限」恰好是 HITL 模式才需要的能力；在 auto 模式下 drive 根本不需要确认脚本，因此该缺失不构成障碍。这显著降低了纯自动编排场景的迁移成本。

1.4 Claude Code Mods 兼容层

v0.2.1-alpha.1 引入（包 packages/experimental/claude-code-mods/）。dsh 官方 release note 定性为设计验证而非可用能力：

「At this stage, the main goal is to verify that the Claude Code Mods API's capabilities are broadly a subset of what DeepSeek Harness plugins can do, rather than to offer users complete, practical compatibility.」

官方文档 docs/subsystems/claude-code-mods.md 实为一张逐条列出差异的对照表，其中对权限语义尤为不利：

能力状态说明
tool.call 时序语义相反Claude Code 在权限检查之前运行；此桥在 tools/execute 周围、权限决定之后运行。改写参数或换工具名会被跳过。

$.model $.agent $.config $.settings $.mcp $.audio $.telemetry $.turn全部拒绝返回 no implementation。
$.session.authorize缺失连同 compact、surfaces 一并缺失。
沙箱无官方文档：「the process's full authority: $.env reads and writes the harness environment, $.http.fetch reaches any URL」
mod tiers / next.to降级一律按 user tier 处理，next.to 直接拒绝（managed settings 非 dsh 概念）。

文档基线为 Claude Code 2.1.287。此外 plugin.json 与 hooks.json 不被读取，mod 的 manifest 会被忽略。

1.6 供应链与安全约束

  • 安装冷却：dsh plugin add 因 pnpm 11 内置默认 minimumReleaseAge = 24h，永远装不到 24 小时内新版本。仓库无 .npmrc，此为上游行为而非 dsh 设计；dsh UI 文案主动承认了该行为（ui-plugin-manager/src/client/locales.ts:426）
  • 安全公告：README.md:13 全大写警告 「THERE WILL BE COMPATIBILITY-BREAKING CHANGES.」；SAFETY.md:7 明言 「has not undergone a security audit and must not be treated as secure or production-ready」。
  • 已知 CVE：CVE-2026-82533（CVSS 9.4，2026-09-08 披露）沙箱逃逸 + 认证绕过，已于 0.1.2-alpha.1 修复。
  • hooks 桥为 opt-in：当前没有任何 preset 组合 hooks-claude-code，须显式启用。

2. drive 现状

2.1 组成

drive 由三类元素构成，均位于 plugin.json 声明之下：

元素数量说明
agents7.claude/agents/*.md，frontmatter 含 tools 窄授权白名单（PascalCase 工具名）

2.2 强制层：双闸门设计

drive 的不变量由两层独立执行，hooks_protocol.py 的 docstring 明确说明其分工：

「与 state_cli 的同名检查是两道独立的门：CLI 那道可能被绕过（模型换别的方式写状态），本道由 harness 强制，模型无法跳过。」

闸门载体职责
CLI 层state_cli.py / dag_runtime.py自校验。含 PROTECTED_FIELDS 保护 confirmed_stages / confirmed_nodes 不被 update --set 直接写
harness 层state_transition_guard.py 等 3 个 PreToolUse hook模型无法跳过的强制执行。drive 的核心保证在此层

2.3 HITL 机制：依赖 dsh 不具备的差分权限

确认门禁的机制：不在 allowed-tools 内 → 弹权限窗 → 弹窗即确认

skills/dag-runtime/SKILL.md:90 原文：「confirm_node.py 不在任何 skill 的 allowed-tools 内：执行时由 Claude Code 弹授权请求作为人工确认。」

该机制的要害是差分：9 个 skill 各有窄授权（如 Bash(python3 *dag_runtime.py*)），其余一律弹窗。deny 消息里也复述了这一契约：「该命令会向用户请求授权 —— 那个授权即人工确认。」

2.4 三个自动化层级

drive 内置了绕过 HITL 的机制，且在 harness 与 CLI 两层一致实现：

层级作用域实现位置
auto_mode=true全局旁路hooks_protocol.py:389（stage）、:474（DAG 节点）、state_cli.py:334、dag_runtime.py:165
skip_when: [auto_mode]逐 gateworkflow.yaml gate 声明式跳过
complexity=trivial部分旁路仅 harness 层（hooks_protocol.py:393，跳过 analyze/plan/execute，evaluate 始终强制）。CLI 层 check_stage_confirmed 无 complexity 分支。DAG 模式明确不认此机制。

默认 auto_mode=false，仅当用户显式说「自动」才置 true。auto_mode 是贯穿两层、最可靠的自动化路径，这正是它能化解 Gap G1 的原因。

2.5 阻断路径恰好落在 dsh 已实现的一侧

HookResult.exit_code() 返回 2 而非 JSON 输出：

# hooks_protocol.py:61-63
def exit_code(self) -> int:
    """deny → 2（Claude Code 回显 stderr 给 LLM），allow → 0。"""
    return 2 if self.is_denied else 0

dsh 的 codec 识别 exitCode === 2（hook-protocol/src/codec.ts:8 的 BLOCKING_EXIT_CODE）。drive 完全不使用 {"continue": false}，因此「只记录不终止」这个缺口对 drive 不适用。这是 drive 阻断路径的一次幸运落位。

2.7 Codex 端口先例（附带发现）

仓库内已有 dist/codex-drive/ 一次跨 harness 移植。核查发现其为近乎机械的复制：hooks.json 仅改 ${PLUGIN_ROOT:-${CLAUDE_PLUGIN_ROOT}}，agents 由 .md 转 .toml，allowed-tools 原样保留在 9/17 个 skill 中。

这意味着该端口的隐含假设是「Codex 支持同样的 allowed-tools 语义」。若该假设不成立，这份产物带着与 dsh 同类的潜在问题，且存在时间更早。建议单独验证 Codex 端口在 Codex 上运行时的 HITL 是否真的弹窗。

3. Gap 分析

G1差分权限机制缺失CRITICAL影响 HITL 模式

drive 的确认门禁依赖 allowed-tools 的差分授权。dsh 的审批只有会话级二值：

// packages/interaction/user-approval/src/index.ts:67
export type ApprovalPolicy = 'ask' | 'never'

全仓 grep allowedTools / Bash( 模式匹配零命中。仅有会话级二值意味着只有两个选项，两条都是死路：

策略后果
ask所有工具调用都弹窗 → 提示疲劳，不可用
never一律不弹，包括 confirm 脚本 → HITL 门禁彻底敞开

放大因素：allowed-tools 是 dsh 不识别的 frontmatter 键，被静默忽略而非报错。9 个 skill 的窄授权会无声消失，不产生任何告警。

缓解：auto_mode=true 下该 gap 完全消失（不需确认脚本）。否则须改造 HITL 机制本身（见 §4）。

G2PreToolUse matcher 全部静默失效CRITICAL影响所有模式

drive 的 hooks.json 使用的 matcher 全为 Claude PascalCase 工具名：

drive matcherdsh 实际工具名结果失效守卫
Write|Edit|MultiEditwrite / edit不触发planning_write_guard

失败模式为 静默不调用，而非 fail-open 报错。这是与 G1 独立的第二个阻断项：即使 G1 在 auto 模式下消失，本 gap 仍使全部状态机不变量失效。

G3子代理定义格式不兼容HIGH

7 个 .claude/agents/*.md 无法直接导入，dsh agent preset 为带 agent.cordis.yml 的目录。各 agent 的 tools 窄授权（["Read","Write","Edit","Bash"]）在 dsh 中亦无等价物——即便转换格式，权限收敛能力仍会丢失。Codex 端口的 .md → .toml 可作为转换脚本的参考，但目标格式不同。

G4插件打包机制不兼容HIGH

.claude-plugin/plugin.json 与 marketplace.json 在 dsh 中不被读取（已在 Mods 桥文档中源码确证：「plugin.json and hooks.json are not read」）。dsh 插件为 npm 包 + cordis.yml，经 profile 层装配。skills 须落入 6 个 rank 之一。这是纯工程量问题，无设计障碍。

G5失效完全静默HIGH横切

G1 与 G2 均无任何错误信号：allowed-tools 被忽略不报错，matcher 不匹配不报错，守卫不触发不报错。workflow 会一路跑完、产出格式完整、看不出异常，但零强制。这是最危险的配置组合——auto 模式叠加失效分发层，等于一个沉默失效的状态机。任何迁移方案都必须包含一个「守卫是否真的在跑」的自检手段。

trivial 旁路疑似单侧harness 层认 complexity=trivial，CLI 层无对应分支，阶段流转实际可能仍被 CLI 拦截。需自行验证。

4. 改造方案：drive 做成 dsh 插件

核心判断：1356 行守卫逻辑一行不用改，需要替换的只是约 50 行接线

drive 的守卫是纯 Python、无 Claude 运行时依赖、输入输出契约（读 hook JSON → 写 stderr + exit 2）与宿主无关。失效的只是「谁来调用它」这一层分发机制。dsh 的 tools/pre-execute 是正式 waterfall 拦截点（core/tools/src/index.ts:154，标注 @mode waterfall，返回 PreToolDecision），原生插件挂上去可直接读 exec.name（小写 bash / write / edit）自行分发，完全绕开那套失效的 matcher。

4.1 目标形态

一个 dsh 插件包 @yourorg/dsh-drive，包含：

  • cordis.yml —— dsh 插件清单，挂载技能包、agent preset、以及强制层插件
  • skills/ —— 17 个 SKILL.md，name 与 body 均无需改动，仅 allowed-tools 键需按 dsh 规则处理
  • agents/ —— 7 个 agent preset 目录，各含 agent.cordis.yml
  • guards/ —— 原生插件，挂 tools/pre-execute，内部 shell out 调用现有 Python 守卫

4.2 任务拆解

阶段任务工作量说明
P0可行性验证：原生插件挂 tools/pre-execute 调 state_transition_guard.py，实测 deny 是否真阻断0.5 天先做这个。成本最低，且直接证实或证伪整条路径。若 exit 2 无法从插件侧可靠传递，后续方案需重估。
P1强制层：编写 dsh 原生插件替代 hooks.json 分发2–3 天挂 tools/pre-execute + tools/post-execute；读 exec.name 自行映射（bash→Bash 语义、write/edit→Write 语义）；shell out 调用现有 Python，透传 exit 2。解决 G2。
P2技能包：17 个 SKILL.md 适配1 天name 与 body 零改动（已验证合规）。仅需处理 allowed-tools：dsh 静默忽略该键，故要么移除、要么改由 P3 的显式机制承担。
P3HITL 改造：从「权限弹窗即确认」改为显式 ask_user_question 调用2–4 天解决 G1。dsh 有 ask_user_question（packages/interaction/tool-ask-user），能力齐全。改法比现在更明确，且不依赖任何权限机制——这是把隐性契约变为显式契约。
P4子代理：7 个 md → agent.cordis.yml 目录2–3 天解决 G3。可参考 dist/codex-drive/ 的 .md → .toml 转换脚本。注意 tools 窄授权无等价物，需在 SKILL.md 或插件配置层另行承接。
P5打包：npm 包 + profile 装配1–2 天解决 G4。发布需提前 24h（安装冷却）。
P6自检机制：守卫存活探针0.5 天解决 G5。不可省略。一个启动时或定期运行的探针，确认 tools/pre-execute 监听器确实挂载且被调用；否则静默失效无法察觉。

合计约 9–16 人日。若仅需 G1 豁免的 auto 编排场景，可只做 P0+P1+P2+P5+P6，约 5–8 人日。

4.3 强制层的两条可选路径

路径 A：dsh 原生插件重实现分发层 推荐

挂 tools/pre-execute，读 exec.name 自行分发，shell out 调现有 Python。

优点：守卫逻辑零改动；绕开 matcher 问题；dsh 一等拦截点，受支持。

缺点：需 TypeScript 胶水层；G1 仍须靠 P3 单独解决。

路径 B：修正 hooks.json 的 matcher

把 Bash 改为 bash、Write|Edit 改为 write|edit，继续用官方桥。

优点：改动量最小（约 3 行）。

缺点：仍受制于桥的能力边界：SubagentStart/Stop 的 kind 匹配写死、continue:false 不终止、Windows 无防护且零测试覆盖、且该桥不在任何 preset 中须显式启用。属治标。

4.4 建议路线

  1. 先跑 P0。零风险地证实或证伪整条路径，再决定投入。
  2. 按目标场景分支。若定位为纯自动编排器 → P0+P1+P2+P5+P6；若需保留完整 HITL 语义 → 全量 9–16 人日。
  3. 独立跟进两件事（与 dsh 迁移无依赖，建议并行）：(a) 验证 Codex 端口的 HITL 是否真的弹窗（§2.7，疑似历史遗留问题）；(b) 验证 complexity=trivial 旁路是否因 CLI 层缺分支而失效（G6）。
