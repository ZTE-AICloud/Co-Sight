Drive 插件架构图（原则 A · 按元素类型分层）

Drive 只由三种元素组成：agents / skills / hooks。 本图严格按"同类成层"绘制：每个 layer 只放一类东西（元素 / 元数据 / skill / script / 产物）， 不混类。scripts 是 skill 内部被 allowed-tools 允许跑的工具，产物是 skill 跑出来的数据 / 文件。

1. 设计目标与边界

Drive 是 基于 Claude Code 的声明式多 agent 编排引擎，v2.3.4。 它不打包独立的运行时引擎 —— Claude Code 自身就是 runtime，Drive 通过 plugin.json 注册插件、由 drive skill（用户通过 /drive 调用）触发、按 workflow.yaml 调度。

组成元素只有三种（理解 Drive 的关键）：

  • agents（7）—— plugin.json 的 agents: [...] 字段定义角色。
  • skills（17）—— 每个 skill 自带 SKILL.md + scripts/ + references/；其中 user-invocable: true 的会暴露成 slash-command（如 /drive、/workflow-builder）。
  • hooks（4 类触发器）—— 由 hooks/hooks.json 声明，实现落在 hooks/*.py。

没有第四种。scripts 不算独立元素，是 skill / hook 内部被 allowed-tools 允许跑的工具。本图严格按"同类成层"原则绘制 —— 每个 layer 只放一类东西。

2. 逐层拆解

L1 · Runtime（宿主）

宿主运行时，不是 Drive 元素。Claude Code 负责接收用户输入、维护会话、调度 Agent(...) 子调用、执行 Bash/Write/Edit 等工具。MCP 提供两个常用集成：

  • AskUserQuestion —— Drive 主对话用来真向用户发起 HITL 决策。
  • chrome-devtools navigate_page —— startup skill 在 live_trace=true 时自动开浏览器看 trace。
  • git / fs —— 宿主基础能力，drive-cleanup / drive-record 间接消费。

L4 · 执行模式 skill

drive skill §3 根据 workflow.yaml 的 mode 字段选一种执行模式；两种模式对应不同 skill：

L4a · phase mode（顺序五段）

经典五段流水线：start → analyze → plan → execute → evaluate。 phases[i].agent 决定每段派哪个 worker；阶段必须出现在 confirmed_stages 里才能流出。

执行 skill：state-machine skill（其脚本 state_cli.py / state_rules.py / audit_append.py）。

对应产物：executeState.json（fcntl 排他锁 + revision 单调自增；agent 自己写自己的阶段状态，编排层只读）。

L4b · DAG mode（拓扑波次 · 并行 fan-out）

把任务图按 depends_on 拆成 wave，每 wave 内部并发跑。

执行 skill × 3：

  • dag-runtime skill（dag_runtime.py）—— active_agents[]、current_wave、confirmed_nodes[]、state.verdicts[id] 四个字段的读写 + HITL 入口。
  • wave-scheduling skill —— Kahn BFS 拓扑排序 + 环检测 → 落 waves.yaml + topo-state.json，不调 LLM。
  • wave-barrier skill —— 每 wave 收尾聚合 aggregate.py，做 task_id 强比对 + fs diff barrier，不通过就不写 state。

对应产物：waves.yaml（权威依赖账）、topo-state.json（运行中间态）、active_agents[]。

失败模式：advance-wave 是 fail-closed —— 当前 wave 还有 running 节点 → wave_barrier_not_ready；跳 wave → wave_skip。

L5 · Worker agents（运行时派发）

七种角色各司其职，由 drive 全局策略派发：

角色职责
analyzer agent解析 / 澄清需求，写 manifest.md。
planner agent拆解为 taskRecord.yaml（带 depends_on / agent_name），调 wave-scheduling。
executor agent实施任务，写 SUMMARY.md；驱动 wave-barrier aggregate。
evaluator agent对 verdict_required agent 做终态判定，写 state.verdict。
code-reviewer agent静态 + 设计评审。
security-reviewer agentOWASP / 凭据 / 注入扫描。
gate-human agentHITL 中介：approve → confirm-node → mark-completed；revise → mark-skipped。

调度策略（全局）：run_in_background=False，并发靠"同消息多次 Agent() 调用"。

L6 · Hooks 元素 + 实现

hooks 这一类元素的全部内容物，4 个 sub-section：

sub-section内容
hooks.json 4 类触发器PreToolUse Write|Edit|MultiEdit / PreToolUse Bash / PreToolUse Task|Agent|Skill / SubagentStop
hooks 实现脚本planning_write_guard / state_transition_guard / audit_events / subagent_report_guard
HITL 校验函数check_stage_confirmation / check_dag_node_confirmation / check_confirmation_tampering（hooks_protocol.py）
skill 内部校验state_rules.VALID_TRANSITIONS / state_cli.cmd_mark_status（state-machine skill 脚本）

HITL 默认人工的奥秘：

  • hooks_protocol._CONFIRM_ENTRYPOINTS = ("confirm_stage.py", "confirm_node.py") —— 唯一写 confirmed_stages / confirmed_nodes 的入口。
  • 这两个脚本刻意不在任何 skill 的 allowed-tools 内 —— 执行时由 Claude Code 弹授权请求，权限弹窗本身即人工确认。
  • hooks_protocol.check_confirmation_tampering 拦截绕过 attempt（如直接改 state.json 字段）。
  • 双重闸门：DAG 模式 mark-completed 既要 hook 通过，又要 dag_runtime.cmd_mark_status CLI 内部校验，单独绕任一道都不够。

L8 · 横切 skill

任意阶段按需调用的 skill：

  • execution-patterns：wave 并行 / retry ceiling / checkpoint trigger 模板
  • eval-fresh-evidence：verdict_required 终态闸的判定规则
  • smart-decomposition：自动拆解任务到 taskRecord
  • critic-3-perspectives：三视角审视方案（事实 / 高级工程师 / 安全）
  • context-packaging：把上下文打包成 worker 可消费的 envelope
  • bootstrap-data-completer：缺 manifest / taskRecord 时诊断 + 补齐
  • drive-cleanup：drive 收尾清理（kill trace server、归档状态）

3. 关键不变量（hard NO）

  1. 阶段/节点必须经 HITL：phase 模式 stage 必须出现在 confirmed_stages；DAG 模式节点必须出现在 confirmed_nodes。
  2. 写入口唯一：confirm_stage.py / confirm_node.py 是唯一合法写入口，不在任何 allowed-tools。
  3. agent 自己汇报状态：编排层只读，agent 履职完毕自己写自己的阶段/节点状态。
  4. wave barrier 强比对：summary task_id 与 waves.yaml 不一致 → 不写 state。
  5. fs diff barrier：status=done 但 files_changed 空 → 不写 state。
  6. retry budget：retry_count >= max-retries（默认 3）时 REASON_RETRY_BUDGET_EXCEEDED。
  7. auto_mode 是唯一全局旁路，开了就跳过 confirm，hook 不挡。

4. 一条典型请求的生命周期

  1. 用户 /drive add-user-auth → drive skill §1 调 startup skill → 跑 init_planning.py + discover_inputs.py + 拉起 drive-trace skill 的 serve.py。
  2. startup skill 写 envelope.data；workflow-builder skill 生成 workflow.yaml。
  3. drive skill §2 跑自己的 read_workflow.py → 拿到 { mode, phases[], agents[] }。
  4. drive 按 phases[i].agent 派 analyzer agent → 写 manifest.md → 通过 state-machine skill 的 state_cli update。
  5. analyzer 完成 → drive 触发 gate-human agent 做 HITL（request-confirmation）→ 用户回 approve。
  6. hook 校验函数 check_stage_confirmation 通过 → drive 推进到 plan 阶段。
  7. 重复 4-6 直到 evaluate 阶段 → evaluator agent 写 state.verdict == pass → drive 收尾。
  8. drive-cleanup skill 关 trace server；drive-record skill 生成复盘报告。

5. 与业界差异

  • 声明式编排：workflow.yaml 把"造编排"和"跑编排"分开。
  • runtime 即 Claude Code：不引入独立 runtime。
  • 钩子即事实权威：HITL / 状态流转 / 写入白名单由钩子层强制。
  • 多层观测：live trace + 离线 record + 视觉 viz + run-log + git 五重追溯。
  • 双模式 + 双闸门：phase / DAG 共享 worker pool，HITL 入口一致。
