# 通用模式:三段式 change_desc v1 (tri_segment_desc_v1)

> **模式 ID**:`tri_segment_desc_v1`
> **创建日期**:2026-07-13
> **来源 bug**:`04_skill_dir/组件间流程设计/` step6 reference 定义的 change_desc 是"变更类型/涉及组件/变更描述",但实际应按【源/目标/业务接口】三段式分段,导致下游渲染混乱
> **适用场景**:任何要求"消息级变更说明"的流程类 Skill

---

## 1. 模式定义

**强制三段式**(`change_desc` 字段),用 `<br>` 分隔:

```
【源子系统变更描述】:{源侧变更内容}
<br>
【目标子系统变更描述】:{目标侧变更内容}
<br>
【业务接口(业务流)变更描述】:{接口/业务流级变更}
```

**示例**:
```
【源子系统变更描述】:MCC调度代理新增 SIB1 的 RV 优化以及 SIB1 的 Mcs 优化配置参数的解析并保存
<br>【目标子系统变更描述】:接收并转发SIB1的RV和MCS优化参数
<br>【业务接口(业务流)变更描述】:SIB1的RV和MCS优化参数
```

---

## 2. 4 类填充规则(根据消息角色)

| 类型 | 适用场景 | 填充规则 |
|------|---------|---------|
| **类型 1:外部↔内部消息行** | 源和目标只有一方属于当前子系统 | 属于当前子系统的一方查组件文档填处理逻辑,外部一方填"无变更" |
| **类型 2:中转行(接收→处理)** | 插入行,接收组件→处理组件 | 源=转发行为,目标=处理组件实际变更 |
| **类型 3:中转行(处理→发送)** | 插入行,处理组件→发送组件 | 源=处理组件实际变更,目标=转发行为 |
| **类型 4:内部组件间行** | 源和目标均属于当前子系统 | 双方各查组件文档填处理逻辑 |

**通用模板**:

```
类型 1 模板:
【源子系统变更描述】:无变更(若源为外部)|{处理逻辑}(若源为内部)
<br>【目标子系统变更描述】:{处理逻辑}(若目标为内部)|无变更(若目标为外部)
<br>【业务接口(业务流)变更描述】:{接口级变更}

类型 2 模板:
【源子系统变更描述】:接收 {外部子系统} 消息并转发至处理组件 {处理组件名}
<br>【目标子系统变更描述】:{处理组件的实际变更描述}
<br>【业务接口(业务流)变更描述】:{接口级变更}

类型 3 模板:
【源子系统变更描述】:{处理组件的实际变更描述}
<br>【目标子系统变更描述】:接收处理结果并转发至 {外部子系统} 子系统
<br>【业务接口(业务流)变更描述】:{接口级变更}

类型 4 模板:
【源子系统变更描述】:{源组件处理逻辑}
<br>【目标子系统变更描述】:{目标组件处理逻辑}
<br>【业务接口(业务流)变更描述】:{接口级变更}
```

## 3. JSON Schema(用于 LLM 响应校验)

```json
{
  "type": "object",
  "required": ["change_desc"],
  "properties": {
    "change_desc": {
      "type": "string",
      "pattern": "【源子系统变更描述】.*<br>【目标子系统变更描述】.*<br>【业务接口(业务流)变更描述】.*",
      "description": "强制三段式 change_desc,三段用 <br> 分隔"
    }
  }
}
```

**校验函数**(bash + jq):
```bash
validate_tri_segment_desc() {
  local desc="$1"
  if [[ ! "$desc" =~ 【源子系统变更描述】 ]] || \
     [[ ! "$desc" =~ 【目标子系统变更描述】 ]] || \
     [[ ! "$desc" =~ 【业务接口(业务流)变更描述】 ]] || \
     [[ ! "$desc" =~ \<br\> ]]; then
    echo "ERROR: change_desc 必须含三段式 + <br> 分隔" >&2
    return 1
  fi
  return 0
}
```

## 5. 通用性验证

其他 Skill 可复用此模式的场景:

- **代码审查说明**:`【问题位置】...<br>【根因】...<br>【修复建议】...`
- **测试用例说明**:`【前置条件】...<br>【测试步骤】...<br>【预期结果】...`
- **API 文档说明**:`【请求参数】...<br>【响应格式】...<br>【错误码】...`
- **变更日志**:`【变更类型】...<br>【影响范围】...<br>【回滚方案】...`

**抽象条件**:任何"对单条记录的说明需要从多个维度描述"的场景,即可用三段式。

## 7. 通用性边界(2026-07-13 增)

### 7.1 模式抽象

**核心抽象**:对单条记录的描述,需要从 N 个独立维度描述时,使用 N 段式格式(`段1标题:内容<br>段2标题:内容<br>...`)。

- 3 段式(本模式)是特例,N 段式可类比
- 段标题(本模式 `【源子系统变更描述】`)由 Skill 自定义
- 段落数量可扩展:2 段/4 段/5 段都适用

### 7.2 与业务解耦点

| 耦合点 | 解耦方式 |
|--------|---------|
| 例子"源/目标/业务接口" | 段标题由 Skill 传入,数量可调 |
| 例子"类型 1/2/3/4 填充规则" | 填充规则由 Skill 业务自己定义 |
| 例子"业务流变更类型" | 不绑死本模式;其他 Skill 可用其他分类 |

### 7.3 适用场景

任何满足以下条件的 Skill 任务:
- 单条记录需要从 N 个独立维度描述(N ≥ 2)
- 各维度内容**互不重叠**,可独立填写
- 下游渲染需要**结构化解析**(而不是一坨文本)

### 7.4 不适用场景

- 单条记录的描述只用一个维度(用普通文本即可)
- 各维度内容**重叠或互斥**(强行分段会丢失信息)
- 描述长度不固定,需要**可扩展段落**(本模式不动态加段)

### 7.5 实施清单

新 Skill 引用本模式时:
- [ ] 定义 N 段标题(2-5 段)
- [ ] 写 N 段填充规则(从业务背景知识抽取)
- [ ] 在 references/stepN-rules.md 中说明 N 段格式 + 必填段
- [ ] 在 LLM 响应校验块检查每段标题存在(`jq -e 'test("【段标题】")'`)
