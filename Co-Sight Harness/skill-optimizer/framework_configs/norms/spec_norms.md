# spec 章节规范(扩展)

> 本文件扩展 `framework_configs/skill-create-guidelines.md` §9(16 章节模板)。
> 适用于所有 `/skill_create` 工作流生成的 `02_skill_spec.md`。

## §1.3 输出产物表(扩展)

**核心规则**:spec 必须显式列出**所有**产物部分。

### 推断产物数量的方法

1. **Read brief + 原文件**,识别业务类型
2. **Read `knowledge/business_patterns.yaml`**,匹配最相关模式
3. **从匹配模式的 `typical_product_parts` 读取**最少产物数量
4. **将每个 required 产物部分列入 spec §1.3**

### 反例(禁止)

- ❌ spec §1.3 只列 1 行产物(如 "时序表"),遗漏 "可视化图" 和 "详细描述"
- ❌ 流程类 Skill 只生成表格,无任何可视化或详细描述
- ❌ 表格 / 图 / 描述 用 1 个 step 步骤合并生成(应该独立步骤)

### 正例(推荐)

- spec §1.3 列出 ≥3 行产物(流程类)
- 每个产物部分对应 spec §4 中 1 个独立步骤章节
- 每个产物部分都有"格式 + 数据来源 + 输出位置"描述

## §4 步骤详述(扩展)

### 流程类 Skill 必含的 7 类步骤

| 步骤类型 | 必含 | 说明 |
|---------|------|------|
| `read` | ✅ | 从源读输入 |
| `filter` | ✅ | 过滤无关行 |
| `transform` | ✅ | 格式转换(如组件引用补齐) |
| `insert` | ✅ | 插入新行(变更消息) |
| `render_table` | ✅ | **独立**生成表格(不与图合并) |
| `render_diagram` | ✅ | **独立**生成可视化图 |
| `render_detail` | ✅ | **独立**生成详细描述 |
| `validate` | ✅ | 校验(3 类:拓扑/内容/产物) |
| `write` | ✅ | 写入产物 |

### 反例(禁止)

- ❌ "生成表格"和"生成图"合并为 1 步
- ❌ "生成详细描述"作为表格渲染的副产品
- ❌ 流程类 Skill 无独立 `validate` 步骤

### 流程类 Skill 的"分类-分支"抽象规则(2026-07-13 新增)

> **抽象规则**:当 `transform` 步骤的输入数据含有"分类列"(即某个字段将数据划分为 N 个类别),
> 该步骤**必须**为每个已知类别定义**独立的处理分支**,严禁合并为单一默认分支。

#### 抽象原则

- **N 个类别对应 N 个独立分支** — 类别数 N 由业务决定,框架不预设具体值
- **每个分支逻辑独立可执行** — 不依赖其他分支的副作用
- **每个分支的错误处理独立** — 异常处理矩阵(附录 B)必须为每个分支列出 1+ 行
- **缺数据/数据错误的分支处理** — 推荐阻断退出 + 写追溯报告(见下"阻断哲学"抽象规则)

#### 反例(禁止)

- ❌ 单一默认分支:`if type == "X": do_x(); else: do_default()` 覆盖所有未知类型
- ❌ 数据缺失/不一致时"跳过该行"而不告知 — 静默错误
- ❌ 把 N 个分支合并为一个 LLM 调用 — 浪费 LLM 算力,信息损失

#### spec 必含的描述

- §4 transform 步骤的"操作"字段必须**显式列出 N 个分支的处理表**(表格结构)
- 附录 B 异常处理矩阵必须为各分支各列 1+ 行
- 校验类步骤必须校验"已知类型"不出现"未分类"占位符

> **说明**:具体的"分类列 + 类别数"由业务决定。常见实例(如 `业务流变更类型 ∈ {修改, 待验证, 新增}`)见
> `framework_configs/norms/flow_design_style_guide.md`(非规范性示例)。

### 流程类 Skill 的"知识结构化提取"抽象规则(2026-07-13 新增)

> **抽象规则**:当 step 涉及"收集知识/上下文"以供后续 LLM 推理时,**严禁 raw dump 整篇文档**,
> 必须按"结构化字段"提取关键信息,字段的**数量、命名、提取规则**由业务决定,框架不预设。

#### 抽象原则

- **结构化字段优于 raw dump** — 提取若干结构化字段而非整篇文档
- **字段数 N 由业务决定** — 框架不预设具体数量,也不预设具体字段名
- **每个字段有明确的提取规则** — 字段可来自文档的某个章节、某个表格、某个代码块等
- **目标集合过滤** — 当收集"实体间关系"时,只保留"两端都在目标集合内"的关系
  (目标集合 = 当前 step 涉及的所有实体,从数据自动推导,不是业务方传入的固定列表)

#### 反例(禁止)

- ❌ `jq -n --rawfile content file.md` 直接整篇 dump → LLM 找不到关键信息
- ❌ 整体 `grep` + 取走 → 含大量无关内容
- ❌ 知识收集无字段标准化 → LLM 必须自己找格式,易漏字段

> **说明**:具体的"5 类字段(responsibility/capabilities/...)"是 flow_design 业务的一个具体实例,
> 见 `framework_configs/norms/flow_design_style_guide.md`(非规范性示例)。

### 流程类 Skill 的"输入解析策略"抽象规则(2026-07-13 新增)

> **抽象规则**:`read` 步骤必须从**业务方实际的输入文件**直接解析,**禁止假设未在 brief 中明示的目录结构**。
> 解析策略由输入文件实际形态决定(单文件 vs 目录 vs 多文件),不预设。

#### 抽象原则

- **以 brief 声明的输入为准** — brief 写"单文件"就解析单文件,写"目录"就扫描目录
- **单文件解析策略**(当输入是单个 markdown 文档):
  1. 在文件内定位章节标题
  2. 取章节后的第一个相关结构(表格/代码块/列表)
  3. 解析结构,根据业务关键键(可能是双键、三键)过滤
  4. 列名/字段名变体匹配:支持多种命名约定
- **目录扫描策略**(当输入是多个独立文件):
  1. 按业务方指定的目录模式扫描
  2. 对每个文件应用文件级解析
- **解析策略必须在 spec §4 显式声明** — 业务方看一眼就知道 Skill 是怎么读输入的

#### 反例(禁止)

- ❌ brief 写"读 X.md 单文件",但 spec 假设存在 `${WORK_DIR}/子目录/{case}.md`
- ❌ 用 `--input-dir` 接收"目录"参数,但 brief 写的是"单文件"
- ❌ 把"单文件 + 章节"误判为"目录"形式

### 流程类 Skill 的"阻断哲学"抽象规则(2026-07-13 新增)

> **抽象规则**:**数据完整性错误必须阻断退出 + 写追溯报告**,严禁静默跳过。
> "数据完整性错误"由业务定义(常见类型见下),框架不预设具体清单。

#### 抽象原则

- **关键数据缺失/不一致 → 阻断 + 报告** — 阻断意味着流程必须停止,不可自动继续
- **追溯报告落盘到 `${STATE_DIR}/step{N}_block_report.json`** — 含阻断位置 + 原因 + 建议
- **断点可恢复** — 用户修复后调 `--resume` 继续,不需要重头开始
- **非关键数据可跳过 + 日志** — 分类标准由业务决定

#### 常见"关键数据错误"类型(非穷举)

- 关键文档缺失(如变更记录为空、规则文件不存在)
- 文档内容与上游不一致(如接口文档子系统 ≠ 交互表记录)
- 必填字段为空且无法代码化兜底
- LLM 响应 schema 错误

#### 反例(禁止)

- ❌ `if [[ ! -f "${file}" ]]; then continue; fi` — 静默错误
- ❌ "跳过该行" 而不告知用户哪一行被跳过 — 无法定位
- ❌ 默认值兜底覆盖真实错误(如"接口待定"覆盖"接口缺失")
- ❌ 阻断后无法恢复 — 必须支持 `--resume` 续跑

### 流程类 Skill 必含的"阻断哲学"(2026-07-13 新增)

> **核心规则**:**数据完整性错误必须阻断退出 + 写追溯报告**,严禁静默跳过。

| 错误类型 | 处理方式 | 反例 |
|---------|---------|------|
| 关键文档缺失(如接口文档) | ❌ 阻断退出 + 写 `step{N}_block_report.json` | ❌ 跳过该行 + 记日志 |
| 文档内容与上游不一致(如接口文档子系统 ≠ 交互表) | ❌ 阻断退出 + 报告 | ❌ 跳过 + 默认值 |
| 必填字段为空(如变更描述) | ❌ 阻断退出 + 报告 | ❌ 留空占位符 |
| LLM 响应 schema 错误 | ❌ 阻断 + 回退到 pending checkpoint | ⚠️ 部分阻断 |

#### 反例(禁止)

- ❌ `if [[ ! -f "${file}" ]]; then continue; fi` — 静默错误
- ❌ "跳过该行" 而不告知用户哪一行被跳过 — 无法定位
- ❌ 默认值兜底覆盖真实错误(如"接口待定"覆盖"接口缺失")

## §6 LLM 断点契约(扩展)

详见 `norms/llm_breakpoint_norms.md`,核心要点:

- 每个 LLM 断点必须在 `references/stepN-rules.md` 顶部含完整 JSON Schema
- Schema 必须含 `required` 字段,且 ≥3 个必填字段
- 必填字段命名应从 `knowledge/llm_breakpoint_templates.json` 选取(非自创)
