# 重构后检查 ② — 等效性验证与回归检测

> **来源**:AgentGenesis-Code `knowledge/skill/optimization-spec-template.md` §5/§7/§8 + verification-checks.md
> **用途**:在 SK-S1~S11 静态验证之外,**用行为层证据**证明重构后的 Skill 与原 Skill 等效(能力不退化)
> **核心问题**:「重构后是否破坏了 Skill 的能力?」

---

## 0. 三层等效性保障

| 层级 | 检查内容 | 谁执行 | 阻断? |
|------|---------|--------|:----:|
| **结构层** | SKILL.md 完整、引用闭合、无占位符 | verifier-agent(对应 SK-S1~S3) | ✅ |
| **内容层** | 步骤逻辑一致、Spec 一致、Delta 完整 | verifier-agent(对应 SK-S4~S6) | ✅ |
| **行为层** | 重构前后跑同一组 CASE,分数不退化 | orchestrator / 用户 | ✅ |

**本文档聚焦行为层 + 内容层扩展**(结构层见 `重构后检查-Skill完整性验证.md`)。

## 1. 回归场景设计(R-01 ~ R-N)

> 来源:`optimization-spec-template.md §8.2 回归检测`

在 Optimization Spec 生成阶段,就必须设计好回归场景,**用测试用例复现诊断中发现的问题,对比优化前后的行为差异**。

### 1.1 场景模板

| 字段 | 含义 | 例子 |
|------|------|------|
| **#** | 场景编号 | R-01 |
| **场景** | 复现什么诊断问题 | "诊断报告中 finding_dim3_2:SKILL.md 步骤 5 缺输入校验" |
| **优化前行为(问题)** | 重构前这个场景的具体错误表现 | "步骤 5 拿到空字符串直接崩溃,返回 exit code 139" |
| **优化后期望行为** | 重构后这个场景的正确行为 | "步骤 5 检测到空字符串时返回明确错误信息 '输入不能为空',exit code 0" |
| **检测方法** | 怎么自动化复现 | "执行 sample_CASE_05,断言 stderr 含 '输入不能为空',assert exit code != 139" |

### 1.2 最小必覆盖场景

| 场景类别 | 至少应覆盖 |
|---------|-----------|
| **诊断中每个 CRITICAL/HIGH finding** | 1 个 R-N 对应(用于证明 fix 生效) |
| **Skill 核心 happy path** | ≥ 3 个 E-N(用于证明非退化) |
| **历史曾经修过的问题** | ≥ 2 个(防止重构重新引入历史 bug) |
| **相邻/类似功能** | ≥ 2 个(防止修改一处破坏另一处) |

### 1.3 回归场景登记表示例

```markdown
## 8.2 回归检测

| # | 场景 | 优化前行为(问题) | 优化后期望行为 | 检测方法 |
|:--:|------|----------------|---------------|---------|
| R-01 | finding_dim3_2:SKILL.md L142 输入校验缺失 | 步骤 5 拿到空字符串直接崩溃 | 返回明确错误信息,exit 0 | sample_CASE_05 + grep stderr |
| R-02 | finding_dim7_1:输出格式不统一 | 输出含 12 种不一致字段 | 输出符合 templates/report.md | 解析输出 + 对照 schema |
| R-03 | 历史 issue #234:批量输入超时 | 100+ 条输入下 timeout 60s | 100+ 条输入 < 30s | benchmark_100.sh |
| R-04 | finding_dim8_2:references/loading-attacks.md 未引用 | LLM 找不到注入类规则 | SKILL.md 含 "见 references/loading-attacks.md" | grep + 实际跑 1 个注入用例 |
```

## 2. Before / After / Reason 三段式 Delta

> 来源:`optimization-spec-template.md §5 + §6.3` + verification-checks.md SK-S6

**目的**:每条修改必须可追溯 — 改了什么、为什么改、改完预期效果。

### 2.1 三段式最小格式

```markdown
### Change #{N}:{变更标题}

**变更范围**:SKILL.md L{N}-{M}({章节名})或 {文件路径}

**Before**:
​```
{原内容,精确到行号或代码块,无歧义}
​```

**After**:
​```
{新内容,与 Before 一一对应}
​```

**Reason**:
- 对应诊断:{diagnosis-report.md 中的 finding_id,例如 dim3_finding_2}
- 根因:{一句话解释为什么这样改能解决 finding}
- 预期效果:{重构后该 finding 应消失,可观测指标是 XXX}
```

### 2.2 反例与正例

| 反例 | 问题 | 正例 |
|------|------|------|
| 只写 "改进了描述" | 不知道改了什么、为什么改 | 写清 Before/After,Reason 指向 finding_id |
| Before/After 行号不对应 | 复盘时无法定位 | 用相同行号范围精确标注 |
| Reason 空泛("为了优化") | 不可验证 | 写 "预期分数从 75 → 85,可被 R-01 验证" |

### 2.3 skillx-alpha-agents 中的落地位置

- 静态优化器:`scripts/optimizers/static_optimizer.py` 生成 `proposal.md` 时,每条 mod 字段应包含三段式
- 演化优化器:`scripts/orchestrator.py` 在 `round_N/proposal.md` 中应包含三段式
- 验证时:`delta-diff.md`(若有)或 `proposal.md` 作为 SK-S6 检查对象

## 3. Spec 一致性(SK-S5 详细内容)

**目的**:重构后的实际文件变更必须与 `optimization-spec.md §5 变更清单` 完全一致,**没多改也没少改**。

### 3.1 双向比对逻辑

```
spec §5 列出的变更 = S
实际 diff 命中的文件 = D

多改 = D - S  (spec 没列出但改了 → 可能是擅自修改)
漏改 = S - D  (spec 列出了但没改 → 可能是 builder 漏执行)
```

### 3.2 自动化检查脚本

```bash
# 1) 提取 spec §5 列出的目标文件
SPEC_FILES=$(awk '/^## 5\./,/^## 6\./' optimization-spec.md | \
  grep -oE '`[A-Za-z0-9_./-]+\.(md|py|sh|json|yaml|yml)`' | \
  tr -d '`' | sort -u)

# 2) 提取实际 diff 的文件
ACTUAL_FILES=$(git diff --name-only before_skill/ after_skill/ | sort -u)

# 3) 多改(擅自修改)
echo "=== 多改(应删) ==="
comm -23 <(echo "$ACTUAL_FILES") <(echo "$SPEC_FILES")

# 4) 漏改(spec 列出但未执行)
echo "=== 漏改(应补) ==="
comm -13 <(echo "$ACTUAL_FILES") <(echo "$SPEC_FILES")
```

### 3.3 失败处理

| 失败类型 | 处理 |
|---------|------|
| 多改(builder 擅自改) | **回滚**额外修改 → 应用 spec 列出的变更 |
| 漏改(builder 漏执行) | **补做**漏掉的变更 → 重跑 SK-S1~S4 |
| 双方都匹配 | PASS |

## 4. 引用完整性 100% 检查(SK-S2 强化版)

> 2026-06-23 治理后强制项,直接回答"重构后是否破坏"

### 4.1 检查范围

SKILL.md 中**所有本地路径引用**(不论以何种形式出现):

| 引用类型 | grep 模式示例 | 验证方法 |
|---------|--------------|---------|
| `references/` | `references/[a-zA-Z0-9_./-]+\.md` | `[ -f "$p" ]` |
| `scripts/` | `scripts/[a-zA-Z0-9_./-]+\.(py\|sh)` | `[ -f "$p" ]` |
| `templates/` | `templates/[a-zA-Z0-9_./-]+\.md` | `[ -f "$p" ]` |
| `rules/` | `\rules/[a-zA-Z0-9_./-]+\.md` | `[ -f "$p" ]` |
| `commands/` | `\commands/[a-zA-Z0-9_./-]+\.md` | `[ -f "$p" ]` |
| `agents/` | `\agents/[a-zA-Z0-9_./-]+\.md` | `[ -f "$p" ]` |

### 4.2 通过标准

- **100% 存在 → PASS**
- **任一不存在 → HIGH FAIL,阻断**(要求补回)

### 4.3 一键脚本

```bash
SKILL="$1"
echo "=== 引用完整性检查 ==="
MISSING=0
grep -oE '(references|scripts|templates|rules|commands|agents)/[a-zA-Z0-9_./-]+\.(md|py|sh|json|yaml|yml)' \
  "$SKILL" | sort -u | while read -r p; do
    if [ -f "$p" ] || [ -d "$p" ]; then
      echo "OK: $p"
    else
      echo "MISSING: $p"
      MISSING=$((MISSING+1))
    fi
done
[ "$MISSING" -eq 0 ] && echo "PASS" || echo "FAIL: $MISSING 个引用断链"
```

## 5. 行为层等效性验证(分数不退化)

> 这是**回答"是否被破坏"的最强证据**:跑同一组 CASE,对比分数。

### 5.1 skillx-alpha-agents 中的回归验证流程

skillx-alpha-agents 天然提供此能力,无需额外配置:

```
refactor 完成
  ↓
run baseline 评测(CASE 集合 = C_refactor)
  ↓  (利用已有 baseline/run_N/score.json)
run refactor 后评测(同一组 CASE)
  ↓
对比分数:
  - score_after ≥ score_baseline → PASS(不退化)
  - score_after < score_baseline → FAIL → revert
```

### 5.2 评分对比标准(与 COSIGHT.md §10 一致)

| 分数对比 | 判定 | 处理 |
|---------|------|------|
| score_after > score_baseline | ✅ 提升 | 保留重构,更新 best_skill/ |
| score_after == score_baseline | ✅ 持平 | 保留重构(若 Token 节省 ≥ 30%) |
| score_after < score_baseline - 5% | ⚠️ 轻度退化 | 人工审查,可选 revert |
| score_after < score_baseline - 10% | ❌ 明显退化 | **强制 revert** 从 before_skill/ 恢复 |

### 5.3 R-01 ~ R-N 场景的具体执行

每个 R-N 场景必须能在重构后的 Skill 上跑通:

```bash
# 对 R-N 设计一个可执行的验证脚本
test_R_01() {
  local input="$1"
  local expected_stderr="$2"
  local expected_exit="$3"

  actual_stderr=$(echo "$input" | bash run_skill.sh 2>&1 >/dev/null)
  actual_exit=$?

  if echo "$actual_stderr" | grep -q "$expected_stderr" && [ "$actual_exit" -eq "$expected_exit" ]; then
    echo "R-01 PASS"
  else
    echo "R-01 FAIL: stderr='$actual_stderr' exit=$actual_exit"
  fi
}

# 用诊断中找到的问题输入执行
test_R_01 "" "输入不能为空" 0
test_R_01 "valid_input" "" 0
```

### 5.4 通过标准

- R-01 ~ R-N 中每个场景都通过
- 整体分数 ≥ baseline - 5%
- N/A 分数(空 case)按 §10.5 归零处理,不计入退化判定

## 7. 执行流程(端到端)

```
refactor 完成
  │
  ├─ Step 1: 提取 refactor 涉及的变更清单
  │    └── delta-diff.md / proposal.md 中的 Change #N
  │
  ├─ Step 2: 跑 SK-S1~S11 静态验证(见 docs/重构后检查-Skill完整性验证.md)
  │    └── CRITICAL 失败 → 阻断 + revert
  │
  ├─ Step 3: 检查引用完整性 100%(本文件 §4)
  │    └── 任一断链 → 补回 → 重跑
  │
  ├─ Step 4: 检查 Spec 一致性(本文件 §3)
  │    └── 多改/漏改 → 回滚额外 / 应用遗漏
  │
  ├─ Step 5: 检查 Delta 三段式(本文件 §2)
  │    └── 缺 Reason → 自动补录 / 人工补充
  │
  ├─ Step 6: 行为层等效性验证(本文件 §5)
  │    ├── 跑 R-01 ~ R-N 场景,每个 PASS
  │    └── 跑 baseline 对比,分数 ≥ baseline - 5%
  │
  ├─ Step 7: 生成验证报告(本文件 §6)
  │
  └─ Step 8: 决策
       ├── overall_verdict == PASS + 分数不退化 → 接受重构 → 更新 best_skill/
       └── 任一失败 → revert 到 before_skill/,记录到 score_history.md
```

## 8. 与 skillx-alpha-agents 工作的衔接

| skillx-alpha-agents 场景 | 应用本文档 |

## 11. 实战 R-N 场景:两类典型退化案例(2026-07)

> 2026-07 组件间流程设计 Skill 重构后暴露的两类 F1 退化,作为后续 R-N 场景设计的「必含项」。

### 11.1 R-ScriptLink 场景:脚本 source 链错位

| 字段 | 内容 |
| --- | --- |
| **复现什么诊断问题** | 重构时合并 `config.sh` → `lib.sh`,但 5 个脚本里的 `if [ -f config.sh ]` 块未更新,导致脚本直接 exit 1,后续步骤输入丢失 |
| **重构前行为** | `bash scripts/extract_design_input.sh 公共调度功能 SPA` 正常返回,生成 63 行 `子系统间设计.md`,含 8 条表格 |
| **重构后期望行为** | 同样调用返回,生成等价的子系统设计文件 |
| **检测方法** | `bash scripts/extract_design_input.sh "<用例>" "<子系统>"` 后 `wc -l` 输出文件行数;断言 ≥ 50 行;且 `grep -c "^|"` 表格行数 ≥ 5 |

**自动检测脚本**:
```bash
test_R_scriptlink() {
  local req_id="$1"
  local subsystem="$2"
  local out=$(bash scripts/extract_design_input.sh "$req_id" "$subsystem" 2>&1)
  local table_count=$(grep -c "^|" .skillx_state/组件间流程设计/子系统间设计.md)
  if [ "$table_count" -ge 5 ]; then
    echo "R-ScriptLink PASS: $req_id ($table_count 表格行)"
  else
    echo "R-ScriptLink FAIL: $req_id (只 $table_count 表格行,预期 ≥ 5)"
  fi
}
test_R_scriptlink "随机接入管理_用例_公共调度功能_SIB1流程" "SPA"
test_R_scriptlink "PDSCH信道管理_场景切片5:PDSCH与DMRS复用" "SPA"
test_R_scriptlink "AMC管理_下行AMC_业务切片与UE能力配置" "SPA"
```

def test_R_midlayer(c_file, r_file):
    c_components = parse_table_components(c_file)  # 提取 (源, 目标) 对
    r_components = parse_table_components(r_file)

### 11.3 必含 R-N 场景类别(基于实战补充)

| 场景 | 复现问题 | 必含? |
|------|---------|:----:|
| **R-ScriptLink** | 脚本 source 链错位 | ✅ 必须 |
| **R-MidLayer** | 中间层被 Agent 跳过 | ✅ 必须 |
| **R-Description** | description 触发词丢失,Skill 不被 Agent 匹配 | 沿用 §1.2 |
| **R-HardConstraint** | 硬约束(步骤日志/Procedure 完成校验)未生效 | 沿用 §1.2 |
| **R-MultiHop** | 多跳链路(MCC → 中间层 → RKC → 中间层 → UPA) | ✅ 必须 |
| **R-BackwardCompat** | 重构后旧调用方式(旧脚本名/旧路径)仍能工作 | 沿用 §1.2 |

**R-N 设计原则(基于两类退化的补充)**:
- **必须含「细节级」场景**(脚本调用、source 链)— 防止"结构通过,行为失败"
- **必须含「完整链路」场景** — 防止 Agent 简化路径
- **必须含「早退检测」场景** — 防止 RAN-6165989 类异常(0 产出 + 0 F1)

## 12. R-N 失败后的回滚决策树(实战补充)

```
R-N 失败
│
├── R-ScriptLink 失败(脚本 exit 1 / 输出空)
│   → 回滚 scripts/ 中的 source 链(保留 config.sh 作为 wrapper)
│   → 或:更新所有脚本的 if [ -f config.sh ] 块,删除整个 if
│
├── R-MidLayer 失败(C 跳过中间层)
│   → 在 router.md 中关键路径标 ⚠️ "必须包含中间组件"
│   → 在 SKILL.md §4 加一句 "不要简化链路,按 R 实际描述生成"
│
├── R-Description 失败(Skill 未触发)
│   → 恢复原 description 中的触发词
│   → 不能为了"简洁"丢失关键动词
│
└── R-HardConstraint 失败(早退 / 不写步骤)
    → 把硬约束从 SKILL.md 主体保留,不外移到 references
    → 或:在每个 Procedure 末尾加 "检查步骤 N.md 是否存在" 校验
```

**与本文档 §5.2 评分对比标准的关系**:
- R-ScriptLink / R-MidLayer 失败 → 立即 revert(对应 `score_after < score_baseline - 10%`)
- R-Description 失败 → 阻断级别,需要人工审查(可能跨多个 CASE 退化)
- R-HardConstraint 失败 → 高优先级(直接影响 F1)
