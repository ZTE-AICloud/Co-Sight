# 重构原则 ③ — Skill 性能优化与 Token 节省

> **来源**:AWS《Harness Agent Application Token》+ 通用工程实践(`AI_Skill性能优化与Token节省设计指导.md`)
> **用途**:重构阶段把「Skill 跑得更快、花得更少」落到具体可执行的优化动作
> **核心思路三句话**:**少传字、少跑大模型、少绕弯**

---

## 1. 总体优化地图

| 维度 | 优化方向 | 典型节省 | 优先级 |
|------|---------|---------|:------:|
| Skill 描述/加载 | 渐进式披露 + 描述压缩 + 延迟加载 | 60~80% Token | P0 |
| 记忆/上下文 | 分层记忆 + 上下文工程 4 项 + 精简返回值 | 40~60% Token | P0 |
| 模型调度 | 任务分级 + 动态路由(Haiku 下沉) | 60~70% 子任务成本 | P1 |
| 可观测性 | 3 层埋点 → 定位瓶颈 → 精准优化 | 间接(找对瓶颈) | P1 |
| 交互方式 | 编辑代替追加 + 沉淀固定背景 | 30~50% Token | P2 |

> **第一性原则**:**不观测就优化,等于盲人摸象**。在动手做以下任何优化之前,先用 §6 的三层埋点定位瓶颈在哪。

---

## 2. Skill 本身:瘦身 + 按需加载

### 2.1 渐进式披露(3 层加载)

不要把 Skill 全部内容一次性塞给模型,而是按"由浅入深"分层:

| 层级 | 内容 | Token 预算 | 加载时机 |
|------|------|-----------|----------|
| **第一层 元数据** | 名称 + 简介 + 触发词 | ~100 Token | Agent 启动 |
| **第二层 指令** | 使用方法、参数、约束 | < 5k Token | 匹配时 |
| **第三层 资源** | 完整脚本、参考文档、示例 | 按需 | 显式引用时 |

**效果**:从原本一次塞 15k Token 的描述,降到首次只需 3~5k Token,提速 3~5 倍。

**重构动作**:
- SKILL.md body 控制在 **2~5k Token**(约 300 行内)
- 详细规范、案例、脚本提取到 L3(`references/` / `scripts/` / `templates/`)
- L1 description 控制在 ~100 Token(30~1024 字符)

> **详见**:`重构原则-skill分层与目录结构.md` §2

### 2.2 描述压缩

冗长描述是**隐形税**,模型每轮都要解析一遍。

- 只保留「**做什么** + **何时用** + **关键触发词**」三要素
- 触发词用**动词**(创建 / 提取 / 转换 / 校验),别用 "处理相关任务" 这种模糊短语
- 描述控制在 **30~1024 字符**

**反例 vs 正例**:
```
❌ 反例: "这是一个通用 Skill,用于帮助用户在多种场景下处理各种代码相关任务"
   → 太宽泛,模型不知道何时触发

✅ 正例: "代码安全审查:检查 Python/JS 代码中的安全漏洞(SQL 注入、XSS、硬编码密钥)。
        当用户请求安全检查或提交前审查时触发。输入文件路径,输出 Markdown 报告。"
```

### 2.3 延迟加载,不要一次全塞

一次对话挂十几个 Skill,模型光是"看清单"就花不少时间。

- 根据用户意图**只暴露 2~3 个 Skill**,其他这次干脆不出现
- 通过**路由机制**动态加载,而不是全部塞进系统 Prompt
- skillx-alpha-agents 处理时,确保被评估/优化的 Skill 是**单 Skill 焦点**,而非批量对比

### 2.4 技能分级管理

按使用频度分两类:

- **核心技能**:高频使用,常驻(系统 Prompt 注入)
- **扩展技能**:低频使用,按需调用

**Skill 之间描述要去重合并**,避免同一能力在多个 Skill 里被反复描述。

### 2.5 任务合并,一次说清

"总结 + 提取要点 + 生成标题"分三次发,等于让模型重读三遍上下文。

- 多个相关操作**打包成一条指令**,一次性把参数给全
- 一个组合调用 > 三个零散调用

**对 skillx-alpha-agents 的启示**:`/skill_optimize` 的 evaluator 子任务应尽量**单次 LLM 调用 + 多维度联合评分**,而不是「先评 dim1 → 再评 dim2 → 再评 dim3」分轮调用。

## 3. 记忆与上下文:别让历史越积越厚

### 3.1 记忆分层(关键设计)

不要把全部对话历史塞给模型,要按"用得上 / 用不上 / 偶尔用"分四层:

| 记忆类型 | 内容 | 用途 | Token 预算 |
|---------|------|------|-----------|
| **语义记忆** | 用户身份、项目背景等稳定事实 | 长期复用 | 低频加载 |
| **情景记忆** | 过去某次交互的成败经验 | 偶尔参考 | 按需加载 |
| **用户偏好** | 格式、风格、术语习惯 | 每次都要用 | 必加载 |
| **摘要记忆** | 长对话阶段性总结 | 代替原文 | 压缩后加载 |

**效果**:分层记忆可降低记忆 Token 消耗 **40~60%**。

### 3.2 上下文工程四项基本功

| 技能 | 做法 | 收益 |
|------|------|------|
| **语义去重** | 同一事实不要在多轮中重复加载 | 减重复 Token |
| **分层摘要** | 旧对话压成阶段总结,细节可以丢 | 减长上下文 Token |
| **按需加载** | 用相关性评分决定要不要塞进当前轮 | 减不必要 Token |
| **Token 预算** | 给每次调用设上限,防止挤占模型主任务的算力 | 防预算溢出 |

### 3.3 控制会话长度

- 每 **15~20 轮**主动开新 Session
- 或设计"**总结机制**",每隔几轮让模型把对话压成一段阶段总结

**对 skillx-alpha-agents 的启示**:orchestrator 的迭代循环应有**轮次上限**(默认 5 轮,`max_rounds`),避免单次任务拖到上百轮耗尽 Token。

### 3.4 精简返回值(高频优化点)

Skill 执行完,不要把日志和底层数据全甩回模型。

- 系统日志、堆栈、原始字节流一律截掉
- 只返回「**对下一步决策有用的摘要**」:成功/失败 + 关键指标 + 必要证据

**反例**(子 Agent 返回 5000 行原始日志):
```json
{
  "stdout": "...(5000 行)...",
  "stderr": "",
  "exit_code": 0
}
```

**正例**(只返回关键摘要):
```json
{
  "status": "success",
  "score": 87.5,
  "gaps": ["dim3 名词一致性偏低", "dim7 步骤顺序错误"],
  "evidence": "phase3-eval/CASE-001/results.json: line 42"
}
```

## 4. 交互方式:少让模型重读

### 4.1 编辑原消息,别追加修正

"不对,我刚才的意思是……"这种追加指令,会让模型把整段历史重读一遍。

- 看到 AI 输出不对,**直接在原消息上改**,再让它重新生成
- 改写比追加省 **30%~50% Token**

**对 skillx-alpha-agents 的启示**:orchestrator 在重新生成优化提案时,**应基于上一轮 proposal 而非重新探索**(prev_failure 注入),避免整段历史重读。

### 4.2 把"固定背景"沉淀到系统层

角色设定、用户偏好每次都重复说一遍,等于每次都在花钱抄写。

- 用**系统级 Prompt 或 Memory 机制**固化
- 用户层只发"这次要做什么",不要重述"我是谁、喜欢什么格式"

## 5. 模型调度:把贵的留给难的

### 5.1 任务分级 + 动态路由

不是所有任务都需要最强模型。

| 任务类型 | 推荐模型 | 理由 |
|---------|---------|------|
| 轻量任务(解析、排版、格式转换) | **Haiku** | 便宜快,Sonnet 90% 能力 |
| 复杂决策(规划、推理、创作) | **Sonnet/Opus** | 需要深度推理 |
| 60~70% 的子任务 | **可下沉到小模型** | 经验值 |

**对 skillx-alpha-agents 的启示**:
- 评测执行(不调 LLM,只跑业务命令):不需要大模型
- 评分提取(填空式两阶段):**可下沉到 Haiku**(事实提取,不需要创造力)
- 优化/分析(生成优化提案、诊断):**保留 Sonnet/Opus**(需要权衡推理)

### 5.2 关掉不必要的附加功能

联网搜索、深度推理等高级能力**不是默认就开**。

- 用不到检索时,**关闭 Web Search**,省下每轮搜索 Token
- 简单问题不要硬上"深度思考"
- 子 Agent prompt 中明确禁止不必要的工具调用

## 6. 可观测性:不埋点就优化不动

不观测就优化,等于盲人摸象。建议在三层都埋点:

| 层级 | 观测什么 | 工具 |
|------|---------|------|
| **模型调用层** | 每次 LLM 调用的 Token、耗时、错误 | 监控平台(CloudWatch / 自建) |
| **Agent 执行层** | 任务/步骤级 tracing,定位卡哪一步 | Agent 框架自带(Langfuse 等) |
| **Prompt 构建层** | 当前上下文的组成、谁贡献了多少 Token | 框架内部埋点 |

**没有这三层数据,任何"我觉得这里慢"都是凭感觉,改完也不知道对不对**。

**skillx-alpha-agents 已落地的可观测性**:
- ✅ `task_state.json`:Phase 状态机 + 重试次数
- ✅ `config.json.history`:每轮分数 + gaps + 优化 mod
- ⚠️ **建议补充**:每 LLM 调用的 {model, input_tokens, output_tokens, latency, status} 字段

## 7. 落地前要回答的两个问题

任何优化动手前必答:

### 7.1 慢在哪里?

| 现象 | 优化方向 |
|------|---------|
| 单次执行慢 | 重点看 Skill 描述、模型选型、上下文窗口 |
| 历史累积长导致贵 | 重点看会话管理、记忆分层 |

### 7.2 Skill 是哪类活?

| 类别 | 典型瓶颈 | 优化重点 |
|------|---------|---------|
| **代码生成** | 工具调用次数 | 减少 tool call(合并命令、缓存结果) |
| **数据分析** | 数据量大 | 分块处理 + 流式返回 |
| **文本客服** | 上下文长度 | 摘要压缩 + 检索增强 |
| **工具编排**(skillx-alpha-agents) | 多 Agent 协调 | 减少串行 LLM 调用,合并并行任务 |

## 8. 效果对照表(可作为优化目标)

| 优化项 | 优化前 | 优化后 | 验证方法 |
|--------|--------|--------|----------|
| 技能描述 Token | 15k(每次全量) | **3~5k(分层披露)** | `wc -c SKILL.md` + 估算 token |
| 记忆管理 Token | 全部上下文 | **降 40~60%** | 对比有无 memory layering 的 Token 数 |
| 多轮追加修正 | 整段重读 | **省 30~50%** | 对比 edit-in-place vs append 的差异 |
| 子任务 Haiku 下沉 | 全用 Sonnet | **60~70% 子任务省 3x 成本** | 统计子 Agent 模型分布 |
| 返回值精简 | 5000 行原始日志 | **10 行 JSON 摘要** | 对比 stdout 体积 |

## 9. 配套机制(可选但推荐)

| 机制 | 做法 | 收益 |
|------|------|------|
| **版本管理** | Skill 描述/参数改动要可追溯,出问题能快速回滚 | 防止优化变劣化 |
| **基准测试集** | 准备一组典型问题,优化前后跑同一组对比 | 量化优化效果 |
| **分级发布** | 优化先灰度给内部或少量客户,确认效果再全量 | 防止线上回归 |
| **基线对比** | skillx-alpha-agents `baseline/` 目录天然提供此能力 | 重构前/后跑同一组 CASE |

## 10. 与 skillx-alpha-agents 工作的衔接

| 场景 | 本原则的应用 |
|------|------------|
| **OptimizerGateway 生成 mod** | mod 字段注明「本次重构节省的 Token 数」+ 「对应的优化模式(A/B/C/2.x)」 |
| **EvaluatorAgent 评分** | dim11_efficiency 维度:按本原则 2.1~2.5 评估 Skill 的瘦身程度 |
| **RefactorAgent(规划)** | 重构优先级 = (本原则节省 Token) × (本原则适用频度) |
| **Orchestrator 调度** | 子 Agent 路由 = 轻量(解析/提取)→ Haiku,复杂(优化/规划)→ Sonnet |
| **回归验证** | 重构前后跑同一组 CASE,对比 baseline/score 与 baseline/score_after 差异 |

> **关键约束**(参见 COSIGHT.md §10):重构后**分数不能比 baseline 低**。优化 Token 节省的同时,必须用评测分数证明能力不退化。skillx-alpha-agents 的 `score_history.md` + `task_state.json` 提供天然对比基线。

## 11. 重构阶段必跑的三层校验

```
优化前:
1. 跑 baseline 评测 → 记录 score + Token 用量
2. 跑 score_analyzer → 定位瓶颈(描述过长 / 子 Agent 重复调用 / 返回值过大)

优化中:
3. 按本原则选择对应的优化模式(2.x / 3.x / 5.x)
4. 应用 mod,记录节省的 Token / 时间

优化后:
5. 跑同一组 CASE → score ≥ baseline?Token 节省 ≥ 30%?
6. 若 score 退化 → 回滚 mod(参见 COSIGHT.md §10 退化处理)
7. 若 score 持平/提升 → 保留 mod,更新 score_history.md
```

> **不要做没验证过的优化**。本原则给出的所有数据(40~60% / 30~50% / 3~5 倍)是经验值,具体项目的节省幅度以**自己的基线对比**为准。

## 12. 实战数据 vs 经验值的对比(2026-07 组件间流程设计 Skill 重构)

> 经验值 40~60% Token 节省是基于描述压缩和分层加载。**实际项目**中,SKILL.md 描述压缩的 Token 节省,**可能伴随**其他维度的代价。

### 12.1 实际数据(6 需求平均值)

| 维度 | 经验值预期 | 实际值 | Δ |
| --- | --- | --- | --- |
| SKILL.md 体积 | -30% ~ -50% | **-55.6%**(243 → 108 行) | 略好于预期 |
| 单 Skill Token | 3~5k(分层后) | 未单独测 | — |
| 任务耗时 | 略减少 | **-29.6%**(31791s → 22377s) | 略低于预期 |
| 工具调用次数 | 减少 | **+52.9%**(1218 → 1862) | **反直觉** |
| Write 次数 | 减少 | **+107.1%**(141 → 292) | **反直觉** |
| 输出体积 | 减少 | **+149.5%**(759KB → 1895KB) | **反直觉** |
| F1 平均 | 持平或提升 | **+1.68**(17.22 → 18.90) | 略好 |

### 12.2 「Token 节省」与「调用次数 / 输出体积」的反直觉关系

按 §2.1 期望,SKILL.md 精简 55% 应带来**调用次数减少**。**实测反而 +52.9%**。原因:

1. **「按需加载」机制副作用**:精简 SKILL.md 把路径从主入口搬到 references/,Agent 每次决策需额外 Read references
2. **「硬约束」副作用**:SKILL.md §4 强制每步写「步骤 N.md + 步骤 N.log」,5 Procedure × 2 文件 = 10 Write/需求,Write 翻倍
3. **「路径外移」副作用**:scripts/ 路由从 SKILL.md 移到 scripts/README.md,Agent 多次 `find` / `ls` 探索

**但单次调用耗时降 -54%**:
- SKILL.md 短 → 上下文聚焦 → LLM 思考更快
- 「步骤日志」模板化生成,决策成本低
- 不再「瞎转圈」(不再反复 Read 主入口找路径)

**结论**:**「调用次数」和「耗时」是反相关的,「Token 优化」和「调用次数」也是反相关的**。优化 SKILL.md 后,不能单独看「调用次数」,必须看「总耗时」和「输出质量」。

### 12.3 对本文档的修正建议

| 维度 | 经验值 | 修正值 | 备注 |
| --- | --- | --- | --- |
| 任务耗时 | 略减少 | **-30% ~ -50%** | 实际验证可达成 |
| 工具调用次数 | 应减少 | **可能 +30% ~ +100%** | 「按需加载」副作用 |
| 输出体积 | 应减少 | **可能 +50% ~ +150%** | 「硬约束」副作用 |
| F1 分数 | 持平或提升 | **可能持平、微涨、或个别需求退化** | 必须配 R-N 场景验证 |

### 12.4 与 §2.1 渐进式披露的关系

§2.1 说「少传字」→ Token 减少。**但「少传字」不直接等于「少调用」**。Agent 拿到精简主入口后,会**主动探索** references、**主动校验** 步骤文档、**主动确认** scripts 路径。

**这与 §2.1 不矛盾,但要补充**:**精简后必须配合「硬约束」(§6.1 重构原则 ② 的硬约束保留)**,否则 Agent 探索后不写步骤文档,会「跳过中间层」导致 F1 退化(参见 `重构原则-skill分层与目录结构.md` §10.2)。

### 12.5 落地动作

`/skill_optimize` 在跑 Token 优化 mod 时:

1. **不要把「调用次数减少」作为优化目标** — 它会因按需加载副作用反增
2. **把「总耗时减少」作为优化目标** — 它是「调用次数 × 单次耗时」的综合,更稳定
3. **必须配 R-N 场景验证 F1 不退化** — 即使耗时降了,如果 6 需求中 2 个 F1=0,也是失败
4. **每个 mod 记录**「预期耗时降低 X%,预期 Token 节省 Y%」,实际跑后对比

## 13. ❌ 禁止为"规范化"增加过程性 print/log 节点

> **这是 2026-07-08 在组件间流程设计 Skill 重构时观察到的反模式**

### 13.1 现象

LLM 重构 Skill 时,倾向加这类"看起来更规范"的过程性输出:

```python
# ❌ 反例:为"展示流程"而加的 print
print(f"[INFO] 步骤 1/5 开始:解析输入")
print(f"[INFO] 步骤 1/5 完成,耗时 0.3s")
print(f"[INFO] 步骤 2/5 开始:校验 Schema")
...
print(f"[INFO] 全部 5 步完成,总耗时 1.5s")
```

```bash
# ❌ 反例:shell 脚本里 echo "checkpoint"
echo "=== [CHECKPOINT] step 1: validate input ==="
echo "=== [CHECKPOINT] step 2: parse json ==="
...
```

```markdown
## 执行日志
- 步骤 1: ✅ 完成
- 步骤 2: ✅ 完成
- 步骤 3: ⏳ 进行中
...
```

LLM 加这些的动机是"让用户看到流程"、"显得专业"、"对标工程规范"。**这种动机是错的**。

### 13.2 为什么不能加

| 维度 | 代价 |
|------|------|
| **Token 消耗** | 每个 print 节点输出几十~几百 token,N 个节点 × 每次调用 = 显著 token 税 |
| **上下文污染** | Skill 执行历史被淹没在过程性输出里,**真正有用的结构化结果被稀释** |
| **认知负担** | 用户 review 报告时,90% 时间在跳过"步骤 X 开始/完成"这类废信息 |
| **固化幻觉** | LLM 把"加 print 节点"当成了"重构做得好"的标志,实际是噪声 |

**用户真正关注的是**:
- Token 消耗
- 任务成功率(F1 / 准确率)
- 总耗时
- 最终结构化产出(报告 / JSON / 文件)

**用户不关注**:
- "步骤 1/5 开始"
- "正在处理 XX"
- "已完成 100%"

### 13.3 修正后的重构原则

| 原则 | 做法 |
|------|------|
| **零过程性 print** | Skill 脚本里**禁止** print / echo / log.info 写"步骤 X 开始/完成" |
| **静默执行** | 正常路径下 Skill 不输出任何过程信息,只在出错时输出 error |
| **结构化结果** | 一次性输出最终结构化结果(报告 / JSON / 文件路径) |
| **调试另开通道** | 需要调试时走 `--verbose` / `DEBUG=1` 环境变量,默认关闭 |
