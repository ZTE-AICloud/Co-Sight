## 一、产品是什么

### 1.1 一句话定义

skillx-alpha-agents 是一套 **AI Agent 评测-优化闭环编排器(Harness)**:把业务方提供的"评测命令"包装成自动化迭代循环,**让 Skill 像工程师一样被反复打磨,直到达标**。

### 1.2 核心模型

```
评测 → 提取分数和缺口 → 生成优化提案 → 应用 → 再评测 → 直到达标
```

工具读取业务方提供的 Skill、评测命令、业务配置,自动在沙箱里反复执行"测、看、改、验、循环"。整个过程不需要人干预。

### 1.3 关键事实

- **通用 Harness**:不绑定具体业务,通过配置适配
- **配置即接入**:换业务只改 YAML,不碰框架代码
- **可联合**:支持 Agent 级多 Skill 联合优化
- **可追溯**:每轮产物、分数、提案全部留痕

## 二、解决什么问题

### 2.1 行业现状痛点

| 痛点 | 表现 |
|------|------|
| **人工调优效率低** | 资深工程师改一份 Skill 几天起步,反复跑评测占满时间 |
| **效果无法量化** | 改完"好不好"靠人工抽样,主观且样本量小 |
| **业务接入成本高** | 换评测场景要重写框架,投入产出比差 |
| **多 Skill 难协同** | 各 Skill 单独优化好,端到端组合却掉链子 |
| **优化过程不透明** | 改了什么、为什么改,事后无法回溯 |

### 2.2 产品价值主张

| 价值 | 体现 |
|------|------|
| **效率** | "周级"人工调优压缩到"小时级" |
| **客观** | 基于评测分数决策,不靠"我觉得" |
| **可复用** | 换业务只改配置,不需改框架代码 |
| **可协同** | Agent 级多 Skill 联合优化 |
| **可追溯** | 每次改动版本、分数、原因都留痕 |
| **可扩展** | 评测管道灵活,业务方决定怎么评,工具只负责编排 |

## 三、核心能力

| 能力 | 说明 |
|------|------|
| **评测-优化闭环** | 沙箱里反复执行"评测→提案→应用",自动循环直到达标 |
| **配置化接入** | 一份 YAML 声明产物结构、算分规则、错误处理,零代码改动 |
| **多模式适配** | 单 Skill 模式 + 多 Skill (Agent) 联合模式 |
| **沙箱隔离执行** | 每轮独立沙箱,不污染业务环境,产物归档,可回滚 |
| **透明可追溯** | 每轮快照、分数、提案、候选全部留痕,产物目录清晰 |
| **评分与归因** | 不止给总分,还按 case 拆分、识别缺口、生成诊断 |

### 3.1 评测-优化闭环

工具在沙箱中反复执行业务方的评测命令,根据分数自动生成优化提案,审批通过后应用到 Skill,继续下一轮迭代。整个过程无需人工干预。**关键特性**:自动循环、每次独立沙箱互不干扰、达标或达到最大轮次自动终止。

### 3.2 配置化接入,零代码改动

业务方**只需要写一份 YAML 配置**声明评测产物结构、提取规则、错误处理,即可接入工具。**对比**:传统方式换业务 = 重写框架代码,本工具换业务 = 改一份 YAML。

### 3.3 多模式适配

支持两种优化模式:
- **单 Skill 模式**:针对单个 Skill 做独立优化
- **多 Skill (Agent) 模式**:针对一个 Agent 下的多个 Skill 做联合优化

**关键差异**:单 Skill 直接针对该 Skill 反复迭代;多 Skill 一起跑端到端,基于聚合分数统一决策。

### 3.4 沙箱隔离执行

每次评测在独立沙箱中运行。**隔离维度**:
- **Skill 工作副本隔离**:每个任务有自己的副本,不污染业务原文件
- **产物目录隔离**:每次评测的产物独立归档,不会读到上次残留
- **执行环境隔离**:并发任务之间互不干扰

**价值**:安全、可回滚、可并行。

### 3.5 透明可追溯

每一轮的 Skill 快照、评测分数、优化提案、候选方案与对比全部持久化,产物目录结构清晰,可随时回看。

### 3.6 评分与归因

工具不止给出"最终分数",还会按评测用例拆分、识别低分缺口点、生成诊断报告,帮业务方理解"为什么是这个分"。

## 四、适用场景

### 4.1 推荐使用

✅ **已有评测管道** ✅ **Skill 内容可调** ✅ **有明确评测标准** ✅ **多 Skill 联合优化** ✅ **长期持续优化**

### 4.2 不推荐使用

❌ **没有评测管道** ❌ **优化目标不是 Skill** ❌ **一次性场景** ❌ **评测不稳定**

### 4.3 决策清单

业务方在引入前自问:

- [ ] 我有可反复跑的评测命令吗?
- [ ] 评测命令能给出 0~1 或 0~100 的量化分数吗?
- [ ] 我愿意写一份 YAML 声明产物结构吗?
- [ ] 我能接受数小时级别的自动化迭代吗?
- [ ] 优化目标是 SKILL.md 这类文档吗?

**如果 ≥ 4 项选"是",强烈推荐使用。**

## 六、关键特性详解

### 6.1 评测-优化闭环

![图 6-1 评测-优化闭环流程](figures/产品手册-图6-1-闭环流程.png)

*PDF 版本:[产品手册-图6-1-闭环流程.pdf](figures/产品手册-图6-1-闭环流程.pdf)*

工具按"基线 → 候选 → 优化 → 下一轮"循环。**终止条件**:分数达标(默认 100)或达到最大轮次。

---

### 6.2 双模式优化

![图 6-2 单 Skill 模式 vs 多 Skill (Agent) 模式](figures/产品手册-图6-2-单vs多Skill模式.png)

*PDF 版本:[产品手册-图6-2-单vs多Skill模式.pdf](figures/产品手册-图6-2-单vs多Skill模式.pdf)*

| 模式 | 适用 | 关键差异 |
|------|------|---------|
| **单 Skill** | 单个独立 Skill | 直接针对该 Skill 反复迭代 |
| **多 Skill (Agent)** | Agent 内多 Skill 联合优化 | 所有 Skill 一起跑端到端,基于聚合分数统一决策,整体考虑进行迭代 |

**关键**:多 Skill 模式不是"各自优化再求平均",而是"端到端一次跑完,基于整体效果决策"。

---

### 6.3 沙箱隔离

![图 6-3 沙箱隔离机制](figures/产品手册-图6-3-沙箱隔离.png)

*PDF 版本:[产品手册-图6-3-沙箱隔离.pdf](figures/产品手册-图6-3-沙箱隔离.pdf)*

**隔离层级**:任务工作空间(跨任务) → 沙箱(跨轮次) → 执行环境(跨次)。**价值**:安全、可回滚、可并行。

---

### 6.4 透明可追溯

每一轮都归档:
- **Skill 快照**:优化前/优化后,任何时候可对比 diff
- **评测分数**:每个用例单独打分,可定位短板
- **候选方案**:每个候选独立存档,事后可复盘"如果当时选了另一个"
- **优化提案**:本轮"为什么改、改了什么、预期效果"全部留痕

工具自动生成诊断报告,识别失分点和建议修复方向,辅助业务方定位优化空间。

## 七、典型应用场景

![图 7-1 skillx-alpha-agents 典型应用场景](figures/产品手册-图7-1-场景象限.png)

| 场景 | 业务背景 | 典型用法 |
|------|---------|---------|
| **AI 测试用例生成 Skill 优化** | 测试用例智能体的 SKILL.md 优化,目标是让生成的用例更准确、更完整 | 单 Skill 模式迭代,3~5 轮 |
| **多 Skill 联合优化** | SDD 需求分析 Agent 内多个 Skill(变更点、用例筛选、文件检索)互相影响 | 多 Skill 模式联合优化 |

| **Prompt 工程自动化** | "Prompt" 就是一份 SKILL.md,想自动化迭代 | 同通用 Skill 优化 |
| **多版本 Skill 对比** | 有多个 SKILL.md 候选,不知道选哪个上线 | 批量跑评测,对比分数 |

## 八、与传统方式对比

![图 8-1 人工调优 vs skillx-alpha-agents 多维度对比](figures/产品手册-图8-1-多维度对比雷达.png)

*PDF 版本:[产品手册-图8-1-多维度对比雷达.pdf](figures/产品手册-图8-1-多维度对比雷达.pdf)*

| 维度 | 传统人工调优 | skillx-alpha-agents |
|------|------------|---------------------|
| 时间效率 | 半天到一天 | 几十分钟到几小时 |
| 评估客观性 | 人工抽样,易受主观影响 | 全量评测,每 case 单独打分 |
| 多 Skill 协同 | 几乎不可行 | Agent 模式联合优化 |
| 业务适配成本 | 改框架代码,侵入性强 | 改 YAML 配置,业务零侵入 |
| 专家综合能力(整体性思考、业务背景、Skill 重构、流程重构) | 强项 | 目前模型暂不能替代 |

> **诚实补充**:上表前 4 项是工具的相对优势——优势大小因业务而异,**评估越能全量量化、Skill 越能解耦为可独立迭代的模块,工具效果越明显**。第 5 项**专家综合能力**——整体性思考、业务背景知识、Skill 重构、流程重构等需要深厚领域积累与创造性判断的工作,**目前仍是人的强项、模型的弱项**。工具定位是放大专家能力,而非替代专家判断。

## 九、局限与边界

| 局限 | 说明 |
|------|------|
| **依赖评测质量** | 工具不能优化"无法量化"的目标,评测管道必须先有 |
| **依赖 Skill 形态** | 当前版本专精优化 SKILL.md,不能直接优化模型/架构 |
| **收敛速度受限于评测稳定性** | 评测分数波动大时工具会震荡,需先稳定评测 |
| **单点工具** | 只覆盖"评测→优化"环节,不替代评测框架本身 |
| **优化结果需人工复核** | 建议业务方 review 后再上线 |
| **不适用小规模场景** | 测试用例 < 5 时统计意义有限,建议 ≥ 5 |

## 九.5、性能与规模

| 维度 | 推荐范围 |
|------|---------|
| **测试用例数** | 5~100 个 |
| **单轮评测时间** | 几分钟到几小时 |
| **迭代轮次** | 1~10 轮 |
| **Skill 大小** | 几百行到几千行 SKILL.md |
| **单 Skill 模式** | 推荐 1~5 个 Skill |
| **多 Skill 模式** | 推荐 2~5 个 Skill |

**资源占用**:磁盘每轮几 MB~几 GB(取决于评测命令);内存/CPU 主要看评测命令,工具本身占用很小。**性能调优**:评测命令单次跑不超过 30 分钟;`--runs` 3~5 次足够稳定;`--candidates` 3~10 个通常足够。

**安全与合规**:工具在本地运行,产物留在本机;沙箱隔离避免污染业务环境;不主动修改业务原 Skill,只在工作副本中改;不会自动部署上线,产出需业务方手动 apply。模型调用通过环境变量注入 API key,不硬编码。

## 十、价值实现路径

![图 10-1 skillx-alpha-agents 价值实现四阶段路径](figures/产品手册-图10-1-四阶段路径.png)

*PDF 版本:[产品手册-图10-1-四阶段路径.pdf](figures/产品手册-图10-1-四阶段路径.pdf)*

### 10.1 引入路径四阶段

| 阶段 | 周期 | 关键动作 | 预期产出 |
|------|------|---------|---------|
| **试点** | 2~4 周 | 选 1 个 Skill,跑 1~2 轮 | 验证可行性,确认分数提升 |
| **验证** | 1~2 个月 | 对比优化前后效果,固化配置 | 沉淀经验,确立基线 |
| **扩展** | 2~3 个月 | 推广到 5~10 个 Skill,启用多 Skill 模式 | 覆盖更多业务场景 |
| **标准化** | 3~6 个月 | 嵌入日常工作流,按需触发 | 形成"Skill 持续优化"机制 |

### 10.2 评估 ROI 的关键指标

**Skill 分数提升** / **迭代效率** / **人力节省** / **覆盖率** / **业务影响**(间接体现)。

### 10.3 风险与缓解

| 风险 | 缓解 |
|------|------|
| 评测不稳定 | 先稳定评测再加自动化 |
| Skill 内容敏感 | 提案人工 review |
| 配置错误 | 配置验证、最小可用配置起步 |
| 效果不达预期 | 试点验证后再扩展 |

## 十一、术语表

| 术语 | 含义 |
|------|------|
| **Skill** | 一份 SKILL.md 文档,描述 Agent 在某个场景下应如何工作 |
| **评测管道** | 业务方提供的一段 shell 命令,运行后产出评测结果 |
| **基线** | 用当前 Skill 跑评测得到的初始分数,作为起点 |
| **候选** | 工具对 Skill 的一个变体,可能比原版好或坏 |
| **优化提案** | 工具基于差距分析生成的下一轮优化方向描述 |
| **沙箱** | 每次评测的隔离执行环境 |
| **单 Skill 模式** | 优化单个 Skill 的模式 |
| **多 Skill 模式(Agent 模式)** | 联合优化多个 Skill 的模式 |
| **聚合分数** | 多 Skill 模式下,所有 case 分数的平均 |
| **轮次(Round)** | 一次完整的"基线→候选→优化"循环 |
| **快照** | 某一时刻 Skill 的副本,用于版本管理和回滚 |

## 十二、常见误解澄清

| 误解 | 澄清 |
|------|------|
| "这是另一个 LLM 微调工具" | 本工具**不训练模型**,只优化 SKILL.md 这类文档 |
| "必须懂框架代码" | 业务方**只需要懂业务**,框架代码由维护者管 |
| "改了一次 Skill 就能变好" | Skill 优化是**迭代过程**,通常 3~5 轮才能稳定提升 |
| "多 Skill 模式就是同时跑多个 Skill" | 多 Skill 是**端到端一次跑完**,基于整体效果决策,不是各自跑最后平均 |
| "优化结果可以直接上线" | **强烈建议人工 review**(`proposal.md` + `round_N_after_skill/SKILL.md`) |
| "跑一遍就一劳永逸" | Skill 是**持续迭代**的,业务变化、用户反馈都需要重新优化 |
