## 一、三分钟快速跑通

### 1.1 你需要准备什么

| 准备项 | 必备 | 说明 |
|--------|------|------|
| 待优化的 SKILL.md | ✅ | 一份 Markdown 文档 |
| 评测命令 | ✅ | 一段 shell 命令,运行后能生成产物 |
| 配置文件 user-config.yaml | ✅ | 告诉工具"产物长什么样、怎么算分" |
| 测试用例 / 金标准 | ✅ | 评测命令的输入和期望输出 |

### 1.2 最简启动

```bash
/skill_evolve '你的评测命令'
```

### 1.3 怎么算"成功"

任务**正常结束**的标志(屏幕输出):

```
[finish] 任务完成,最终分数 X.X
```

任务目录在 `evolution_workspace/taskid_YYYYMMDD_HHMMSS/` 下,里面有完整的分数历史、最佳 Skill 副本、评测报告。

### 1.4 跑通后的下一步

| 情况 | 下一步 |
|------|--------|
| 分数已达目标 | 拿最佳 Skill 替换原文件上线 |
| 分数有提升但未达标 | 检查产物,人工微调 Skill,再跑一轮 |
| 分数没变或下降 | 检查配置,可能产物结构声明不对 |
| 任务报错 | 翻到第十章错误排查 |

## 二、配置文件怎么写

业务方唯一要写的配置文件:**`config/user-config.yaml`**(项目根目录)。

### 2.1 文件作用

告诉工具三件事:
- **产物结构**(structure):评测命令会生成什么目录/文件/JSON
- **算分规则**(extraction):从产物里提取哪些字段、怎么聚合
- **错误处理**(handling):数据缺失、解析失败时怎么办

### 2.2 三段自然语言声明

```yaml
score_extraction:
  structure: |
    产物在 data/phase3-eval/ 下,每个 JSON 含 total_score、case_id 字段。
  extraction: |
    读取每个 JSON 的 total_score,按 case_id 分组,所有 case 的算术平均作为总分。
  handling: |
    若 total_score 缺失则记 0,若文件无法解析则在 zero_root_cause 字段记录。
```

**只需写这三段自然语言**——工具会自己读产物、自己解析、自己算分。

### 2.3 配置文件查找顺序

1. 当前工作目录:`./config/user-config.yaml`(优先)
2. 项目根目录:`<项目>/config/user-config.yaml`
3. 框架默认模板(可能不准)

**建议**:在项目根目录维护一份,所有任务共用。

### 2.4 配置示例:三种形态

#### 形态 1:最简(产物固定)

```yaml
score_extraction:
  structure: "data/eval/ 下每个 JSON 含 score 字段(0~1)"
  extraction: "所有 JSON 的 score 求平均"
  handling: "缺失记 0"
```

#### 形态 2:标准(按 case 拆分)

```yaml
score_extraction:
  structure: |
    data/phase3-eval/ 下,文件名 {case_id}_results.json,每个 JSON 含
    total_score、case_id、metrics 子对象。
  extraction: |
    读取每个 JSON 的 total_score,按 case_id 分组,所有 case 算术平均。
  handling: |
    若 total_score 缺失,记 0 并在 zero_root_cause 记录 case_id。
```

#### 形态 3:高级(加权聚合)

```yaml
score_extraction:
  structure: |
    data/phase3-eval/ 下有两类文件:
    - {case_id}_results.json:case 级分数
    - summary.json:含 metadata.weights(各 case 权重)
  extraction: |
    读 summary.json 获取各 case 权重,读每个 {case_id}_results.json 的 total_score,加权平均。
  handling: |
    若 summary.json 缺失,降级为算术平均;若 case 级 JSON 缺失,记 0。
```

### 2.5 配置验证

```bash
# 跑一轮,看产物目录里的 score.json
cat evolution_workspace/taskid_xxx/baseline/run_1/score.json
# 检查 result_score 是否合理(不是 0 也不是 1)
```

## 三、启动任务详解

### 3.1 命令格式

```bash
/skill_evolve [选项] '评测命令'
```

### 3.2 常用选项

| 选项 | 含义 | 默认值 |
|------|------|--------|
| `--skill-path` | 待优化的 SKILL.md 路径 | 从评测命令自动推断 |
| `--rounds N` | 最大迭代轮次 | 5 |
| `--candidates N` | 每轮生成的候选方案数 | 5 |
| `--runs N` | 每个候选的评测次数(取平均) | 3 |
| `--agent-name 名字` | 多 Skill 模式下的 Agent 名称 | 自动推断 |
| `--workspace 路径` | 已有任务目录(用于恢复中断任务) | 自动创建新目录 |

### 3.3 启动流程

`/skill_evolve` 启动时会问三个问题:

| 问题 | 选项 |
|------|------|
| **评测范围** | 用命令行传入的 case 列表 / 调整子集 / 跑全量 |
| **清理目录** | 从配置读取 / 手动指定 |
| **产物结构配置** | 沿用 user-config.yaml / 我要修改 |

回答后,工具才会真正启动。

### 3.4 单 Skill 模式 vs 多 Skill 模式

```bash
# ★ 推荐(简化入参):cwd 显式拆出
/skill_evolve --skill-path /path/to/SKILL.md \
  --pipeline-base-dir /path/to/SDD评测 \
  --pipeline-eval-cmd 'python3 scripts/run_eval.py --req-id RAN-123'

# ★ 纯 shell 命令(明确"非 slash command",跳过 wrap/extract/warn)
/skill_evolve --skill-path /path/to/SKILL.md \
  --pipeline-base-dir /path/to/SDD评测Agent \
  --pipeline-eval-sh 'python3 run_pipeline.py --req-id RAN-123 --activity 需求分析'

# 单 Skill 模式(简化前)
/skill_evolve --skill-path /path/to/SKILL.md \
  'python3 scripts/run_eval.py --req-id RAN-123'

# 多 Skill (Agent) 模式(简化入参)
/skill_evolve --skill-paths "/path/to/S1.md,/path/to/S2.md,/path/to/S3.md" \
  --agent-name 我的Agent \
  --pipeline-base-dir /path/to/SDD评测Agent \
  --pipeline-eval-cmd 'python3 scripts/run_eval.py --req-id RAN-123'
```

**多 Skill 模式关键差异**:所有 Skill 一起跑一次端到端评测,基于**聚合分数**(所有 case 的平均)统一决策,最终产出"联合审查报告"。

## 四、任务执行全过程

![图 4-1 任务执行全流程阶段总览](figures/用户手册-图4-1-阶段总览.png)

*PDF 版本:[用户手册-图4-1-阶段总览.pdf](figures/用户手册-图4-1-阶段总览.pdf)*

### 4.1 阶段 0:初始化

**屏幕**:`[init] 创建任务目录…加载配置…准备 Skill 副本…进入基线评测阶段`
**文件夹**:`evolution_workspace/taskid_xxx/{config.json, task_state.json, skill/SKILL.md}`
**持续**:几秒到几分钟。

### 4.2 阶段 1:评测基线

**屏幕**:`[baseline] 第 1/N 次评测…基线平均分 X.X`
**文件夹**:`baseline/{score_baseline.json, score_baseline_analysis.md, proposal.md, run_1..N/}`
**关键**:`score_baseline.json` 是起点分数。**基线为 0 必须先排查**(否则工具跑空轮);**基线已达标则跳过所有迭代,直接进入阶段 5 任务结束**。

### 4.3 阶段 2:生成基线优化提案

**屏幕**:`[baseline→round 1] 基于基线缺口,生成首轮 Skill 优化提案…提案已应用`
**文件夹**:`baseline/proposal.md`、`round_1/round_1_before_skill/SKILL.md`、`round_1/round_1_after_skill/SKILL.md`
**关键**:
- `baseline/proposal.md` 描述基线阶段识别到的缺口、生成的修改建议
- `round_1_after_skill/SKILL.md` 是首轮候选评测所用的 Skill 版本(基线提案已应用)
- 人工 review:`diff round_1_before_skill/SKILL.md round_1_after_skill/SKILL.md`
- 不满意可手动改 `skill/SKILL.md` 后用 `--workspace` 重启

### 4.4 阶段 3:进入第一轮,生成候选 1~n 并评测

**屏幕**:`[round N] 已生成 K 个候选…最优候选 candidate_X, 平均分 X.X`
**文件夹**:`round_N/{round_N_score.json, round_N_score_analysis.md, round_N_before_skill/, round_N_after_skill/, candidate_1..K/}`
**关键**:
- `round_N_score.json` 是本轮最优候选分数
- 各候选分数对比可看出"哪个方向更好"
- 候选分数都=0 → 评测命令或配置有问题
- 候选分数差异小 → 加大 `--candidates`

### 4.5 阶段 4:选取最优 → 生成下一轮优化提案 → 进入下一轮

**屏幕**:`[round N] 选取最优候选 candidate_X…生成下一轮 Skill 优化提案…提案已应用…进入 round N+1`
**文件夹**:在 `round_N/proposal.md` 追加本轮提案,生成 `round_{N+1}/` 目录
**关键**:
- **循环体**:每轮重复阶段 3 → 阶段 4,直至分数达标或达到最大轮次
- `score_history.md` 持续更新所有轮次的分数趋势
- 终止条件:分数≥目标 → 进入阶段 5(达标终止);轮次≥最大 → 进入阶段 5(预算用尽终止)

### 4.6 阶段 5:任务结束

**屏幕**:`[finish] 任务完成…最终分数 X.X…最佳 Skill: best_skill/SKILL.md`
**触发条件**:①分数≥目标(达标终止);②轮次≥最大轮次(预算用尽终止);③基线已达标(无迭代终止)
**关键产物**:`best_skill/SKILL.md`(跨 baseline + 所有候选的最高分副本)。

## 六、关键文件详解

### 6.1 score.json(分数)

```json
{
  "result_score": 0.85,
  "result_score_per_case": {"RAN-123": 0.9, "RAN-456": 0.8},
  "info": {"case_count": 3, "elapsed_time": "120s"},
  "round_num": 1, "candidate_id": 3, "run_index": 2,
  "timestamp": "2026-06-15T12:34:56"
}
```

| 字段 | 含义 |
|------|------|
| `result_score` | 总分 |
| `result_score_per_case` | 各 case 单独分数 |
| `info` | 附属信息 |
| `round_num` / `candidate_id` / `run_index` | 轮次/候选/run 编号 |
| `timestamp` | 评测时间 |
| `zero_root_cause` | 分数=0 时记录原因(可选) |

```bash
jq .result_score baseline/run_1/score.json   # 看总分
jq .result_score_per_case baseline/run_1/score.json   # 看每 case 分数
```

### 6.2 score_analysis.md(评分分析)

人类可读,包含:总分、达标状态、各 case 分数明细表、分数趋势、缺口识别、改进方向。自上而下读即可。

### 6.3 score_history.md(分数历史)

跨所有轮次汇总,**持续更新**:

| 轮次 | 分数 | 状态 | 说明 |
|------|------|------|------|
| 基线 | 68.0 | 未达标 | 起点 |
| Round 1 | 72.0 | 未达标 | ↑4.0 |
| Round 2 | 78.0 | 未达标 | ↑6.0 |
| Round 3 | 85.0 | **达标** | 超过目标分 80 |

### 6.4 proposal.md(优化提案)

本轮改了什么章节、为什么改、预期效果、下一轮建议。

**人工 review**:
```bash
cat round_N/proposal.md   # 看提案文字
diff round_N_before_skill/SKILL.md round_N_after_skill/SKILL.md   # 看具体 diff
```

**若不满意**:手动编辑 `skill/SKILL.md`,用 `--workspace` 指定已有 taskid 重启任务。

### 6.5 config.json(任务配置)

任务总配置和历史:

```json
{
  "taskid": "taskid_20260615_120000",
  "mode": "single",
  "skill_path": "/path/to/SKILL.md",
  "history": [
    {"round": 0, "score": 68.0, "type": "baseline"},
    {"round": 1, "score": 72.0, "type": "candidate", "best_candidate": 3}
  ],
  "best_score": 85.0, "best_round": 3, "best_candidate": 1,
  "created_at": "2026-06-15T12:00:00", "finished_at": "2026-06-15T16:23:00"
}
```

### 6.6 审查报告.md(多 Skill 模式)

多 Skill 任务结束时生成,包含各 Skill 独立分数表、聚合分数、各 Skill 优化提案汇总、联合审查意见。

## 七、分数怎么看

![图 7-1 四级分数聚合层次结构(case → run → 候选 → 轮次)](figures/用户手册-图7-1-分数聚合.png)

*PDF 版本:[用户手册-图7-1-分数聚合.pdf](figures/用户手册-图7-1-分数聚合.pdf)*

### 7.1 三层分数

| 层级 | 含义 | 文件 |
|------|------|------|
| **总分** | 所有 case 平均,代表整体效果 | `round_N_score.json.result_score` |
| **每 case 分数** | 单个 case 的效果,可定位短板 | `round_N_score.json.result_score_per_case` |
| **候选分数** | 同一轮内不同候选的对比 | `round_N/candidate_K/candidate_K_score.json` |

### 7.2 分数趋势判断

- **↑ 上升**:优化方向正确,继续
- **↓ 下降**:方向不对,可回滚上一轮
- **→ 平**:可能已收敛或评测波动大

### 7.3 分数段位解读(以 0~1 分数为例)

| 分数段 | 业务含义 | 建议 |
|--------|---------|------|
| 0.0~0.3 | 严重不达标 | 重新审视评测命令和 Skill 内容 |
| 0.3~0.5 | 远低于目标 | 检查产物结构,可能配错了 |
| 0.5~0.7 | 部分场景可用 | 工具迭代可能有效 |
| 0.7~0.85 | 接近达标 | 工具迭代效果较好 |
| 0.85~1.0 | 高质量,接近上限 | 工具迭代收敛中 |

### 7.4 分数为 0 怎么办

**先排查**:
1. 评测命令本身能跑通吗(手动跑一次)
2. `user-config.yaml` 是否正确声明了产物结构
3. 产物目录里是否有分数文件(JSON 含 `score`/`total_score` 等字段)

最常见原因是**配置不对**——产物结构声明与实际产物不匹配,工具没找到分数字段。

```bash
# 手动跑评测,看产物
'评测命令'
ls data/
cat data/some_file.json | head
# 对照 user-config.yaml 的 structure 描述,确认字段名匹配
```

### 7.5 分数震荡不收敛

| 原因 | 应对 |
|------|------|
| 评测本身不稳定 | 先稳定评测(固定随机种子/多取平均) |
| 候选方案差异太小 | 加大 `--candidates` |
| 目标分设得太高 | 适当降低目标 |
| 单次评测偶然性大 | 加大 `--runs` |

| 关注点 | 看哪里 |
|-------|-------|

| **手动微调** | `vi skill/SKILL.md` + `--workspace` 重启 |
| **调整参数** | 加大 `--candidates` / `--runs` 重跑 |
| **重置任务** | 删除旧 taskid 目录,从零开始 |

## 九、调优与高级用法

### 9.1 调优建议

| 参数 | 建议范围 |
|------|---------|
| `--runs` | 评测稳定 3 / 轻微波动 5 / 波动大 7~10 / 探索 2 |
| `--candidates` | Skill 简单 3~5 / 复杂 5~10 / 冲刺 10~15 |
| `--rounds` | 快速验证 2~3 / 常规优化 5 / 深度优化 8~10 |

**配合策略**:先 `--rounds 2 --candidates 8 --runs 2` 快速试错,锁定方向后加大 `--runs` 稳分。单 Skill 各打到 80+ 再联合优化(`--skill-paths` + `--agent-name`)。

### 9.2 高级用法全景

![图 9-1 高级用法全景](figures/用户手册-图9-1-高级用法.png)

*PDF 版本:[用户手册-图9-1-高级用法.pdf](figures/用户手册-图9-1-高级用法.pdf)*

| 用法 | 适用场景 | 关键命令 |
|------|---------|---------|
| **暂停与恢复** | 长任务意外中断 | `Ctrl+C` + `--workspace 路径` |
| **并行任务** | 多 Skill 互不相关 | 多终端同时启动 |
| **多 Skill 联合** | 多 Skill 端到端互相影响 | `--skill-paths` + `--agent-name` |
| **跨任务对比** | 对比两个不同配置的效果 | `diff taskid_A/ taskid_B/` |

## 十、错误排查

![图 10-1 错误排查决策树](figures/用户手册-图10-1-错误排查决策树.png)

*PDF 版本:[用户手册-图10-1-错误排查决策树.pdf](figures/用户手册-图10-1-错误排查决策树.pdf)*

### 10.1 常见错误速查表

| 错误现象 | 可能原因 | 排查方法 |
|---------|---------|---------|
| **基线分数=0** | 评测命令报错 / 配置不匹配 / 产物路径不对 | 手动跑命令,对照 user-config.yaml 字段名 |
| **候选分数全=0** | 候选生成失败 | 看日志,可能是 Skill 太大 |
| **分数波动剧烈** | 评测不稳定 | 加大 `--runs`,固定随机种子 |
| **分数不提升** | 已收敛或方向不对 | 看 `score_analysis.md` 找短板 |
| **任务卡住** | 评测命令挂死 | 中断任务,看 `task_state.json` |
| **磁盘占满** | 产物太多 | 清理旧 taskid 目录 |
| **LLM 调用失败** | 网络/API key 问题 | 检查环境变量配置 |
| **配置文件报错** | YAML 语法错 | 用 yamllint 校验 |

### 10.2 排查操作清单

```
1. 看屏幕最后几行日志 — 定位失败阶段
2. 看 task_state.json — 当前进度和历史
3. 看对应阶段的 score.json — 分数是否合理
4. 手动跑评测命令 — 验证命令本身
5. 检查 user-config.yaml — 验证配置
6. 看 round_N/proposal.md — 看本轮提案(如果生成了)
7. 翻阅 FAQ(10.3) — 找类似问题
```

### 10.3 高频 FAQ

| 问题 | 解答 |
|------|------|
| **任务跑到一半能中止吗** | 可以,`Ctrl+C`。已完成的轮次产物保留,可用 `--workspace` 恢复 |
| **怎么恢复中断的任务** | `/skill_evolve --workspace /完整路径/taskid_xxx '评测命令'` |
| **基线分数就是 0** | 按"分数为 0 怎么办"排查(7.4)。基线为 0 通常意味着评测命令或配置有问题 |
| **分数一直在震荡不收敛** | 可能是评测本身不稳定 / 候选差异太小 / 目标分太高 |
| **多 Skill 模式下分数怎么算** | 所有 Skill 一起跑端到端,聚合分数 = 所有 case 的平均 |
| **怎么只跑部分 case** | 启动时选"调整子集"指定具体 case |
| **产物目录能不能清理** | 不建议手动清理;实在太多可在 `evolution_workspace/` 下手动删旧目录 |
| **任务目录里有错误日志** | 看 `task_state.json` 的 `phase_history` 定位失败阶段 |
| **能实时观察吗** | 屏幕打印 + 文件夹实时更新 + `task_state.json` |
| **任务跑完一轮大概多久** | 取决于评测命令 + `--runs` + `--candidates`,通常十几分钟到几小时 |
| **为什么手动改的 Skill 没生效** | 工具读的是 `skill/` 或 `skills/` 下工作副本,**不是原文件** |
| **优化提案看不懂怎么办** | 看 `round_N/proposal.md` + diff + `score_analysis.md` |
| **分数已经达标还需要再跑一轮吗** | 不需要,达标即终止 |
| **配置错了怎么办** | 中断 → 改 `user-config.yaml` → `--workspace` 重启 |
| **产物里的 data/ 目录是什么** | 沙箱产物的归档,不影响任务但占磁盘 |

## 十一、附录速查

### 11.1 命令行速查

```bash
/skill_evolve 'cmd'                                                  # 最简启动(旧式兼容)
/skill_evolve --pipeline-base-dir X --pipeline-eval-cmd 'cmd'        # ★ 简化入参(推荐,含 slash command 自动 wrap)
/skill_evolve --pipeline-base-dir X --pipeline-eval-sh 'cmd'         # ★ 简化入参(纯 shell,跳过 wrap/extract/warn)
/skill_evolve --skill-path ./SKILL.md --pipeline-base-dir X --pipeline-eval-cmd 'cmd'  # 单 Skill + 简化
/skill_evolve --skill-paths "./S1.md,./S2.md" --agent-name MyAgent \
  --pipeline-base-dir X --pipeline-eval-cmd 'cmd'                    # 多 Skill + 简化
/skill_evolve --rounds 3 --candidates 5 --runs 3 --pipeline-base-dir X --pipeline-eval-cmd 'cmd'  # 调参
/skill_evolve --workspace /path/taskid_xxx --pipeline-base-dir X --pipeline-eval-cmd 'cmd'  # 恢复
```

### 11.2 文件路径速查(任务根目录:`evolution_workspace/taskid_xxx/`)

| 内容 | 路径 |
|------|------|
| 业务配置 | `config/user-config.yaml` |
| 当前 Skill | `skill/SKILL.md` |
| 最佳 Skill | `best_skill/SKILL.md` |
| 分数历史 / 任务状态 / 任务配置 | `score_history.md` / `task_state.json` / `config.json` |
| 基线 / 各轮产物 | `baseline/` / `round_N/` |
| 审查报告(多 Skill) | `审查报告.md` |

### 11.3 术语速查

| 术语 | 含义 |
|------|------|
| **Skill / 评测管道 / 基线 / 候选 / 优化提案** | 见产品手册第十一章 |
| **沙箱** | 每次评测的隔离执行环境 |
| **单 Skill 模式 / 多 Skill 模式** | 优化单个 Skill / 联合优化多个 Skill |
| **聚合分数** | 多 Skill 模式下,所有 case 分数的平均 |
| **轮次(Round)** | 一次完整的"基线→候选→优化"循环 |
| **快照** | 某一时刻 Skill 的副本,用于版本管理和回滚 |
| **taskid** | 任务唯一标识,格式 `taskid_YYYYMMDD_HHMMSS` |
| **workspace** | 任务工作空间的根目录 |

### 11.4 评分与产物

- **分制**:由业务方决定(0~1 / 0~100 / 自定义),在 `user-config.yaml` 中声明
- **产物大小**:轻量(纯文本)几 MB、中等(含图像)几十 MB、重量(含视频)几百 MB,单轮产物。任务目录需定期归档/清理
