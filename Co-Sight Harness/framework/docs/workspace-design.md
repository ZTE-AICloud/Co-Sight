# 工作区方案：目录、命名与磁盘边界

> 读者：**框架维护者**，以及**需要帮用户建工作区的模块作者**。
> 接口形状（两个面、七个端点、真实的请求与响应）见 [`workspace-api.md`](workspace-api.md)，
> 本文讲的是背后的规则与取舍；模块面的令牌与门禁见 [`module-facing-api.md`](module-facing-api.md) 第 2、5 节。

## 0. 一句话

工作区是「逻辑容器 + 可选目录绑定」（D16 = A）。D32 把"可选"那一半**做实**了：
**不填目录时，框架在自己的工作区根下建一个目录并绑定；填了就只绑定，不创建**。

**§7 之前，框架对工作区目录只做"建一个空的、记住它在哪"。从那节起它还会 READ 里面的文件**
（只读浏览，给会话区右侧的「工作区文件」面板用）——**不写、不移动**这条边界没动；
**删除**在 D43 之后有了一个例外：删工作区会删掉框架自己创建的那个目录（§4）。
读进来的东西要过哪些关、上限是多少、为什么要额外加回环门禁，全在 §7。

## 1. 目录布局

```
$COSIGHT_HOME/                     默认 ~/.cosight-harness，0700
├── sqlite.db                      工作区记录（真相是库，见下）
├── .credentials.yaml              0600
├── .module-token                  0600
├── modules/<任意目录名>/module.json
└── workspaces/                    ← 工作区根，可用 COSIGHT_WORKSPACES_ROOT 覆盖
    ├── _public/                   ← 公共空间（框架自用的命名空间）
    ├── 周报助手开发/
    └── 数据分析-2/
```

这套布局**只在 `framework/server/src/config/paths.ts` 定义一次**，`ensureDataPaths` 在启动时建齐。
别在别处再拼一遍路径——"工作区到底建到哪去了"是这套东西里唯一会让人真去翻磁盘的问题。

**工作区记录在库里，不在目录里**：目录是可选的绑定，不是身份的来源。
两条记录可以绑定同一个目录（框架不禁止，也不去重），一条记录也可以谁都不绑。

## 2. 为什么目录由框架创建（与 deepseek-harness 的刻意分叉）

dsh 的工作区**只接受已经存在的目录**（`realpath` 规范化，不存在就 `ENOENT` 拒绝），
而且创建工作区时**不往目录里写任何脚手架文件**。我们的做法与它不同，这是刻意的：

| | dsh | 本框架 |
|---|---|---|
| 心智模型 | **认领**一个已有的代码目录 | 使能中心里的一个**项目位** |
| 不填目录 | 不允许（目录是工作区的本质） | 在根下建一个同名目录并绑定 |
| 目录内容 | 用户自己的代码 | 用户自己的代码（框架同样不写任何脚手架） |

理由很实际：用户点"新建工作区"时脑子里没有"先准备好一个目录"这一步。
要求先有目录，会把新建流程变成一次导览——"请先去终端 `mkdir` 再来"。
而"项目位"这个心智模型下，"帮我建个地方"才是预期行为。

分叉的边界收得很紧，这是这条设计能被接受的前提：

- **只在框架自己的工作区根之下创建。** 用户在请求体里手填的绝对路径**只绑定、不创建**
  （见 §4）——对任意绝对路径执行 `mkdir -p` 等于把一个写原语交给调用方去碰用户整台机器。
- **不写任何脚手架文件。** 建出来的就是一个空目录，与 dsh 一样。

## 3. 目录名是怎么来的

工作区的 `name` 契约只做 `trim()` 和 1–64 限长，**不限制字符**——它是给人看的显示名，
凭什么不让人叫「周报助手 / 2026 Q1」。但它现在要变成一个**路径段**，而 `../../etc`
完全是一个合法的显示名。所以中间必须有一层 slug 化（`lib/slug.ts` 的 `toDirectorySlug`）。

**这是安全项，不是美化项。** 规则用**白名单**而不是黑名单：黑名单要枚举 `..`、`~`、`/`、
`\`、NUL、各平台的保留名，漏一个就是漏洞；白名单漏掉的只是"某个字符没能出现在目录名里"，
代价是零。

六步，每一步都有理由（细节见 `lib/slug.ts` 的文件头）：

1. `NFKC` 规范化 —— `ＡＢ` 与 `AB` 折成同一个东西；
2. 保留 `\p{L}`、`\p{N}`、`_`、`-`，**其余连续字符折成一个 `-`**；
3. 折叠重复的 `-`；
4. 去掉首尾的 `-`、`.`、`_`；
5. 空结果 → `workspace`；
6. 按**码点**截断到 48。

| `name` | 目录名 |
|---|---|
| `周报助手开发` | `周报助手开发` |
| `周报助手 / 2026 Q1` | `周报助手-2026-Q1` |
| `../../etc/passwd` | `etc-passwd` |
| `..` | `workspace` |
| `_public` | `public` |
| `ＡＢ` | `AB` |

**中文会被保留**，这也是刻意的：若按 `[a-z0-9._-]` 那种常见做法过滤，`周报助手开发` 会变成
一串 `-`，用户打开工作区根目录看到一屏 `-----`。按码点截断（而不是字节或 UTF-16 单位）
是为了不在多字节字符中间切出一个半个汉字或孤立代理项。

### 保留名：靠剥前缀，而不是靠黑名单

**`_` 开头的是框架自用的命名空间**（当前只有 `_public`）。
第 4 步剥掉首尾的 `_`，于是**用户在结构上就落不到框架的命名空间里**——
比维护一张"不许叫 `_public`"的清单彻底。

### 重名

不区分大小写地判重：`readdir` 的结果**小写化**后，加上库里那些"父目录正好是工作区根"的记录。
小写化是因为 macOS APFS / Windows NTFS 上 `Report` 与 `report` 是同一个目录，
而 SQLite 的文本 `=` 是大小写敏感的——只查库挡不住这一层。

候选依次是 `<slug>`、`<slug>-2` … `<slug>-99`，还撞就 `<slug 前 32 位>-<6 位随机>`。
加数字后缀而不是换一套前缀或加时间戳，是因为 `ls` 出来的人一眼能看出这几个目录是同一批重名的工作区。

**真正的判重靠 `mkdir` 抛不抛 `EEXIST`**，不靠上面那个集合：`readdir` 与 `mkdir` 之间存在
真实的 TOCTOU 窗口（同机两个进程、或一个进程两次并发请求），而 `mkdir` 不带 `recursive` 时
对已存在的路径**必然**抛 `EEXIST`——这是内核给的原子判重。集合的作用只是让常见情况一次就选中。

创建成功后存进 `directory` 的是 **`realpathSync` 的结果**，不是拼出来的字符串：
符号链接、尾斜杠、大小写（macOS 上 `/Users/x` 与 `/users/x` 是同一个目录）都收敛成一个规范形式，
于是"两条记录指向同一个目录"在字符串比较下也成立。

## 4. 哪一步动磁盘

| 操作 | 磁盘 |
|---|---|
| 建工作区，**不填** `directory` | **建** `<工作区根>/<slug>`，绑定它的 realpath |
| 建工作区，填了绝对路径 | **不建**、**不要求存在**，只绑定 |
| 改工作区（含改名） | **不动**。目录在创建那一刻绑定，之后是稳定的；改名不重命名目录 |
| 删工作区 | **删**框架自己创建的直接子目录；外部绑定目录**不动** |

三条要展开说：

- **手填的绝对路径不创建。** 而且仍然**不要求它已存在**——D16 那句"绑定目录时不要求目录已存在
  （创建与使用解耦）"依然成立。用户可以先把工作区登记好，之后再准备目录。
- **改名不重命名目录。** 跟着改名走意味着"用户改个显示名，磁盘上少了一个目录、多了一个目录"，
  而任何指向旧路径的东西（编辑器、终端、另一个模块记下的路径）会当场失效。
- **删除只清理框架自己建的目录。** 判定条件是"工作区根的直接子目录、且不是 `_public`"——
  这类目录确定是框架按工作区名建出来的，连同内容删掉。用户填绝对路径绑定的目录
  （`/srv/projects/existing`）只解除记录，**绝不 `rm -rf`**：那里是用户自己的文件。
  删除时会打一条 info 日志，带 `directory` 与 `directoryDisposition`
  （`deleted` / `external` / `absent` / `unbound` / `not-directory`），
  "目录怎么还在"能直接按日志回答。
  `PATCH` 把 `directory` 传 `null` 仍然只是解绑，不动磁盘。

## 5. `COSIGHT_WORKSPACES_ROOT`

工作区根默认是 `$COSIGHT_HOME/workspaces`，可以用环境变量整体指到别处
（`/srv/projects`、团队共享盘…）。解析口径与 `COSIGHT_HOME` **完全一致**：
不展开 `~`、相对路径按进程 cwd 解析（`config/env.ts`）。两边口径不一致的表现是
"目录建到了另一个地方"，而这类问题最难查。

**权限策略随"在不在 home 之内"改变**：

| 位置 | 行为 |
|---|---|
| 在 `$COSIGHT_HOME` 之内（默认） | `0700`，与 home 同口径的最小权限 |
| 在 `$COSIGHT_HOME` 之外 | **只创建，不 chmod** |

第二条是刻意的：把根指到 `/srv/projects` 的人多半是在**有自己权限模型**的地方放工作区，
框架再去改它的权限就是越界。创建出来的**工作区子目录本身**则一律用进程 umask 的默认值——
里面装的是用户的代码，不该由框架收紧。

## 6. 与 D16 的关系

D16 = A 的原文是「逻辑容器 + 可选目录绑定」，并注明"绑定的目录不要求已存在（创建与使用解耦）"。

**D32 只改了一件事**：不填目录时的默认行为，从"不绑定"改成"在框架自己的根下建一个并绑定"。
D16 的其余部分——uuid 是主键、目录是可选属性、不要求目录存在——一个字没变。
那一句说的是**用户填的路径**，与"框架自己建的那个"是两件事。

### 6.1 首次启动的默认工作区

`server/src/seed/seed.ts` 的 `seedDefaultWorkspace()` 在框架启动时（**监听端口之前**）执行：
`workspaces` 表为空就建一条「默认工作区」（`directory = null`，走与界面新建完全相同的
`WorkspaceService.create`，于是目录按 §3 的规则建在 `<工作区根>/默认工作区`）并设为当前工作区。

它不做"每次启动都确保有个默认值"：**只要表里还有任意一条记录就完全跳过**。
删光之后重启会重建，与预置专家的语义一致（D16/D32 的契约没有变化——这条记录与
用户建的那条在 schema 上没有任何区别）。

动机在下游：smart-factory 的预置智能体恒为 `workspace_id = null, builtin = true`，
服务端把它们混入**每个**工作区的列表；但它的前端在 `activeId === null` 时连列表都不请求。
没有这条种子，"开箱即用"的预置智能体在界面上一条也看不到。

失败只记 `warn`、不阻断启动：建目录可能因为权限或磁盘满失败，而用户仍可在界面上
手工新建一个。

## 7. 只读浏览：框架现在会**读**工作区里的文件

加这一节之前，本文与 `workspace-api.md` §11.6、`module-facing-api.md` §8 都写着一句承诺：
「不读工作区目录里的任何内容」。**那句话现在只剩"不写、不移动"成立**——**读**加进来了：
会话区右侧的「工作区文件」面板要能预览工作区里的东西；**删**也有了 D43 那条受边界约束的
清理（只限框架自己建的目录，§4）。

面板由**宿主**画（模块 iframe 没有 postMessage 桥，见 D24 与 D35），下面三个端点是它唯一的
数据来源，**只开在浏览器面**：

| Method | Path | 返回 |
|---|---|---|
| `GET` | `/api/workspaces/:id/files?path=` | `{ root, path, entries: [{name, type, size?}], truncated }` |
| `GET` | `/api/workspaces/:id/files/content?path=` | `{ path, size, text, truncated }` |
| `GET` | `/api/workspaces/:id/files/image?path=` | `{ path, size, contentType, dataUrl }` |

规则与磁盘访问全在 `server/src/services/workspace-files.ts`；路由
（`server/src/routes/workspace-files.ts`）是它的薄壳，只做"校验入参、调服务、包信封"。
**包含规则只有那一份**，别在路由或别处补第二个判断。

### 7.1 包含规则：四道，缺一道就有洞

请求里**永远没有绝对路径**。根目录由服务端按工作区 id 从库里取，客户端只说"根下面的哪一段"
（`?path=`，省略/空串即根）。整个攻击面因此收在一个字符串上，它要过四道：

| # | 关卡 | 挡的是什么 | 位置 |
|---|---|---|---|
| 1 | 分段拒绝 | 绝对路径、`..`、`\`、NUL 字节、`C:` 这种盘符段 | `normalizeRelativePath` |
| 2 | 末段不跟随软链 | "这个路径指的是哪个文件"要能一眼看出 | `#resolve` 里的 `lstat` |
| 3 | `realpath` 之后判包含 | 中间某一段是软链、指到了工作区外 | `#resolve` 里的 `isInside` |
| 4 | 错误消息只回显用户给的那段相对路径 | 服务端的文件系统布局不外泄 | `#resolve` / `missingPath` |

几句要展开说的：

- **`..` 一律拒，哪怕 `a/../b` 最终绕回工作区内。** 一条规则比"看得出意图的那种才算错"
  更容易被审计。
- **`\` 一律拒，不做平台适配。** `path.join` 在 Windows 上把 `\` 当分隔符，于是 `a\..\..\x`
  就是一次跨目录跳转；一个"怎么解析取决于运行平台"的安全检查不可接受。代价是 POSIX 上
  文件名里真带 `\` 的文件点不开。
- **第 2、3 关的顺序不能反。** 先 `realpath` 的话末段软链已经被解掉，就再也分不出"用户点的
  是个软链"还是"用户点的是那个文件"。所以要先用 `lstat` 判末段，再 `realpath` 解中间各段，
  最后判包含。
- **不跟随软链是刻意的一条，没有例外**——指向工作区**里面**的软链也照拒。这是与 dsh 的
  **又一处刻意分叉**：dsh 的 `read` 明确允许读到工作区外（它的消费方是 cc 的资源地址），
  我们不是那个场景。一条没有例外的规则让"读的是哪个文件"不需要任何推理。
- 列目录时软链**看得见**（条目 `type: "other"`），只是点不开——列表要如实反映磁盘上有什么。

### 7.2 四个上限：拦的是体积，不是敏感性

| 常量 | 值 | 越界表现 |
|---|---|---|
| `maxEntries` | 2000 | 列表截断 + `truncated: true` |
| `maxTextBytes` | 512 KiB | 只读前 512 KiB + `truncated: true`；`size` 仍是**文件真实大小** |
| `maxImageBytes` | 2 MiB | `413` |
| `SNIFF_BYTES` | 8 KiB | 只影响判定过程，不上契约、客户端看不见它 |

前三个**从响应里看得见**，所以定义在契约里（`shared/src/contracts/workspace-file.ts`）：
前端要用同一组数把"只显示了前面多少"说准，两边各写一份必然漂。

实现上三处取舍：

- **截断靠 `readSync` 只读前 N 字节，不是 `readFileSync` 再切。** 一个 10 GB 的日志会把内存
  吃满再被切掉。
- **截断点落在多字节字符中间时不误报。** 按字节切可能把一个中文切成两半，致命解码会失败，
  于是一个正常的中文文件被报成"不是文本"（`415`）。所以截断时依次丢掉尾部 1–3 字节再试。
  容忍范围**仅限这一次重试**——整段非致命解码会让真正的二进制带着一堆替换字符显示出来，
  那是更糟的失败。
- **二进制判定要两条判据**：前 8 KiB 含 NUL 字节，**或**整段解不成 UTF-8。只留第一条会漏掉
  "没有 NUL 但不是合法 UTF-8"的文件。

图片**按内容认**（魔数表 + WebP 的 RIFF 容器判定 + SVG 的文本前缀），不按扩展名——扩展名是
用户随手改的。SVG 进 `<img src="data:image/svg+xml;...">` 是安全的：`<img>` 里的 SVG
不执行脚本、不加载外部资源，这是浏览器规范行为，不是我们的假设。

**图片走 base64 内联，不做裸二进制端点**：仓库的硬规矩是每个响应都是同一套信封，而一个
`content-type: image/png` 的响应会让**出错时**前端读到一张读不懂的图而不是一句人话。
4/3 的体积代价由 2 MiB 上限兜住。

### 7.3 回环门禁，以及它的代价

这三个端点在 `/api/workspaces` 下，但**额外**在插件自己的 `onRequest` 里要求 `Host` 与来源
socket 都是回环（复用 `server/src/http/loopback.ts`），不满足 → `403`。

理由很具体：浏览器面对 **DNS rebinding** 本来没有防线——恶意站点把自己控制的域名解析到
`127.0.0.1`，浏览器就当成同源，CORS 完全不介入。在此之前这条攻击面只够翻一翻工作区**记录**
（名字、绑定路径、顺手改模型配置），代价有限；这一组一旦开口，它够读**文件内容**。
`Host` 头是客户端自己写的，是这条链上唯一会露馅的地方。

**代价明说，不留给下一个人猜：**

- **把 UI 部署到非回环地址时这三个 GET 会 403**，文件面板打不开。
- 回环校验**挡不住**同机同用户的其他进程（它们本来就能直接读磁盘），也挡不住浏览器扩展。
  这是本机单用户模型的固有形状，与 D25 令牌那一节是同一口径。
- 它**只加在文件浏览上**，浏览器面其余接口维持原样——一刀切在这里是"最敏感的接口"与
  "最广的入口"之间的权衡。`server/tests/api-workspace-files.test.ts` 有一条用例专门守着
  "这一刀没切到别处"。

### 7.4 面板本身：左右分栏、挤窄会话区、可全屏（D38、D39）

界面部分不属于"工作区"这套语义，但它与本节的三个端点是一起长出来的，形状记在这里：

- **左右分栏**：左边 260px 的目录树（**基准值**，窄端可与右栏一起收），右边是预览，**同时**
  在屏幕上。理由是浏览文件时"我在哪个目录"与"这个文件里是什么"这两条信息要同时可读；
  单栏靠返回按钮轮换，等于每次看文件都要多按两下。
- **挤压，不是遮盖**（D39）：面板绝对定位在 `<main>` 里，但 `<main>` 在面板打开时给自己加
  `padding-right` = 面板宽度，于是内容区（那个跨源 iframe）跟着变窄。**代价**：留白有 300ms
  过渡，那 300ms 里 iframe **逐帧重排**——那是同事的代码，我们保证不了它撑得住；
  拖拽期间过渡关掉。
- **左缘一条 8px 手柄可拖**，宽度**默认 = 上限 = 页面宽度的三分之一**（下限 **320**），
  键盘 `←/→` 走 16px、`Home`/`End` 跳两端。上限是**比例**而不是常数：写死的 960 表达不了
  "页面的三分之一"，在 4K 屏上会把用户锁住。宽度**放 store 但不持久化**，与侧栏宽度同口径。
  因为默认就在上限上，**默认位置往左拖是空操作**——这是取舍，不是 bug（D39）。
- **可以全屏展示，也可以收起全屏**（D39）：铺满的是**内容区**（左侧栏留着），
  全屏期间不渲染拖拽手柄、也不动 `<main>` 的留白（退出那一帧就不用重排）。
- 面板自己的上限是 `max-width: 100%`：宽度越界而上层容器更小时贴满容器，不画到容器外面。
- **一个只有真浏览器才看得见的坑**：分栏容器是 flex 子项，`min-width: auto` 的下限是内容的
  min-content 宽度，而右栏里是 `white-space: pre` 的代码——一行长 README 会把整块顶出面板，
  被 `.main` 的 `overflow: hidden` 裁掉（表现是"长行不滚动、直接看不见"）。`min-width: 0`
  修掉它，长行回到由正文自己横向滚。

完整取舍见 D38（分栏、拖拽调宽）与 D39（挤压、上限取比例、全屏），
两条与 dsh 的分叉都在那里给了理由。

### 7.5 绑定目录：服务端弹系统选择器（D52）

「绑定目录」以前只能手输。浏览器**给不出绝对路径**（`showDirectoryPicker()` 只给句柄、
`webkitdirectory` 只给 `File` 对象），而工作区存的是这台机器上的绝对路径，所以对话框
放到服务端拉起：

| Method | Path | 返回 |
|---|---|---|
| `POST` | `/api/workspaces/pick-directory` | `{ path: string \| null }`（`null` = 用户取消） |

请求体是 `{ initialPath: string \| null }`，契约在 `shared/src/contracts/workspace.ts`
（`pickDirectoryInputSchema` / `PickDirectoryResult`）。起点只当"从哪儿打开"，不存在
时退回系统默认位置。

- **只跑固定命令，不开 shell**：Windows 用 `pwsh` → `powershell.exe`（`FolderBrowserDialog`，
  必须 `-STA`，管道输出显式切 UTF-8）；macOS 用 `osascript` 的 `choose folder`；Linux 用
  `zenity` → `kdialog`，没有图形会话时**连 spawn 都不试**。起点只经 argv / 环境变量传，
  绝不拼进 PowerShell 源码。
- **三种结果分开**：选中 `200 + path`；取消 `200 + {path:null}`；弹不出来 `501`；工具报错
  或 5 分钟超时 `500`。前端对失败说的是"请手动输入路径"，不把输入框标红。
- **回环门禁**：与 §7.3 同一套（`Host` 与来源 socket 都得是回环，否则 `403`）——它会在
  桌面上弹模态窗口并把路径回给调用方。**把 UI 部署到非回环地址时这个按钮用不了。**
- **单飞**：并发的两次调用共用同一个对话框，模态窗口不会叠两个。

界面侧：输入框右侧常驻「选择目录」；输入框为空时点它本身也打开；已有值时点击只当普通
点击（D16 允许绑一个还不存在的目录）。工作区名称与绑定目录都关掉了浏览器的表单历史
下拉（`autoComplete="off"`）。理由与代价见 D52。

## 8. 不做的事

- **不删、不移动、不重命名外部目录。** 唯一的删除是 `DELETE` 工作区时清理**框架自己建的**
  直接子目录（§4、D43）；外部绑定的目录、`_public`、以及根之外的任何路径都不会被删。
- **不给用户填的绝对路径建目录。**
- **不写、不移动工作区目录里的任何内容。** §7 那三个**只读**端点只会读；
  服务里没有 `writeFile` / `mkdir` / `rename`，唯一的删除是 D43 那条受边界约束的清理。
  **注意这句不能再写成"不读"**——§7 之后框架会读。
- **不做目录内容的去重**：两条记录指向同一个目录是允许的，框架不管。
- **不做文件变更监听、不做行分页、不做 `.gitignore` 与点文件过滤**（如实显示）、
  **不做写操作**。与 dsh 的 tab 停靠、change feed、行分页、每 session 持久化，全部刻意不做，
  理由见 D35/D38。**拖拽调宽从"不做"改成了"做"**（D38）：面板一分为二之后，"左栏导航 +
  右栏代码"再也塞不进一个固定宽度里，而 dsh 那条理由（"要一整套 dock 系统"）本来就不适用于
  dsh 自己的宽度手柄——那只是一个 8px 的 `<div>` 加一段指针捕获。
- **"面板遮盖会话区"从"这样做"改成了"挤压"**（D39）：D35 当年为了避开跨源 iframe 重排而选了
  遮盖，需求方明确要求会话区跟着让开，那条代价因此被买下（见 §7.4）。**遮盖这个形状本身不做**：
  面板在任何宽度下都不压在会话内容上，`<main>` 让出的留白与面板等宽。
- **不做"盖满整个窗口"的全屏**（D39）：全屏铺满的是内容区，左侧栏留着。要盖满窗口是
  `position: fixed; inset: 0` 一行的事，等有人真的要它再说。

## 9. 残余风险

- **同一个 `$COSIGHT_HOME` 只能跑一个框架实例。** 工作区记录走 SQLite，库本身没问题；
  限制来自 `.credentials.yaml` 的跨进程写入（见 `module-facing-api.md` 第 6.3 节）。
  要跑第二个实例，用另一个 `COSIGHT_HOME`。
- **工作区目录里是用户的真实文件，现在框架会读它们了。** §7 的上限拦的是**体积**，
  不是**敏感性**：面板会把工作区里任何 UTF-8 文本原样显示出来，包括用户自己放进去的凭据文件。
  这是"让用户预览自己的工作区"这个需求的直接后果，不装作它不存在。
- **工作区根指向共享目录**（`/tmp`、NFS、云盘同步目录）：slug 化挡住了路径穿越，
  但挡不住"另一个用户在同目录里建同名工作区"和"同步软件半途复制出半个目录"。
  与 `COSIGHT_HOME` 指向 `/tmp` 是同一类风险，一条口径说完。
- **符号链接可以绕过"在根之下"的判断吗？** 建目录这一步不会：slug 里不可能有 `/` 或 `..`，
  目标路径必然是根的直接子项。但如果**用户自己**在根目录里放一个指向 `/etc` 的符号链接
  命名为 `foo`，那么后续 `mkdir foo` 会失败（`EEXIST`）而不是写进 `/etc`——绕不过去。
  真正要注意的是"根目录本身"是个符号链接：那种情况下存的是 `realpath`，一致性仍然成立。
