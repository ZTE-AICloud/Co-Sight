### D3 · 样式方案 🟡
**背景**：UX 稿是**像素级规格**（间距 268/150/16px、4 种边框色、7 档圆角），且有"禁止模板味 UI"的设计要求。
**选项**
- **A. CSS Modules + CSS 自定义属性 + lightningcss** — 精确控制、零抽象泄漏，与 deepseek-harness 一致（其 244 个 `*.module.css`）。

- **C. vanilla-extract** — 类型安全 + 零运行时，但引入新构建概念。

**建议**：**A**。规格是像素级的，utility 框架在这里是负资产。
**影响**：P1 全部 UI 与 design token 落地方式。

**决策**：☐ A ☐ B ☐ C   备注：____A______

### D32 · 工作区的默认目录由谁创建 🔴（修订 D16 的一处）

**背景**：D16 = A 定的是「逻辑容器 + 可选目录绑定」，并写明"绑定的目录不要求已存在"。
但代码里 `workspace.directory` 从来只是一个字符串，**框架从没建过目录**。
再往下走（模块面也要建工作区、同事要照着写代码）之前，这个语义必须一次定死。

**选项**
- **A. 不填目录 = 不绑定**（维持现状字面）。新建工作区后没有任何实际目录，用户自己找地方。
- **B. 不填目录 = 框架在自己的工作区根下建一个同名目录并绑定** — 建议。
- **C. 不填目录就报错**（强制用户先手填绝对路径）

**决策**：**☑ B**，配套三条边界：

1. 工作区根 = `$COSIGHT_HOME/workspaces`，可用 `COSIGHT_WORKSPACES_ROOT` 整体覆盖；
   解析口径与 `COSIGHT_HOME` **完全一致**（不展开 `~`）。
2. 目录名从工作区名**派生**（slug 化），**用户输入永不直接进路径**。
3. **用户手填的绝对路径只绑定、不创建、不要求存在**——对任意绝对路径 `mkdir -p`
   等于把一个写原语交给调用方去碰用户整台机器。

**为什么不是 A/C**：dsh 的工作区是"**认领**一个已有代码目录"，所以它只接受已存在的目录；
本框架的工作区是"使能中心里的一个**项目位**"，用户点"新建"时脑子里没有"先准备好一个目录"
这一步。要求先有目录会把新建流程变成一次导览。这是与 dsh 的**刻意分叉**，
完整理由与规则见 [`workspace-design.md`](workspace-design.md)。

**D16 只被改了这一点**：其余（uuid 是主键、目录是可选属性、不要求目录存在）一个字没动。
那句"不要求目录已存在"说的是**用户填的路径**，与"框架自己建的那个"是两件事。

**同时定死的两条**：`PATCH` 改名**不重命名目录**（改名不该让磁盘上的路径失效），
`DELETE` **不删目录**（`rm -rf` 误删不可逆）。
> 后一条已被 **D43** 修订：删除时只清理框架自己创建的目录，外部绑定目录仍保留。

**影响**：P2 数据模型、`config/paths.ts` 的布局定义、模块面工作区接口、
所有既有 `api-workspace.test.ts` 用例（`POST` 之后磁盘上会真的多一个目录）。

### D33 · 模块面是否开放写接口 🔴

**背景**：上一轮把模型配置的**只读**模块面接口做完了，当时的结论是"模块面不开写接口"，
理由有两条：消费方是读消费者；以及 `.credentials.yaml` 没有跨进程文件锁，
开了写接口就会有"两个进程同时 read-modify-write 丢更新"。

**选项**
- **A. 维持只读。** 要改配置去框架界面（设置 → 模型设置）。
- **B. 开放写接口**（模型增删改 + 工作区整套 CRUD） — 建议。
- **C. 开放写，但新发一枚"写令牌"**，读令牌保持只读。

**决策**：**☑ B**。

**上一轮那条硬理由为什么不成立**：模块面的写**全部经 HTTP 打到那一个框架进程**，
写入串行化的那个 `CredentialStore` 实例始终只有一个。跨进程风险只存在于
"有人绕过 HTTP 直接改那个文件"（手工编辑、另起一个框架实例），
这与浏览器面今天的情况**没有任何区别**——它从来不是"模块面写入"引入的。
C 被否掉的理由是：本机单用户下多一枚令牌只是多一份要管的东西，
真正的边界是"能读到 0600 文件"，不是令牌的作用域。

**代价要写进文档，不能含糊**：令牌的**爆炸半径**变了。原来泄漏一枚令牌只能读走密钥；
现在还能把 `baseUrl` 改到攻击者控制的端点（密钥自动送过去，界面看不出来），
以及**在磁盘上创建目录**。缓解措施是三条，都落在实现里：

1. 会话**写操作记 warn 日志**（方法、路径、对端地址）——模块面没有操作者身份，
   这条日志是事后唯一能回答"哪台机器、什么时候"的东西；
2. 工作区**只在框架自己的根之下创建目录**，用户手填的绝对路径只绑定（D32 第 3 条）；
3. 文档口径**明确反转**：不再说"这组接口是只读的"，改为"不该要写权限的模块就别要"。

**顺带定死的一件事**：模块面的**门禁上提到唯一的 `moduleFaceRoutes` 插件**上
（`onRequest` 钩子），子树注册在它内部。理由是"忘记挂门禁"的失败形态**不报错**——
它只是静默多出一个不需要认证的读写接口。上提一层之后，往模块面加第四条子树时
门禁自动继承，结构上无法忘记。

**影响**：`module-facing-api.md`、`model-config-api.md`、`module-integration-smart-factory.md`
（明确告诉对方**不要顺手用**写接口）、`ModuleAccessCard` 上的界面文案。

### D34 · 模块产物该由谁在启动前刷新 🟡

**背景**：有的模块的**开发态入口就是产物**。`cosight-viewer` 的 server 在
`CO_SIGHT_MODE=claude` 下是生产模式，静态托管 `client/dist`；而 `client/dist` 在
`.gitignore` 里——`git pull` 更新源码，**不会**更新产物。于是本机跑的是几天前的包。
实测踩到过：同事合进来的对话页在本机 404，因为旧包里连那条 hash 路由都没有，
而唯一的现象是"页面没更新"，这个现象很容易被读成"功能没做"（上一次排查就绕了圈）。
这类故障的共性是**不报错**：产物旧了不会有人告诉你。

**选项**
- **A. 保持现状**，靠人记得手工 build。失败形态不报错，等于把正确性押在记忆上——迟早忘。
- **B. `dev:all` 每次启动无条件重建所有模块产物**。方向对，代价错：每次白等一次全量构建，
  而走 `npm run dev` 的模块（smart-factory 的两个服务）压根不吃产物。
- **C. 清单里声明一段可选的 `build`（命令 + 输入 + 产物），启动前按**时间判据**决定要不要重建** — 建议。

**决策**：**☑ C**，配套四条边界：

1. **`outputs` 必填**（`inputs` 省略即 `["."]`）。没有 `outputs` 就只能无条件重建，
   而这个字段存在的全部理由就是**不**无条件重建。
2. **判据保守**：输入里最新的一个（严格大于）产物里最旧的一个 → 重建。
   目录产物取它树里最新的文件时间（"最后一次写产物"的时刻）。方向是宁可多建一次，
   不会少建一次——判错的代价是白等一次构建，而不是被骗一次。
3. **`--rebuild` / `--no-build` 两个显式出口，且互斥**。不给"删掉字段绕过"留路。
4. **失败即该模块的服务不启动**（构建失败、`inputs` 里的路径不存在、构建目录没有
   `node_modules`）。要用旧产物启动，就显式写 `--no-build`——让"我在用旧产物"这件事
   由人说，不由脚本猜。

**为什么登记在 `launch.json` 而不是别处**：

- 不进 `module.json`：那是**运行时契约**（`/api/modules` 会把内容发给浏览器），
  而"本机启动前要不要重打一遍产物"是开发编排。与启动方式同一条理由，见 D24 与
  [`dev-all.md`](dev-all.md) 开头那段。
- 不进 `package.mjs`（打包脚本）：打包打的是**框架自己**的交付产物，模块产物是
  **本机开发态**的事，消费方与生命周期都不一样。
- 脚本**永不执行 `npm install`**：这条既有边界没有被这个字段放宽，缺依赖只报错并给指引。

**影响**：`scripts/dev-all.mjs`、`scripts/lib/module-build.mjs`（新）、
`docs/modules/cosight-viewer.launch.json`（唯一声明者）、[`dev-all.md`](dev-all.md)、
`server/tests/module-launches-doc.test.ts`（守住"这个模块必须声明 `build`，且产物就是它托管的那个 dist"）。

### D35 · 会话区右栏（工作区文件预览）画在哪一侧 🟡

**背景**：需求是在会话内容区的右上角加一个"展开右侧边栏"的图标，点开预览工作区里的文件，
写法参考 dsh。但**会话页不是我们的页面**：它是 `cosight-viewer` 的前端，以**跨源 sandbox
iframe** 嵌在宿主里，而且宿主**刻意不做 postMessage 桥**（D24）。于是宿主既读不到 iframe
里的状态，也画不进 iframe 里——"把按钮画到会话区右上角"这件事本身就需要一个决策。

**选项**
- **A. 给 `ModuleHost` 加一条 postMessage 桥**，让模块自己渲染那个按钮。
- **B. 宿主画一个悬浮按钮压在 iframe 右上角，面板也由宿主画** — 建议。
- **C. 把右栏做成与 `<main>` 并列的一列**（挤压 iframe 的宽度，不覆盖）。

**决策**：**☑ B**，配套四条：

1. 按钮与面板都画在 `AppShell` 的 `<main>` 里并**绝对定位**（`.main` 加 `position: relative`
   提供定位上下文），盖在 iframe 之上，不与它争宽度。
2. **面板打开时那个悬浮按钮不渲染**（dsh 也是 `if (expanded) return null`），收起按钮改在
   面板自己的标题栏上。任何时刻只有一个切换控件、一个 `aria-expanded` 在读——用户不需要想
   "这两个哪个是开的"。理由照抄 dsh：折叠态要让会话区零成本。
3. **只在会话页（`/`）渲染。** 会话的两个阶段（新建对话态、进入对话态）是同一个路由上的
   同一个 iframe，一个宿主按钮同时覆盖两个状态，不需要模块配合。
4. 面板是 `<aside role="complementary">` + `aria-labelledby` 指向可见的 `<h2>`。
   **`role` 不能省**：HTML-AAM 规定 `<aside>` 只有在不是 `main`/`article`/`nav`/`section`/`aside`
   的后代时才映射成 `complementary`，而本面板正是在 `<main>` 里（为了拿到那个定位上下文）。
   不写 role 它会落成 `generic`，`aria-labelledby` 无处附着——面板对读屏软件等于没有名字。

**为什么不是 A**：那是**为了一枚按钮给所有模块开一条双向通道**，而 D24 定"不做桥"时考虑
的正是"让宿主不需要理解模块内部"。它还会要求同事改自己的页面。**为什么不是 C**：C 每次
展开/收起都要让一个**跨源 iframe** 重新布局一次，从而触发模块自己的重排逻辑——那是别人的
代码，我们没法保证它处理得好。宁可盖住（dsh 的右栏也是 `position: absolute`）。

> ⚠️ **上面这条"为什么不是 C"已被下面的 D39 推翻**：面板现在**正是**挤压会话区
> （实现的正是 C 这个形状）。当时的取舍是宿主自己的口味，
> 而需求方要的是"我读文件时会话区跟着让开"，于是那条代价（跨源 iframe 逐帧重排）
> 被明确买下。本条的其余四条（宿主画按钮、面板由宿主渲染、只在会话页、`role="complementary"`）
> 不受影响，仍然有效。

**代价要写进对接说明**：那个按钮占着会话区右上角一小块，**压在同事页面的内容上**。
他们以后在自己页面右上角加东西时会被压住，而他们看不见我们的组件。这是"不能改同事模块"
这条约束的直接代价，不是疏忽。

**影响**：`web/src/components/shell/AppShell.tsx` 与 `.module.css`、
`web/src/components/shell/WorkspaceFilesToggle.tsx`（新）、
`web/src/features/workspace-files/*`（新）、`stores/ui.ts` 的 `filesPanelOpen`
（**不进 `partialize`**，与 `sidebarCollapsed` 同待遇）、`module-integration-*.md` 的对接说明。

### D36 · 文件浏览接口开在哪一面、要不要额外门禁 🔴

**背景**：工作区只读浏览的三个端点（列目录 / 读文本 / 读图片）吐的是**用户文件的内容**。
D33 之后模块面已经有了写权限，令牌的爆炸半径里已经有"改 `baseUrl`"和"在磁盘上建目录"。
这组接口是挂上去，还是另开一条口径？

**选项**
- **A. 挂模块面**，令牌一并管住，省一道门禁。
- **B. 只开浏览器面，并给这三个端点单独加回环 Host 校验** — 建议。
- **C. 只开浏览器面，沿用浏览器面其余接口的原样口径**（不加任何额外门禁）。

**决策**：**☑ B**，配套三条：

1. **两道一起判**：`Host` 与来源 socket 都要是回环（复用 `http/loopback.ts`）。缺一不可——
   只判 socket 的话，rebinding 场景下 socket 恰恰就是回环，正好漏掉。
2. **只加在这一组上**，浏览器面其余接口一个字不动。这一刀切在"最敏感的接口"上，
   `api-workspace-files.test.ts` 有一条用例专门守着"没切到别处"。
3. **不区分"哪个不满足"**：说了等于把服务端看到的头回显给一个外部来源。

**为什么不是 A**：消费方**是框架自己的界面**，不是模块。而且令牌的爆炸半径每加一样都要
重新论证一次——"读走用户文件内容"比"改配置"更靠近数据本身，这一样没有必要加。
**为什么不是 C**：浏览器面对 **DNS rebinding** 本来没有防线——恶意站点把自己控制的域名
解析到 `127.0.0.1`，浏览器就当成同源，CORS 完全不介入。在此之前这条攻击面只够翻一翻工作区
**记录**（名字、绑定路径、顺手改模型配置），代价有限；这组接口一旦开口，它够读**文件内容**。
回环校验挡的是浏览器，而浏览器里本来就拿不到令牌（这正是模块面的设计），所以令牌在这里
没有意义；`Host` 头是客户端自己写的，是这条链上唯一会露馅的地方。

**代价明说**：**把 UI 部署到非回环地址时这三个 GET 会 403**，文件面板打不开；回环校验也
挡不住同机同用户的其他进程（它们本来就能直接读磁盘）与浏览器扩展——这是本机单用户模型的
固有形状，与 D25 同一口径。

**影响**：`server/src/routes/workspace-files.ts`（新）、`server/tests/api-workspace-files.test.ts`
的「回环门禁」一组、`workspace-design.md` §7.3、`workspace-api.md` §11.6 与
`module-facing-api.md` §8（都写明"模块面不开这三个"）。

### D37 · 文件浏览要不要跟随软链 🟡

**背景**：列目录时软链**看得见**（条目 `type: "other"`），读内容呢？
dsh 的 `read` 明确**允许读到工作区之外**（它的消费方是 cc 的资源地址）。

**选项**
- **A. 跟随软链**，只靠 `realpath` 之后判包含兜底（软链指到工作区内就放行，指向外面才拒）。
- **B. 末段是软链一律拒，没有例外** — 建议。

**决策**：**☑ B**。

**为什么不是 A**：A 其实也挡得住逃逸，但它留下一个**每次都要推理**的问题——"我点的这个
路径，读到的到底是哪个文件？"判据变成"解完软链之后在不在工作区内"，用户得自己解一遍。
B 把这件事变成**不需要推理**：路径指向什么就读什么。代价是"用软链整理目录"的人点不开那些
条目（仍然列得出来，只是不可点），而判断"这条规则会不会挡住真实需求"的成本，比每次审查
"这个软链有没有指出去"低得多。

**实现顺序容易写反**：先 `lstat` 判末段是不是软链（是就拒），**再** `realpath` 解掉中间各段，
**最后** `isInside` 判包含。反过来先 `realpath` 的话，末段软链已经被解掉了，就再也分不出
"用户点的是个软链"还是"用户点的是那个文件"。这也是**与 dsh 的又一处刻意分叉**。

**影响**：`server/src/services/workspace-files.ts` 的 `#resolve`、
`api-workspace-files.test.ts` 里两条用例（指向外面的软链、指向里面的软链各一条，
证明"没有例外"）、`workspace-design.md` §7.1 的分叉说明。

### D38 · 「工作区文件」面板是分栏还是单栏、宽度谁来定 🟡（推翻 D35 的一条附带结论）

**背景**：D35 定"面板画在宿主侧的右缘"时，顺带按 dsh 的取向写了「一次看一个文件、
宽度固定 320px、不做拖拽调宽」——那是**默认沿用**，不是论证过的结论。
面板落地后实际用起来是这样的：点一个文件，目录树整块消失、换成内容，顶部一条返回；
用户在一个目录里连着看三个文件，就要在"树 → 内容 → 返回树 → 内容"之间来回跳四次。

**选项**
- **A. 维持单栏**：树和预览轮流占满面板，靠返回按钮切换。
- **B. 左右分栏 + 左缘可拖**：面板宽度翻倍（320 → 640），左 260px 固定给目录树，
  右边剩下的全给预览；面板左缘一条 8px 的手柄可拖，480–960。
- **C. 分栏但宽度固定**：只做 B 的分栏，不做手柄。

**决策**：**☑ B**。

**为什么不是 A**：A 的代价不是"少一个功能"，而是**导航与内容互斥**——这正是分栏要解决的那件事。
树是"我在哪一个目录",预览是"这个文件里是什么",浏览文件时这两条信息要同时在屏幕上，
和 IDE 里目录树与编辑器并存是同一条理由。

**为什么不是 C**：分栏之后"面板该多宽"这个问题**没有全局答案**，它取决于用户此刻在做什么——
读代码要宽，只看一眼文件名要窄，而那台显示器的宽度只有用户自己知道。
给一个固定值就是在替用户猜，猜错的代价是面板把会话区挤掉一半。
所以 C 不是省了工作量，是把一个必须给的旋钮藏起来。

**为什么 dsh 的"不做拖拽调宽"不能照抄**：dsh 那条结论是和 tab 停靠系统**一起**下的——
它的右栏是 dock 容器，宽度由 dock 布局管，所以单个 panel 不谈宽度是自洽的。
我们不做 dock（D35），面板就是一块普通的面板，"谁来定它的宽度"这个问题就落回我们头上。
**同一个词（"不做拖拽调宽"）在两边的含义不同，抄过来会抄错。**

**取值与来历**

> ⚠️ **下表里除了"键盘步长"与"左栏"两行，其余的数都已被下面的 D39 换掉了**
> （默认 480、下限 320、上限 = 页面三分之一）。这一段留下来是为了让"为什么当初
> 是这几个数"可查；**当前取值以 D39 为准**。

| 值 | 数 | 为什么 |
|---|---|---|
| 默认宽度 | **640**（= 320 × 2） | 需求原话是"展示宽度变大一倍"，于是它不是拍出来的数，是同一条 320 的继承 |
| 下限 | **480** | 必须显著大于左栏的 260，否则拖到底右栏只剩一条缝，等于把分栏拖回单栏 |
| 上限 | **960** | 1440 视口减去侧栏与两个 `--panel-inset` 之后，再宽就开始吃会话区的主体宽度 |
| 键盘步长 | **16** | 与 `SIDEBAR_RESIZE_STEP` 一致；`Home`/`End` 跳两端，让键盘用户不必按 30 下 |
| 左栏 | **260 固定** | 按 `FileTree` 的缩进（行首 8 + 每层 14）算，三层深处还留得下约 210px；再窄，`WorkspaceFilesPanel.tsx` 这类长名字在第二层就只剩半截 |

（同一段的"左栏 260 固定"在 D39 里改成了 `flex: 0 1 260px`：260 仍是基准，
但在窄端允许两列按比例一起收，否则面板拖到 320 时右栏只剩 60px。）

**实现上的两处分叉，各付了什么价**

1. **宽度状态放在 store 而不放在组件里，但**不持久化**。放组件里的话，收起面板再打开
   就回到 640——用户刚拖好的宽度被丢掉，而他能看到的因果只有"我点了一下收起"。
   不持久化则是与 `sidebarWidth` 同一口径：宽度是"这一次怎么看屏幕"，不是"我是谁"。
   代价是刷新页面回到 640，与侧栏宽度**行为一致**，不是特例。
2. **面板自己的宽度上限是 `max-width: 100%`，不是按容器算出来的值**。拖到 960 而上层
   只剩 700 时，面板贴满容器而不是画到容器外面（`.main` 有 `overflow: hidden`，画出去
   会被裁成半块）。代价：这时行内宽度与实际渲染宽度不一致，`aria-valuenow` 读的是行内那个。
   换成"按容器算上限"要一个 `resize` 监听来保持新鲜，而这里只需要它**不破相**。
   **将来若要加"面板宽度跨会话记住"，先把这一条解掉**——持久化的值 + 窄容器是唯一会露馅的组合。

**一条只有真浏览器才看得见的坑（写在这里是因为单测永远抓不到它）**：
面板里是 `white-space: pre` 的代码，一行可以很长。分栏容器 `.columns` 是 flex 子项，
而 `min-width: auto` 的 flex 子项下限是**内容的 min-content 宽度**——那个长行会把它顶到
1200px 以上，超出面板右缘，被 `.main` 的 `overflow: hidden` **裁掉**。
表现是"预览里的长行不滚动、直接看不见了"，而 `jsdom` 不做布局，**一条单测都不会红**。
判据写在 CSS 注释里（`.columns` 的 `min-width: 0`），验证靠真浏览器脚本。

**影响**：`web/src/lib/filesPanelWidth.ts`、`web/src/components/ui/ColumnResizer.tsx`
（从 `SidebarResizer` 抽出来的通用手柄，两处共用）、
`features/workspace-files/WorkspaceFilesPanel.module.css` 的分栏与 `min-width: 0`、
`stores/ui.ts` 的 `filesPanelWidth`、`files-panel-width.test.ts`（6 条）、
`workspace-files-panel.test.tsx` 的分栏与拖拽两组；
`workspace-design.md` §8 的"拖拽调宽"由不做改为做、`task-list.md` 的 dsh 分叉表、
`module-integration-smart-factory.md` §7 的对接说明（面板宽度已从 320 变 640 且可拖）。

### D39 · 面板挤压还是遮盖会话区、宽度上限怎么定、要不要全屏 🔴（修正 D35 与 D38 的取值）

**背景**：三条需求，都是**推翻我们已经落地的东西**，而且推翻的理由是需求方的使用感受，
不是新的技术事实：

1. 「右侧边栏的拖拽，应该对中间的对话页面的宽度做缩小挤压，**而不是遮盖**」——
   这正是 D35 里被否掉的选项 C（当时的理由是"跨源 iframe 每次都要重排"）。
2. 「而且应该允许拖拽到**整体页面的三分之一**」——D38 的上限是一个写死的 960，
   在 1440 的窗口上只到 2/3 的五分之一，够不着"三分之一"这个说法。
3. 「右侧的工作区，需要支持**全屏展示，和收起全屏展示**」——D38 里根本没有这一项。

**决策**

- **A. 挤压方式**：**☑ 内容区让路**。面板仍然绝对定位在 `<main>` 里（右缘钉在内容区右缘），
  但 `<main>` 在面板打开时给自己加 `padding-right` = 面板宽度。面板的包含块就是 `<main>` 的
  padding box，于是它正好落在让出来的那条空白里——**视觉结果就是"会话区被挤窄了"**。
- **B. 宽度范围**：**☑ 上限随页面走**。上限 = `pageWidth / 3`（下限 320 兜底：窗口窄到
  三分之一还不如下限时退化成下限），下限 320，**默认 = 上限**。步长 16 不变。
- **C. 全屏**：**☑ 铺满内容区**（`width: 100%`），**左边侧栏留着**；再点一次回到拖出的宽度。

**为什么挤压方式选"内容区让路"而不是别的**

- 不选"保持遮盖"：需求方要的就是会话区跟着让开，理由很实在——读文件时对话内容被挡掉三分之一，
  而挡住的恰好是**刚生成出来的那段**（会话区最后一行在底部，面板盖的是右侧一整条）。
  这不是我们替用户猜的取舍，是用户明确的偏好。
- 不选"真拆成并列的一列"（把面板做成 `<main>` 的 flex 兄弟）：那要把 `.main` 拆成
  "内容 + 面板"两层，`.main` 现在同时是圆角容器、滚动容器、绝对定位祖先与 iframe 宿主，
  拆一次四个角色的归属都要重写。`padding-right` 拿到的是同一个结果，只影响内容盒宽度。
- **代价明说（D35 否掉 C 的那条代价，现在由需求买下）**：留白有 300ms 过渡，那 300ms 里
  跨源 iframe **逐帧重排**，模块自己的布局逻辑要撑住这种连续变宽；而它是别人的代码。
  拖拽期间过渡被关掉（`.mainResizing`），所以拖拽本身不会拖着内容区走。
  这条代价写在 `AppShell.module.css` 与 `WorkspaceFilesPanel.tsx` 的文件头里，
  并写进对接说明让同事自己验一遍他们的页面在 2/3 宽度下长什么样。

**为什么上限是比例而不是一个数**

写死的 960 表达不了"页面的三分之一"：1440 上三分之一是 480，4K 上就是 1280。
一个固定常数在宽屏上会把用户锁在"拖不到自己屏幕尺寸下的合理宽度"里。
比例的代价是**上限随窗口变**，于是"用户存下来的宽度"可能在窗口拉窄后越界——
这一条由**渲染时再夹一次**解决（`useFilesPanelWidth`），store 里存的始终是"用户要的宽度"
（与 `sidebarWidth` 同一条：拖过的宽度不该被一次无关的操作弄丢）。

**为什么默认 = 上限**

需求方选的就是这一条（"默认打开也是页面的三分之一"）。诚实地说，它的直接后果是
**默认位置上"往左拖"是一个空操作**——没有比上限更宽的地方可去。这是取舍，不是 bug：
打开面板的意图就是"我要看文件"，先给足；要腾地方往右拖即可。
这条被写成 `workspace-files-panel.test.tsx` 里一条**独立的用例**，
就是让后人看到它是"已知的"而不是"拖拽坏了"。

**取值**

| 值 | 数 | 为什么 |
|---|---|---|
| 上限 | **页面宽度 / 3**（下限 320 兜底） | 需求原话；用比例而不是常数，宽屏上才够得着 |
| 下限 | **320** | 与 D38 的 640 减去左栏基准后大致同量级，是"两栏都还读得下去"的下界 |
| 默认 | **= 上限** | 需求方指定；代价见上 |
| 键盘步长 | **16** | 不变（D38） |
| 左栏 | **260 为基准，可收缩**（`flex: 0 1 260px`） | 面板 ≥ 460 时分配结果与 D38 的"固定 260"完全一致；320 时两列按比例一起收（≈181 / 139），而不是让树死占 260、右栏只剩 60 |

**全屏为什么是"铺满内容区"而不是"盖满整个窗口"**

这一列仍然属于会话页，而左侧栏回答的是"我在这个平台的哪里"。全屏时把它一起盖掉，
用户在全屏看一个文件的过程中要跳到别处，就得先退出全屏——而"看一个文件时顺手跳到专家页"
本来就是一个随时会发生的动作。铺满内容区同时保住了导航与全部的文件宽度，
**要改成盖满窗口是 `position: fixed; inset: 0` 一行的事**，这不是一个锁死的选择。

配套两条：

1. 全屏期间 **`<main>` 的 `padding-right` 刻意不动**（仍是拖出来的那个宽度）。
   此刻内容区被完整盖住，留白宽不宽没人看得见；留着它，**退出全屏那一帧什么都不用重排**——
   否则每次进出全屏都要让同事的 iframe 连续重排两次。真浏览器脚本里有一条断言专门守着
   "全屏前后 iframe 宽度一像素都没变"。
2. 全屏期间**不渲染拖拽手柄**：那时面板的左缘就是内容区的左缘，把手柄放在那里，
   拖它只会改到一个此刻看不见的宽度。拖动屏幕最左边却什么都没发生，比没有这个按钮更让人困惑。

**全屏状态放在哪**：`stores/ui.ts` 的 `filesPanelFullscreen`，与 `filesPanelResizing` 同一条理由——
面板与 `<main>` 是兄弟（都由 `AppShell` 渲染），状态只能放在它们之上；
**不持久化**，且**收起面板时一并复位**（`closeFilesPanel`）：全屏是"这一列现在铺满内容区"
的临时形态，下次打开直接铺满整屏会让人以为会话页不见了。这与 `filesPanelWidth`
刻意不同——那个留着是用户的资产。

**影响**：`web/src/lib/filesPanelWidth.ts`（上限改成比例 + 默认 = 上限）、
`web/src/lib/usePageWidth.ts`（新）、`features/workspace-files/useFilesPanelWidth.ts`（新，
宽度换算的唯一入口，面板与 `<main>` 共用）、`stores/ui.ts`（`filesPanelResizing`、
`filesPanelFullscreen`）、`AppShell.tsx` 与 `.module.css`（`padding-right` + `.mainResizing` +
绝对定位，仍需 `position: relative`）、`WorkspaceFilesPanel.tsx` 与 `.module.css`
（`width: '100%'`、全屏开关、分栏改 `flex: 0 1`）、`components/ui/Icon.tsx`
（`maximize` / `minimize` 两张图）、`i18n/messages/*` 的 `files.fullscreen`、
`files-panel-width.test.ts`（改成按页面宽度参数化）、`workspace-files-panel.test.tsx`
（新增"挤压会话区"与"全屏展示"两组）；
`workspace-design.md` §7.4 与 §8、`task-list.md` 的 §WF、
`module-integration-smart-factory.md` §7（**对接说明必须改口**：现在会话区是被挤窄的，
同事要自己验一遍 2/3 宽度下的布局）。

### D40 · 产物怎么做到"一份包在 Linux 与 Windows 上都能装能跑" 🟡

**背景**：需求是「设计整体的打包脚本，以及安装启动脚本，可以通过打包后的包，让用户在
Linux 或 Windows 上安装并启动」。把当时的产物拆开看，有**两个硬缺口**和一个空白：

1. **产物事实上只能跑 Linux x64。** 依赖树里只有 `@libsql/linux-x64-gnu` 与
   `@esbuild/linux-x64`，而这两个都是原生的：libsql 用 `@neon-rs/load` 的
   `currentTarget()` 拼出包名再 `require`（`win32 + x64 → @libsql/win32-x64-msvc`），
   esbuild 同理。Windows 上启动即 `ERR_MODULE_NOT_FOUND`。
2. **依赖树是符号链接编织的。** 归档里 tar 有 230 条 `lrwxrwxrwx`、zip 有 8312 条
   含 `S_IFLNK` 的条目（`server/node_modules/tsx` 就在其中）。Windows 自带解压器与
   7-Zip 默认都不创建软链，`tsx` 会落成一个 0 字节文件，`start.mjs` 解析 loader 失败、
   启动即退。README 里那段"请优先用 tar.gz、Windows 请用支持符号链接的工具"就是这个
   坑的自白——**把选择解压工具的责任推给了用户**。
3. **产物里没有任何地方能回答"这个包要哪个 Node"**：`engines` 只在仓库根
   `package.json`，而根清单不进产物。安装脚本与启动脚本都需要这个答案。

**决策**

- **A. 一份通用包**：同一个归档同时含 linux-x64 与 win32-x64 两套原生件，
  用户不需要先判断自己在哪台机器上该下哪个包。
- **B. 零软链**：打包时用 `--config.node-linker=hoisted --config.preferSymlinkedExecutables=false`
  安装出一棵实体目录树（符号链接 230 → 0），zip 与 tar.gz 因此**等价**。
- **C. 不自带 Node 运行时**：安装脚本只做预检（不满足就打印当前版本 / 要求版本 /
  下载地址），不下载、不解压运行时。**版本要求落在 `framework/server/package.json`
  的 `engines`**（产物里读得到的那一份），并由启动入口在启动时硬校验一次。
- **D. 安装与启动都是薄壳 + 单一实现**：产物里的 `install.sh` / `install.cmd` /
  `start.sh` / `start.cmd` 只负责"找到 node 然后调 `start.mjs`"，真正的活
  （版本校验、建数据目录、生成配置）在 `start.mjs --init` / `--self-check` 里做一次。
- **E. `.cmd` 纯 ASCII + CRLF**：中文说明一律只在 README；行尾在打包期规整并断言。

**为什么是一份通用包，而不是每个平台一份**

体积不是主要成本（+15–20 MB），**选错包才是**：拆成两份时用户得先判断自己是哪个平台、
哪个架构，而判断错的表现是"启动失败"或"缺原生件"，不是一个能读懂的提示。
一份包把"我该下哪个"这个问题整个删掉。代价是两套原生件都在包里，
但它们在磁盘上互不相关、只加载各自平台那一份，不存在冲突。

**为什么零软链是必须的，而不是"更保险"**

软链在这件事上没有任何收益：产物是要**被解压**的独立物，不是被 `require` 的工作副本，
没有"共享 store 省空间"可言（tar 里软链省的那点字节，抵不过一次解压失败）。
而它的失效方式是**静默的**——解压器不建软链、落一个空文件，然后在运行时报一个
和软链无关的错。所以这条不做成"README 里提醒一句"，而是做成打包期断言：
整棵树里**一条软链都不许有**，`tsx` / `harness-shared` / `fastify` / `@libsql/client`
必须是实体目录。归档写完还会读回来再验一遍。

**代价（明确记下）**：`pnpm-workspace.yaml` **没有**写进 `supportedArchitectures`，
而是把平台信息放在打包命令的 CLI 旗标上（`--os=linux --os=win32 --cpu=x64`）。
两种做法都能让 deploy 出双平台原生件，差别是副作用落在哪：
写进 workspace 配置会让**仓库自己的开发态安装**也多拉两份可选依赖（约 +20 MB，
每个开发者的 `node_modules` 都变大），而我们只需要打包时那一次。
选 CLI 旗标的代价是"平台清单在命令里而不是配置文件里"——所以它写在
`lib/project.mjs` 的 `ARTIFACT_TARGETS` + `deployPlatformArgs()` 里，有测试钉着，
不是散在脚本里的魔法参数。

**为什么安装脚本不动系统**

不 sudo、不写 `/opt` 或 `%LOCALAPPDATA%`、不改 PATH、不注册服务、不建快捷方式。
产物自带依赖树、没有编译步骤，"安装"实际只剩三件事：预检、数据目录、一份配置。
固定安装位置换不来任何东西，只会带来权限与卸载问题。**卸载 = 删目录**，
这是能对用户说的最干净的一句话。

**顺带修的三处"只在 Windows 上发作"的问题**（都是这一轮才暴露的，都在宿主侧代码里）

1. **权限自检在 Windows 上每次启动都误报。** 判定从 `index.ts` 里抽成纯函数
   （`server/src/lib/file-mode.ts` 的 `checkSecretFileMode`）：`0o666 + win32`
   判为"这个平台不按 POSIX 权限位管访问"，降级成一条 info；只有真的在 POSIX 上
   权限过宽才 WARN。同时把原子写的 `chmodSync` 换成 `chmodBestEffort`——
   原来它没有 try/catch，在没有 chmod 的文件系统上会**把"收紧权限失败"升级成
   "写不进令牌、服务起不来"**（`config/paths.ts` 一直是吞 ENOSYS 的，两处不对称）。
2. **带 BOM 的 `module.json` 被静默判非法。** Windows 记事本存"UTF-8"就是带 BOM 的，
   而 `JSON.parse` 碰到 BOM 直接抛 → 模块被收进 `invalid`、静默不注册。
   读取前统一切 `stripBom`（`server/src/lib/text.ts` 与 `scripts/lib/text.mjs` 各一份，
   两侧不能互相 import）；`cosight.env` 与旁挂的 `launch.json` 同理。
3. **Windows 保留设备名。** `lib/slug.ts` 原来只剥尾随 `.`，`CON` / `NUL` / `COM1`
   这类名字在 Windows 上建不出目录。撞上时接一个 `-ws` 后缀。

三条都**无法在本机（Linux）复现**，所以做法一致：判定抽成纯函数，
测试直接喂 `'win32'` / `0o666` / 带 BOM 的字节，把整类问题钉在测试上，
而不是靠"在 Windows 上试试看"。

**影响**：`framework/scripts/lib/project.mjs`（`ARTIFACT_TARGETS`、`nativePackagesFor`、
`deployPlatformArgs`、`ENTRY_SCRIPT_SOURCES`、产物内条目常量）、`framework/scripts/package.mjs`
（双平台安装、零软链断言、归档内 `REQUIRED_PATHS` 与可执行位）、
新增 `framework/scripts/artifact/`（`install.sh` / `install.cmd` / `start.sh` / `start.cmd` /
`cosight.env.example`，产物里唯一的那份真相）、新增 `framework/scripts/lib/artifact-scripts.mjs`
（编码与行尾规则）、`framework/scripts/start.mjs`（`--init` / `--self-check` / `--config`）、
`framework/scripts/smoke-package.mjs`（新增"模拟安装"段）、
`framework/server/package.json` 的 `engines`、新增 `server/src/lib/file-mode.ts`、
`server/src/lib/text.ts`、`scripts/lib/text.mjs`、`server/src/lib/slug.ts`、
`config/paths.ts`、`lib/atomic-file.ts`、`modules/registry.ts`；
新增文档 `framework/docs/packaging.md`；产物内 README 重写为两平台两条路径。

### D41 · 装配态要不要拉起模块？怎么拉起？🟡

**背景**：用户装完包、跑 `start.sh`、打开 `http://127.0.0.1:4300/` 后发现两件事：

1. 「新建对话」落在观测页，不是对话页；
2. smart-factory 的端口根本没起来。

查下来的结论是同一个：**产物里没有任何模块**。第一条是因为首页那个 `conversation`
capability 由 cosight-viewer 提供，而它的页面没随包发出去，iframe 打不开、落回宿主；
第二条是因为 `start.mjs` 只对模块**探活**——旁挂清单 `launch.json` 是开发编排用的
（`npm run dev`、相对仓库根），产物里既没有仓库也没有那套工具链，这段描述根本不成立。

原先 `lib/module-probe.mjs` 的口径是「开发态由 `dev-all.mjs` 拉起，装配态只探活」。
这条口径在"模块真的进包"之后就是假话：探活只能告诉你"没起来"，而用户要的是它起来。

**决策**

- **A. 装配态也拉起模块。** `start.mjs` 在产物布局下按顺序拉起 `modules/<id>/` 里
  声明的服务，等就绪后再起框架服务端。~~模块起不来不拖垮框架（记一行 `✗` 继续）~~
  —— 这一条已被 **D45** 反转：默认失败即停，`--keep-going` 保留旧语义。
  "不守护、不自动重启"的口径不变：就绪之后再崩的模块只报警。
- **B. 用第二份清单，不复用 `launch.json`。** 新增
  `docs/modules/<id>.artifact.json`（schema v1），消费者是打包脚本与 `start.mjs`；
  `launch.json` 继续只服务 `dev-all.mjs`。两份的 `cwd` / `command` 基准不同，
  不是同一件事的两种写法。字段与规则见 `packaging.md` §6。
- **C. 判定规则只有一条**：`docs/modules/<id>.artifact.json` 存在 ⇒ 这个模块进产物。
  没有硬编码名单；有 `module.json` 却没有 artifact 清单的模块会在打包输出里
  列为「未打进」，不允许静默漏掉。
- **D. 数据目录由 `start.mjs` 注入。** 清单里唯一支持的占位符是 `{{dataDir}}`，
  替换成用户数据目录（`--home` / `COSIGHT_HOME` / 默认 `~/.cosight-harness`）。
  模块自己决定把库、隔离 home 放到它的哪个子目录下。
- **E. 运行时契约不变。** `module.json` 仍然只描述怎么嵌（`entry` / `mounts` /
  `healthcheck`），`/api/modules` 不增加"是否可达"这类字段。
- **F. 只对产物布局生效。** 仓库布局下没有 `modules/`，开发态仍然只有
  `pnpm dev:all`（D27 不变）。`--no-modules` 可以只起框架。

**为什么不把启动命令塞进 `module.json`**

`module.json` 会被服务端读出来、经 `/api/modules` 发给浏览器。它天然是"给宿主看的
公开契约"。把进程命令放进去，等于把"怎么在这台机器上启动"也公开给前端，
而且开发态与装配态的命令本来就不同（`npm run dev` vs `node server/index.js`）。
分成两份文件，各自的消费者只有一个，边界才守得住。

**为什么允许 `bundle` 与 `services` 在同一份文件里**

它们描述的是同一个模块的"怎么打包"与"怎么运行"，分到两个文件会漂移
（改了 include 忘了改构建产物路径这类）。代价是打包脚本与 `start.mjs` 各读一段，
所以解析层把边界写死：`resolveSpecForRuntime()` 返回的对象里**没有** `bundle`。

**越界检查不是洁癖**：清单里的 `cwd` 最终会变成一次 `spawn`。能改产物的人本来就能改
`start.mjs`，所以这里不新增信任边界；但一个写错的 `"cwd": "../../.."` 会让模块进程
跑到框架目录外面去，排查时完全看不出是清单的问题。因此在解析期就拒绝。

**影响**：新增 `framework/scripts/lib/artifact-spec.mjs`（解析 + 严校验）、
`framework/scripts/lib/artifact-modules.mjs`（判定 / 构建 / 展开条目 / 打包期断言）、
`framework/docs/modules/cosight-viewer.artifact.json`、
`framework/docs/module-artifact-integration.md`；
`framework/scripts/start.mjs`（多进程监督、清单同步、`--no-modules`、自检新增模块行）、
`framework/scripts/lib/project.mjs`（`modulesSubdir`、`artifact-spec.mjs` 进 import 闭包）、
`framework/scripts/package.mjs`（模块条目与必需路径）、
`framework/scripts/smoke-package.mjs`（模块端到端断言、步骤序号由数组派生）、
`framework/scripts/lib/runtime.mjs`（`waitForAnyHttpOk` 支持中止）、
`framework/scripts/lib/module-probe.mjs` 与 `module-launch.mjs` 的头注释（不再说"只探活"）；
`packaging.md` 新增 §6。**没有改** `smart-factory/` 与 `cosight-viewer/` 的任何文件；
smart-factory 的缺口写进对接说明，等模块方补生产链路。

### D42 · 多服务模块与 smart-factory 的生产链路 ✅

**背景**：D41 的机制只覆盖"一个模块一个服务、纯 JS 依赖"的形态。smart-factory 是
反例：前端是 Vite 构建产物、接口写死根相对 `/api/...`（含 WebSocket）、后端要
Prisma + 原生查询引擎、还要读框架的 `.module-token`。它没有根 `package.json`，
`server/` 与 `web/` 各自装依赖。

**决策**

- **一个模块可以声明多个服务。** `services[]` 逐项有 `cwd` / `command` / `port` /
  `readyPath`；`start.mjs` 逐个探活，任一失败只跳过该模块。这样 API 与前端页面可以
  在同一个模块里分别起进程。
- **同源由产物里的辅助件解决，不改模块源码。** 新增
  `scripts/artifact/module-web-server.mjs`：一个端口同时做静态托管（含 SPA 回退）、
  `/api/*` 的 HTTP 反代与 WebSocket 升级代理。它通过 `bundle.assets` 从框架仓库
  搬进模块目录，不进入模块的版本控制。没有它，页面在 5173、接口在 3000，
  根相对 URL 全部打空。
- **数据库模板在打包期生成，运行时只复制。** `bundle.database` 用临时的
  `COSIGHT_HOME` 跑一次模块自己的 `db sync`，把结果作为 `db-template.sqlite` 进包；
  新增 `scripts/artifact/module-db-init.mjs` 在每次启动前幂等复制（目标已存在就不动）。
  这样用户机器上不需要 Prisma CLI（71 MB），也不需要联网。
- **需要框架上下文的模块用 `startAfter: "framework"`。** 启动顺序改为
  「立即可起的模块 → 框架 → 延迟模块」。`.module-token` 与框架实际端口在框架就绪后
  才存在，起早了只会看到连接失败。`{{frameworkUrl}}` 在同一时刻注入。
- **多构建与可执行件。** `bundle.builds` 让服务端 `tsc` 与前端 `vite build` 各自
  判定新旧；`bundle.executable` 钉住 SDK 自带 `claude` 的可执行位；
  `bundle.dependencyRoots` 让"前后端各自装依赖"的模块也能核对完整性；
  `bundle.required` 覆盖构建产物之外必须存在的运行时文件。
- **平台范围**：最初只声明 `platforms: ["linux-x64"]`，Windows 上启动时跳过
  （打包仍带文件，同一份包不拆）。2026-10-27 实测通过后改为
  `["linux-x64", "win32-x64"]`：服务端代码里没有 POSIX 专有调用，阻塞只在两个
  原生件。两处改动——`bundle.required` / `bundle.executable` 同时钉住两个平台的
  SDK 可执行件，`prisma/schema.prisma` 的 `binaryTargets` 加 `windows`——

### D43 · 删除工作区时同步删除框架创建的目录 ✅

**背景**：D32 定的是"`DELETE` 不删目录"。实际使用中，用户在工作区弹窗里删除工作区后，
框架按工作区名创建的 `<工作区根>/<slug>` 仍留在磁盘上，看起来像删除没做完。用户明确要求
删除记录时把工作区目录一并删掉。

**决策**

- **只删框架自己创建的直接子目录**：`path.dirname(directory) === realpath(工作区根)`，
  且 basename 不是 `_public`。这类目录是 `POST` 不传 `directory` 时框架亲手建的，
  语义明确。
- **外部绑定目录不删**：用户填绝对路径绑定的目录（`/srv/projects/existing`）只解除记录。
  对任意绝对路径递归删除等于让一次 HTTP `DELETE` 决定用户项目目录的命运，误删不可逆。
- **`_public` 永不删除**，即使某条记录把它绑成工作区目录。
- **符号链接不跟随**：如果目录被替换成链接，只 `unlink` 链接本身，目标内容原样保留。
- **先删目录、后删记录**：目录删不掉（权限、占用）时记录仍在，用户可以修好后重试；
  反过来会留下"记录没了、目录还在"的脏状态。
- **路径是文件系统根时拒绝删除**：`COSIGHT_WORKSPACES_ROOT=/` 属于误配置，
  此时任何直接子目录都不再能确定是框架建的。

**代价**：`DELETE` 从"纯数据库操作"变成有磁盘副作用，且返回前要递归删除目录——
工作区很大时会慢，但这是用户点了删除后期待发生的事。外部绑定目录的行为与之前一致。

**验证**：`workspace-directory.test.ts` 覆盖"框架目录连同内容删除 / 外部目录保留 /
`_public` 保留 / 符号链接只删链接"；`api-workspace.test.ts` 与
`api-module-workspace.test.ts` 各覆盖一次经 HTTP 的删除。

**影响**：`services/workspaces.ts`（`deleteById` 返回处置结果）、两个工作区路由的日志、
`config/paths.ts` 的布局注释、`workspace-design.md` / `workspace-api.md` /
`module-facing-api.md`、前端删除确认文案。

### D44 · 专家页改为 smart-factory 模块，原生页删除 ✅

**背景**：框架原来自己渲染「专家」页（C1 的最后一个原生页面），数据来自框架后端的

**代价**

- 专家页不再由框架控制：空态、错误态、卡片排版、搜索行为都随 smart-factory 的版本走。

- smart-factory 的「使用」要跳到框架首页 `?expert=`：iframe 没有
  `allow-top-navigation-by-user-activation`，模块方已经做了兜底（开新标签），
  所以原标签页不会跳转。要改成原页跳转需另开一条沙箱权限，本轮不做。
  **2026-10-21 补充（用户要求）**：设计页「返回」同样要整页回 `/experts`，
  新标签落地的体验不成立，于是补上 `allow-top-navigation-by-user-activation`，

  顶层跳转仍被挡。模块侧"被挡就开新标签"的兜底保留，用于宿主还是旧版本时。
- 模块未接入时 `/experts` 显示「模块尚未接入」，用户无法从框架里管理专家——这是

**验证**：`module-host.test.tsx` 覆盖 entryPath 与 entry 查询串的拼接；

钉住 smart-factory 的 `experts` 挂载与 `entryPath`；web 全量 343 条、server 346 条通过。

**没有做**：不改 `smart-factory/` 的任何文件（同事的模块）；不删后端专家接口；
不给**无用户激活**的顶层跳转权限（`allow-top-navigation` 仍不加；2026-10-21 只补了
`allow-top-navigation-by-user-activation`，见上文代价一节）。

### D45 · 启动失败即停（`--keep-going` 回退旧行为）✅

**背景**：原来模块起不来只记一行、框架照常运行——理由是"模块是外挂，坏了不该拖垮
框架"。但产物里自带的模块（cosight-viewer、smart-factory）是产品的一部分：
"专家页打不开"不是可接受的降级，而且用户看到的是一份"启动成功"的日志加一个空页面。
用户要求「如果中间存在缺失或者异常，则启动失败，并给出异常的打印」。

**决策**

- **默认反转**：以下任一情况都算启动失败——模块准备步骤失败、服务 spawn 失败、
  `readyPath` 超时、框架 30s 内 `/api/health` 不就绪、框架端口试绑失败；
  失败时先 `await supervision.stopAll(13)` 再退出，避免 `detached` 进程变孤儿占端口。
- **退出码 13**，并打印固定四段：阶段 / 原因 / 处理 / 影响。插件阶段仍是 12，
  预检 10——三个码对应"该改哪里"。
- **不算失败**：平台不支持的模块（`skipped`）、`--skip-module <id>` 明确排除的模块。
  它们仍留在注册表里，前端能看到"已注册但未拉起"。
- **`--keep-going`** 恢复旧语义（记一行、继续），给"我只想要会话"的场景留口子。
- **端口先试绑**：框架端口在 spawn 之前用 `checkTcpBind` 试一次，失败直接给
  "端口被占 + 换端口/查占用"；否则用户看到的是服务端的一大段栈。

**代价**：一个可选模块的缺陷会阻塞整个产品启动；`--keep-going` 是逃生舱，
但默认路径更符合"交付物要么能用、要么明确说哪里不能用"。

**验证**：`runtime.test.mjs` 覆盖端口试绑三种情况；手工占住 4300 后启动，
输出四段并退出 13；正常启动仍能到达"已就绪"并随 SIGTERM 干净停止
（模块与框架进程组都回收，端口立即可复用）。

### D48 · 产物里旧数据库的结构升级（只做加法，自动备份）✅

**背景**：产物里的模块库原来只在**文件不存在**时从模板拷一次。smart-factory 加了
`agents.builtin`、把 `agents.workspace_id` 放宽成可空、给 `runs` 补了 `stage` 之后，
已经跑过的数据目录仍然是旧结构，服务启动即报
`The column 'main.agents.builtin' does not exist in the current database`，
整次启动按 D45 退出 **13**。产物里**没有 Prisma CLI**（开发依赖、体积大），
模块自己的 `server/scripts/db.mjs sync` 跑不起来，所以升级路径必须由宿主侧补上。

**决策**

- `db-init.mjs` 在目标库已存在时做一次**结构比对**（用 Node 内置的 `node:sqlite`，
  不新增依赖），模板是唯一真相。差异分三种处理：

  | 差异 | 动作 |
  | --- | --- |
  | 模板有、旧库没有的表 / 可 ADD 的列 | `CREATE TABLE` / `ALTER TABLE ADD COLUMN` |
  | 列定义变了（可空性、默认值、类型）或新增必填无默认列 | 按模板**重建表**：建新表 → 拷公共列 → 换名 |
  | 索引 | 缺的补建、定义变了的重建、模板里没有的移除（索引不含数据） |

- 重建时，历史行里新增的必填无默认列用**类型空值**顶上（`''` / `0`），
  这个值只用于拷贝，不写进 schema。
- **模板外的列**默认保留（数据可能来自别的分支）；只有 `NOT NULL` 且无默认值时失败——
  留着它会让模块自己的 INSERT 失败，不如当场说清楚。
- 真要写文件前先 `wal_checkpoint(TRUNCATE)`，再备份成 `<文件名>.bak-<时间戳>`。
  没有差异时**一个字节都不写**，重复启动不会累积备份。
- 不兼容时**保持原样**退出 1，打印目标库路径与"备份后删除重建"的处理办法；
  绝不擅自删库。

**代价**：宿主侧多了一份"通用 SQLite 结构同步"的维护面（约 200 行，无模块特定 DDL）。
带语义的迁移（列改名、数据回填、触发器）仍然得由模块方提供，这里只保证
"旧库还能被新版本打开"。模板外的列会留在库里，所以升级后的库与模板**不是逐字节一致**。
另：Node 22/24 的 `node:sqlite` 仍会打印 ExperimentalWarning，prepare 命令里用
`--disable-warning=ExperimentalWarning` 压掉，避免混进启动日志。

**验证**：`module-helpers.test.mjs` 新增三条（结构追平 + 数据/外库列/备份、不可保留的
外库列失败且原库不变、纯加列不重建）；拿一份真实的旧 `smart-factory.db`

`builtin` 等列补齐，历史行保留，索引集合与模板一致，第二次运行零输出、零备份。

### D49 · SPA 回退不接管"看起来像资源"的路径 ✅

**背景**：框架服务在生产态用 `@fastify/static`（`wildcard: false`）托管 `web/`，
未命中的 GET 交给 404 处理器回退到 `index.html`，保证 `/experts` 这类前端路由刷新不白屏。
问题出在**带扩展名的路径**上：升级或重装后，浏览器里还留着旧页面的 HTML，它引用的
`/assets/index-<旧哈希>.js` 已经不在新包里。服务器把它也回退成 `index.html`（200 + `text/html`），

真正的"资源缺失"被伪装成了 200。

**决策**：只有**不带扩展名**的 GET（且非 `/api`）才回退到 `index.html`；带扩展名的路径
（`/assets/*.js`、`/fonts/*.woff2`、`/favicon.ico`……）缺文件时如实返回 **404 信封**。
判定用 `path.posix.extname(pathname) !== ''`，与模块侧 `module-web-server.mjs` 完全一致
（那边早就这么做并有用例）。

**代价**：如果将来出现"路径里带点"的合法前端路由，刷新时会得到 404 而不是页面。
当前路由（`/experts`、`/agent-dev`、`/history`、`/knowledge`、`/observability`）都不带点；
真遇到时把该路径加白名单即可，而不是放宽整条规则。

**验证**：`error-handler.test.ts` 新增「缺失的带扩展名资源返回 404 信封」；
原有的「前端路由回退到首页」「未知 API 仍 404」「真实静态文件优先」继续通过。

### D50 · 静态资源缓存不吃文件 mtime ✅

**背景**：D49 让"资源缺失"显形之后，升级后仍会稳定复现同一类白屏——浏览器请求
上一版 `index.html` 里引用的 `index-KENmPXQz.js`，服务器返回 404。服务端自己检查却
完全正常：`GET /` 返回的正是当前 `index-CNHzbQK2.js`，且该文件可访问。

根因在**协商缓存**：打包追求可复现，归档里所有文件的 mtime 都是 1970；
`@fastify/static`（底层 `send`）默认的 ETag 是「**字节数 + mtime**」。
`web/index.html` 两版都是 493 字节，于是新旧文件的 ETag 都是 `W/"1ed-0"`。
浏览器（`cache-control: public, max-age=0` 要求每次回源）带着旧 ETag 发
`If-None-Match`，服务器判"没变"回 **304**，浏览器继续使用缓存里的旧 HTML，
再去要旧哈希资源——此时旧文件已经不在包里，于是 404 + 白屏。硬刷新能绕过，
但用户没有任何线索知道要这么做。

**决策**

- 静态插件关掉 `etag` 与 `lastModified`：不再产生基于大小/mtime 的校验器，
  条件请求不会得到 304。
- 缓存策略改由 `cache-control` 显式表达：
  - `index.html` 及未哈希文件 → `no-cache`（每次回源；体积很小）；
  - `assets/**`（文件名带内容哈希）→ `public, max-age=31536000, immutable`。
- 模块侧 `module-web-server.mjs` 本来就不发 ETag/Last-Modified，`index.html`
  固定 `no-cache`；两套静态托管现在行为一致。

**代价**：`index.html`（约 500 字节）每次导航重新下载；未哈希的字体/图标失去 304
省流。相比"升级后白屏且无法自查"，这个成本可以忽略。

**验证**：`static-cache.test.ts` 三条（旧 ETag 换不到 304、`assets/` immutable、
深链接仍回退首页）；实机用旧 ETag `W/"1ed-0"` 请求 `GET /`，修复前为 **304**、
修复后为 **200** 且响应不再带 ETag。

### D51 · 知识库路由设置：单条生效、侧栏唯一的打开入口、模块面只读、不探测可达性 🔴

**背景**：用户能配多个知识库界面，但各模块只需要"现在该把用户带到哪个地址"。
配置入口要跟模型设置平级，模块要能查到；写入只归设置里的用户。

**决策**

1. **一张表 + 至多一条生效**。`rag_knowledge_bases.is_active` 上加**部分唯一索引**
   （`WHERE is_active = 1`）：应用层用事务"先清后置"保证切换，索引则兜住绕过仓储的写入
   （手工改库、并发写、将来新增的代码路径）。只有应用层自觉的话，一次疏忽就是两个"当前可用"。
2. **激活是切换，不是置位**。`POST /:id/activate` 与 `PATCH {isActive:true}` 等价；
   旧的自动变回 `false`。列表里永远至多一个徽标。
3. **删除不自动补位**。删掉生效项后就是"没有可用知识库"（`/active` → `200 + null`），
   与模型/代理的既有口径一致：前端不替用户选，确认语里明说后果。
4. **模块面只读，两个 GET**（列表 + `/active`）。写入者是用户，模块没有写理由；
   门禁沿用 `module-face.ts` 的父级 `onRequest`（回环 + 无 `Origin` + 令牌）。
5. **不做可达性探测**。保存时不发请求去试 `routeUrl`：地址可能是内网服务，
   服务端主动连就是 SSRF 跳板，而且"这一刻连不上"不说明配置错。
6. **地址两条硬规则**：`http(s)` 绝对地址；**不得内嵌账号密码**（`user:pass@`）。
   前后端各校验一次——契约里的 refine 是边界，表单里的检查是别让用户先吃一次 422。
7. **编辑表单不含生效开关**。`PATCH` 不带 `isActive`：混进保存里会让"只改个名字"
   顺手换掉正在用的那条，而界面上看不出异常。切换只在列表行上。
8. **打开入口只有侧栏「知识库」一处**。设置里的列表行**不**给「打开」按钮：同一个动作
   留两个入口，行为迟早会漂。侧栏这一项：配好了渲染成指向 `routeUrl` 的外链，**在新的
   浏览器标签页打开**（`target="_blank" rel="noopener noreferrer"`；2026-10-28 修订，
   取代"宿主内嵌套 `/knowledge`"的口径）；没配时渲染成按钮，点了**直接**打开
   「设置 → 知识库路由设置」并展开新增表单——不再先弹一层"去配置"的提示，用户点菜单
   想要的是一张能填的表单。从这条路径进入的新增表单预勾「设为可用」：否则照提示填完保存，
   侧栏仍是按钮，会落进"建了却还是打不开"。面板自己的「新增」按钮保持默认不勾。
   生效项走 `useActiveRagKnowledge()`，写操作后整组键失效，**保存完立刻可点，不用重启**。
9. **`/knowledge` 由 `KnowledgePage` 承载，保留为直接访问时的内嵌视图**（2026-10-28 修订：
   侧栏已改为新标签页打开，本页不再是从菜单进入的落点）。该页把 `routeUrl` 放进 iframe：
   沙箱与模块宿主同一份白名单，另给剪贴板读写；未配置时给空态与「去设置新增」；读取失败
   与"没配置"分开呈现（错误 + 重试），避免把后端故障说成未配置。保留这条路由还有两个
   具体理由：`NAV_ITEMS` 的一致性测试要求每条 `to` 都有落点；旧书签不应变成 404。
   这是 D24 `allowedOrigins` 边界的一个**有意例外**：被嵌地址由本机用户在设置里当场选定、
   且至多一条，与"模块自带任意来源"不是一回事；模块侧仍不得自行嵌入（见 `rag-knowledge-api.md` §6）。
10. **侧栏元素的类型跟着数据走**。有生效项时是外链、没有时是按钮，因此导航表的
   "每条都是一个链接"不再是全局成立的约定；外链也不参与当前页高亮（不会出现
   `aria-current`）。`NAV_ITEMS` 的一致性测试为它留了例外。

**代价**：多一条近似重复的配置表；"至多一条生效"需要三处（契约、仓储事务、索引）保持同步，
漏掉任一处都不会立刻报错。用户不能一次配"每类知识库各一条"——那需要分组，
现在明确不做（等真出现第二个消费方再谈）。侧栏这一项与其余导航项不再是同一种元素，
导航表的"每条都是一个链接"不再是全局成立的约定，读代码时要知道这个例外。

**验证**：`shared/src/contracts/rag-knowledge.test.ts`（25 条：协议、凭据、长度、默认值）；

### D52 · 绑定目录由**服务端**弹系统目录选择器 ✅

**背景**：工作区的「绑定目录」此前只能手输绝对路径，用户反馈"体验差"。浏览器这一侧
拿不到绝对路径——`<input webkitdirectory>` 只给 `File` 对象、`showDirectoryPicker()`
只给 `FileSystemDirectoryHandle`，两者都没有路径；而工作区存的是**这台机器上**的绝对
路径。后端与本机桌面在同一个用户会话里，所以对话框只能在服务端拉起。

**决策**

1. **服务端 spawn 固定命令，不开 shell**。候选命令是一张常量表
   （`server/src/services/directory-picker.ts` 的 `dialogCommands`）；用户给的"起始目录"
   只以 **argv 元素**或**环境变量**传下去。Windows 那条尤其如此：脚本是 `-Command` 的一个
   参数，往脚本源码里拼路径等于把用户输入当 PowerShell 代码执行。
2. **平台回退顺序**：win32 → `pwsh`（PowerShell 7，Vista 风格对话框）→ `powershell.exe`
   （带 `-STA`，`FolderBrowserDialog` 是 COM 组件；显式把管道输出切成 UTF-8，否则中文
   系统回 GBK）；darwin → `osascript` 的 `choose folder`（取消的 `-128` 在脚本里接住）；
   其余 → `zenity` → `kdialog`，**没有 `DISPLAY`/`WAYLAND_DISPLAY` 时一条候选都不给**。
   候选"启动失败"或"带 stderr 退出"都换下一个，只有一个坏掉的工具不该让另一套桌面
   的用户用不了这个功能。
3. **三种结果必须分得开**：选中 → `200 { path }`；取消 → `200 { path: null }`（正常结果，
   前端保持原值）；这台机器弹不出来 → `501 NOT_IMPLEMENTED`；工具报错/超时（5 分钟）→
   `500`。把"打不开"说成"你取消了"，用户会以为是自己点错了。
4. **回环门禁**（复用 `server/src/http/loopback.ts`）：`Host` 与来源 socket 都必须是回环，
   否则 `403`。这个接口会在用户桌面上弹模态窗口、并把选中路径回给调用方，正是 DNS
   rebinding 那条链上代价更高的一端。代价明说：**把 UI 部署到非回环地址时这个按钮用不了**。
5. **一次只开一个对话框**：`pick()` 上的并发请求复用同一个 promise。模态窗口同时开两个
   会把用户逼进"关掉一个才能操作另一个"。
6. **起点只接受真实存在的目录**；选中路径去掉尾分隔符（`POSIX path of` 一定带）但保留
   根目录本身。
7. **界面**：输入框右侧常驻「选择目录」按钮；输入框**为空**时点它本身也打开选择器
   （用户最自然的动作），**已有值时只当普通点击**——D16 允许手输一个还不存在的目录，
   想微调路径的人不该每次都被对话框拦住。选择器的失败单独一行提示（"请手动输入路径"），
   **不**塞进字段错误里：坏的是机器，不是用户填的值，输入框不该因此变红、也不该带
   `aria-invalid`。
8. **关掉浏览器的表单历史下拉**：名称与绑定目录两个输入框（连同 `<form>`）都写
   `autoComplete="off"`。用户点名称框看到的「默认工作区」是浏览器保存的历史值，
   工作区名是一份配置、不是一次搜索。字段级也写一遍，只写在表单上有实现会忽略。

**代价**：回环限制（远程访问 UI 时按钮不可用）；Linux 需要 `zenity` 或 `kdialog`，
两个都没有时只能手输；原生窗口可能被浏览器挡在后面，等待期间按钮文字改成「等待选择…」
是唯一的反馈；Windows 上的 PowerShell 脚本依赖 .NET 的 `System.Windows.Forms`
（桌面版 Windows 自带，Server Core 没有）。实现全在服务端，前端只发一次 POST。

**验证**：`server/tests/directory-picker.test.ts`（命令表按平台、起点不进入脚本源码、
UTF-8 标记、取消/失败/超时不混、候选回退、单飞、真实 spawn 的 stdout/ENOENT/超时）；
`server/tests/api-workspace-picker.test.ts`（200 选中 / 200 取消 / 501 不可用 / 500 异常 /
422 相对路径在入口被拒 / 起点透传 / 非回环 Host 403）；`web/tests/workspace-dialog.test.tsx`
的「选择目录」六条（填值、空框点击、有值时点击不发请求、起点与取消、失败提示不改
`aria-invalid`、两个输入框 `autocomplete="off"`）。

### D53 · 知识库 API Key：每条路由可选 + 服务端默认回落 ✅

**背景**：知识服务（RAG Studio）的 Agent API 用 `X-API-Key` 鉴权，smart-factory 从自己的
`CO_KNOWLEDGE_API_KEY` 取值。此前框架只知道知识库的登录地址与账号密码，这枚 Key 只能
散落在模块各自的 `.env` 里。用户要求把它收进「设置 → 知识库路由设置」，并给一个默认值。

"把值预置进代码"这条路走不通：仓库正在准备开源，D26 也要求明文只进
`.credentials.yaml`。默认值因此不能是提交物的一部分。

**决策**

1. **两层，职责分开**：每条路由可配自己的 Key（D26 引用，键 `rag-knowledge-api-key:<id>`）；
   服务端可用环境变量预置一枚全局默认。模块面 `/active` 返回的 `apiKey` 是**生效的那一枚**
   ——自己的优先，没配回落默认。回落放在 `services/module-rag-knowledge.ts` 而不是仓储：
   默认值属于服务端配置，写进库会让"改了环境变量却不生效"（旧值早被复制进每一行）。
2. **默认值不落库、不回显**：浏览器面只多一个 `GET /rag-knowledge/defaults`，回
   `{hasDefaultApiKey: boolean}`。前端据此把"留空 = 用默认"写进提示语，而不是让用户对着
   空输入框猜。任何浏览器响应里都不出现默认值本身。
3. **双读变量名**：`COSIGHT_KNOWLEDGE_API_KEY` 优先，其次 `CO_KNOWLEDGE_API_KEY`。
   后者正是模块的同名变量，一份 `cosight.env` 写一行就能同时喂框架与模块；前者用来
   只想给框架配时与模块解耦。候选取**第一个非空白值**（不是 `a ?? b`）：显式的
   `COSIGHT_KNOWLEDGE_API_KEY=` 不该把另一枚能用的变量挡掉。
4. **界面沿用 D26 的三态**：留空保持、送值覆盖、`null` 清除；"已配置"用掩码表达。
   清除后自动回落到默认，不需要二次确认——它不是删除数据，只是回到默认。
5. **预置值不进 seed**：出厂默认路由不带 Key；默认只从部署环境来。开发态用 shell 环境
   变量，产物态写进 `cosight.env`（`cosight.env` 已加进 `.gitignore`）。

**代价**：改默认 Key 要重启服务端（配置只在启动时读一次）；浏览器面无法得知"实际生效的
是路由自己的还是默认的"（有意——知道这一点没有用，反而泄露默认是否存在之外的部署信息）；
smart-factory 目前仍读自己的 env，框架不代改模块，对接方式写在
`module-integration-smart-factory.md` §11。

**验证**：`server/tests/config.test.ts`（空白/优先级/显式留空回落）；`api-rag-knowledge.test.ts`
（`/defaults` 不被 `/:id` 吞掉、增删改只写不读、删除清两枚凭据）；`api-module-rag-knowledge.test.ts`
（`/active` 给明文、列表只给 `hasApiKey`、默认回落与"自己的优先"）；`web/tests/settings-rag-knowledge-panel.test.tsx`
（填了就送出、留空 PATCH 无键、清除送 `null`、有默认时提示语换成"使用默认"）。

### D54 · Agent 代理没有新增入口；模型首次配置默认设为当前使用 ✅

**背景**：两处设置界面的语义修正。一是模型设置里新增表单的「设为当前使用」恒为关，
用户配第一个模型时还要额外点一次行上的「设为当前使用」，否则平台有配置却没有可用模型。
二是 Agent 代理配置面板上的「新增代理」按钮——它开出的空表单与"模块实际在跑哪个代理"
没有关系，保存下来的一条只是个孤立记录。

**决策**

1. **Agent 代理配置取消「新增代理」**。界面只做查看 / 编辑 / 删除 / 设为默认；
   写入方是接口 `POST /api/agent-proxies`（后端接口与契约**保留不动**，只摘掉前端入口）。

**代价**：代理配置从此**没有 UI 新增路径**，只能用接口（curl / 模块侧写入）建；
