# 验收与测试指南

> 面向提交功能改动、做版本回归和评审测试覆盖的贡献者。
> 工具层入口见 [`tools/verify/README.md`](../tools/verify/README.md)（接口/链路脚本）、
> [`e2e/README.md`](../e2e/README.md)（浏览器用例）、[`TECHNICAL-GUIDE.md`](TECHNICAL-GUIDE.md) §10.4（单测与 CI）。

验收不是把功能点挨个点一遍，而是**用用户真实会走的路径证明：任务能完成、失败能恢复、结果能解释**。
只测函数、不测用户路径，容易漏掉交互反馈、错误恢复、边界数据和文案一致性问题。

---

## 1. 测试分层与入口

每一层只负责它能负责的事，**不要把上层的问题压给下层**。

| 层 | 位置 / 命令 | 负责什么 | 不负责什么 |
|---|---|---|---|
| 单元测试 | `cd frontend && npm run test:unit`；`cd backend && python -m pytest -q`（基线见 [技术文档 §10.4](TECHNICAL-GUIDE.md#104-测试)） | 纯函数、状态机、API 语义、契约快照 | 页面反馈、布局、跨页流程 |
| 契约一致性 | `tools/verify/generate-rkb-openapi.py --check`、`verify-agent-openapi.py` | 运行时路由与 `contracts/openapi/*.yaml` 一致 | 参数语义是否满足产品承诺 |
| 接口 / 链路验收 | `tools/verify/*.py` | 建库→上传→检索、编排→发布→执行、图谱抽取等真实链路 | 浏览器交互 |
| E2E | `e2e/`（Playwright） | 用户旅程、弹窗、错误分支、筛选组合 | 深层检索质量 |
| 视觉回归 | Playwright 截图：320 / 768 / 1024 / 1440 关键页与弹窗 | 布局重叠、断点溢出、主题 | 功能正确性 |
| 评测 | `eval-data/`、`tools/rag-metrics/`、`docs/rag-benchmark-20261101.md` | 召回/重排/端到端质量指标 | 功能是否可用 |
| 人工探索 | 本指南 §3 清单 | 产品判断、文案语气、市场定位 | 重复机器能跑的回归 |

**硬约束**：后端单测 `skip` 必须为 0；E2E 与验收脚本必须跑在**与部署同一构建**上。

## 2. 通用验收判据

### 1）缺陷即用例（bug → regression test）

每个修复都必须附一条**先红后绿**的回归用例（单测 / 组件 / E2E / 配置断言任选其一）。
没有用例的"已修复"不算完成。

- 修复前：先写用例并确认它在旧代码上失败（记录失败输出）。
- 修复后：用例转绿，并入回归集；下一轮先跑回归集，再做探索。

### 2）错误分支三问

每个 4xx/5xx 路径都要回答：

1. **有没有恢复入口？**（409 重复文件 → 能不能覆盖；目录同名 → 能不能改名）
2. **是不是只提示一次？**（批量失败不能每个文件刷一行）
3. **成功/失败有没有反馈？**（复制、上传、保存不能"点了没反应"）

典型的"死胡同"是：导入遇到同名文件时把后端 409 文案直接展示给用户，但页面上没有执行覆盖的按钮，
用户只能反复点导入。这类分支必须由 E2E 覆盖。

### 3）UI 文案的承诺 = 后端必须有的能力

搜索框写"搜索名称、ID 或创建人"，后端就必须同时匹配这三列，并有对应用例；
占位符、空态、帮助文案里承诺的字段/动作，逐条落到测试里。

### 4）标签与取值同源

标签写什么，值就必须是什么：写"命中文档"就不能展示切片数，
写"总耗时"就要在超过 1 秒时换单位。i18n key 建议带语义（`metricChunks` 而不是 `metricHits`），
改文案时必须回看取值来源。

### 5）边界与"恶意"夹具

常规数据测不出问题，验收必须带一组固定夹具：

- 重复文件名（同名同内容 / 同名不同内容）
- 数量超限（上限 +1、一次选 50+ 个）
- 超大文件（单类型上限附近、总大小上限附近）
- 超长/非法目录名（1 字符、30 字符、31 字符、含非法符号）
- 嵌套目录 + 不同子目录同名文档
- 只绑图谱库的 Blended 工作流、未发布工作流
- 筛选组合（状态 × 类型 × 名称/ID/创建人）

### 6）构建可追溯

验收报告必须记录**被测版本**（git commit + 镜像 tag/构建时间）。界面或 `/system/info` 应能直接看到版本。
版本对不上时，任何"已修复/未修复"的讨论都失去前提。

## 3. 提交前自查清单

**开始前**

- [ ] 记录被测版本：commit / 镜像 tag / 构建时间
- [ ] 确认部署的就是这个构建
- [ ] 准备边界夹具（§2 第 5 条）

**回归**

- [ ] 相关回归集全绿
- [ ] 单测基线不下降（passed / deselected / skip 0）
- [ ] 契约快照一致（`generate-rkb-openapi.py --check`、`verify-agent-openapi.py`）
- [ ] E2E 冒烟通过

**探索**

- [ ] 错误分支抽查：409（冲突）、413/超时（大文件）、422（校验）、504（网关）
- [ ] 反馈抽查：复制、保存、上传、下载、删除是否都有明确结果
- [ ] 视觉抽查：320 / 768 / 1024 / 1440 下弹窗、抽屉、工具条不重叠不溢出
- [ ] 中英文各走一遍关键页面（文案长度与提示差异）
- [ ] 筛选/搜索组合至少覆盖：状态 × 类型 × 名称/ID/创建人
- [ ] 键盘导航与 reduced-motion 行为在受影响的页面上可用

**收尾**

- [ ] 新问题登记：现象 / 影响面 / 是否已补用例
- [ ] 非缺陷项写明结论理由
- [ ] 删除临时夹具与调试数据，确认没有把本地状态写进仓库

## 4. 从问题到回归用例

```text
问题报告
    │
    ▼
复现并记录被测版本 ──► 判定：缺陷 / 非缺陷（附理由）
    │ 缺陷
    ▼
先写失败用例（单测 / 组件 / E2E / 配置断言）
    │
    ▼
修复 ──► 用例转绿 ──► 并入回归集
    │
    ▼
下一轮：先跑回归集 + 版本核对，人只做探索性验证
```

**判定为非缺陷也要落字**：属于产品语义选择的结论要写明理由，避免下一轮重复讨论。
质量类问题（推荐问答命中无关片段等）用评测集跑指标，不混进缺陷单。

## 5. 自动化守卫建议

新增或修改功能时，优先把可机器判定的规则固化成测试：

- 页面不得直接调用底层复制函数，必须走统一的带提示封装；
- 批量上限错误按原因聚合，只出现一条提示；
- 搜索字段、筛选类型与界面标签保持同源；
- 目录名等输入规则与后端校验保持一致；
- 上传链路的关键 nginx 配置（`proxy_read_timeout`、`client_max_body_size`）有配置断言；
- 关键弹窗、删除确认、目录栏、工具条有截图基线；
- 版本号在界面或 `/system/info` 可见；
- 边界夹具落成可复用的脚本或种子数据；
- 检索质量变化接入评测基线（`docs/rag-benchmark-20261101.md`）。
